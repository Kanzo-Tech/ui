Every refusal that carries a code — from the auth routes, the API forwarder and the proxy — is an RFC 9457 problem: `application/problem+json` with `status`, `title`, `detail` and the `AuthErrorCode` as `code`. Every code has one status everywhere (`organization/denied` is 403 from the routes as from the forwarder). The forwarder now names the code it refused with, so you can route `organization/denied` or `token/exchange-failed` instead of coining your own code for a bare status, and when your API does not answer at all — connection refused, a name that does not resolve, a reset — it answers 502 with the new code `api/unreachable` instead of a bare 500, so you can drop a code of your own for that too. An API that answers with an error status is still passed through untouched. Refusals with no code stay bodiless: a cross-site request's 403, a path under no mount, and no API configured. **Breaking:** read `code` and `detail` where you read `{ error, message }`; a forwarder or proxy refusal that had no body and now has a code carries one.
