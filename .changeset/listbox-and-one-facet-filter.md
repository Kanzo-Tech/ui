**A filter is a value, not a command — so the two facet filters stop being menus, and the surface they now share is a new `FacetFilter` over a new `Listbox`.**

`DataTableFacetFilter` and `ChartMenu` were the same control written twice: the same trigger with a count `Badge`, the same checkbox rows with counts, the same "Clear filter", and — the tell — the same two list rules independently rediscovered on both sides and commented in nearly the same words. Both were built on `Menu` + `MenuCheckboxItem`, which is `role="menu"`: a list of **commands**. A filter is a **value**. The distinction is now written down in DESIGN.md as an admission rule, with the one-line test — *if closing the surface leaves state, it is a listbox; if it leaves only an effect, it is a menu* — and `DataTableViewOptions` is the counter-example that stays a menu, because column visibility really is a view command that is nobody's data.

Mis-roling costs more than purity: a `menuitemcheckbox` list cannot announce "2 of 5 selected", and a menu has nowhere to grow a search field the day a column has 200 values.

**`Listbox`** is vendored from Shark's registry source, not guessed from its page — same anatomy and the same eleven part names, plus a `ListboxLabel` Shark omits. It is the only member of the family with no popover of its own, which is the point: it renders no portal, no positioner and no trigger, so the caller places it. Its items borrow `SelectItem`'s geometry rather than Shark's own listbox look, so a listbox rendered beside — or inside the same popover as — a `Select` agrees with it about row height, indent and where the check lives. Five divergences, all declared in the file.

**`FacetFilter`** is that listbox in a `Popover` behind a counting trigger, and it owns the two rules its callers used to duplicate: a ticked value that another filter has faceted away **stays listed**, or the filter is stuck with nothing to untick; and rows are ordered by label, **never by count**, because ordering by frequency reshuffles the list under the cursor every time another filter moves. It lives on the root barrel because its two consumers sit on subpaths that must not see each other — `/table` would drag in Mosaic, `/analytics` would drag in TanStack — and being presentational it needs neither. Clearing is a `Button`, not a row: a command does not belong in a listbox.

Two behaviours differ from the menus they replace, both deliberate:

- **The popover is not modal.** Our `Popover` defaults to `modal`, which marks the rest of the page `aria-hidden` — so the table being filtered went unreadable to a screen reader at the exact moment it was being filtered. A filter is judged by what changes behind it.
- **`deselectable` is not set, and that is load-bearing.** Zag documents the prop as "whether to disallow empty selection"; the machine assigns it to `selection.deselectable`, and the selection manager only unticks an already-selected value *when it is true* — so it **allows** an empty selection, and it is off by default. Setting it also binds Escape to `VALUE.CLEAR` with a `stopPropagation()`, which made the key everyone presses to back out of a popover silently discard the filter. Leaving it off matches `Select`, where clicking the chosen option does not unchoose it either; clearing is what the clear affordance is for. All three branches are pinned by tests in `listbox.test.tsx`, because a version bump could reverse either half of this without anything else complaining.

**`ChartMenu` is now `ChartFilter`** (with `ChartMenuProps` / `ChartMenuOption` following), because it contains no menu and it filters the page rather than one chart. No alias: the package is unpublished, so a clean rename is free and an alias would be permanent. Every Mosaic behaviour is unchanged — the faceted `GROUP BY … LIMIT n+1`, the `clausePoints` / `clausePoint` switch, the `defaultValue` that publishes once on connect, `as` / `filterBy`, and the truncation the control owns up to instead of pretending the tail is absent. `DataTableFacetFilter` keeps its props and its exported types; only its body changed, and it shrank from 79 lines to 28.

One correction that came out of the same reading: the previous changeset for these inputs claims `ChartFilter` "upgrades from `Select` to a searchable `Combobox` above 12 options" and latches the decision. No such code exists — grep finds no threshold, no `Combobox` and no latch in `chart-inputs.tsx`. The claim is removed rather than inherited.

**`searchable` on `FacetFilter` is the honest version of that idea, and it shipped here.** It is a prop and deliberately **not** a count threshold: a control that changes shape when the crossfilter shrinks transforms itself under the cursor — tick a value, the facet narrows, the field vanishes and every row moves up — which is the problem the latching was invented to hide. The adapter knows whether the column is `provider` or `subject_uri`; the component only knows how many rows survived the last filter, and that is a different question.

It is also not a nested `Combobox`. That would put two machines in one popover, sharing one open-state and one positioner. Ark's listbox already has the part — `Listbox.Input`, which Shark's own listbox file omits — so it is vendored as a declared addition alongside `ListboxLabel`, styled from the same `inputVariants` as `Input` so a searchable listbox and a `Combobox` are the same box. What the machine does *not* do is the load-bearing half: `@zag-js/listbox` holds no input value and no `onInputValueChange`, so the part is an uncontrolled `<input>` that contributes ARIA (`aria-controls`, `aria-activedescendant`, `aria-autocomplete="list"`) and forwards keys to the content — arrows always, `Home`/`End` only under `keyboardPriority="navigate"`, `Enter` as a click on the highlighted row. Filtering is entirely the caller's, as in `Combobox` and rather more so. `FacetFilter` therefore does it with `useFilter({ sensitivity: "base" })`, so `coruna` matches `A Coruña`, and builds the collection from what it draws — Ark navigates the collection, so a row filtered out of the DOM but left in the collection is one the arrow keys highlight and nobody can see. `autoHighlight` is passed, which re-aims at the first surviving row on every keystroke and puts the top match under `Enter`.

The two rules `FacetFilter` owns had to survive the query, and there are tests for both: a **ticked** value is never hidden by it, because unticking is the only way back out; and the surviving rows are still in label order. Emptiness split in two, because the states are not the same news — `empty` is "this facet offers nothing", usually still loading, and new `searchEmpty` is "your query excluded everything it did offer", which clears itself when you retype.

Both adapters expose it, with different honesty. `DataTableFacetFilter searchable` is total: the table holds its rows, so the field searches every value the column has. `ChartFilter searchable` narrows the **fetched page** — the `limit` most frequent values, 50 by default — and asks DuckDB nothing new, so when that page is truncated the footnote and the no-match message both name the scope (`No match among the top 50 values.`) rather than letting a client-side miss read as a statement about the database. Searching the column is `ChartSearch`, which publishes a match clause.

Two things the tests found that reading would not have. The popover now passes `initialFocusEl` at the field: zag aims a popover's opening focus at the *content*, and late enough that a keystroke typed straight after opening arrives first — so the key reached the list as typeahead and then focus moved out from under the caret, which makes a filter field pointless. Without a field, focus still lands on the list, where typeahead is the right answer. And `useFilter` memoises on its options object by identity, so the idiomatic-looking `useFilter({ sensitivity: "base" })` returns a fresh `contains` every render and rebuilds the collection with it; the object is hoisted instead.
