## Usage

```tsx
import {
  WorkspaceLayout,
  WorkspaceFloatingControls,
  WorkspaceStatusStart,
  PanelHeader,
  useWorkspacePanel,
} from "@kanzo-tech/ui";
```

```tsx
<WorkspaceLayout panels={panels}>
  <YourCanvas />
  <WorkspaceFloatingControls>
    <Button aria-label="Fit to screen"><MaximizeIcon /></Button>
  </WorkspaceFloatingControls>
  <WorkspaceStatusStart>aemet.fossil · 1,204 triples</WorkspaceStatusStart>
</WorkspaceLayout>
```

It owns the [`StatusBar`](/docs/layouts/status-bar) at the bottom — it has to, since the bar's
toggles are rendered from `panels` — and splits the remainder into your canvas plus a
resizable dock. Toggle the dock with `⌘/Ctrl+\`, close it with `Esc`, drag the divider to
resize it, or drag it to the edge to collapse it fully.

It is not a sidebar. A navigation rail is [`Sidebar`](/docs/simples/sidebar) around it, and a
back control belongs in the page chrome — a [`Toolbar`](/docs/composites/toolbar) above the
canvas — where it can be read and reached rather than floating over what it obscures.

## Sizing

`WorkspaceLayout` sizes itself with `height: 100%`, and a percentage against an auto-height
parent falls back to `auto` — which collapses the splitter and the canvas to content height.
Give the parent a resolved height (`h-svh` on a `SidebarProvider`, a fixed height in a demo).

## Anatomy

```text
WorkspaceLayout                     (children = the canvas)
├── WorkspaceFloatingControls       (anchored to the canvas)
├── WorkspaceStatusStart            (portals into the status bar)
├── (dock, rendered from `panels`)
│   └── PanelHeader                 (inside each panel's `content`)
└── (StatusBar, owned by the layout)
```

`WorkspaceStatusStart` portals into the bar's start cluster instead of taking a `statusLeft`
prop, so the status text is written next to the canvas whose state it describes. Because it is
a portal it renders nothing until the bar mounts — keep it to status text, not content that
must be in the server-rendered HTML.

`WorkspaceFloatingControls` is reserved for things that act *on* the canvas — zoom, fit to
screen, run. It hugs the inline end (`end-3`, not `right-3`), so it mirrors in RTL.

## Panel content

`panels` stays a prop: it is data and behaviour, not a layout region — the layout renders the
toggles, the dock and the open/close state from it. Put a `PanelHeader` at the top of each
panel's `content` for a titled header with a close button; it reads the close action from
context, as does `useWorkspacePanel` if you need it yourself.

## API Reference

### WorkspaceLayout

| Prop | Type | Default |
| --- | --- | --- |
| `children` | `ReactNode` | — |
| `panels` | `PanelDef[]` | — |
| `defaultPanel` | `string` | first panel's `id` |
| `defaultDockSize` | `number` | `28` |
| `maxDockSize` | `number` | `55` |
| `storageKey` | `string` | `"kz:workspace"` |
| `onActivePanelChange` | `(id: string \| null) => void` | — |

`defaultDockSize` and `maxDockSize` are percentages of the workspace width; the canvas keeps
the remainder as its minimum. `storageKey` is where the open panel is persisted in
`localStorage` — give each workspace its own.

### PanelDef

| Prop | Type | Default |
| --- | --- | --- |
| `id` | `string` | — |
| `icon` | `ReactNode` | — |
| `label` | `string` | — |
| `content` | `ReactNode` | — |

### PanelHeader

| Prop | Type | Default |
| --- | --- | --- |
| `title` | `ReactNode` | — |

### useWorkspacePanel

Returns `{ closePanel: () => void; statusStartEl: HTMLElement | null }` — the same context
`PanelHeader` and `WorkspaceStatusStart` use.

### WorkspaceFloatingControls / WorkspaceStatusStart

`WorkspaceFloatingControls` renders a `div` and takes its props. `WorkspaceStatusStart` takes
only `children`.
