title: The services
description: Why a capability's server half ships beside its client half, in one repository under one tag; why Compose is the whole of it; and why the service names no application and carries no production configuration.
---

A sibling package reads something a server emits: `@kanzo-tech/auth` reads a Keycloak realm's
tokens. That server is in this repository too, under `services/` —
[the identity service](/docs/auth/service). This page is why it is here, what keeps it generic, and
why there is no second one for models.

## Each capability ships both halves

The server half of a capability and its client half live in **one repository and are released under
one tag**: `services/auth` beside `packages/auth`. An
application pins one release — its packages and the compose files it includes name the same tag —
and gets a server and a client that were checked against each other, rather than two version
numbers whose agreement is its own problem.

The contract between the halves is what makes this more than packaging. The package reads
`organization.<alias>.resource_access.<clientId>.roles`; the realm is what writes it, and only
Keycloak 26.7 and later can. Kept apart, a change to a claim mapper and a change to the reader land
in two repositories on two schedules, and the first place they meet is a consumer's sign-in. Kept
together, one pull request changes both, and the same CI run brings Keycloak up, signs every seeded
person in and checks the claims, while the package's tests read a token recorded off that service.

**What would reverse it:** the halves moving on different clocks — releases that carry a service
change and nothing for the packages, or the reverse, often enough that one version number is
costing consumers upgrades they did not need. Or a service operated by a team with its own release
cadence, at which point the tag is a promise this repository cannot keep. Neither has happened; the
services arrived in the same pull request as the reader that needed them.

*Held by* the job `services` in `.github/workflows/ci.yml`, which runs `services/auth/scripts/verify.sh`
on live tokens for every seeded person; `packages/auth/src/claims.test.ts`, "a real token, taken off a
live Keycloak 26.8.0" and "reads a composite with the role it contains, as Keycloak expanded it".

<Callout type="warn">
**The recorded token is recorded, not regenerated.** `verify.sh` checks the live realm against the
contract and `claims.test.ts` checks the reader against a token taken off it once; nothing rewrites
the fixture when the realm changes. A mapper change that keeps `verify.sh` green but alters the
token's shape elsewhere would pass both. Re-record the token in the same pull request as any change
to `realm/token-claims.tf`.
</Callout>

## Compose is the whole of it

Each service is a `compose.yaml` that runs as it is wherever it runs, and a `compose.dev.yaml` that
development adds on top. An application includes them by URL, at its release, beside its own
services; a deployment is the same files with its own values in the environment. The system is
described once: there is no second description for production — Terraform resources, a Helm chart —
that has to be kept saying what the compose files say.

The second description is what it replaced. Production was Terraform on Docker Swarm, rewriting
Keycloak, Postgres and the AI gateway as resources, because `docker stack deploy` cannot read these
files: measured on 9 October 2026 against Docker 29.8, it refuses `include:` and secrets read from
the environment, and has no `models:`. Two descriptions meant two ways to choose a model, the
organizations written in three places, and a production realm that failed on an empty Keycloak
because only development knew it had to be applied twice. And the Swarm was one node: local volumes,
a single replica each, SQLite behind the products. `docker compose up -d` converges a host to its
files as declaratively, and `--remove-orphans` takes away what a file no longer names.

**What it cost.** Swarm's rolling update with no gap: a stateless service can keep it with
`docker rollout`, but a single-writer one (a Postgres, an SQLite file) restarts. And Compose has no
loop: a product with one service per tenant writes one small file per tenant.

**What would reverse it:** more than one machine for one deployment, or a scheduler a deployment
already runs. Then the services would ship for that scheduler — Kubernetes is the likely one — and
the price is a second description, paid deliberately.

*Held by* the job `services` in `.github/workflows/ci.yml`, which brings the platform up from
`services/compose.dev.yaml` — the realm applied, the seed run — and proves the realm
on live tokens.

## The service names no application

Nothing under `services/` knows `board` or `ledger`. **An application declares itself**, from its
own repository: an `x-application` — its client, its own API, its roles
with their composites — and an `x-organization` per organization it serves, mounted into the realm's
one-shot `auth-realm` service. The realm reads every declaration it is given
(`services/auth/realm/declarations.tf`) and registers them with `modules/app` and `modules/api`; it
never names one, and it ships no API of its own: every API is an application's, declared with it.
The development realm declares `kanzo-conformance` in `services/auth/dev/`, which exists to prove
the contract and which only development mounts.

The alternative is the one every shared realm drifts into: each new application is an edit to the
platform's configuration, the platform's repository becomes a list of its consumers, and removing
one is an archaeology exercise. With the declaration in the application's repository, adding an
application is that application's pull request, deleting it deletes its file, and two applications'
roles cannot reach each other because neither is declared where the other can see it.

**What would reverse it:** something an application needs that a client registration cannot express
from outside the realm — a realm-wide setting one application wants and another cannot live with.
That would have to be declared in the realm, and the honest shape then is an input the realm takes,
still named for what it does rather than for who asked. None has appeared: every setting the claim
contract needs is realm-wide and generic, and everything per application is a client attribute.

*Held by* the job `services` in `.github/workflows/ci.yml`, which validates `modules/app` and
`modules/api` as modules with no caller, and proves the realm through `kanzo-conformance` alone.

## There is no model service

The model runs in the page ([Tasks](/docs/design/tasks)): a small model on the person's own device,
held to a schema or a grammar and checked by oracles. So no server stands between the page and a
model, no provider key exists to keep, and a question about a tenant's data does not leave the
browser to be answered. The gateway that was here — agentgateway, chosen on 5 October 2026 because it
validated the realm's tokens and budgeted per organization in one open-source binary, where LiteLLM
needed its Enterprise edition and Agent Router needed Kubernetes — went with its last consumer, and
so did the realm's `ai-gateway` API, the only API the realm registered for itself.

**What would reverse it:** a Task no model that fits a device can do, measured on the evaluation set
after everything computable has moved out of the model. Then a model goes behind a server again, and
the contract it starts from is the one above: the realm's token, exchanged for one organization, is
the credential, and nothing names a tenant but the token.

## Production configuration belongs to the deployment

The services ship **development** values and the **shape** of production ones, never production
values. The hostnames, the passwords, the realm's identity provider, SMTP and TLS are the
deployment's, and membership is runtime: development seeds it, production invites.

A shipped production value would be one deployment's choice presented as the platform's, and every
other deployment would start by undoing it. What the service does own is what does not vary between
them: the claim mappers, the image pins, the rule that an exchanged token names one organization.

A password is the sharpest case, because the deployment that forgets to undo it runs: `compose.yaml`
defaulted the database's to `keycloak` and the admin's to `admin`, so a deployment that set neither
came up with the passwords printed in this repository. So `compose.yaml` names the two and gives
them no value — `${KC_DB_PASSWORD:?…}`, Compose's required variable — and refuses to start without
them. Development's are a file, `auth/dev/dev.env`, which `compose.dev.yaml` hands Compose as its
`include`'s `env_file`, and which the environment or an application's own `.env` overrides.

**What would reverse it:** two deployments that want the same production values verbatim, written
twice. Then the duplication is real and the choice has earned a place — as a named example
deployments copy, not as a default `compose.yaml` falls back to.

Held by nothing: a default added to `compose.yaml` would pass every gate here, and review is what
stands in front of it. The `services` job in CI runs `compose.dev.yaml`, so it proves development's
values reach the service, not that production's are absent.
