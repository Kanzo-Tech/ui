The rule spans three repositories, and its argument lives once, in fossil's
`docs/content/docs/design/failure.mdx` (*Every wait ends, every failure is seen*). This page holds
the two things only this library can: what its signatures promise a host, and the list of codes it
names itself.

## The thrown value, whole, by one path

Every surface that hands a host a failure hands it the `unknown` that was thrown: `GraphRoot`'s
`onFailure`, `MosaicProvider`'s `onFailure`, `AssistProvider`'s `onFailure`, `useBlocker`'s `onFailure`,
`useSession()`'s `error` beside `status: "failed"`, `useAgentChat()`'s `error`, `engine()`'s rejection. A `FossilError` arrives as
a `FossilError`. The library never reduces a failure to its message, never depends on fossil's types
to pass one, and never turns one into another state — an empty chart, `"anonymous"`, a spinner.

**What would reverse it:** a second consumer that wants failures in a vocabulary of its own. Then the
codes below become `data` on one kanzo-ui error type rather than a list a host must know.

*Held by* `packages/ui/src/failures-reach-the-host.test.ts`, "bites on onFailure, onError or error
typed string" and "bites on a class extending MosaicClient with no queryError".

## The codes this library names

Each is a kernel `Problem` with `code` and `data`, in the `area/kind` grammar fossil's and a host's codes use,
so one host registry keys all three. One area per package, named for it. `@kanzo-tech/llm` broke that with an `AiError` coding `ai/unavailable`, while keasy coded its own
model failures `llm/failed`, so one area had two names; its area is `llm`. Every one is the kernel's `Problem`.

| Code | Thrown by | When | `data` |
| --- | --- | --- | --- |
| `engine/unavailable` | `@kanzo-tech/mosaic` | DuckDB-WASM would not boot | `after` when the 60 s deadline fired |
| `graph/no-webgl` | `@kanzo-tech/graph` | no WebGL, a renderer that would not start, or no device within 10 s | `after` when the deadline fired |
| `graph/context-lost` | `@kanzo-tech/graph` | the browser took the WebGL context back | — |
| `graph/no-positions` | `@kanzo-tech/graph` | a device that came up holds no positions for the points it was given: a frame's read-back failed | — |
| `graph/nothing-to-draw` | `@kanzo-tech/graph` | an attached corpus with no vertex | — |
| `llm/unavailable` | `@kanzo-tech/llm` | the page cannot run the model: no WebGPU for `localModel` | `reason` |
| `llm/truncated` | `@kanzo-tech/llm` | a structured answer the model's context cut off | `reason` `"context"` |
| `session/*`, `idp/*`, `api/*`, `callback/*`, `token/*`, `organization/*`, `claims/*` | `@kanzo-tech/auth` | see [the auth layer](/docs/design/auth) | `after`, `status` where named |

**What would reverse it:** a code a host never branches on. Then it folds into its neighbour; the
list is short because every row is a different thing to show.

## The waits it bounds

The figures are fossil's table, and move there with the measurement beside them. Two are this
library's own: DuckDB's boot, 60 s, and cosmos.gl's device, 10 s — the second is not in fossil's
table yet. Work inside the process — a query, a layout — has a signal and no deadline, and so does
fossil's `attach`, which the host awaits before it names the catalog: the network waits inside it are
fossil's to bound.

**What would reverse it:** a device that legitimately takes longer than 10 s to come up, measured.

*Held by* `packages/mosaic/src/engine-boot.test.ts`, "rejects with data.after when the worker never
answers within the 60 s deadline".

## One deadline per wait

**A wait is bounded by the party that makes the request, once; whoever passes a transport or calls
a door does not add a second bound around it.** Two bounds on one wait race to name one failure, and
whichever wins, the other's code is what a host's registry was told to expect. keasy's session read
was the case: `bffAuth` bounds `/session` and `/refresh` at 30 s as `session/silent`, keasy handed it
a `fetch` that bounded every request at 30 s as `server/silent`, and `bffAuth` rewrapped the loser as
`session/unavailable`. So `bffAuth`'s `fetch` is a transport, documented as one and not as a test
seam, and a host bounds its own API calls in the requests it makes
([the auth layer](/docs/design/auth#one-party-bounds-each-wait)).

**What would reverse it:** a wait two parties must each bound for a reason of their own — a host
that must give up sooner than the library on one screen. Then the host passes a signal, which the
library's bound composes with, and the code is still the library's.

*Held by* `packages/auth/src/bff-auth.test.ts`, "gives up on a session endpoint that never answers,
after 30 s and not before".

## A model's failure is shown once, on the first attempt

The model runs in the page ([Tasks](/docs/design/tasks)), so there is no request to a server to bound
and no limit to be told about: what can fail is the device. `localModel` checks for WebGPU before it
downloads anything and fails as `llm/unavailable` with `reason` `"webgpu"`, and a page that serves no
such model fails the same with `reason` `"unserved"`, so a host says the model cannot run here rather
than waiting on a load that will not finish.

**The library's own asks are made once, through `@kanzo-tech/llm`.** Every model call the library
makes goes through one of `llm`'s two doors, `stream` and `generate` — `streamText` and
`generateText` with `maxRetries: 0` — so the first attempt's error is the one shown. The Task layer
did not: `runTask`, its repairs and `propose` called the AI SDK's `generateText` straight, with the
SDK's default, so every draft retried twice. The SDK's default is two retries with backoff, and a
generation that failed on this device fails the same way asked again — three waits where the person
sits through one.

**What would reverse it:** a model the page reaches over the network again. Then the request has a
silence to bound and a limit to name, and both belong to the one door that makes the request, not to
`Assist` or `Chat` above it — two bounds on one wait are two parties racing to name one failure.

*Held by* `packages/llm/src/local.test.ts`, "fails as llm/unavailable without WebGPU, before anything
loads or is fetched"; `packages/ai/src/assist.test.tsx`, "asks once: an error the SDK would retry is the failure,
not a retry after it"; `packages/llm/src/stream.test.ts`, "never retries a refused call";
`packages/llm/src/generate.test.ts`, "never retries a refused call"; `packages/ai/src/task/task.test.ts`,
"asks once: an error the SDK would retry is the failure, not a retry after it".

## A generation that did not finish is not an answer

WebLLM ends a generation three ways, and `@browser-ai/web-llm` kept two apart on one path and none
on the other: its `doGenerate` maps `length` to `stop` and `abort` to `other`, and its `doStream`
reports `stop` whatever happened except an abort. A generation stopped at `"y": ` was therefore a
finished one, handed to `Output.object`, and the person read "No object generated: could not parse
the response" for what was an interrupt. `localModel` is the one choke point: an interrupted
generation (raw finish `abort`) rejects as an `AbortError`, on the generate and the stream paths
alike, and never returns the text it had written; a structured answer (a JSON Schema or a grammar)
that the context cut off (raw `length`) rejects as `llm/truncated`; text cut off by the context is
returned with the finish `length`, which a reader of text can see. `generateHeld` reports the same
three finishes. A stream cannot report `length`: the provider says `stop` for it, and the model's
context is not ours to measure.

**What would reverse it:** `@browser-ai/web-llm` reporting the finish of a generation honestly on
both paths. Then the middleware's check is the provider's, and the code goes.

*Held by* `packages/llm/src/local.test.ts`, "rejects as llm/truncated a structured answer the context
cut off, not as JSON that does not parse"; "returns text the context cut off with the finish length,
not stop"; "rejects an interrupted generation as an AbortError, with the text it had written never
returned"; "ends an interrupted stream as an AbortError".

## An interrupt is a call's own

WebLLM's `interruptGenerate()` is the engine's: it sets one flag, and whichever generation is
running stops. `@browser-ai/web-llm` registers it on a call's `abortSignal` when the call is made,
before the call has the engine's lock, so aborting a call that was only waiting — a starters query
React Query cancelled, a second Enter — stopped the first question mid-JSON. `localModel` takes the
turns itself, one call at a time per engine, and hands a call to the provider only when its turn
begins, so the provider's listener is registered for the one request the engine is running. A call
aborted in the queue is dropped, and the engine never hears of it. The queue costs nothing WebLLM
did not already charge: its own lock serialised non-streaming requests.

**What would reverse it:** WebLLM interrupting a request by id. Then the queue is the engine's and
the one here goes.

*Held by* `packages/llm/src/local.test.ts`, "drops a call aborted while it waits, without the engine
hearing of it, and the running call finishes"; "interrupts the running call when its own signal
aborts, and the caller sees an abort, not text".

## A load ends warm

`loadLocalModel` resolves, and `ready` is published, after one generation of two tokens under a
trivial JSON schema, run through the engine's turn. **This is justified by analogy and by reading
the code, not by a measurement.** Model servers warm up before they serve (llama.cpp does by
default, `--no-warmup` turns it off), and in WebLLM the XGrammar token table is built on the first
structured request and the GPU's pipelines run for the first time on the first generation, while
"Model ready" only says the engine exists. Nothing in WebLLM documents the practice or confirms that
this is where the first call's time goes, and no GPU was available when it was written. The warm-up
pays nothing a real schema needs compiled — each schema still compiles on its first use. A warm-up
that fails does not fail the load; the next call pays what it would have. `ready` stays "the engine
can generate", and is published once it has, so a screen that waits for it does not start its
questions behind a warm-up. The load, the warm-up and the first call (to its first token, or to its
result when asked whole) are `performance.measure` spans named `kanzo:llm:load`, `kanzo:llm:warm-up`
and `kanzo:llm:first-call`, readable under Timings in Chrome's Performance panel.

**What would reverse it:** the first call costing no less after the warm-up than before, in those
spans, on a device that runs the model. Then it is removed, with its changeset.

*Held by* `packages/llm/src/local.test.ts`, "is ready only after one tiny structured generation,
through the engine's turn"; "loads all the same when the warm-up fails"; "marks the load, the warm-up
and the first call in the performance timeline, once each".
