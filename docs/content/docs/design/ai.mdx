[Ask your data](/docs/ai/data) is what `@kanzo-tech/ai/data` ships. This page is why an answer is
shaped the way it is.

## An answer is a tile over a relation, and the model fills it from typed names

**The model does not write SQL. It fills an answer whose every name is an enum the page generated
from the data it shows.** An answer is the dashboard's own vocabulary:

```ts
interface Answer {
  /** What is asked about: a type, and the hops from it. The `JoinGraph`'s, as `relationQuery` reads it. */
  relation: Relation;
  /** What it is narrowed to, with the clauses the dashboard's filters publish. */
  where?: readonly Condition[]; // { field, in } | { field, between } | { field, contains }
  /** How it is shown: a figure, a chart or a table — the dashboard's `Tile`. */
  show: Tile;
  /** Rank `show`'s x by its measure and keep these many. */
  top?: number;
}
```

`answerSchema(graph, relations)` is the tool's JSON Schema. The relations offered, by key, their
fields — one list under `$defs` — the aggregates and the chart kinds are enums, so a provider that
decodes against the schema cannot write a field that does not exist. The schema is one object, not one
branch per relation, because Anthropic and OpenAI both refuse a tool whose input is an `anyOf` at
the top; so its field enum is every offered relation's, and `checkAnswer` holds each field to the
relation the answer names. It is the AI SDK's `validate` on the tool's input, so input that does not
pass is refused before `execute` runs, and the model reads why. The instructions list each type's
fields once, with their kind and most common values, *gender: category (female, male)*, read from
`FieldStat` and one count per category by `readAnswerRelations`, rather than DDL; [Asking within a
context](/docs/design/ai-context) is why once.

**It compiles with what the dashboard already compiles with.** `relationQuery` makes the relation;
each condition is the clause a dashboard filter would publish; `plotRelation` and `measureExpr` make
the tile's query. All of it runs under the page's crossfilter at the moment of asking — the clauses whose columns the
relation has, as `clauseColumns` reads them. The page's filter is not something the model names: it
is the predicate the answer is read under, as every tile's is. What the model reads back is what was
true then; the card is a tile, and follows the page afterwards like any other.

**A clause left out is said, with what it lacks.** Skipping silently made an answer look filtered
when it was not: under a chip on a city, a count over a relation with no city is every row, and
neither the model nor the reader could tell. So the result carries each skipped clause and the columns it names that
the relation lacks, the model reads it beside the clauses that applied, and the card prints both
under the tile. What would reverse it is a page that maps a clause onto any relation — a semi-join
through the join graph for every chip — at which point nothing is skipped and the line goes.

**The read goes through the engine's door, not the coordinator's queue.** The queue batches behind
`requestAnimationFrame` for the charts, and a hidden tab never fires one: a question asked before
switching tabs waited forever, and *Stop* only dropped the late answer. `Engine.query` takes the
chat's signal, so an abort ends the wait at once. An answer is one statement, which the queue had
nothing to consolidate with. What would reverse it is a coordinator whose queue takes a signal and
does not wait for a frame: then the agent goes back to reading where the charts read.

**The card is a dashboard tile.** `QueryResult` gives way to the dashboard's `ChartCard` over the
answer, with two actions that fall out of the shape: **Filter to it** publishes the answer's
conditions and, for a bar chart, the categories it answered, mapped to the page as one semi-join on
the relation's root key (`semiJoinOf`, as a relation dashboard's tiles are), and **Add to the
dashboard** puts the tile in the relation's spec, because it already is one. A kept answer is names,
not SQL, so a restored transcript draws it again over the host's graph, and nothing a transcript
carried reaches the engine as a statement.

**The references are the semantic layer's**: Looker's Conversational Analytics and ThoughtSpot Sage,
where a question is answered by picking fields of an explore or a worksheet, and Cube, LookML and
Malloy, where SQL is compiled from a model of the data rather than written against tables.
`relationQuery`'s own page names Looker's explore and Malloy's source as its reference, so the
answer and the dashboard share a model.

**It replaced Databricks Genie's and Hex Magic's loop**: one SQL query per answer, written by the
model against DDL, and `gateStatement` between that text and the page's engine. The gate kept the
engine safe, but it could not make the model right. A local model shown
`"cac8fcfb-…"."Person"` wrote `"Person"` in one take and `"cac8fcfb-…"."scope"` in the next, and
both were refused. Making the gate tolerant guessed what the model meant, and showing plain names
moved the same mistake one step along. Every mistake of that kind is a name, and an enum removes
names from what the model writes. Genie and Hex run frontier models against warehouses whose
names are the reader's own. A page that runs whatever model its host points it at, over names a
corpus generated, cannot count on either.

**What it costs:** a question the spec cannot say, such as a window function, a ratio of two
aggregates or a join the `JoinGraph` does not have, gets no answer, and the model says so. There is
no SQL tool kept beside it as a fallback: two doors means two things to secure and two answers that
look different, and the spec is where the missing words get added.

**What would reverse it:** questions readers ask and the spec cannot say, recorded often enough that
growing the spec costs more than a second door. Then a SQL tool returns beside the spec, behind
`gateStatement` as it was — with `@kanzo-tech/mosaic`'s engine loading DuckDB's `json` again, whose
`json_serialize_sql` was the gate's parser — and the card says which one answered.

*Held by* `packages/ai/src/data/answer.test.ts`, "the enums are the relations offered, by key, and their fields, listed once"; "an
answer compiles to the same query the dashboard tile reads"; "input outside the schema is refused
before it runs"; and `packages/ai/src/data/answer-card.test.tsx`, "Add to the dashboard hands the
host its dashboards with the tile in the relation's spec, and where it landed".

## Whether a tile is on the dashboard is the host's spec, read

**`AnswerCard` takes the host's `Dashboards` and hands `onAdd` the whole next document, and *On the
dashboard* is the tile's id found in its relation's spec.** It is `Dashboard`'s own contract — a
value and the whole next value — and the controlled answer to a flag a card kept: that flag said
*added* the moment `onAdd` returned, before the host's save had succeeded, and a remount forgot it.
The tile goes on under the answer's id, the call's, which is what lets the spec be asked. A write the
host answers with a promise is waited on: pending until it settles, whatever the spec shows, and a
rejection drawn as a `Problem` beside the button, the thrown value whole.

`onAdd` is told the relation as well as its key, because a host's dashboard view is driven by a
`Relation` and a key cannot be read back into one.

**What would reverse it:** a host that keeps its dashboards in some shape other than `Dashboards`,
asking for the card. Then the card takes a predicate and a callback that build the next spec, and the
document is the host's again.

*Held by* `packages/ai/src/data/answer-card.test.tsx`, "is on the dashboard while the host's spec
holds the tile, after a remount, and offered again once it is removed"; "is pending while the host's
write is, never on the dashboard before it settles, and draws a rejection as a Problem".

## Which relations are offered

**`answerRelationsOf(graph)` offers each type alone and through each of its hops, and a host on a
large graph narrows the hops with `from`, or offers none.** A question across a hop is what the
reader cannot see in any one table, and what the starter questions favour, so it is the default. It
is also nearly all of the cost, measured 2026-10 with `readAnswerRelations` in DuckDB-WASM's Node
build, over a graph shaped like LDBC's social network benchmark — its 8 types, its 23 edges, its
columns and its row counts, the values synthesised:

| Scale | Offered | Relations | Queries | Read | Fields | Prompt |
| --- | --- | --- | --- | --- | --- | --- |
| 0.1 (0.3 M vertices, 1.7 M edges) | the types alone | 8 | 16 | 0.4 s | 31 | 3,520 characters |
| 0.1 | and every hop | 54 | 290 | 9.4 s | 455 | 36,749 characters |
| 1 (3.2 M vertices, 17 M edges) | the types alone | 8 | 18 | 1.2 s | 31 | 3,581 characters |
| 1 | and every hop | 54 | 308 | 41.5 s | 455 | 39,018 characters |

The prompt is `dataInstructions`, sent with every question and, as `dataSuggestions`' relations,
with every set of starters; the tool's schema is 8,724 characters beside it for the types alone and
13,485 with the hops. The read is queued on the page's one connection, ahead of the dashboard's own
charts. One hop relation read alone took 0.8 s at the median and 3.0 s at the slowest, at scale 1.

Two other shapes were weighed. **Reading a relation's fields when the model picks it** costs that
0.8–3.0 s inside the question rather than before it, and gives up what the design rests on: the
schema's field enum must exist before the model writes a name, so a lazy read becomes a second tool
call per question and an enum widened to names nobody has read. **A cap on the prompt** would drop
relations by an order nobody chose, and the model is told the list is the whole of the data. So the
helper names the cost and the host chooses: `from` keeps the hops of the types the reader is looking
at, and `hops: 0` keeps none.

`readAnswerRelations` takes a `signal`: a page left mid-read cancels what is still queued on the
coordinator, so a 40-second read does not hold the engine from the next page.

**What would reverse it:** a host that needs every hop on a graph where the read or the prompt is
measured past what a reader waits for, or past a model's context. Then a relation's fields are read
when the model picks it, by a tool of their own, and the field enum is the graph's columns rather
than a read's.

*Held by* `packages/ai/src/data/answer.test.ts`, "offers each type alone and through each of its
hops, in the graph's order"; "offers the types alone at hops 0, and only the types named in from";
"hands each query the signal, and ends on an abort with its reason, cancelling what is still queued".
