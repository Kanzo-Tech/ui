[The graph page](/docs/graph) is what `@kanzo-tech/graph` ships. This page is how it is built and
why.

<Callout type="info">
The package reads `fossil/1`, which `@fossil-lang/corpus` publishes from `0.3.0-alpha.15` (the floor is `0.3.0-alpha.19`, whose failures are coded): a
`fossil.json` manifest, one Parquet table per vertex type and per relation, and a `dense_id` that is
global and dense. It imports fossil's types and nothing else.
</Callout>

## One path: fossil is the backend, this package is the view

fossil reads the corpus and this package draws it. The host opens a corpus with fossil's `open`, and
a corpus is fossil's one door — `manifest`, `scan`, `sql` and `close` — with one layer behind each
thing the door does (fossil's design page *One door*, in
[fossil-lang](https://github.com/Kanzo-Tech/fossil-lang)). The view uses two of those members: the
`manifest` it names every table and column from, and `scan({ table, filter, select })` with the
scan's `plan()` and `read()`. **No SQL is written in `@kanzo-tech/graph`**, and there is no second
way to reach the same bytes.

```text
fossil (backend)                               @kanzo-tech/graph (view)
open(url, { engine })  → Corpus                parts     GraphCanvas · GraphLegend · GraphCounts · GraphToolbar · GraphInspector · GraphSearch · GraphLooks
manifest → vertex_tables · edge_tables         adapter   useGraph · GraphRoot · GraphRootProvider · useGraphContext · useGraphState
scan({ table, filter, select })                render    typed arrays → cosmos.gl, uploaded once per corpus
scan.read(scan.plan()) → Batch[]               core      load: one scan per table · store · filter
```

**Column names come from the manifest** — a table's `key`, its `position`, its `identity`, a
relation's `source` and `destination` keys — so nothing of the writer's is spelled here.

**What would reverse it:** a question the view has to ask that the corpus door cannot express and
fossil declines to add. That is a gap raised on fossil's side, never a licence to write the query
here: a query written here is a second reader.

*Held by* `packages/graph/src/layers.test.ts`, "writes no SQL, and reaches fossil only through its
types"; `packages/graph/src/index.test.ts`, "keeps the second reader deleted: no opener, no source,
no slice", `!openCorpus`.

## ADR 0001 — the canvas holds the whole graph

fossil cites this decision by its number, so the label stays.

**The canvas holds the whole graph.** One scan per vertex table with a position, one per relation
between drawn tables, read into arrays sized from the manifest and uploaded to cosmos.gl once.
**Detail is fetched, not carried**: the loaded graph holds positions, the bound channels and the
links, and a focused vertex's row, or a label's text, is read when it is needed. **Identity is an
id, and the id is the index**: `dense_id` numbers every vertex `0 … V − 1`, the drawn types take the
first ids, and index `i` of every buffer is vertex `i` for as long as the corpus is open.

It rests on one premise: **the graph is not edited.** It is fossil's compiled output, so what was
loaded stays true until the host opens another corpus. Two consequences hold everywhere below:
positions are uploaded as the corpus wrote them, because the corpus's coordinate space is the
camera's; and the canvas element is mounted before the corpus answers, because a canvas gated on its
first answer has no renderer to answer to.

**What would reverse it:** a corpus whose first paint or memory passes a threshold agreed with the
owner, or one past cosmos.gl's link addressing (see [*A dense id is a buffer
index*](#a-dense-id-is-a-buffer-index)). Then a partial read comes in **behind the loader**, through
the scan's `plan()`: never a prop, and never a camera in the store.

*Held by* `packages/graph/src/core/store.test.ts`, "loads every vertex type with a position, indexed
by its dense_id", "loads the relations whose two ends are drawn, and no other";
`packages/graph/src/index.test.ts`, "ships a canvas that owns the renderer, and neither load nor
Loaded".

## The viewer costs what cosmos.gl costs

At 200,000 vertices, measured with `graph-bench`'s `measureViewer` in a foreground window, the
viewer's p95 frame interval is **9.0 ms against 9.3 ms for cosmos.gl alone** on the same positions
and camera path. The gate is 15%. The difference had been ours, and each cause is now a rule:

| the cause | the rule |
|---|---|
| a live simulation over positions the corpus had already laid out | `simulate` is off at load; the toolbar runs and stops the layout |
| every upload animated for cosmos.gl's default 800 ms | `transitionDuration: 0` |
| buffers re-uploaded on every change | positions and links upload once per corpus; the rest by kind |
| a selection called `render()`, which walks every point and link in JS | a state change is `setConfigPartial` |
| a hover re-rendered the canvas and read positions back from the GPU | the hover card re-renders; the renderer reports where the point is |
| camera events reached the store | the camera reaches nothing |
| painting allocated per link, and labels sorted every vertex | arrays allocated once; labels picked in one pass |
| the canvas re-rendered on every `setOptions` | parts read the fields they show |

**What would reverse it:** the same measurement outside 15% with the cost in our code. That adds a
row here.

*Held by* `packages/graph/src/render/renderer.test.ts`, "constructs cosmos.gl with no simulation and
no transition", "a camera move notifies nobody", "a selection sets config and calls no render and no
setter", "runs only when asked, from the positions it has, and stops where they are";
`packages/graph/src/parts/parts.test.tsx`, "re-renders the card on a hover, and not the canvas".

## The layers, and the reference each one copies

Each layer has a named reference whose shape it takes. A layer with no reference is a black box.

| layer | reference | owns | owns nothing of |
|---|---|---|---|
| **core** — the loader and the store | TanStack Query's `QueryObserver` | what is read, once, and the state a reader selects from | React, the DOM, cosmos.gl, SQL |
| **render** | cosmos.gl's own buffer API | typed arrays → cosmos.gl, one upload per changed kind, one render per frame | what to read |
| **adapter** | TanStack Query's core/adapter split; Ark's root/provider/context | the store's lifetime in React, and the context the parts read | how the graph loads |
| **parts** | Ark's flat parts over one context | the canvas element, legend, toolbar, inspector | any product's policy |
| **filter** — the bridge | Mosaic's `Selection` | the page's crossfilter as scan's typed `filter`, and the clause the graph publishes | the coordinator's queries |

Every module stays under four hundred lines:


## The store reads the whole corpus, once

When a corpus is adopted the loader takes the manifest's vertex tables that declare a `position` and
reads each with `scan({ table, select: [key, x, y, …bound columns] })`, and each relation whose
`source` and `destination` both reference a drawn table with `scan({ table, select: [src, dst] })`.
They run in parallel. Nothing else is read until a binding changes or the page filters.

**The arrays are sized before a row arrives.** The drawn vertices are ids `0 … N − 1`, `N` the sum
of the drawn tables' `record_count`: positions are a `Float32Array` of `2N` filled with `NaN`, the
table of each vertex a `Uint16Array`, the category ranks a `Uint32Array`, and the links a
`Float32Array`. A row is written at the index its `dense_id` names. A vertex with no position stays
`NaN`, which cosmos.gl draws as no point; a type with no `position` is not drawn.

**The vertex type is a channel, not a prop.** Every drawn table is on the canvas at once. Unbound,
**colour is the vertex type** — the legend's rows are the tables in the manifest's order — and a
label's text is each table's `identity`. Binding `fill` to a column spends colour on the column; a
table without that column draws its vertices as the null category.

**A binding re-reads its columns and nothing else.** Positions and links stay as they were uploaded.
`title` is not read at load: a label's text is read for the few vertices that carry one, and the
hover card's for the one under the pointer.

**What would reverse it:** a binding change measured slower than a full reload, which would mean
splitting the scans is not paying.

*Held by* `packages/graph/src/core/store.test.ts`, "reads once per question, never per camera move",
"colours by vertex type unless fill binds a column", "notifies subscribers once when the graph
loads"; `packages/graph/src/parts/parts.test.tsx`, "draws the vertex types when nothing is bound, with
what each has drawn".

## A filter is a predicate, applied as a mask

The page's crossfilter reaches the corpus as scan's typed `filter` — `{ column, op, value }`,
`{ column, op, values }` for `in` and `not in`, `{ column, op }` for the null tests, joined by `and`,
`or` and `not`. For each drawn table that holds every column the filter names, the store reads
`scan({ table, filter, select: [key] })`, and **what comes back is a mask**: a vertex that did not
survive has its position set to `NaN` in one upload of positions. The predicate runs where the data
is; the canvas only hides.

**A table without a column the filter names is not filtered**, which is what a `WHERE` over a union
of the tables would do. A filter no drawn table can answer is refused through `onFailure`, so the
unfiltered picture is never drawn as the filtered one.

**The graph listens to the selection; it is not a client of the coordinator.** A Mosaic client hands
the coordinator SQL to run, and the graph has none. So it takes the half of the protocol that is
about filtering: it listens for the `Selection`'s `value` event, reads `selection.predicate(graph)`,
and translates mosaic-sql's expression nodes — column references, literals, binary comparisons,
`BETWEEN`, `IN`, the null tests, `AND`, `OR` and `NOT` — into scan's `filter`. The `MosaicClient` it
holds is an identity for a clause's `clients` set and is never connected. **A node it cannot
translate is reported through `onFailure`, never dropped.**

**The graph's own clause is exempt for the graph.** A lasso or a click publishes the selected ids on
the tables' `key`, naming the graph in the clause's `clients`, so `Selection.predicate` applies it
to every chart and skips it for the graph — a canvas that draws only what survives would otherwise
answer a lasso of thirteen by removing the rest. `total` is the manifest's count and takes no
filter.

**What would reverse it:** the mask measured over about 50 ms at the scale that exists — then a
filtered vertex becomes a size of zero, which touches no geometry — or a common clause that does
not translate into scan's filter.

*Held by* `packages/graph/src/core/filter.test.ts`, "translates the clauses a chart publishes", "is
re-asked when the page filters something", "is exempt from a clause that names it", "reports a node
it cannot translate, and never draws the unfiltered picture as filtered";
`packages/graph/src/core/store.test.ts`, "a filter masks the survivors and reads no geometry".

## The renderer uploads once, and renders once a frame

cosmos.gl 3.4 replaces a whole buffer per setter, so **what changed** is decided per kind of
buffer:

- **A corpus uploads positions and links once.** A filter uploads positions alone; a binding, a look
  or a theme change uploads colours, sizes and shapes.
- **A state change uploads nothing.** A selection, a focus or a pin sets config — the ids are the
  indices — and calls no `render()`.
- **One frame renders once, and only for an upload.** Every dirty flag is discharged in one
  `requestAnimationFrame`.
- **Nothing animates.** `transitionDuration` is 0.
- **The layout runs only when asked.** cosmos.gl is built with its simulation off; `simulate` or the
  toolbar starts it from the current positions and pauses it where they are. Dragging a node moves
  it; it is pinned only while a layout is running or paused, because a pin nothing pulls against
  means nothing — d3-force's drag-to-fix. Releasing the pins reheats the layout, so the released
  points visibly flow back: a running layout takes the heat, a settled one cools to settled on its
  own, and a paused one gets a bounded burst and is paused again.
- **The camera is cosmos.gl's.** A zoom repaints the overlays and reaches no store. A placed corpus
  is framed, and framed again when the device comes up and on every resize of the canvas, until the
  reader zooms or pans; `render/camera.ts` owns who holds it. While a layout
  runs, the renderer re-frames the moving points every 900 ms and once more when it settles —
  Cosmograph's fit-on-settle, kept up so a contracting graph never leaves the screen — until the
  reader zooms or pans, which hands the camera back until the next run. Once a layout has moved the
  points, Fit frames where they are rather than the extent they came from.
- **`status` is the data's life and `motion` the layout's.** A running layout over a drawn graph is
  `idle` and `running`: each moves without the other, so neither word absorbs the other.

**What would reverse it:** cosmos.gl gaining a sub-range upload, so a filter could upload only what
it hid; or a picture that needs a transition to be read, measured against the frames it costs.

*Held by* `packages/graph/src/render/renderer.test.ts`, "uploads positions and links once per corpus,
and renders once", "repaints colours, sizes and shapes on a look change, and uploads no geometry",
"uploads positions alone for a filter", "starts and stops with the simulate prop, after the first
load", "moves a dragged node and pins nothing while no layout runs", "releases a paused layout with a
bounded burst, then pauses it again"; `packages/graph/src/react/graph-root.test.tsx`, "does not rebuild the renderer because a
callback changed identity".

## The React API is a store and an adapter

The graph's state changes outside React and at frame rate, so the core owns it as a **store** in
TanStack Query's observer shape, and React subscribes:

- **The core** is `createGraph(options)`: `subscribe`, `getSnapshot`, `setOptions` and `destroy`. It
  knows nothing about React.
- **The adapter** is `useGraph(props)`: `useBaseQuery`'s three moves — create the store once in
  `useState`, subscribe with `useSyncExternalStore`, hand it the latest props with `setOptions` in an
  effect whose dependencies are the props themselves. Callbacks are read through a ref, so an inline
  `onFailure` is never a change of options.
- **The surface is Ark's.** `useGraph` creates the api, `GraphRoot` is `useGraph` plus the context,
  `GraphRootProvider` takes an api a host built, and `useGraphContext` reads it — `useDialog`,
  `DialogRoot`, `DialogRootProvider`, `useDialogContext`.
- **The api is the commands, and the state is a selector.** The api is stable for the root's life,
  and `useGraphState(selector)` reads a slice and re-renders only when it moves. Each part renders
  one element the context fully describes, so there are no prop getters.

**`status` is one word:** `none` without a corpus, `opening` while the promised corpus settles,
`loading` while the graph, a binding or a filter is unread or undrawn, `idle` once all of it is
drawn, `failed` when the corpus would not open or read, or the canvas has no GPU device — none came
up, or its context was lost.

**What would reverse it:** the store costing more than it buys — measured as renders per hover with
and without `useSyncExternalStore`.

*Held by* `packages/graph/src/core/store.test.ts`, "keeps getSnapshot stable between notifications",
"lets the graph go when the last subscriber leaves", "says it is opening while a promised corpus
opens, and has none without one", "is idle only once the graph is loaded and drawn";
`packages/graph/src/react/graph-root.test.tsx`, "does not reach setOptions on a render that changed
no prop", "keeps the api's identity across hovers, and re-renders a part only on the slice it
selects"; `packages/graph/src/index.test.ts`, "is Ark's four: useGraph creates, GraphRoot provides,
GraphRootProvider takes, useGraphContext reads".

## The parts own the vocabulary; the host owns the policy

`GraphRoot` is a facade: the host gives it a corpus and a few props, and the parts under it read
the root.

- **`GraphCanvas`** — the element, and what the look declares over it: grid, vignette, labels and
  the hover card, plus the marquee and lasso gesture.
- **`GraphLegend`** — the categorical scale, or the vertex types when nothing is bound, with how many
  of each are drawn. Its domain is fixed before the graph loads, so a row never moves.
- **`GraphCounts`** — what is drawn of the whole, in one sentence: nodes drawn of the manifest's
  total, and edges drawn. A footer carries it, which is why it is not the legend's last line.
- **`GraphToolbar`** — the tools, the selection, zoom and fit, and the layout's run and stop.
- **`GraphInspector`** — the focused vertex's row, in its table's `properties` order, with a render
  prop for fields a product adds.
- **`GraphSearch`** — every drawn vertex's text, read once and filtered in the browser, ordered by
  the `r` ramp and named by `categories`; picking one is `reveal`.
- **`GraphLooks`** — the three looks as presets over `GRAPH_SECTION`'s axes, with the axes under
  Customize. It writes preferences rather than reading the root, so it needs the theme provider and
  no `GraphRoot`.

**Names are data on the root.** The manifest names no category values, so the host passes
`categories` on the root, where the legend, the hover card and the inspector all read it.

**Policy stays out, through the root's callbacks** — `onSelect`, `onFocus` and `onFailure`. No part
takes a callback of its own. `onFailure` is the one required prop: unhandled, a browser with no WebGL
context shows an empty box. It receives what was thrown, whole — fossil's errors keep their `code`,
and the graph's own are a `GraphError` — `graph/no-webgl`, `graph/context-lost`,
`graph/nothing-to-draw` or `graph/untranslatable-filter` — so a host chooses
what to show by code.

**What would reverse it:** a part a second host cannot use without a prop that encodes that host's
policy. That part goes back to the call site and is deleted from the package.

*Held by* `packages/graph/src/index.test.ts`, "carry no callback but the root's";
`packages/graph/src/parts/parts.test.tsx`, "draws the domain before the graph has loaded, named by
the root", "reads the focused vertex's row, and draws a host's extra fields after the corpus's own";
`packages/graph/src/core/store.test.ts`, "fixes the categorical domain before the graph loads".

## The reference composition

```tsx
// @fossil-lang/corpus: open · @kanzo-tech/mosaic: engine
const corpus = engine().then((e) => open(url, { engine: e }));
<GraphRoot corpus={corpus} filterBy={crossfilter} look={look} title="label" onFailure={setFailure}>
  <GraphCanvas>
    <GraphToolbar />
    <GraphLegend />
  </GraphCanvas>
  <GraphInspector />
</GraphRoot>
```

**Opening is the host's**, and so is closing. `GraphRoot` takes the corpus or the promise of it and
never opens a second copy. `@kanzo-tech/mosaic` and `@fossil-lang/corpus` are required peers: there
is one path and nothing on it is optional.

**The graph bounds the one wait it owns.** A `corpus` promise that never settles leaves the root
`opening`, because the waits inside `open` are fossil's and fossil bounds them; the reads after it
have a signal, not a deadline. The graph's own outside wait is cosmos.gl's device: `ready` never
settles when none can be made, so after 10 s the root fails with `graph/no-webgl` and `data.after`.

**What would reverse it:** an opening that can hang where fossil cannot bound it. Then `corpus`
takes a signal, or the deadline moves into the root.

*Held by* `packages/graph/src/core/store.test.ts`, "waits on a corpus promise that never settles,
with no deadline of its own, and lets it go when replaced"; `packages/graph/src/render/renderer.test.ts`,
"fails with graph/no-webgl and when the deadline fired, if WebGL exists but no device ever comes up".

[The workspace showcase](/docs/showcases/workspace) is the reference composition: one `GraphRoot`
around a shell whose main region switches between **Graph** and **Sightings**, with a dock of Info,
Ask, Orders and Settings. What it writes itself is the product's — the named pairings of look and
channels, the hall's name in the inspector and the panels — and nothing in it
reads a renderer or a buffer. A host copying it and drawing without a prop added for it is the test that admits these parts.

**What would reverse it:** the composition needing a prop only one host passes — the parts rule
above, firing. Or a host drawing a corpus that was not opened on `engine()`; then the bridge to
Mosaic goes behind an entry of its own.

*Held by* `packages/graph/package.json`, `//peers`.

## The coordinate box is the corpus's extent

The package declares no coordinate-space constant. The renderer is built with no `spaceSize` and
`rescalePositions: false`, and the first upload sets `spaceSize` from the larger side of the loaded
positions' extent, which the loader computes in the pass that reads them. The box belongs to
whatever wrote the positions; a number here would be this side stating a fact the other side owns.

**The extent is centred in that square on upload, at its own scale.** Drawing is
translation-invariant, but the layout is not: cosmos.gl's gravity pulls toward `spaceSize / 2` and
its many-body force bins points on a grid over `[0, spaceSize]²`. An extent uploaded where it was —
a fossil layout starts near the origin, so its centre is nowhere near the square's — contracted
toward a corner the moment a layout ran, and lost its far side off the grid. The placement is a
translation, plus a scale only past half the device's `MAX_TEXTURE_SIZE`, where cosmos.gl would shrink
the square under the positions anyway; `render/placement.ts` owns it, and the camera frames the
placed corners.

**One case does not fit.** cosmos.gl's zoom floor is `1e-3`, and framing a five-million-vertex extent
at 800×600 wants 0.000151, so only part of it fits on screen.

**What would reverse it:** cosmos.gl making `spaceSize` init-only, or a simulation whose centre is a
parameter rather than the square's middle — then the placement is a config value and not an upload.

*Held by* `packages/graph/src/coordinate-box.test.ts`, "declares no coordinate-space constant of its
own", "never writes a number where cosmos.gl asks what the space is";
`packages/graph/src/render/renderer.test.ts`, "frames the corpus again when the canvas settles its
size, as a split panel does after mount", "stops re-framing when the reader takes the camera, and
starts again with Fit", "centres the corpus's extent in it, at the corpus's own
scale", "scales the extent down only past the box the device simulates in";
`packages/graph/src/render/renderer.test.ts`, "frames the corpus's extent before it draws anything,
and only once".

## A dense id is a buffer index

`VertexId` is a `number`: fossil's `dense_id`, a `uint32` numbering every vertex of the corpus
`0 … V − 1`, the drawn types first. It is the index into every buffer, the value a selection
publishes, and the key the inspector filters on.

**The limit is cosmos.gl's.** It addresses a link's ends with a `Float32Array`, exact up to 2²⁴ —
about 16.7 million ids. Past it, a link's end silently rounds to a neighbouring id, so a corpus near
it is the day ADR 0001's partial read arrives, not a day to widen a type.

**What would reverse it:** a manifest that breaks density — ids with holes, or drawn types not
first — which brings back a map built once at load; or a corpus past 2²⁴ drawn vertices.

*Held by* `packages/graph/src/core/load.ts`, `Float32Array`; `packages/graph/src/core/store.test.ts`,
"loads every vertex type with a position, indexed by its dense_id".

## A look is form, and a channel is a binding

`Look` is form and carries no encoding. What a channel carries is **bound on the root**, under
Plot's names and Plot's rule that a CSS colour is a **constant** and anything else is a **column**:
`fill`, `symbol`, `r`, `stroke` and `title`. `symbol` stands beside `fill`, so identity may be drawn
as colour, as shape or as both. `stroke` absent tints each link by the vertex it leaves.

**A binding is a projection.** `fill` and `r` as columns become the scan's `select` where a table has
them. `fill` as a constant and `stroke` never reach a scan, and `symbol` reaches it only as the one
categorical column when `fill` is a constant or absent. `isColour` is the constant test, narrowed to
`var(…)`, a hex and the colour functions, so **a bare word is always a column**. A theme may not
rebind an encoding — Vega-Lite's `config` rule.

**The case that does not fit.** Ink's radius floor exists because it spends shape on identity and
size on degree at once, so that obligation is graded against the composition.

**What this does not touch.** The graph holds **one** categorical column. `x` and `y` are not
channels: in a laid-out corpus a position is a fact. And the graph authors no colour; it reads the
page's categorical scale.

**What would reverse it:** the composition check never firing — if every host that binds `symbol`
also asks for the form bundled with it, the pairing was the abstraction.

*Held by* `packages/graph/src/render/graph-looks.ts`, `Look`; `packages/graph/src/core/channels.ts`,

## A look declares what it changes

A look declares only what it moves from the shared defaults, and the preferences panel offers the
**axes a reader can name** — `marks`, `additive-links`, `bowed-links`, `labels`, `vignette` — which
recover the three shipped looks and combine into others.

| field | nebula | atlas | ink | nebula → atlas |
|---|---|---|---|---|
| point radius | 2 → 8 | 2.2 → 9 | **4 → 13** | +10% / +12.5% |
| link opacity | 0.42 | 0.45 | **0.28** | +7% |
| link width | 0.6 | 0.7 | 0.5 | +0.1 px |
| link fade | 200–1400 | 220–1500 | 180–1200 | ±10% |
| **link curve** | 0 | **0.12** | 0 | straight → bowed |
| **additive links** | **yes** | no | no | on → off |
| **label budget** | **14** | **26** | **40** | ×1.9 |
| **vignette** | **yes** | no | no | on → off |

Six of the ten fields separate Nebula from Atlas by 7–17%, below a luminance JND of 6.5–11.3 ΔL\*.
**Ink is a real form.** An empty look is Atlas.

**The three names live on as presets over the axes, not as a fourth axis.** `PRESETS` writes each
look as axis values and `GraphLooks` offers them as cards, GitHub's appearance settings: pick by
looking, then customise. A look is worn exactly when the resolved axes equal its own, so there is no
stored name to disagree with them, and `useGraphPrefs` answers `preset` for a host that pairs
channels with a look — the pairing stays the host's, because a look is form. A `preset` preference
was the alternative and is refused: it would be a key no reader reads, which the axes guard forbids.

**What would reverse it:** a reader telling Nebula from Atlas in a blind pairing on those six fields.

`packages/graph/src/render/graph-looks.ts`, `lookFrom`.

## What is still open

- **Names for a channel's values.** The manifest names no categories, so the host passes
  `categories`. If the manifest ever carries them, the manifest's win.
- **A column two types share.** A crossfilter clause carries no table, so a filter on `name` filters
  every drawn type that has one — a `WHERE` over a union. keasy reading it wrongly would reopen it.
- **The extent.** The manifest publishes none, so the loader computes it. A partial read would need
  it from the manifest.
- **The mask at scale.** The filtered scan plus one upload of positions has not been timed at
  145,000 vertices.
