[The graph page](/docs/graph) is what `@kanzo-tech/graph` ships. This page is how it is built and
why.

<Callout type="info">
The contract is a catalog. fossil's `open(name, { engine, host | url })` (`@fossil-lang/corpus`
`0.3.0-alpha.24` or later) attaches a `fossil/1` corpus to the page's DuckDB as the catalog `name`:
a view per table, `"<name>".fossil_tables(table_name, kind, rows, first_id, source, destination, …)`
and `"<name>".fossil_columns(table_name, column_name, ordinal, type, role, …)`. A vertex table holds
`dense_id` — global, contiguous per table from `first_id` — its identity column and the program's
columns; an edge table holds `src` and `dst`, both `dense_id`s. The corpus carries no position.
</Callout>

**The reference is Cosmograph v2**, read from its shipped 2.5.1 bundle — its code is CC-BY-NC, so
only the architecture is borrowed: DuckDB-WASM, a Mosaic coordinator and cosmos.gl; points indexed
`0 … N − 1` and links as index pairs, which is exactly fossil's `dense_id`, `src` and `dst`; position
as a view choice, with a GPU simulation from a seeded start when nothing places the points; a
cluster column fed to `setPointClusters`; filtering as a query for the surviving indices, drawn as a
GPU greyout; widgets and search as clients of the same coordinator. It has no map mode, and neither
does this: `lon`/`lat` as `x`/`y` is what there is.

## The graph reads SQL, through the page's coordinator

The host attaches the corpus and names the catalog; `GraphRoot` reads it with SQL — `fossil_tables`
and `fossil_columns` for the structure, the views for rows and links, one `SELECT` for a focused row,
a `LIMIT`ed `ILIKE` for a search, a count per relation for a neighbourhood — every statement built
from mosaic-sql's nodes and run through `coordinator.query(query, { type: "arrow" })`. A search is text
a reader typed, so no statement is a template string: the nodes quote their own identifiers and
literals. It imports nothing of fossil's.

```text
host                                                    @kanzo-tech/graph
engine() → DuckDB-WASM + coordinator                    parts     GraphCanvas · GraphLegend · GraphStatus · GraphCounts · GraphToolbar · GraphInspector · GraphSearch · GraphLooks
open(name, { engine, url }) → "<name>".<Table>          adapter   useGraph · GraphRoot · GraphRootProvider · useGraphContext · useGraphState
           "<name>".fossil_tables · fossil_columns      render    typed arrays → cosmos.gl, uploaded once per corpus
<GraphRoot from={name} coordinator filterBy>            core      source: SQL through the coordinator · client · load · store
```

**It replaced "no SQL in `@kanzo-tech/graph`"**, under which every read went through fossil's
`scan` on a connection of its own: rows decoded on the main thread, a cache nobody else shared, and a
second reader of the same bytes beside the coordinator every chart used. Through the coordinator
there is one connection and one cache, and a chart and the graph asking the same question get one
answer.

**What would reverse it:** a corpus the page cannot reach as SQL — served only through an API with
no DuckDB views — or a second host that has to draw without Mosaic. Then a reader comes back behind
the loader, and the parts do not move.

*Held by* `packages/graph/src/layers.test.ts`, "builds statements only where it reads, writes none in
a string, and imports nothing of fossil's"; `packages/graph/src/index.test.ts`, "keeps the second reader deleted: no opener, no
source, no slice"; `packages/graph/src/core/store.test.ts`, "reads the structure from fossil_tables
and fossil_columns, and every vertex by its dense_id".

## The graph is a client of the page's coordinator

`GraphClient` is a `MosaicClient` connected to the page's coordinator, like every chart beside it.
The coordinator hands it the crossfilter's predicate minus the graph's own clause, and it answers
with the vertices that survive: `SELECT dense_id … WHERE <predicate>` per vertex table, `UNION ALL`.
**The predicate runs as Mosaic wrote it** — nothing is translated. Which table a clause filters is
[the clause rule](#the-clause-rule-column-predicates-or-a-semi-join-on-identity): a table that cannot
answer a clause is not filtered by it, which is what a `WHERE` over a union of the tables would do;
a clause no table can answer is `graph/unfilterable`, and the graph is drawn unfiltered rather than
as filtered.

**A filtered-out vertex is greyed, never hidden.** The surviving ids become cosmos.gl's
`highlightedPointIndices` and the links between two of them `highlightedLinkIndices` — cosmos.gl does
not grey a link by itself. No buffer is uploaded, so a running layout is never reset by a brush.

**The reader's pick is published from the client.** A lasso, a marquee, a click or a host's
`GraphSelect` is a `clauseSemiJoin` on `dense_id`, labelled with the selection's own label, whose
source is the graph, so the crossfilter applies it to every client whose rows carry a `dense_id` and
skips it for the graph — a canvas that greyed all but a lasso of thirteen would hide the
neighbourhood the reader was looking at. Retracting it where it was published — a chip's remove,
the page's reset — calls the graph back, and the pick leaves the canvas too.

**It replaced "the graph listens to the selection; it is not a client"**, under which the graph
translated mosaic-sql's nodes into scan's typed filter, refused every node it could not translate,
ran the filter as a second scan, and hid the losers by uploading every position again with `NaN` —
which snapped a running layout back to where the corpus had put it. A client runs the predicate it
is handed, and a mask is config.

**What would reverse it:** the greyout measured too slow at the largest scale — the index lists are
built on the main thread — which moves them into a shader; or a reader who needs filtered vertices
gone rather than grey, which brings hiding back as a size of zero, still with no position upload.

*Held by* `packages/graph/src/core/client.ts`, `GraphClient`, `publish`;
`packages/graph/src/core/store.test.ts`, "asks the coordinator which vertices survive, and keeps every
buffer it has", "runs the predicate as Mosaic wrote it, on every table that has its columns",
"refuses a clause no vertex type can answer, as graph/unfilterable, and draws the graph unfiltered",
"publishes the reader's pick as a semi-join on dense_id, and is exempt from its own clause";
`packages/graph/src/render/renderer.test.ts`, "greys out a filter with config alone: no upload, no
render, links said out loud"; `packages/graph/src/render/motion.test.ts`, "is what the filter keeps,
and the links whose two ends it keeps".

## The clause rule: column predicates, or a semi-join on identity

**A clause on the page's selection is one of two things.** Either it is **column predicates on the
same relation** — a brush, a pick, a search: `hour BETWEEN 2 AND 5` names `hour`, and only a relation
with an `hour` answers it. Or it is **a semi-join on vertex identity**: `dense_id IN (3, 4)`, or
`dense_id IN (SELECT …)` over any relation at all. A relation answers a clause when it has every
column the clause names *on it*, and a subquery's columns are not among them — they are another
relation's. So a semi-join on `dense_id` names `dense_id` alone and every vertex table answers it,
whatever its subquery reads: a dashboard over an edge table, a rule's findings, an answer to a
question — each filters the graph, and the graph's pick filters each of them, through the one
identity they share.

`clauseSemiJoin(key, ids | query, { source, label })` in `@kanzo-tech/mosaic` is the constructor of
the second form, built from mosaic-sql's nodes; `clauseColumns(filter)` is the reading of both, and
`GraphClient` applies it clause by clause. Neither names the graph: the key is the caller's, and a
relation keyed by anything else crosses the same way. `graph/unfilterable` is what is left of the
column form — a clause no vertex table can answer.

**Any panel is a client of the selection by the same protocol.** `useChartQuery` is a panel's query
filtered by the live selection and re-run when it changes; a panel over a union of relations reads
`clauseColumns` to apply each clause where it can, as the graph does; and `FilterChips` over the
crossfilter is the scope every client is under — a semi-join wears its publisher's label.

**It replaced a graph that answered only column predicates**, which read every column of every
clause, subqueries included, so a set of vertices found in an edge table or another type named
`src` and `dst` and was refused. The alternative was a second clause kind the graph alone
understood; it would have filtered the graph and nothing else.

**What would reverse it:** an identity two corpora do not share — two corpora attached on one page,
whose `dense_id`s collide — which would make the key a pair, `(corpus, dense_id)`, and the semi-join
a tuple; or a relation whose rows carry a vertex's IRI and not its `dense_id`, measured common enough
that joining through the identity column on every read costs more than carrying the id.

*Held by* `packages/mosaic/src/clause.test.ts`, "builds a semi-join on identity from keys, or from a
statement that selects them", "names the key alone: a subquery's columns are another relation's";
`packages/graph/src/core/store.test.ts`, "answers a semi-join on dense_id on every table, whatever
relation its subquery reads", "publishes the reader's pick as a semi-join on dense_id, and is exempt
from its own clause", "lets the pick go when its clause is retracted where it was published";
`packages/ui/src/charts/filter-chips.test.tsx`, "names a semi-join by its publisher's label, and
counts its members when they are keys".

## ADR 0001 — the canvas holds the whole graph

fossil cites this decision by its number, so the label stays.

**The canvas holds the whole graph.** The links — one statement per relation — and the bound
columns of every vertex table are read into arrays sized from `fossil_tables`' `rows` and uploaded to
cosmos.gl once. **Detail is fetched, not carried**: a focused row, a label's text, a hover card and a
search are statements of their own, read when needed. **Identity is an id, and the id is the
index**: a vertex table is the contiguous range `first_id … first_id + rows − 1`, so its answer in
`dense_id` order is written into its own slice of every buffer and nothing is resolved row by row.

It rests on one premise: **the graph is not edited.** It is fossil's compiled output, so what was
loaded stays true until the host attaches another corpus.

**What would reverse it:** a corpus whose first paint or memory passes a threshold agreed with the
owner, or one past cosmos.gl's link addressing (see [*A dense id is a buffer
index*](#a-dense-id-is-a-buffer-index)). Then a partial read comes in **behind the loader** — a
`WHERE` on the statements it already runs — never a prop, and never a camera in the store.

*Held by* `packages/graph/src/core/store.test.ts`, "reads the structure from fossil_tables and
fossil_columns, and every vertex by its dense_id"; `packages/graph/src/index.test.ts`, "ships a canvas
that owns the renderer, and neither load nor Loaded".

## Position is a channel

`x` and `y` are bindings, Cosmograph's `pointXBy` and `pointYBy`. **Both bound, the data places the
points and nothing simulates. Unbound, they start from a seeded Gaussian and cosmos.gl's force
simulation runs on the GPU** — `simulate` overrides either way. `cluster` feeds `setPointClusters`.
fossil's writer stopped carrying a layout because a picture is a view's choice, not the corpus's:
the same graph is a map with `lon`/`lat`, and a force layout without them. How long the layout
cools, the square it runs in and when it hides links follow the vertex count;
[Layout and camera](/docs/graph/layout#how-the-layout-scales) has the rules and the gate that set
them.

**What would reverse it:** a layout worth computing offline again — a settle time past what a reader
waits, at the scale that exists. Then fossil writes the columns and the host binds them, and nothing
here changes.

*Held by* `packages/graph/src/render/motion.test.ts`, "runs when the positions are a start, stands
when they are data, and simulate overrides both", "cools in 600 frames up to 200,000 vertices and 240
past them"; `packages/graph/src/core/store.test.ts`, "starts a layout from a seeded square when x and
y are unbound, the same start every time", "draws the data's positions when x and y are bound, and
leaves a table without them unplaced"; `packages/graph/src/render/renderer.test.ts`, "runs the layout
by itself when x and y are unbound, in the square and with the decay for its size".

## The viewer costs what cosmos.gl costs

At 200,000 vertices, measured on 2026-09-30 with `graph-bench`'s `measureViewer` in a foreground
window, the viewer's p95 frame interval was **9.0 ms against 9.3 ms for cosmos.gl alone** on the same
positions and camera path; the gate is 15%. The difference had been ours, and each cause is now a
rule:

| the cause | the rule |
|---|---|
| every upload animated for cosmos.gl's default 800 ms | `transitionDuration: 0` |
| buffers re-uploaded on every change | positions and links upload once per corpus; the rest by kind |
| a filter re-uploaded every position | a filter is config: highlighted indices |
| a selection called `render()`, which walks every point and link in JS | a state change is `setConfigPartial` |
| a hover re-rendered the canvas and read positions back from the GPU | the hover card re-renders; the renderer reports where the point is |
| camera events reached the store | the camera reaches nothing |
| painting allocated per link, and labels sorted every vertex | arrays allocated once; labels picked in one pass |
| the canvas re-rendered on every `setOptions` | parts read the fields they show |

**What would reverse it:** the same measurement outside 15% with the cost in our code. That adds a
row here.

*Held by* `packages/graph/src/render/renderer.test.ts`, "constructs cosmos.gl with no simulation and
no transition", "a camera move notifies nobody", "a selection sets config and calls no render and no
setter"; `packages/graph/src/parts/parts.test.tsx`, "re-renders the card on a hover, and not the
canvas".

## The layers, and the reference each one copies

Each layer has a named reference whose shape it takes. A layer with no reference is a black box.

| layer | reference | owns | owns nothing of |
|---|---|---|---|
| **core** — the reads and the store | TanStack Query's `QueryObserver` | what is read, once, and the state a reader selects from | React, the DOM, cosmos.gl |
| **client** — the bridge | Mosaic's `MosaicClient` | the crossfilter's predicate as surviving ids, and the clause the graph publishes | the coordinator's connection |
| **render** | cosmos.gl's own buffer API | typed arrays → cosmos.gl, one upload per changed kind, one render per frame | what to read |
| **adapter** | TanStack Query's core/adapter split; Ark's root/provider/context | the store's lifetime in React, and the context the parts read | how the graph loads |
| **parts** | Ark's flat parts over one context | the canvas element, legend, toolbar, inspector | any product's policy |

Every module stays under four hundred lines:

```text
packages/graph/src/
├── core/                     no React; nothing here imports cosmos.gl
│   ├── source.ts             the catalog's statements: structure, columns, links, a row, titles, search, neighbours
│   ├── client.ts             GraphClient — the crossfilter's survivors — and the clause the graph publishes
│   ├── load.ts               answers → buffers by dense_id; the seeded start; the layout's square
│   ├── channels.ts           Plot's bindings, and the columns they read
│   ├── store.ts              createGraph(options): subscribe · getSnapshot · setOptions
│   ├── state.ts              the options, the state a host selects from, and the store's shape
│   └── categories.ts         the categorical domain, fixed before the graph loads
├── render/
│   ├── renderer.ts           cosmos.gl's lifetime, dirty flags by kind, one render per frame
│   ├── motion.ts             how long a layout cools, when it hides links, whether it runs, what is in full colour
│   ├── placement.ts · camera.ts   where bound positions sit in the square; who holds the camera
│   └── graph-looks · graph-model · graph-sim · obligations · css-color · webgl
├── react/                    use-graph · use-graph-state · graph-root · use-graph-prefs
├── parts/                    the canvas, legend, counts, toolbar, inspector, search, looks; overlays · gesture · shape-glyph
├── index.ts
└── section.ts                the ./section entry
```

**What would reverse it:** a layer whose reference stops describing what it does. Then either the
page names a better reference, or the behaviour is in the wrong layer.

*Held by* `packages/graph/src/layers.test.ts`, "keeps every module under four hundred lines", "keeps
the core free of React and of cosmos.gl".

## The renderer uploads once, and renders once a frame

cosmos.gl 3.4 replaces a whole buffer per setter, so **what changed** is decided per kind of
buffer:

- **A corpus uploads positions and links once**, and binding `x` or `y` uploads positions again. A
  binding, a look or a theme change uploads colours, sizes and shapes.
- **A filter and a state change upload nothing.** The surviving ids, a selection and a focus are
  config — the ids are the indices — and call no `render()`.
- **One frame renders once, and only for an upload.** Every dirty flag is discharged in one
  `requestAnimationFrame`.
- **Nothing animates.** `transitionDuration` is 0.
- **The layout runs by the rule above**, from wherever the points are. A drag moves a node and holds
  nothing: there is no pinning, because a held node is a second state beside the selection that no
  panel can read, and an arrangement worth keeping is a placement.
- **The camera is cosmos.gl's.** A zoom repaints the overlays and reaches no store; `render/camera.ts`
  owns who holds it, and [Layout and camera](/docs/graph/layout#the-camera) says when it moves.
- **The arrangement is the store's.** A destroyed renderer writes cosmos.gl's positions and the camera
  back with `store.keep`, and the next one uploads them and goes on as the layout was: model and
  view, the way cosmos.gl's own `setPointPositions` / `getPointPositions` split them. A canvas that
  is not shown holds no GPU context; a new geometry drops what was kept.

**What would reverse it:** cosmos.gl gaining a sub-range upload, so a binding could upload only what
it changed; or a picture that needs a transition to be read, measured against the frames it costs.
The arrangement goes back to the renderer if reading every position back on detach — one `readPixels`
of the position texture — costs a switch of views more than a re-layout does.

*Held by* `packages/graph/src/render/renderer.test.ts`, "uploads positions and links once per corpus,
and renders once", "repaints colours, sizes and shapes on a look change, and uploads no geometry",
"starts and stops with the simulate prop, after the first load", "leaves a dragged node free, with or
without a layout running", "leaves the points and the camera to the next canvas, which starts settled
from them and runs nothing", "drops what it kept when the geometry changes, and the next canvas places
the new one";
`packages/graph/src/react/graph-root.test.tsx`, "does not rebuild the renderer because a callback
changed identity".

## The React API is a store and an adapter

The graph's state changes outside React and at frame rate, so the core owns it as a **store** in
TanStack Query's observer shape, and React subscribes:

- **The core** is `createGraph(options)`: `subscribe`, `getSnapshot`, `setOptions` and `destroy`. It
  knows nothing about React. The first subscriber connects its client to the coordinator and the last
  one lets it go.
- **The adapter** is `useGraph(props)`: `useBaseQuery`'s three moves — create the store once in
  `useState`, subscribe with `useSyncExternalStore`, hand it the latest props with `setOptions` in an
  effect whose dependencies are the props themselves. Callbacks are read through a ref, so an inline
  `onFailure` is never a change of options.
- **The surface is Ark's.** `useGraph` creates the api, `GraphRoot` is `useGraph` plus the context,
  `GraphRootProvider` takes an api a host built, and `useGraphContext` reads it — `useDialog`,
  `DialogRoot`, `DialogRootProvider`, `useDialogContext`.
- **The api is the commands, and the state is a selector.** The api is stable for the root's life,
  and `useGraphState(selector)` reads a slice and re-renders only when it moves. `status` is the
  data's life and `motion` the layout's — two axes,
  [Layout and camera](/docs/graph/layout#status-and-motion-are-two-axes).

**What would reverse it:** the store costing more than it buys — measured as renders per hover with
and without `useSyncExternalStore`.

*Held by* `packages/graph/src/core/store.test.ts`, "keeps getSnapshot stable between notifications",
"connects its client on the first subscriber and lets it go with the last, as StrictMode does twice",
"is idle only once the graph is loaded and drawn, and has none without a corpus";
`packages/graph/src/react/graph-root.test.tsx`, "does not reach setOptions on a render that changed
no prop", "keeps the api's identity across hovers, and re-renders a part only on the slice it
selects"; `packages/graph/src/index.test.ts`, "is Ark's four: useGraph creates, GraphRoot provides,
GraphRootProvider takes, useGraphContext reads".

## The parts own the vocabulary; the host owns the policy

`GraphRoot` is a facade: the host names a catalog and a coordinator and a few props, and the parts
under it read the root.

- **`GraphCanvas`** — the element, and what the look declares over it: grid, vignette, labels and
  the hover card, plus the marquee and lasso gesture.
- **`GraphLegend`** — the categorical scale, or the vertex types when nothing is bound, with how many
  of each are drawn. Its domain is fixed before the graph loads, so a row never moves.
- **`GraphStatus`** — where the graph is, in one word: Loading, Laying out with the percentage, Ready,
  Failed. It owns the fold of the two axes, `status` and `motion`, because a host that folded them
  itself read `status` alone and said "idle" over a running layout. What would reverse it: a host
  that needs the two axes apart in its footer, which `useGraphState` already gives it.
- **`GraphCounts`** — the corpus and what the page's filter keeps of it, in one sentence: "N nodes"
  unfiltered, "X of N nodes match" filtered. "Drawn" was the wrong verb — a vertex the filter drops is
  greyed, never hidden — and unfiltered it always read "N of N". A footer carries it, which is why it
  is not the legend's last line.
- **`GraphToolbar`** — the tools, the selection, zoom and fit, and the layout's transport.
- **`GraphInspector`** — the focused vertex as a card, Linkurious's inspector: its row in
  `fossil_columns`' order, grouped as identity, values and dates, its neighbourhood counted per relation
  and direction, Zoom / Focus / Copy, and a render prop for fields a product adds.
- **`GraphSearch`** — a palette in cmdk's shape, Raycast's and Linear's: a `LIMIT`ed `ILIKE` per pause
  in typing, with Bloom's `type:` and `<column>:<value>` prefixes, grouped by type and counted past the
  limit; picking one is `reveal`, and the root remembers it.
- **`GraphSelect`** — a selection the host offers, as a toggle: `load` reads the ids when pressed,
  and pressed is derived from the live selection, never stored beside it.
- **`GraphLooks`** — the three looks as presets over `GRAPH_SECTION`'s axes, with the axes always in
  view under them. It writes preferences rather than reading the root, so it needs the theme provider
  and no `GraphRoot`.
- **`GraphPlacement`** — Force, Map or Clustered, with the corpus's fields to bind inside the checked
  card. Controlled, because `x`, `y` and `cluster` are the root's bindings and the host holds them.

**A selection names its gesture, never its host's panel.** `SelectionSource` is the canvas's own
gestures — `marquee`, `lasso`, `node` — and `external`, any selection a host set through `select`,
whose identity is its `label`. It was `order` and `ask` besides, which were one host's two panels
spelled into the renderer's type; a second host would have had to add its own or borrow those.
What would reverse it: a part of this package that must tell two host sources apart, which a
`label` cannot.

**Names are data on the root.** The catalog names no category values, so the host passes
`categories` on the root, where the legend, the hover card and the inspector all read it.

**Policy stays out, through the root's callbacks** — `onSelect`, `onFocus` and `onFailure`. No part
takes a callback of its own, and `GraphSelect`'s `load` is not one: it answers *which vertices*, data
the part reads when pressed, and a failure of it reaches `onFailure` like any other read's. `onFailure` is the one required prop: unhandled, a browser with no WebGL
context shows an empty box. It receives what was thrown, whole — a read's own error with its `code`,
or a `GraphError`: `graph/no-webgl`, `graph/context-lost`, `graph/no-positions`, `graph/nothing-to-draw` or
`graph/unfilterable` — so a host chooses what to show by code.

**What would reverse it:** a part a second host cannot use without a prop that encodes that host's
policy. That part goes back to the call site and is deleted from the package.

*Held by* `packages/graph/src/index.test.ts`, "carry no callback but the root's";
`packages/graph/src/parts/parts.test.tsx`, "derives pressed from the live selection, so a gesture or
another label unpresses it", "draws the domain before the graph has loaded, named by
the root", "reads the focused vertex's row with one statement, grouped, and draws a host's extra fields after
its values"; `packages/graph/src/core/store.test.ts`, "fixes the categorical domain before the
graph loads".

## Attaching is the host's

**Where the corpus is and what signs it are the host's**, and so are attaching and detaching: `open`
answers the `close` that gives the catalog back. The graph is handed a name and the page's one
coordinator — one per page, because `MosaicProvider` makes its coordinator vgplot's active one and
that setter is process-wide. [Discovery workspace](/docs/graph/workspace) is the wiring, and
[the workspace showcase](/docs/showcases/workspace) the reference composition: what it writes is the
product's — the pairings of look and channels, the hall's name in the inspector, the panels — and
nothing in it reads a renderer or a buffer.

**The graph bounds the one wait it owns.** The waits inside `open` are fossil's, and the host awaits
them before it names the catalog; the reads after that have no deadline. cosmos.gl's `ready` never
settles when no device can be made, so after 10 s the root fails with `graph/no-webgl` and
`data.after`.

**What would reverse it:** a host that draws a corpus on a second engine — two coordinators, two
caches — which is the cost this design removed; or the composition needing a prop only one host
passes, which is the parts rule above firing.

*Held by* `packages/graph/package.json`, `//peers`, `//fossil`;
`packages/graph/src/render/renderer.test.ts`, "fails with graph/no-webgl and when the deadline fired,
if WebGL exists but no device ever comes up".

## Where the points sit in cosmos.gl's square

cosmos.gl simulates in `[0, spaceSize]²`: gravity pulls toward its centre and many-body bins points on
a grid over it. **The square is decided in one place, never written where it is used.** Unbound, it
is the layout's own — `spaceFor`, 4,096 up to 200,000 vertices and 8,192 above, measured. Bound, it is
the data's extent, **centred in the square at its own scale** — an extent left where it was contracts
toward a corner the moment a layout runs over it — and scaled down only past half the device's
`MAX_TEXTURE_SIZE`, where cosmos.gl would shrink the square under the positions anyway.

**One case does not fit.** cosmos.gl's zoom floor is `1e-3`, and framing a five-million-vertex extent
at 800×600 wants 0.000151, so only part of it fits on screen.

**What would reverse it:** cosmos.gl making `spaceSize` init-only, or a simulation whose centre is a
parameter rather than the square's middle — then the placement is a config value and not an upload.

*Held by* `packages/graph/src/coordinate-box.test.ts`, "never writes a number where cosmos.gl asks
what the space is", "declares no coordinate-space constant of its own";
`packages/graph/src/core/load.ts`, `spaceFor`; `packages/graph/src/render/renderer.test.ts`,
"centres bound positions' extent in it, at the data's own scale", "scales the extent down only past
the box the device simulates in", "frames bound positions' extent before it draws anything, and only
once".

## A dense id is a buffer index

`VertexId` is a `number`: fossil's `dense_id`, numbering every vertex of the corpus `0 … V − 1`, each
table one contiguous range. It is the index into every buffer, the value a selection publishes, and
the key the inspector reads by.

**The limit is cosmos.gl's.** It addresses a link's ends with a `Float32Array`, exact up to 2²⁴ —
about 16.7 million ids. Past it, a link's end silently rounds to a neighbouring id, so a corpus near
it is the day ADR 0001's partial read arrives, not a day to widen a type.

**What would reverse it:** a corpus that breaks density — ids with holes, or a table that is not one
range — which brings back a map built once at load; or a corpus past 2²⁴ vertices.

*Held by* `packages/graph/src/core/source.ts`, `Float32Array`; `packages/graph/src/core/store.test.ts`,
"reads the structure from fossil_tables and fossil_columns, and every vertex by its dense_id".

## A look is form, and a channel is a binding

`Look` is form and carries no encoding. What a channel carries is **bound on the root**, under
Plot's names and Plot's rule that a CSS colour is a **constant** and anything else is a **column**:
`fill`, `symbol`, `r`, `stroke`, `title`, and the position channels `x`, `y` and `cluster`. `symbol`
stands beside `fill`, so identity may be drawn as colour, as shape or as both. `stroke` absent tints
each link by the vertex it leaves; `r` absent is degree.

**A binding is a column read.** `fill`, `r` and `cluster` as columns are read where a table has them.
`fill` as a constant and `stroke` are never read, and `symbol` is read only as the one categorical
column when `fill` is a constant or absent. `isColour` is the constant test, narrowed to `var(…)`, a
hex and the colour functions, so **a bare word is always a column**. A theme may not rebind an
encoding — Vega-Lite's `config` rule.

**The case that does not fit.** Ink's radius floor exists because it spends shape on identity and
size on degree at once, so that obligation is graded against the composition.

**What this does not touch.** The graph holds **one** categorical column, and it authors no colour;
it reads the page's categorical scale.

**What would reverse it:** the composition check never firing — if every host that binds `symbol`
also asks for the form bundled with it, the pairing was the abstraction.

*Held by* `packages/graph/src/render/graph-looks.ts`, `Look`; `packages/graph/src/core/channels.ts`,
`Channels`, `bindingOf`; `packages/graph/src/render/obligations.ts`, `gradeComposition`;
`packages/graph/src/core/store.test.ts`, "sizes by degree when r is unbound, and by the column when it
is bound", "colours by vertex type unless fill binds a column".

## A look declares what it changes

A look declares only what it moves from the shared defaults, and the preferences panel offers the
**axes a reader can name** — `marks`, `edges`, `additive-links`, `labels`, `vignette` — which
recover the three shipped looks and combine into others. `edges` and `labels` are Cosmograph's
configuration read as choices: `showLinks` and `curvedLinks` as Hidden, Straight or Curved, and the
hovered, top and dynamic labels as one ordered scale, None to All, because a reader asks *how much
text* rather than which of three switches. `additive-links` stays its own switch: it is how links
composite, not the path they take, and Nebula is additive *and* straight.

| field | nebula | atlas | ink | nebula → atlas |
|---|---|---|---|---|
| point radius | 2 → 8 | 2.2 → 9 | **4 → 13** | +10% / +12.5% |
| link opacity | 0.42 | 0.45 | **0.28** | +7% |
| link width | 0.6 | 0.7 | 0.5 | +0.1 px |
| link fade | 200–1400 | 220–1500 | 180–1200 | ±10% |
| **link curve** | 0 | **0.12** | 0 | straight → bowed |
| **additive links** | **yes** | no | no | on → off |
| **label budget** | **14** | **26** | **40** | ×1.9 |
| **vignette** | **yes** | no | no | on → off |

Six of the ten fields separate Nebula from Atlas by 7–17%, below a luminance JND of 6.5–11.3 ΔL\*.
**Ink is a real form.** An empty look is Atlas.

**The three names live on as presets over the axes, not as a fourth axis.** `PRESETS` writes each
look as axis values and `GraphLooks` offers them as cards, GitHub's appearance settings: pick by
looking, then customise. A look is worn exactly when the resolved axes equal its own, so there is no
stored name to disagree with them, and `useGraphPrefs` answers `preset` for a host that pairs
channels with a look — the pairing stays the host's, because a look is form. A `preset` preference
was the alternative and is refused: it would be a key no reader reads, which the axes guard forbids.

**What would reverse it:** a reader telling Nebula from Atlas in a blind pairing on those six fields.

*Held by* `packages/graph/src/section.test.ts`, "still draws the three pictures the three names drew",
"wears the three pictures as presets, and knows one when the axes are it";
`packages/graph/src/render/graph-looks.ts`, `lookFrom`.

## What is still open

- **Names for a channel's values.** The catalog names no categories, so the host passes
  `categories`. If `fossil_columns` ever carries them, the catalog's win.
- **A column two types share.** A column clause carries no table, so a filter on `name` filters
  every vertex type that has one — a `WHERE` over a union. A host reading it wrongly would reopen it;
  a clause that means one type is a semi-join, whose subquery names it.
- **The greyout at scale.** The surviving-id query and the two index lists have not been timed at
  500,000 vertices.
