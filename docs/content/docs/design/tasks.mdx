Two things in the platform asked a model to decide something. **Ask** (`@kanzo-tech/ai/data`) let an
agent pick a relation, its fields, an aggregate and a filter in one call, among every relation
`answerRelationsOf` enumerated. **Fossil's assistant** (keasy's new-graph wizard) asked one call,
`writeProgram`, for a whole program, which the checker read only afterwards. Both were an agent with
a free hand and an oracle that ran too late.

They became one pattern, a **Task**: the model fills a small artefact whose shape is a JSON Schema, an
oracle that is a fact of the data or of the program checks it, and a bounded loop sends the typed
failures back or turns them into a question for the person. Keasy's side (the assistant, a guided
chat) and fossil's side (`fossil-profile` and the mapping grammar) are on their own sites and link here.

## The premise: a small model, in the browser

**The system is designed to work with a small local model.** It is the premise that makes the rest
make sense — bounded Tasks, `compute` steps, constrained decoding — and it changes what the
evaluation set is for: it does not decide *whether* a small model is good enough, it points at *which
Task is not yet bounded well enough*. Every failure is a lead to move one more fact into a
deterministic step.

The model runs in the page through [WebLLM](https://github.com/mlc-ai/web-llm), behind the AI SDK's
`LanguageModel` by way of `@browser-ai/web-llm`. The repository ships no gateway, key or forward.
**Remote models are not designed.** `LanguageModel` stays open and the library enforces no locality;
[Asking data](/docs/design/ai#the-model-is-open-and-where-it-runs-is-not-the-librarys-to-enforce)
has why, and the work list the day one is admitted.

**What would reverse it:** a Task that, after everything computable has been moved into `compute`
steps, still fails the evaluation set with a small model. Then that Task, and only that Task, takes a
remote model, and the work list on that page starts with it.

## A Task has four ports

```
Context ──limits──▶ Model ──proposes──▶ Verify ──diagnostics──▶ Repair
closed vocabulary   local by default    deterministic oracle    bounded policy
        Contract (a JSON Schema) ──constrains──▶ Model
```

- **Context** is a closed vocabulary computed from the data: the linker's candidates for Ask, the
  Profile's columns, keys and inclusions for the assistant. Nothing is described to the model that
  the model is not allowed to name.
- **Contract** is the artefact's JSON Schema, with enums from the context. The provider decodes
  against it, so a name that does not exist cannot be written.
- **Verify** is a list of oracles, each a fact: reachable, compiles, non-empty, conforms to the
  shape, answers the competency question.
- **Repair** reads the oracles' typed diagnostics. A `fixable` one goes back to the model with its
  location, a bounded number of times. A `decision` — two candidate keys, a property with no column
  — goes to the person as options, never as free text; a decision that declares a safe default is
  taken, recorded as an assumption, and can be changed later.

The states — `linking`, `drafting`, `verifying`, `repairing`, `needs-input`, `done`, `failed` —
travel as data parts of the message, the AI SDK's standard form for application data, so `useChat`
does not change. Presenting leaves the Task and becomes the UI layer's: a Task is tested without
React and runs the same on a server or in a browser.

**What would reverse it:** a free agent with the same small model that matches the Task's execution
accuracy across the whole evaluation set.

## Repair is bounded and reads how a generation ended

**A Task's loop is bounded in attempts (three by default), keeps only its last attempt in the
feedback, and reads why a generation ended before it reads what it wrote.** The AI SDK reports a
finish as `stop`, `length`, `content-filter`, `tool-calls`, `error` or `other`, and `output` throws
unless the final step is `stop`. The loop's rules, one per ending:

| Ending | The loop | Because |
| --- | --- | --- |
| `stop` | runs the oracles; a `fixable` diagnostic goes back, a `decision` goes to the person | the loop's job |
| `llm/truncated`, `reason` `"context"` | retries once with the diagnostics only, the previous answer dropped, and a Task's compact context if it declares one | the context filled, so the retry must be shorter than the attempt that filled it |
| `llm/truncated`, `reason` `"budget"` | retries once with a larger `maxOutputTokens` | the Task capped the answer and the cap was hit; Anthropic's guidance for the same condition is to retry with a higher `max_tokens` |
| `content-filter`, `error`, `other` | does not repair; the failure goes to the host whole | the same request meets the same refusal |
| `llm/silent` | does not repair | a model that made no progress will not on a second asking, and its turn is already free |
| `AbortError` | ends | it is the person's, never a failure |

**The failure that decided this.** `generate()` threw `llm/truncated` and `runTask` had no catch
(`packages/ai/src/task/index.ts`), so the first truncation ended the Task instead of becoming a
repair. The repair prompt embedded the whole previous answer (`JSON.stringify(value)`) with the
diagnostics, so for a model near its context an oracle failure became a truncation on the retry:
a failed mapping in Fossil text is as long as the context allows. The feedback replaces the last
attempt's, never accumulates, and a truncation is the signal to drop it. **Nothing counts tokens**:
the truncation is the budget, as [Asking within a context](/docs/design/ai-context#the-linker-is-the-budget)
has it for the linker. `reason: "budget"` is new with `maxOutputTokens`; the retry factor is the
Task's, and two is the default.

**What would reverse it:** evidence on a device that runs the model that a retry after a truncation
never succeeds; then the retry goes and the failure is shown at once. A finish the SDK adds that a
retry can fix joins the table.

*To be added:* `task.test.ts`, "repairs a truncated answer once, without the previous answer in its
feedback", "does not repair a refusal or a silent model" and "ends on an abort without a failure";
the scripted model's replies gain a finish (`length`, `content-filter`), since these need a double
that ends a generation each way.

## Three kinds of step

**A step is deterministic when its answer is a fact of the data or the program** — columns, keys,
paths in the join graph, whether it compiles, whether a competency question returns rows.
Interpreting what someone meant is not a fact, and turning it into hand-written rules (written
synonyms, heuristics over the question) only moves the guess into code, where it is more fragile and
nobody evaluates it.

| Kind | When | Examples |
| --- | --- | --- |
| `compute` | The answer is a computable fact | Profile, the value linker, the resolver, the checker, a dry run |
| `propose` | Intent must be interpreted or a design chosen | Ask's planner, competency questions, shapes, the mapping |
| `decide` | More than one answer is valid, and it is the person's | The key of an award; counting universities or awards |

The working rule: every time a `propose` fails on the evaluation set, look at whether part of what it
decided was a fact. If it was, it moves into a `compute` and the `propose` shrinks.

**What would reverse it:** nothing found. The rule is a definition of where a step belongs, and it
is reopened per step, by the evaluation set, not as a whole.

## Ask: from agent to form

**The model fills the spec, and the spec says its joins.** It writes every field as a dotted path
from the type it measures, as Malloy writes one from its source — `affiliation.university.name`,
`category.name` — and `JoinResolver` turns the paths into the relation the answer shows and the
semi-joins it is narrowed by. Nothing is chosen: a path either names steps the join graph has, or it
is a diagnostic at its pointer before anything runs. A follow-up such as *and in Germany?* is still a
patch to the previous spec, one more `where`.

```
Question ─▶ Linker ─▶ Planner ─▶ JoinResolver ─▶ tileQuery ─▶ Check ─▶ Chips
            words→     fills     paths → relation  the tile's   empty,   editable
            types      paths     filters → crossing  SQL        reach
```

The model touches only the planner, which writes paths from a closed enum. Every chip opens its
computed alternatives, and editing one re-checks without the model. The sentence in the reply is
written from the rows, not by the model.

This replaced the agent's relations ([Asking data](/docs/design/ai#which-relations-are-offered)), its
token budget ([Asking within a context](/docs/design/ai-context#the-linker-is-the-budget)) and a
resolver that *chose* the relation, which the owner rejected on 13 October 2026 as a heuristic:
*base it on existing things, don't invent.*

### A field is a path from what is measured

**The reference is Malloy.** A Malloy source declares its joins, and a query names a joined field by
its dotted path from the source — `group_by: carriers.nickname`, `aircraft.aircraft_models.manufacturer`
— in `group_by`, `aggregate` and `where` alike; a join that no field names is not in the SQL. Here the
join graph is the source's declarations, already: `JoinGraph`'s edges are the joins, and the measured
type, the spec's `of`, is the source. So a spec's every field — `show.x`, a measure's `field`,
`color`, `facet`, `trend`, a table's `columns`, each `where[].field` — is a path:

| Segment | Means | Reference |
| --- | --- | --- |
| `category` | the out-edge labelled `category` that leaves the type reached so far | Malloy's join name |
| `^laureate` | the in-edge labelled `laureate`, walked backwards: the awards *of* a laureate | SPARQL 1.1's inverse path `^iri` (§9.1); ShExJ's `inverse: true`, `^` in ShExC |
| `Award_category_Category` | the edge by its name, where two edges of one label leave the same type the same way | Malloy's join names are unique in a source; fossil's edge `name` is unique because the label repeats |
| `name` (last) | the column of the type reached | Malloy's field |

The empty path is the measured type: `gender` on `of: "Laureate"` is the laureate's own. Paths are
walked from the root, never back along the edge just taken, within three hops.

**A relation's column is named by its path, everywhere.** `relationQuery` names a column by the path
that reaches it from the root — `year`, `affiliation.university.name`, and on a self-join
`knows.firstName` — so the name Ask's model writes is the name the SQL has, the name a dashboard's
tile stores and the name a chip publishes a clause on. The root's key is on the empty path, so it
keeps its bare name, which every crossing depends on, for the reason
[the graph's page](/docs/design/graph#a-relations-columns-are-named-by-their-path-and-the-roots-key-is-bare)
gives. It replaced `<alias>.<column>` (`University.name`, `Person2.firstName`), which gave a field two
spellings and a self-join a name that is not a type.

**The schema offers only paths the graph has.** The spec is the one property, `spec`, of an object,
and its schema is an `anyOf` with one branch per type the linker offers, each `of: { const }` beside
its own enum of paths under `$defs`, so a decoder cannot write a path from one type on an answer about
another. The object is there because a tool's input schema must be one: Anthropic's and OpenAI's APIs
refuse a root `anyOf`, and the branches were once the root. The model writes `{ spec }` and the
schema's `validate` hands the Task the spec. A provider that does not constrain is checked by
`JoinResolver.relation` and `field`, whose misses — `join/no-step`, `join/no-field`, `join/branches` —
are diagnostics at the field's pointer, sent back for a repair. A count may name a path too,
`{ op: "count", path: "affiliation" }` ([Analytics](/docs/design/analytics#count-counts-the-measured-type)).

**What the path removes.** Two questions the resolver answered for the model are written by it now.
*Which way:* *prizes by country* on the Nobel corpus has two countries two hops from a prize; the model
writes `laureate.birthPlace.name` or `university.addressCountry.name`, that is the answer, and the
chip offers the other first. *Which step, when a type repeats:* on `Person>knows>Person` a condition
on `Person` could not say the person or the one they know, so *people who know an Ann* was not
expressible; `firstName` and `knows.firstName` are two strings.

**What would reverse it:** an evaluation set on which the small model, writing paths under the enum,
answers a shape of question worse than the resolver's choice did; then that shape, and only it, gets a
`compute` step back, as a rule with an evidence line, not a search. Or an enum too large to compile at
the linker's widest context: then the field becomes a grammar, `segment ("." segment)* "." column`,
which a Task may already declare. Or a provider that refuses an `anyOf` anywhere: then the branches
fold into one object and the oracles hold each path to its `of`. *Not measured:* the size of the
schema, which lists every path to three hops for each type offered, on a graph like SNB's.

*Held by* `packages/ai/src/data/ask.test.ts`, "is one branch per type offered, each its own enum of
paths from it"; "hands the model an object at the schema's root, and reads the spec out of it"; "says
what the joins refuse: no such step, no such field, two branches, a chip out of reach"; "asks nothing
when two paths reach one field: the model's path is the answer's".

### Physics awards by university, as the model writes it

```json
{
  "of": "LaureateAward",
  "where": [{ "field": "category.name", "in": ["Physics"] }],
  "show": { "kind": "chart", "type": "bar", "x": "university.name", "y": { "op": "count" } }
}
```

In Malloy this is `group_by: university.name` with `where: category.name = 'Physics'` over the
`laureate_award` source. `JoinResolver.relation("LaureateAward", ["university.name"])` is the relation
the answer shows, `LaureateAward>university>University`, whose column is the path itself.
`JoinResolver.field(relation, "category.name")` finds that `category` is not a step of it, so it is read
through the branch `LaureateAward>category>Category` and crossed at the root's key —
`dense_id IN (SELECT dense_id FROM (…) WHERE "category.name" IN ('Physics'))` — and the bars count
`count(DISTINCT dense_id)`, each prize once per university. *Laureates with a Physics prize, by
gender* is `"of": "Laureate"` with `"field": "^laureate.category.name"`: the shown relation is
`Laureate` alone, the condition is read through `Laureate<laureate<LaureateAward>category>Category`
and crossed at the laureate's key, so a laureate with two Physics prizes is counted once.

### A filter off the shown path is crossed in, not joined

**`JoinResolver.crossing`, the semi-join the page already uses.** A condition whose path leaves the
shown relation is read through the branch from the step it leaves at, and narrows the answer as a chip
on another relation narrows a tile: `step key IN (SELECT branch root key FROM branch WHERE …)`. A
condition on the shown relation is its clause, as it is.

**Malloy's way, and what it costs here.** Malloy joins every path a query names into one query (left
outer joins, `join_many` declared on the join) and keeps every aggregate right over the fan-out by
computing it *symmetrically*: `sum` and `avg` over a joined row are deduplicated by key, which its
DuckDB dialect writes as `(SELECT sum(a.val) FROM (SELECT UNNEST(list(distinct {key: k, val: v})) a))`
per group (read in `packages/malloy/src/dialect/duckdb/duckdb.ts`, 13 October 2026).

| | Semi-join (`crossing`) | Joins and symmetric aggregates |
| --- | --- | --- |
| Rows the measure sees | the shown relation's, never multiplied by a filter | multiplied by every many-branch, then deduplicated |
| Measures | `measureExpr` as it is, all eight | a symmetric variant of each; Malloy lists only `count`, `sum` and `avg` as having one |
| mosaic-sql | `InOpNode` over a `ScalarSubqueryNode`, what `crossing` builds | no node for `list(distinct {…})`: raw `sql` in every measure |
| DuckDB-WASM | a hash semi-join on keys, one per branch | the fanned rows held per group in lists, inside the page's memory |
| The page | one way to narrow by another relation: a chip and a condition are the same predicate | a second way beside the crossfilter's |

Where the two agree is every question a filter asks — *awards with a Physics category* is the same set
of awards either way, and a count of them is the same number. Where they differ is a measure *on* the
branch, which is no longer a filter: it is a second shown path.

**Two shown paths must be one path.** The relation an answer shows is one path — what a tile is keyed
by, what a clause is published on, what `relationQuery` compiles. Paths that diverge
(`x: category.name`, `color: university.name`) are a `join/branches` miss, said before anything runs.

**What would reverse it:** a condition whose meaning needs the branch row and the shown row to be one
row — *awards by university where that university's laureate is a woman* — which a semi-join on the
branch's root cannot say; or a question that shows two branches. Either makes the relation a tree,
and a tree is Malloy's: joins, `join_one`/`join_many` declared from the shape's cardinality, and
symmetric aggregates.

*Held by* `packages/ai/src/data/answer.test.ts`, "crosses a condition off the shown path in at the
root's key, counting each person once"; `packages/mosaic/src/crossfilter.test.ts`, "crosses a
condition off the relation in at the step its branch leaves, not the first of its type".

### `JoinResolver` is the one door to the joins

**Resolving a path and crossing a clause are one thing: resolving joins over the graph.** So they are
one class, `JoinResolver` in `@kanzo-tech/relations` (Mosaic's own resolver extended), sharing the
graph and one notion of a step and its key: `steps(relation)`, `paths(root, hops)`, `relation(root,
shown)`, `field(on, path)`, `at(to, from)` and `crossing(from, predicates, to, at?)`. The dashboard
reaches it through the page's selection; Ask reaches the same instance through the same selection, or
one over its graph where there is no page. Nothing of the shortest-path search survives — the walk that
enumerates paths for the schema chooses nothing. `crossing` takes `at`, because a branch says which
step it leaves from: on `Person>knows>Person` a condition on `knows.knows.firstName` is crossed at the
`knows` step's key, where the type-matching rule would have taken the root.

**What would reverse it:** a caller of the joins that is neither a page nor an answer, a second resolver
with no selection; which splits the path half into a module beside the crossing half, not a second
concept.

*Held by* `packages/mosaic/src/crossfilter.test.ts`, "names each step of a relation by its path from
the root, with its key: the root's bare"; "finds the one relation the shown paths lie on, each path
its own column there"; "says why a path is not the graph's, at the segment that is not".

### Two paths of one length are the model's, with the other on the chip

**The model's path is the answer, and the chip on that field offers the other path of the same
length to the same column of the same type first** — `laureate.birthPlace.name` beside
`university.addressCountry.name`. Nothing is asked before the answer is read. *What would reverse
it:* the evaluation set showing readers take the chip's alternative more often than they keep the
model's path — then that shape asks, as a decision with the two paths as its options, through the
question part ([Asking data](/docs/design/ai#a-question-to-the-person-is-the-question-part)).

*Held by* `packages/ai/src/data/ask.test.ts`, "offers the other of two paths of one length to the same
field first".

### Titles name no plural

**A tile's title is *\{measure\} by \{field\}* — *Count by university.name*, *Mean age* — and Ask's
words are the paths it wrote.** No title in any language then asks for a plural, and no labelling
vocabulary carries one: a plural is always derived, and derived English is wrong outside English and
for every irregular noun. The words a field is read by — its `rdfs:label`, in the page's language —
come with [What a field is](/docs/design/fields); until then a field is read by its path.
*What would reverse it:* a labelling vocabulary that carries a plural — then it is read, not derived.

### The sentence after a chart is a minimal template

**A template built only from `Intl` and the data's own words, with its punctuation the host's to
translate.** The figure for a stat; for a chart of a measure by x, the leading two groups of bars and
their value, ties named together through `Intl.ListFormat`, numbers through `Intl.NumberFormat`:
*Univ. of California: 12; Harvard University and MIT: 9.* No verb that needs agreement, no plural
noun, so nothing in it is English but its two separators, which are entries of `useAskChat`'s
`translations` ([Naming](/docs/design/naming#one-prop-translates-translations)). A table or a plot
gets none. It is written once, by Ask's transport, from the rows the answer read, and never stored in
the tile. No reference writes one: Looker's Conversational Analytics and Power BI's Q&A word a reply
with a model, the free hand Tasks take away.

**What would reverse it:** readers reading the sentence as wrong where the chart is right — a tie named
as a lead, a figure without its unit. Then the sentence goes and the chart and its title say it alone;
a model's wording comes back only as a Task with an oracle that checks every figure against the rows.

*Held by* `packages/ai/src/data/ask-chat.test.ts`, "words a bar chart's leading groups with Intl, ties
named together, through its translations".

### Discarded, and what would bring each back

- **`resolveRelation`'s choice of the shortest path** covering the spec's types and the page's
  clauses, and **#199's branches from the nearest step**: a search that guessed what a question meant
  wherever two ways existed and could not name a step of a repeated type. *Back if* the evaluation
  set shows the model writing paths worse than the search chose them, for a shape of question; then
  that shape gets a `compute` step inside `JoinResolver`, not a module beside it.
- **Joins and symmetric aggregates for a filter off the path** (Malloy's, LookML's). *Back if* a
  condition needs the branch row and the shown row to be one, or an answer shows two branches.
- **`<alias>.<column>` as `relationQuery`'s column names.** Two spellings of one field, and a name on a
  self-join that is no type. *Back if* a column name must be a valid identifier somewhere a path
  cannot go; none has been found, since every reader quotes it.
- **A choice put to the person between two paths of one length** gives back the search, as a question.
- **English pluralisation** of a word, and a column named `name`, `label` or `title` standing for its
  type. *Back if* a labelling vocabulary carries a plural, or corpora without IRIs are the common
  case, and then as a host's labels first.
- **`toLocaleString("en")` and a list joined by hand.** The platform has both, in every locale.
  Nothing found would bring them back.

## Suggest and complete stop being the split

`chat` and `complete` mixed three things: a verb, a model size and a context window. **The unit is the
proposal.** `Proposal` has the shape of the LSP's `InlineCompletionItem`: with a range at the cursor
it is a continuation, with the whole value a replacement, with no range a new item. What changes
between surfaces is how a proposal is shown and which oracle backs it, not what is generated.

| Form | Target | Where |
| --- | --- | --- |
| Ghost text | a range at the cursor | free fields; Tab accepts, word by word with ⌘→ |
| Card | no range, a list | competency questions, shapes, mapping rows |
| Chip | a replacement of one field of a spec | Ask's rephrasing; each chip opens its alternatives |
| Choice | a `decision` diagnostic | an ambiguity the oracle found; never free text |

**There is one `Proposal`, the Task's** (decided 13 October 2026). `Assist`'s `{ text, range }` was the
Task's proposal of a string with its `Target` under another name, so `Assist` has no proposal of its
own: it asks for candidates through `propose`, each a `Proposal<string>` whose `target` is `{ replace }`
over the value or `{ add }` in a list, and its continuation is the same `Proposal` with `{ insert }`
at the caret. It still streams, because ghost text is drawn as it arrives. A proposal may carry the
model's `rationale`, which a chip's tooltip reads. A list's offers are a Task's `propose`, and `Chat`
takes them whole: **pressing one sends its value, never its words**, so a starter question is not
re-read by the model. A Task's model is resolved by the Task's name in one place. `AssistEvent`
covers every form and carries no value ([Asking data](/docs/design/ai#what-a-person-typed-and-a-store-held-leave-by-no-default-path)).

## The API

A small declarative surface on top; underneath, only parts that already exist. Whoever writes a Task
declares what the model knows, what it may return and how it is checked. Whoever writes a screen asks
for proposals and presents them. Nobody writes a loop or deduplicates text.

```ts
import { defineTask, runTask, propose, verify } from "@kanzo-tech/ai/task";
import { useTask } from "@kanzo-tech/ai";
import { localModel, loadLocalModel, localProvider, setLocalProvider } from "@kanzo-tech/llm/local";

// A Task: what the model knows, what it may answer, and which facts check it.
export const requirements = defineTask({
  name: "requirements",
  context: (input) => vocabulary(input.profile), // compute: the closed list it may name
  instructions: REQUIREMENTS,
  prompt: (input, names) => `${input.domain}\n${names.join(", ")}`,
  output: (_, names) => questionSchema(names), // the schema, its enums from the context
  verify: [answerable], // an oracle: a fact of the data, never the model's opinion
});

// An artefact that is text in a language declares its grammar instead of a schema.
export const mapping = defineTask({ name: "mapping", grammar: (input) => input.grammar, verify: [compiles] /* … */ }); // fossil's grammarFor gives it

// Once, at the composition root: the models the host's origin serves under /models.
setLocalProvider(localProvider({ baseURL: "/models", worker }));

// The model — the first one served — loaded when the screen opens.
const model = localModel();
void loadLocalModel();

// A screen: a list of checked proposals, and the person's edits checked with no model.
const { proposals, state, propose: ask, edit, dismiss } = useTask(requirements, input, { model });

// One artefact, repaired against the oracles until it holds or the attempts run out.
const proposal = await runTask(mapping, input, { model, onState, temperature: 0 });
```

A `Proposal` carries its `value`, the `Target` it lands at — an LSP `TextEdit` or a JSON Pointer —
and a `Verdict`: accepted (with the decisions it `assumed`), its `Diagnostic`s, or a `Decision` in
the shape of MCP's elicitation, options and never free text.

### Under the hood

Every name above is a thin layer over something that exists. If one of those pieces changes
tomorrow, its row changes, not the API.

| Ours | Over | Dependency |
| --- | --- | --- |
| `defineTask`, `runTask` | `@kanzo-tech/llm`'s `generate` — `generateText` with `maxRetries: 0` — and `Output.object`, which WebLLM constrains with XGrammar, inside a loop of our own: generate, verify, retry with the diagnostics until the attempts run out — Instructor's pattern | `ai`, already a peer |
| a Task's `grammar` | the same call with `providerOptions.kanzo.grammar`, which `localModel` hands WebLLM's engine as `response_format: { type: "grammar" }` | — |
| `propose` | `Output.array` of the same schema, each element checked on its own | — |
| `useTask` | React state over `propose` and `verify`; never asks on mount | — |
| `useAskChat` | the AI SDK's `useChat` with a `ChatTransport` that writes through `createUIMessageStream`, the states as its data parts | — |
| `Verdict` | the LSP's `Diagnostic`; `Decision` in the shape of MCP's elicitation | types only |
| `localModel` | `@browser-ai/web-llm` over WebLLM, one engine per model per page, resolved by id through one registry in the AI SDK's `customProvider` shape; what is served is WebLLM's own `AppConfig` | optional peer of `@kanzo-tech/llm/local` |

**Why no `submit` tool.** `@browser-ai/web-llm` 3.0.4 constrains JSON and not tools: structured
output sends `response_format: json_object` with the schema and WebLLM decodes against it, while
tools are described in the prompt and parsed out of the text. So `defineTask` generates with
`Output.object` and loops itself, and a small model cannot return a malformed call. The one artefact
that is not JSON is a Fossil mapping, and it is held by a grammar fossil projects from `grammar.bnf`
with the names closed — so it cannot be malformed either.

**Not built, because nothing has needed them.** The direction named four more: `defineFlow`, to chain
the assistant's steps; `defineModels`, to resolve a model per Task; `useTaskChat`, a chat over any
Task; and `evaluate`, a harness in `@kanzo-tech/testing`. A screen chains its Tasks as an async
function does, the page has one model, Ask is the one Task in a chat, and Ask's evaluation is
[its own runner](/docs/design/ai#ask-is-evaluated-as-a-dataset-a-solver-and-a-scorer). *What would
reverse it:* a second caller for any one of them — two flows written the same way, two Tasks that
want different models, a second Task in a chat, a second product's evaluation set.

### Where each dependency lives

The third party is a peer, and ours is only the door it lacks. Mosaic's surface is re-exported by
`@kanzo-tech/mosaic`, because one copy on a page is what keeps one coordinator (the engine holds it), and
no host imports `@uwdata/*` for anything else. The AI SDK's is **not** re-exported by `@kanzo-tech/llm`: `ai` is a
required peer every host already imports by name, so a re-export was a second way to write one
import, and nobody used it. What `llm` carries is the two doors every model call passes, `stream`
and `generate`, each asking once ([failure](/docs/design/failure#a-models-failure-is-shown-once-on-the-first-attempt)).
Two copies of WebLLM would be two engines and two models in GPU memory.

*What would reverse it:* a name of the SDK's that a host must not import from `ai` because its version
must be the library's. Then that name is passed through with the reason beside it, and the rest still
is not.

*Held by* `packages/llm/src/index.test.ts`, "carries the two doors and the failure, and none of the AI
SDK's names".

| Package | Third-party peer | What it carries |
| --- | --- | --- |
| `@kanzo-tech/llm` | `ai`, required | `stream`, `generate`, the call settings and `finishReason`, `ModelLoad` |
| `@kanzo-tech/llm/testing` | `ai`'s own `ai/test`; `@kanzo-tech/testing`, optional | the one scripted model double ([Testing](/docs/design/testing#one-model-double)) |
| `@kanzo-tech/llm/local` | `@browser-ai/web-llm`, `@mlc-ai/web-llm`, optional | `localModel` (one registry, a grammar per call), `loadLocalModel`, `localProvider`, `setLocalProvider`, `serveLocalModel`; `llm/unavailable` without WebGPU or with nothing served. It names no test ([Testing](/docs/design/testing#a-model-is-resolved-through-one-registry)) |
| `@kanzo-tech/ai/task` | none | the types, `defineTask`, `runTask`, `propose`, `verify` |
| `@kanzo-tech/ai` | none beyond the root's | `useTask`, `Assist`, `Chat` |
| `@kanzo-tech/ai/data` | `@kanzo-tech/relations` and the engine, per [the entry's peers](/docs/design/architecture#packaging-follows-the-entry) | `ask`, `useAskChat`, `askOffers`, `AskChips`, `AnswerCard` |

`/local` is a subpath for the reason [the optional-peer door](/docs/philosophy#the-engine-rule) exists:
a static import of WebLLM from a root barrel breaks `import { Assist }` for every host that did not
install it.

## Everything in the browser, the model too

The deterministic parts — linker, resolver, Profile, checker, executor, DuckDB — and the model run in
the client. Outside it stay two things, and the AI depends on neither: file storage, with credentials
keasy vends as today; and the evaluation in CI, on a native llama.cpp server as a proxy for the
browser's weights ([Asking data](/docs/design/ai#ask-is-evaluated-as-a-dataset-a-solver-and-a-scorer)).

| Engine | Where it runs |
| --- | --- |
| DuckDB-WASM | the engine's own worker ([the engine](/docs/design/engine)), no threads |
| `fossil-wasm`: compiler, checker, Profile, the mapping grammar | the page |
| `fossil-df-wasm`: executor | the page's main thread (keasy's `startRun` constructs `FossilExecutor` in the calling realm; nothing in its `web/src` creates a `Worker`) |
| WebLLM | its worker (`WebWorkerMLCEngine`), memory on the GPU |
| A fallback without WebGPU | none |

**No fallback without WebGPU.** `@browser-ai/transformers-js` 3.0.4 warns that `responseFormat` is
unsupported, so a CPU fallback through it generates unconstrained JSON that only the oracles and
retries catch; llama.cpp in WASM (wllama) constrains with grammars but has no AI SDK provider.
Without WebGPU there is no assistant and no Ask, said plainly; the rest of keasy works the same.
WebGPU is in Chrome and Edge (Windows, macOS, ChromeOS), Safari 26 and Firefox on Windows and ARM
Macs; the gaps are mostly Linux and Android outside Chrome on Qualcomm or ARM GPUs.

**What would reverse it:** the evaluation set showing that unconstrained output passes the oracles
nearly as often, or a CPU provider that constrains. A threaded WASM fallback also needs cross-origin
isolation, which keasy can afford: with `Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp`, its e2e passed 14 of 15 against the dev stack (the one
that did not fails the same with the headers off), `crossOriginIsolated` read true, and a ranged
`fetch` of a presigned S3 object answered 206 (checked 12 October 2026). **Not proved:** a read from
Azure, which the dev stack has no emulator for, and that this holds once the host's CSP is nonce-based
with `'strict-dynamic'`, which ignores host allow-lists for scripts
([hardening the auth layer](/docs/design/auth-hardening#a-script-on-the-origin-is-api-access-so-no-inline-script-runs)).

## Decisions, and what would reverse each

| Decision | Why | What would reverse it |
| --- | --- | --- |
| Ask's set is small and by shape: Nobel, plus SNB for what Nobel lacks | What it must cover is the shapes of a question, not a count; two corpora from two domains catch a linker fitted to one vocabulary | A Task that passes the set and fails a third corpus's questions of a shape the set has; then that corpus joins the set |
| Every piece on a standard or a reference library | Less code of our own, known behaviour, someone else's documentation | A reference that requires a server runtime or persistent state not needed here; then we take its shape, not its package |
| Generate, verify, repair instead of a free agent | The model decides little and every decision has an oracle | A free agent with the same small model matching execution accuracy across the set |
| The relation is the paths the model wrote, resolved | A path is checked before anything runs, and two ways to one field are the model's to write, not the code's to guess | The set showing the model writing paths worse than a search chose relations, for a shape of question |
| The mapping is Fossil, written under a grammar with the names closed | The language is statically typed: the grammar stops a name that does not exist and the checker judges the rest; a format of our own in between was built, and reverted | A small model under the grammar failing the competency questions where a spec it filled and an emitter wrote passes them |
| Profile replaces introspect, and is sans-IO inside the wasm closure | One way to read sources for the compiler, the assistant and the linker, watched by the wasm gate | A host that cannot afford the statistics (a mode of Profile, not a second package); a query only one host can run (marked per host) |
| A truncation is repaired once; a refusal and a silence are not | The context filling is the budget, and the same request meets the same refusal | A device where a retry after truncation never succeeds |
| Everything in the browser, the model too | The data stays, and the AI depends on no server | An oracle with no wasm32 build at reasonable cost |
| Designed for a small local model; remote models not designed | No API dependency, the data stays, and it forces each Task to be bounded; locality is the host's CSP and not a flag | A Task that fails the set with a small model; or a host that must run a remote one ([the work list](/docs/design/ai#the-model-is-open-and-where-it-runs-is-not-the-librarys-to-enforce)) |
| No fallback without WebGPU | The one CPU provider with an AI SDK binding does not constrain JSON | The set showing unconstrained output passes nearly as often, or a CPU provider with constraints |
| One `Proposal`, the Task's, for a field, a list and a chat | A value, where it lands and what backs it is one idea; an offer sent by its words was checked by the oracles and then asked again of the model | A field whose proposals need what a `Target` cannot say, such as a command to run on accept; LSP's own extension of the item is the place to look first |
| One local multi-task model, named per Task in `customProvider` | One download; changing a Task's model is configuration | A Task whose quality needs a model of its own; then that Task gets its entry |

## What a product's Tasks are

**Keasy's assistant (`requirements`, `model`, `mapping`) is product code, and stays in keasy.** The
library ships the loop, the proposal, the oracle and decision types and `useKeptChat`; a Task that
names a product's sources and its wizard's steps is not a part to grow from. A package that exposes
a capability is not rewritten by the product that uses it: where keasy built the pre-run shape of
a program itself (`joinGraphOf`), fossil's `describe` returns it from declared types
([Relations](/docs/design/relations#the-pre-run-shape-comes-from-the-compiler)) and the product's
copy goes. *What would reverse it:* a second product writing the same three Tasks; then they are
a part, on the admission rule's second call site.
