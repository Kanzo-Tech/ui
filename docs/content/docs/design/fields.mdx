---
title: What a field is
description: Why a field's facts are the graph's — what it is from the property the Graph describes, what it holds from the statistics the chunks state — so nothing in the library guesses them from a column's name or a threshold, and nothing reads them twice; and what would reverse each part.
---

A dashboard, Ask, an answer's card and keasy's assistant each need to know two things about a
column: **what it is** — a number, a date, a key — and **what it holds** — how many distinct values,
how many missing, its range. The library used to throw the first away on the way in and re-derive a
cruder version of it from the column's name, and to read the second twice, by two `SUMMARIZE`s that
need not agree, and a count per category on top for Ask.

A graph reaches the library as the `Graph` `@kanzo-tech/graphar-duckdb`'s `attachGraph` answers
([The graph](/docs/design/graph#the-graph-is-graphars-to-read)), and every fact below is a field of it:

| Fact | The `Graph` | Before |
| --- | --- | --- |
| a vertex type, its count | `vertexTypes[].type`, `count` | parsed out of view names |
| an edge's label and its ends | `edgeTypes[].edgeType`, `srcType`, `dstType` | parsed out of `<Source>_<label>_<Destination>` |
| a property's DuckDB type | `properties[].type` | `duckdb_columns()` on our side |
| the key | `properties[].primary` | `ID_NAME` re-guessed identity by name; a 50-value cut-off |
| nullability, a list | `nullable`, `list` | not read |
| what a property holds | `properties[].stats`, from each chunk's Parquet `Statistics` | a `SUMMARIZE` in `fieldStats`, another in `AnswerCard`, a count per category for Ask |
| an IRI, a term type, a datatype, a label in a language | not in it | not read; words split out of identifiers |

## What a field is comes from the graph, through one reader

**Every fact the `Graph` states about a type, an edge or a property reaches a field unchanged, and
nothing downstream re-derives one.** GraphAr's information files are read by graphar's own reader,
the one place their names are known; kanzo-ui reads the `Graph` and writes no GraphAr column name
([The graph](/docs/design/graph#the-graph-is-graphars-to-read)). `patternColumns(graph, pattern)`
describes a pattern's columns under the names `relationOver` reads them by: a column per named vertex
for its index, which is no field, then `variable.property` for every property of every named element,
described by its type's property — so its counts are the type's, which is what a default needs, and
not the join's.

**What would reverse it:** a reader that needs a fact the `Graph` does not hold. Then it is added to
what the writer states and graphar reads, and travels the same path — never derived on the reader's
side.

*Held by* `packages/ui/src/charts/field-stats.test.tsx`, "reads a column per named vertex for its index,
then every property of every named element as variable.property", "reads nothing of an element the
pattern leaves unnamed"; `packages/graph/src/layers.test.ts`, "builds statements only where it reads,
writes none in a string, names no GraphAr column, and takes only types from graphar".

## What a field holds comes from the chunks' statistics, and nothing is read for it

**A field's distinct count and its extent are its property's `stats`, which the writer's Parquet
`Statistics` state — the nulls, the minimum, the maximum and the distinct count — and the library runs
no `SUMMARIZE`.** `useFieldStats(pattern)` queries nothing: the descriptions and the counts are the
page's `Graph`, and it throws where the page has none. Ask is offered each type's fields off the
graph; `AnswerCard` draws by the facts the answer was asked over, so the model and the card are told
the same figures.

**A distinct count does not combine across row groups**, so where the chunks only bound it the field
carries the least they allow, and where they say nothing it carries none — `0`, a field with no count
and no extent, which the defaults treat as a dimension of unknown width. Refusing such a property
would have been a failure for a reader to see where a missing figure does; summarizing it would have
been the second reader of one fact, which is the thing this page removed. The only `SUMMARIZE` the
library ran before was over a relation nothing counted — the vertex union, a joined relation, a host's
own table — and a dashboard now reads only a pattern, whose every field is a property the graph
describes.

**What would reverse it:** a graph written by something other than fossil, as the common case, whose
chunks state no distinct count. Then the counts are a reader's step, run once per graph by graphar
through the host's engine and stated on the `Graph` — still not one per component, and still not
here.

*Held by* `packages/ui/src/charts/field-stats.test.tsx`, "answers a pattern's fields from the graph's
description, reading nothing", "counts the least distinct values the chunks allow where they only
bound it, and none where they say nothing"; `packages/ai/src/data/answer.test.ts`, "reads nothing from
the engine: what a field is and holds is the graph's"; `packages/ai/src/data/answer-card.test.tsx`,
"draws an answered tile at once, never busy: its fields are the graph's, and nothing is read for them".

## A field's kind and role are read, not guessed

**A field's kind is Mosaic's `jsType` of its DuckDB type; its role is `identifier` where it is its
type's primary key, and otherwise the kind's.** No `ID_NAME`, no `DIMENSION_LIMIT`.

| Field | Decided by | Reads as |
| --- | --- | --- |
| its type's primary key | the `Graph` | identifier |
| a number | its DuckDB type | numeric, a measure |
| a date or a time | its DuckDB type | temporal, a dimension |
| a text or a boolean | its DuckDB type | categorical, a dimension |
| a list, a struct, a blob, or a type a mark throws on | its DuckDB type | no field |

**What it costs:** a text nearly but not quite unique per row, which the graph does not declare a
key, reads as a dimension — the dashboard offers a facet filter over thousands of values, and a chart
over it thousands of bars, which the bar chart's own band still cuts. The 50-value cut-off hid that
case and misfiled every category of 51 values with it. And a year written as an integer is a number:
the datatype that said it was a year was the RML mapping's, which the `Graph` does not carry
([The graph](/docs/design/graph#the-graph-is-graphars-to-read)).

**What would reverse it:** dashboards defaulting, in readers' hands, to charts over columns the data
never declared and that are identifiers to anybody who reads them — then the remedy is in the graph (a
key), and if no graph can say it, a rule with its evidence beside it, never a spelling. Or the `Graph`
stating a property's datatype, which would make a year a time again with no change here but a row of
the table above.

*Held by* `packages/ui/src/charts/field-stats.test.tsx`, "reads a kind from Mosaic's type words, and a
role from what the graph says and nothing else", "classifies every precision DuckDB reports, reads a
zoned extent, and drops the three types a mark throws on".

## A multi-valued property is a value, not a step

**A list property is a column of the type that owns it, a `VARCHAR[]`, which Mosaic's `jsType` has no
word for and which is therefore no field.** fossil's decision (2026-10-14) is that a multi-valued
property is a GraphAr `list` property ([The graph](/docs/design/graph#a-vertex-type-is-a-node-type-a-list-property-is-a-value)),
and a pattern reaches only vertices and edges, so there is no hop to a property table to name. A host
that wants *laureates by nickname* needs the values as rows — a vertex type of its own, written by the
writer.

**What would reverse it:** readers asking to group by a list's members, measured — then graphar's
`match` unnests a list property into rows, and a field names it as `variable.property` like any other.

## The words are names

**A type's, an edge's and a property's words are its name as the graph states it**: a tile's title, Ask's
chips and `RelationPicker`'s sentences read `variable.property`, the path the reader edits in the
tile's field pickers. The `Graph` states no label, so there is nothing in a language to choose among;
the RML mapping's labels, which `withMapping` once put on the old join graph, went with it.

**What would reverse it:** the `Graph` stating labels — a vertex type's `rdfs:label` read from the
mapping graphar already writes beside the graph — then a title reads the label in the page's language
and falls back to the name.

## What it changed for a consumer

- `useFieldStats` takes a `Pattern` and reads the page's `Graph`; it runs no `SUMMARIZE` and throws
  where the provider has no `graph`. It answers `{ fields, columns }` at once: `FieldStatsState`, its
  loading and its failure are gone, because nothing is read. `fieldStats` takes column descriptions — `name`, `type`,
  `primary` and `stats` — and `patternColumns(graph, pattern)` makes them.
- A field's `name` is `variable.property`. `FieldStat.label` is gone: a field is called by its name.
- A column named `id`, `uri` or `iri` is no longer an identifier because of its name, and a text of
  more than 50 values is no longer one because of its count. An identifier is its type's primary key.
- A year the mapping typed `xsd:gYear` and the writer stored as an integer is a number.
- A field whose property the statistics say nothing of has `distinct: 0` and no extent.
