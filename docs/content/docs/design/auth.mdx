[The auth pages](/docs/auth) are what `@kanzo-tech/auth` ships. This page is why it is shaped that
way — and more of it than usual is decided by somebody else, because the protocol, the claim
vocabulary and the architecture catalogue are all external and all citable. What the layer does to
resist attack and failure, and the limits it states instead of fixing, are on
[Hardening the auth layer](/docs/design/auth-hardening).

*Status: partly built.* The tree has `AuthError`, a status table kept by hand in `problem.ts` and a
server that answers its own shape; [how the layer fails](/docs/design/auth-failure) says what
replaces them. The *Breaking* list at the end is what a consumer edits.

## Auth is a package, and the admission rule excludes it by name

`@kanzo-tech/auth` is a **sibling** of `@kanzo-tech/ui`, not a part of it. The first [admission
rule](/docs/philosophy#admission) is *domain-free — nothing about RDF, SHACL, fossil, graphs or auth*,
and auth is on that list by name. The rule was written after the library shipped one: a sidebar
composite carried a hard-coded log-out flow, its confirmation dialog and untranslatable English copy
included. The fix that did not hold made the flow one entry in an array of menu items the caller
passed, trading a domain leak for a [layout tree written as an
attribute](/docs/design/admission), so the composite went too. A log-out item is markup a product
writes out of the menu and sidebar parts.

The package **depends on nothing of `@kanzo-tech/ui`'s**; it lives here for the build, the release,
the guards and the docs pipeline, which is what makes moving it later cost a directory rename and no
consumer's line. It does depend on [the kernel](/docs/design/kernel) as every package may, for the
`Problem` it throws and the `within` it bounds waits with. The budget on the root barrel notices the
day the first part stops being true: a recipe, a component or a second engine does not fit in it.

**What would reverse it:** the first admission rule losing that word. There is no measurement and there
should not be; the evidence that it was right is one composite, not a number.

*Held by* `packages/ui/src/index.test.ts`, `!SidebarUser` and `!InstanceSwitcher` — the composite
that shipped the flow, asserted absent under both of the names it had;
`packages/auth/package.json`, `gauges`.

## The client draws; the resource server decides

[The rule itself](/docs/auth#the-one-rule-to-read-before-anything-else) is on the package's front page,
where a consumer meets it. What is here is why it is the *first* thing that page says, and what follows
from it that would otherwise look like four unrelated decisions.

Two are realm configuration ([the Keycloak page](/docs/auth/keycloak)): the role mappers are marked for
[**both** tokens](/docs/auth/keycloak#role-claims-on-both-tokens), the access token so an API can
authorise and the ID token so an interface can draw, and the token an API receives names [that API and
no other](/docs/auth/keycloak#the-apis-an-application-calls), because a resource server validates `aud`
before it trusts anything else. The third is a division of labour that is easy to lose: the package
obtains and attaches the credential and defines the claim model; **validating is the API's**, and ours
are Rust. That agreement is a contract in words — what is validated (`iss`, `aud`, `exp`, the signature
via JWKS) and what is authorised on (`resource_access.<clientId>.roles`,
`organization.<alias>.resource_access.<clientId>.roles`) — and [the Keycloak
page](/docs/auth/keycloak#what-your-api-must-validate) is its only copy. The fourth is a subtraction:
nothing in this package decodes an access token, so there is no code to get wrong. Roles for drawing
come from the ID token's claims, read once on the server by the one claim reader and handed to the
browser through the session endpoint, and a `Session` handed to a browser holds no token at all.

**What would reverse it: nothing**, for two reasons. The decision has to be made where the attacker is
not, and the attacker is on the other side of the `fetch`. And an access token's format belongs to the
authorization server and the resource that consumes it; publishing it *to clients* as a contract is
precisely what an access token is defined not to do.

*Held by* `packages/auth/src/can.ts`, `can`; `packages/auth/src/can.test.ts`, "is closed by default";
`packages/auth/src/gate.tsx`, `Gate`; `packages/auth/src/server.test.ts`, "exchanges the code and
reads the claims into a Session" and "holds no refresh token on the Session it hands out".

<Callout type="warn">
No guard can fail on a product that decides in the browser, and none here claims to — the code that
would be wrong is in the consumer. What the tests hold is that the predicate answers `false` for an
absent session and never widens a role, so a product following the rule is not fighting the library.
</Callout>

## One pattern: the Backend For Frontend

RFC 10017 (BCP 212, *OAuth 2.0 for Browser-Based Applications*) names **three** architectures for
browser applications, and this package implements one of them.

| pattern | who here | why |
| --- | --- | --- |
| **Backend For Frontend** | every host | *"strongly recommended for business applications, sensitive applications, and applications that handle personal data"* (§6.1.4.3) |
| **browser-based OAuth 2.0 client** | nobody | shipped as `browserAuth` for a SPA with no server; removed with its `oidc-client-ts` peer when nothing consumed it |
| *token-mediating backend* | nobody | the norm itself says to evaluate a full BFF instead |

A door nobody opens is maintenance with no reader, so the second pattern went, and with it the second
implementation of `Auth`. The interface stays — `useSession`, `Gate` and a test double are written
against it — with one transport under it.

**The renewal is single-flight because a rotated token spent twice is a revocation, not because of
performance.** RFC 10017 does not require rotation. RFC 9700 §2.2.2 requires a *public* client's
refresh token to be sender-constrained or rotated, and a confidential BFF client is not bound by that
MUST. Rotation is the realm's choice (`revoke_refresh_token=true`, `refresh_token_max_reuse=0`,
`services/auth/realm`), and §4.14.2 says what a spent token costs: the server cannot tell which party
presented it and revokes the active one. [The renewal path](/docs/auth/session#keeping-requests-authenticated)
is single-flight per ticket for that reason; across processes it is a stated limit
([Hardening](/docs/design/auth-hardening#one-web-host-for-now-and-the-race-that-limits-it)).

**What would reverse it:** a consumer with no server and personal data to protect — the public client
is then the only architecture available, and it comes back behind its own door with its own engine.
Short of that, a revision of RFC 10017 that recommends the token-mediating backend.

*Held by* `packages/auth/src/types.ts`, `Auth`; `packages/auth/src/bff-auth.test.ts`, "attaches no
Authorization header, because the cookie rides along by itself"; `packages/auth/src/server.test.ts`,
"spends one refresh token for a burst of concurrent renewals"; `packages/auth/src/single-flight.test.ts`,
"runs the work once for every caller that arrives while it is running".

## The session is the platform's edge

**The relying party is a platform service, oauth2-proxy (`services/auth`, `auth-proxy` with
`auth-valkey`), in front of each application; the application holds no client secret, no session
and no refresh token, and reads the person from the access token the proxy hands it** (the owner's
decision, 15 October 2026). It is the same BFF pattern as the section above, run as a maintained
component instead of written here: the code that keeps a session, renews it and signs out was this
package's largest part (`server.ts` 875 lines of about 4,000), and the size gauge of `./next` had
been raised three times in ten days, the reversal the next section names.

Measured on 15 October 2026 against Keycloak 26.8.0 with the `kanzo` realm of v0.47.0 and keasy's
client as registered, through Chromium: sign-in at `acme.localhost` and single sign-on at
`globex.localhost` with no form (118 ms), one client serving every organization's host because the
redirect URI is taken from the request's host; the session cookie is 176 bytes (the sealed record
was 6,407); signing out at the application ends the session at Keycloak; asking for the API's scope
at sign-in puts it in `aud` (`["keasy-api", "account"]`, `azp` the application), so the exchange the
next section describes is not needed for an application's own API. A sign-out made at Keycloak
itself reaches the proxy when the access token next needs renewing: oauth2-proxy has no
back-channel logout endpoint, a failed renewal leaves the session until its token expires, and it
was refused 5 minutes after sign-in, the realm's `access_token_lifespan`. That lifespan is therefore
the revocation bound. The resource server still verifies the token itself against the realm's keys
(RFC 9068); it never trusts a header the proxy set.

`--cookie-secret-file` signs nothing in oauth2-proxy 7.12.0 (every session cookie failed
validation); 7.15.5 reads it, so both secrets are files and neither is in the environment.

**What would reverse it:** a requirement that a sign-out at Keycloak end the application's session
at once, which brings back a back-channel logout receiver (the proxy has none) or introspection per
request (RFC 7662); or an application whose API the access token cannot name, which brings back the
exchange below.

## One token per API and organization, exchanged

The session's access token never leaves the server. It is asked for with `organization:*`, so it
names every organization the person belongs to and no API. What a resource server receives is that
token exchanged — [OAuth 2.0 Token Exchange](https://www.rfc-editor.org/rfc/rfc8693), as Keycloak
26.8's standard token exchange implements it — for one whose `aud` is that API and whose
`organization` claim is the one organization the call is in. A tenant's API and whatever comes next are
each a client of the realm, registered with `services/auth/modules/api`, and an application lists the
ones it calls.

None of it is ours. [RFC 9700 §2.3](https://www.rfc-editor.org/rfc/rfc9700#section-2.3) restricts an
access token to one resource server, RFC 9068 has the resource server reject any `aud` but its own,
and Keycloak's guide says *"ideally use a single audience"*. Auth0 issues one token per API and
organization (`audience`, `org_id`); Entra's on-behalf-of flow is an exchange with one resource per
token; Zitadel takes RFC 8693 with the organization and audience as scopes. Storage is the same shape
one step further: an Iceberg REST catalog validates the person's token and vends a short credential
with its **own** cloud identity, which is what fossil's `Host.credentials` expects of a host.

What it buys is the line between customers. Forwarded as it was, the session's token was as good at
`globex`'s API as at `acme`'s for anyone in both; exchanged, it is good at one API in one organization
for five minutes. Three things were measured on Keycloak 26.8 by `scripts/verify.sh`:

- **The API is asked for by its scope, not by RFC 8693's `audience`.** Keycloak reads that parameter as
  a filter and keeps only the requested audience's client roles, so the application's own roles held
  outside any organization did not arrive. The token also names `account`, as every token of the
  realm does from its default roles: a small set RFC 9700 allows when one is not feasible.
- **A non-member's organization is dropped, not refused.** The granted `scope` says so, and `token`
  refuses there (`organization/denied`) rather than forward a token with no organization in it.
- **A scope the application does not list is refused** with `invalid_scope`.

Two alternatives lost. **One token with every API in `aud`** is the multi-audience token RFC 9700 and
Keycloak advise against. **RFC 8707's `resource`** is the more exact standard, and it is experimental
in Keycloak 26.8, whose exchange does not take it. Not claimed: that the access token carries
`typ: at+jwt`, which RFC 9068 §2.1 requires and which Keycloak's option for it was not confirmed here.
The Rust resource server checks `aud` and `azp`, not `typ`.

**What would reverse it:** Keycloak's resource indicators leaving experimental with exchange support
moves the request from the scope to `resource` and changes nothing a consumer writes. A delegation
chain with `act` is RFC 8693's delegation, still preview, and would extend this. The exchange goes only
if Keycloak stops being the one realm, which is a different platform.

*Held by* `packages/auth/src/server.test.ts`, "exchanges the session's token for one naming the
audience and the organization alone" and "refuses an organization the person is not a member of";
`packages/auth/src/next-proxy.test.ts`, "attaches a token exchanged for the mount's audience as a
bearer, never the session's own"; `services/auth/scripts/verify.sh`.

## The identity provider is Keycloak, and the package says so

**`@kanzo-tech/auth` is a Keycloak backend for frontend by design. It supports no other identity
provider, and a second one is a stated non-goal** (the owner's decision, 15 October 2026). Three
things follow, and each deletes a layer that would otherwise have to be kept in step with Keycloak.

- **`Session` is Keycloak-shaped.** It carries organizations, `resource_access` roles and group ids
  as Keycloak writes them, and there is no claim-mapping layer between a token and a session. A
  mapping layer would be a second description of one token, written twice for every claim added.
- **Keycloak's own features are used, not rebuilt:** brute-force detection, the password policy,
  login and admin events, `sso_session_idle_timeout` and `sso_session_max_lifespan`, `acr` and
  `max_age` step-up through authentication flows, token exchange, back-channel logout and
  organizations. The realm baseline is owned by the platform realm (`services/auth/realm`), and the
  idle timeout and step-up are Keycloak's policy; [hardening](/docs/design/auth-hardening#the-realm-ships-a-baseline)
  says what the package then adds.
- **The two claim readers answer to one recorded token.** The TypeScript reader (`claims.ts`) and
  keasy's Rust reader (`token.rs`) are each tested against the same recorded Keycloak token as their
  fixture, and the Rust reader accepts the `organization` and group shapes the TypeScript one does.
  They were two readers of one claim with two sets of tests. *To be built:* the shared fixture.

**What would reverse it:** a consumer who must sign in against another provider and cannot be asked
to run Keycloak in front of it (Keycloak can broker one, which is the answer until then). Then the
claim reader becomes the one place a second provider's claims are mapped onto `Session`, and
everything below it stays; the package is not otherwise rewritten. No such consumer exists.

## The protocol is somebody else's

Admission rule 3 is *wraps, does not reinvent*, so the first question was who had already done this.

| | what it is | why it does not win the whole |
| --- | --- | --- |
| **Auth.js** | route handlers for Next, Qwik, SvelteKit, Express | owns the session model and drags a registry of providers nobody here uses |
| **better-auth** | an auth framework with SSO and organization plugins | *"Better Auth requires a database to store user data"*: it would own the user store Keycloak already owns |
| **oidc-client-ts** | the browser protocol | won the browser half while there was one |
| **openid-client** | the server protocol, and what Auth.js is built on | **wins** the server half |

So PKCE, the confidential client, discovery and RP-initiated logout are **not written here**, and
neither is JWT verification for a back-channel logout token, which is `jose`'s. `./server` is a
configuration and a set of verbs over `openid-client`, and [what is left after that
subtraction](/docs/auth#what-it-is-not) is the whole package.

**What would reverse the `./next` choice** — the one place Auth.js genuinely competes, because it does
that half entire — **is our own cookie and session handling growing to rival Auth.js's in size; then
the answer is to adopt it rather than keep growing.** The `size-limit` entry on `dist/next.js` is where
it shows, and it has been raised three times in ten days
([the gauges](/docs/design)); [Hardening](/docs/design/auth-hardening#production-grade-axes) says
what the next additions cost.

*Held by* `packages/auth/src/issuer.ts`, `discovery`;
`packages/auth/src/cookie-session.test.ts`, "refuses a cookie sealed with another secret".

## One door per engine, and the door everyone opens carries none

The placement rule is the library's own: *a part belongs on a subpath only if it imports that
subpath's engine.* Here that produces one door per engine — `openid-client` and `jose` behind
`./server`, `next` behind `./next` — and a **root barrel with no engine at all**. That is why the BFF
transport lives on the root: with the token on the server there is no protocol left in the browser,
only a `fetch` to a session endpoint. Its one peer beyond React is `@tanstack/react-query`, the host's
cache, because the session is [read like any other datum](/docs/design/auth-failure#a-session-is-read-like-any-other-datum).
Each door is declared in `exports` on the day its file exists and never before.

The precedent is not hypothetical. `@kanzo-tech/graph/duckdb` reached its coordinator through
`@kanzo-tech/ui/analytics`, whose barrel names `@uwdata/vgplot` on the way past, so a host that
installed the two peers the docs named still could not open the subpath. The same shape in the other
direction is what `./server` must not do: importing the root barrel to reuse the claim reader would
drag a provider and three hooks into a Node process, so modules import each other directly.

A leaked engine does not make the barrel throw: it keeps working while pulling `openid-client` in
behind it, and the consumer finds out when a `node:` scheme breaks their web build. What reads that
today is the source's imports (`server.test.ts` below). **Nothing reads the built bytes**: the install
smoke test that compared `src/` and `dist/` was deleted on 2026-09-29, so a lost `"use client"` is
caught by no gate, and `auth` is outside `client-boundary.test.ts`, whose corpus is the packages
declaring `tailwind-variants`, which `auth` deliberately does not because nothing here draws. Its
`use-*.ts` modules are hooks by name, where the likely error is a **missing** directive.

**The guard is the corpus rule applied a second time — widen it, never copy it — with its own
derivation: `client-boundary` runs over every package declaring `react` as a peer, and
`entry-peers.test.ts` reads each entry's static closure against the peers its entry declares**
([Architecture](/docs/design/architecture#packaging-follows-the-entry)). Both are to be added.
*Cannot prove:* what the built bytes hold; only the docs build, which evaluates the boundary, does.

**What would reverse it:** an engine that every consumer installs anyway is not paying for its door.

*Held by* `packages/auth/src/server.test.ts`, "imports no React, no barrel and no component from the
server door".

## Membership is stored; the current organization is resolved per request

[The rule itself](/docs/auth/session#the-current-organization-is-resolved-per-request) is on the
Session page, with the two tabs that are the whole of the argument. The product's resolver derives the
current organization from each request — its host, its path, a cookie — and the answer rides on
`Session.organization` without ever being written to the record. That makes **the request the truth**,
and it has a second face: the address is a [hint and never an
authority](/docs/auth/roles#which-organization-a-page-is-in), so `can` resolves it against the signed
`organization` claim and answers `false` on a miss. Those are one decision, and together they are the
line between a multi-tenant product and a leak between customers: the resolver says where to look, the
claim says whether to believe it.

Two claims about the realm sit under it, and the difference between them is the difference between a
rule this repository can hold and one it cannot. That the `organization` claim reaches the **access**
token, with each organization's id and the application's roles, is held by a *recorded* token in the
test corpus, the only thing that would notice Keycloak changing its mind. That plain `organization`
stops a multi-organization sign-in on a chooser page instead of issuing a code is held by nothing, and
nothing here could hold it: it is a page Keycloak draws. It is why [the default scope is
`organization:*`](/docs/auth/keycloak#the-scope-with-the-star), and the shape of claim this section is
most likely to be wrong about later.

**What would reverse it:** a consumer whose organization is not addressable — no per-organization host,
no route, nothing in the URL to derive from. Then the active organization has nowhere else to live and
the two-tab cost is real. Every consumer so far addresses by hostname or by deployment.

*Held by* `packages/auth/src/types.ts`, `Session`; `packages/auth/src/can.test.ts`, "asks inside the
current tenant when none is named" and "is closed for a current tenant the person does not belong
to"; `packages/auth/src/next-auth.test.ts`, "reads the session the request carries, with the tenant
the resolver names"; `packages/auth/src/claims.test.ts`, "a real token, taken off a live Keycloak
26.8.0".

## A role in one scope does not authorise in another

Roles held **inside** an organization live on that organization and are never merged into the global
ones — [not once, and not for convenience](/docs/auth/roles#asking-the-question). Two separations do
that work and only the second costs anything: it is why the claim reader takes a client id at all.
That second one is the application's key inside each organization's entry,
[`organization.<alias>.resource_access.<clientId>.roles`](/docs/auth/roles#roles-inside-an-organization-are-read-from-its-entry).
Keycloak keeps the two levels apart itself: the recorded token carries a person's roles in acme and
globex inside those entries and none of them in the top-level `resource_access`, so the session copying
them up would undo a separation the identity provider makes. [There is no hierarchy in the
predicate](/docs/auth/roles#no-hierarchy-and-no-way-to-configure-one) either, the same separation
refusing a third time.

**What would reverse it: nothing**, because the alternative is already expressible. A role meant to hold
everywhere is a realm or client role, and one meant to hold across an organization is the application's
role mapped onto a group everyone there is in. A deployment asking for the merge is asking for one of
those and has picked the wrong one.

*Held by* `packages/auth/src/can.test.ts`, "does not carry a role from one organization into
another" and "does not mix the global roles into an organization's, or the reverse";
`packages/auth/src/claims.test.ts`, "does not merge an organization's roles into the session's own"
and "keeps the organization's roles out of the session's own".

## Roles are read; an organization's groups are not

An application's roles in an organization are the ones its administrator **mapped onto** the
organization's groups, and Keycloak writes them into the entry with composites expanded. The group
names ride along and the reader never looks at them. This replaced a convention that read a group
path whose first segment named the application, `/board/editor`, which made an organization's own
arrangement of its people into the application's authorization model: a customer renaming a group
revoked a role. A hierarchy sits on the same line. A product declares `admin ⊃ editor ⊃ reader` once,
as composite roles in its client registration, and the token carries the expanded set, so the browser
and the resource server read one order from the realm. `can` never ranks.

**What would reverse it:** Keycloak withdrawing `addGroupRoleMappings`, or ceasing to expand composites
inside the entry — the recorded token would notice. Or a product whose roles depend on *which* group
granted them, which no mapping of roles can express and a group name could; none has asked.

*Held by* `packages/auth/src/claims.test.ts`, "never reads a role from a group's name" and "reads
a composite with the role it contains, as Keycloak expanded it".

## A group is granted to by id, with Entra's overage rule

Some applications also let a person grant to a group — keasy shares a dataset with *Research* — and
then the server needs, from the token, which of the organization's groups the person is in. The token
carries their **ids**, in the organization's entry, or says it cannot:

```json
"organization": {
  "acme":   { "id": "…", "groups": ["<group id>", "…"], "resource_access": { … } },
  "globex": { "id": "…", "groups_overage": true,         "resource_access": { … } }
}
```

`Session.organizations[]` reads them as `groups` and `groupsOverage`. **The reference is Microsoft Entra
ID's groups claim**: group object ids, not names, and past 200 groups in a JWT no groups at all and an
*overage* indicator, the application asking Microsoft Graph for the membership
([group claims](https://learn.microsoft.com/en-us/security/zero-trust/develop/configure-tokens-group-claims-app-roles),
[the overage claim](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/get-signed-in-users-groups-in-access-token)).
Both halves are taken, inside each organization.

**Ids, never names.** A name is the organization's to change, and a grant keyed by it moves with a
rename or reaches the next group to take the name; acme's *Research* and globex's are two groups with
one name and two ids. Auth0 says the same of its organization claim
([organization names](https://auth0.com/docs/manage-users/organizations/configure-organizations/use-org-name-authentication-api)).
The reader drops anything under `groups` that begins with `/`: Keycloak's own organization group mapper
writes **paths** under the same key, and a realm that forgot the mapper must read as *no groups*.

**Keycloak has no mapper for it, so the platform ships one, at the documented extension point.** The
Organization Group Membership mapper has no option for ids, in 26.8.0 or on `main`. A protocol mapper is
a provider (a class, a `META-INF/services` line, a jar in `/opt/keycloak/providers`);
`services/auth/mappers` is that jar, one mapper, `Organization Group Ids`, compiled against the pinned
Keycloak and mounted by the identity service. It runs after Keycloak's two organization mappers and
writes only into the entries they wrote, so which organizations a token names stays Keycloak's
decision, and it is on the clients that ask for it. The cost is named by Keycloak: it classes
`protocol-mapper` as an internal SPI and logs `KC-SERVICES0047`, *may change without notice*. What
answers it is the pin (`keycloak.version` in the pom beside `KEYCLOAK_VERSION`), CI building and
testing it, and `verify.sh` proving it on live tokens, so an upgrade that moves the API fails a build
rather than a sign-in.

**Two alternatives lost.** *A role per group, named by the group's id*, needs a reconciler because
groups are created at runtime and the role is not, so a new group is absent between its runs; it was
built first. *A script mapper* is the same provider with JavaScript in it and less checking at build.

**Ancestors count, by default**: a member of *Research/ML* carries ML's id and Research's, as Entra's
transitive membership does; `inheritedGroups: false` turns it off, and an application's own overage
lookup must walk the same way. **The threshold is 100**: an id is 52 bytes base64url-encoded, the
exchanged token names one organization, so a full entry adds about 5.2 KB to an `Authorization` header
of about 1.5 KB, under nginx's default 8 KB `large_client_header_buffers`, the tightest limit between a
BFF and an API here; past 100 the header would cross it near 120. Okta's group functions stop at the
same 100. **An overage is a question, never an answer**: an empty `groups` beside `groupsOverage`
means *look it up*, and reading it as *in no group* is Entra's documented trap. The lookup is the
application's (a service account with `view-organizations` and `view-users` the package does not hold);
`organizationGroups`, a sketch with no caller, went on 14 October 2026. *Back if* a second product
writes the same lookup.

**What would reverse it:** Keycloak giving its organization group mapper an option for ids — the jar
goes and the claim stays. Keycloak reshaping the internal SPI past what a pinned rebuild can follow —
then the role-per-group reconciler is the fallback. A tighter header limit lowers the threshold.

*Held by* `services/auth/scripts/verify.sh`, which proves the mapper on live tokens for every seeded
person, and the mapper's own tests in `services/auth/mappers`;
`packages/auth/src/claims.test.ts`, "reads the ids of the person's groups in each organization",
"never reads a group's path as its id", "reads an overage as no ids, and says so" and "carries the
ids of the groups held in each organization, two Researches apart".

## The signature check follows the channel, not a default

`openid-client` does not verify the ID token's signature in an authorization code grant, and it is
right not to: an ID token arriving over TLS from the token endpoint, in the answer to a request
authenticated as this client, is vouched for **by the channel** (OpenID Connect Core §3.1.3.7 step 6),
which is why a sign-in normally fetches no JWKS at all. This package keeps the exemption and derives it
instead of inheriting it. **The exemption is a claim about the channel**, and an internal origin of
`http://keycloak:8080` withdraws the channel: the hop TLS was to protect is plaintext. So the default
is read off the protocol of the origin this process actually reaches, and can still be set either way.
[The origin rewrite](/docs/auth/server#discovery-and-reaching-keycloak-from-inside-a-cluster) rewrites
the *transport* and not the issuer, which is what leaves a plaintext hop to notice.

**What would reverse it:** a plaintext hop authenticated some other way — mutual TLS in a sidecar, a
mesh that proves both ends — which restores the premise without `https:`; the derivation is then wrong
in the safe direction. Or `openid-client` changing its default, or the specification withdrawing the
step-6 exemption.

*Held by* `packages/auth/src/issuer.ts`, `verifySignatures`; `packages/auth/src/server.test.ts`,
"fetches no keys when the token endpoint is reached over TLS, because the channel vouches" and
"fetches the keys when the hop is plaintext, because then nothing vouches".

## No sign-in screen ships

[No sign-in screen, no user menu and no organization switcher](/docs/auth#what-it-is-not) — stated on
the front page rather than discovered, because a shape stated late reads as a gap. The design decision
is that **nothing in this package draws at all**, which is why it declares no `tailwind-variants`:
that keeps it out of the appearance guards, correctly, and is the tripwire. What is shared sits
underneath the screen: the claims, the predicate, the derivation, the `fetch`. The three screens are
ordinary arrangements of `@kanzo-tech/ui`'s parts, where an arrangement belongs. The documentation
demonstrates the **model**, [a claim set and the session it becomes](/docs/auth/keycloak#reading-it-yourself)
and [the decision made from it](/docs/auth/roles#gate), because an arrangement over a fake `Auth` can
only show a button pressed, and the protocol needs a realm.

Because nothing draws, the package owes no WCAG of its own; what it owes is state a product can draw
from: `status`, the thrown value, and `expiresAt`. `Gate` renders nothing while `loading` or `failed`,
which is a product's to wrap.

**What would reverse it:** two products whose sign-in screens differ only in the logo, the same
condition that admits any composite: a second call site that wants the same arrangement.

<Callout type="info">
Nothing fails when a screen is added, and no guard could. The nearest tripwire is the budget on the
root barrel, which a drawn component would blow, and `tailwind-variants` pulling this package into the
appearance corpus in a commit somebody has to write. Both are tells rather than gates.
</Callout>

*Held by* `packages/auth/package.json`, `//peers` and `gauges`;
`packages/ui/src/guard-corpus.ts`, `IDIOM`.

## The organization's console is a link the library computes

**`organizationConsoleUrl(issuer, organization)` is the URL of Keycloak's admin console page for an
organization, computed from the issuer and the organization the session already names, beside
`accountUrl`.** Keycloak 26 manages an organization's members, domains and identity providers in the
realm's admin console, at `{origin}/admin/{realm}/console/#/{realm}/organizations/{id}/settings`, where
the public issuer is `{origin}/realms/{realm}` and the id is the one `organizationOf(session, alias)`
returns. So a product's *Members* page links there with nothing configured. An organization the realm
sent without its `id` has no link: the console finds an organization by id. It is `accountUrl`'s shape
and reasoning: a pure function of the public issuer, on the root barrel, because a link is drawn
wherever the session is. Whether a person may open it is the console's to decide, and a product shows
the link to those its `can` says manage the organization.

**What would reverse it:** an organization managed somewhere other than the realm's admin console.
Then the function returns that console's route, or a host passes its own URL.

*Held by* `packages/auth/src/account.test.ts`, "is the realm's admin console at the organization's
settings, by its id" and "has no link for an organization the realm sent without its id".

## A name on a door has a product's call site

The doors carried names no product called, each one more thing to keep: `singleFlight` and
`readSession` on the root; `claims` on the root, where the browser has no claim set to read; and on
`./server`, `sealedCookie`, `cookieValue`, `rewriteOrigin` and `organizationGroups`. They went with
the cleanup of 14 October 2026, by the rule [an export needs a call
site](/docs/design/admission#an-export-needs-a-second-call-site-and-one-example-is-not-it). A name is
added the same way: `fakeAuth`, on `./testing`, has two ([Hardening](/docs/design/auth-hardening#one-session-reader-and-one-test-double)).

**What would reverse it:** a product that calls one of them. Then that name comes back to the door the
call site is on, and no other.

*Held by* `packages/auth/src/index.test.ts`, "are the session, the role question and the two console
links on the root" and "are the relying party, its claim reader, its issuer and its stores on the
server door".

## Breaking, in the consumer's words

- `AuthError` is gone; test with `isProblem(error, "session/absent")` from `@kanzo-tech/kernel`. The
  codes are unchanged, and `AuthError.data` is the problem's `data`.
- The forwarder, the routes and the proxy answer their status from the generated registry; a host that
  read a status off a code from a table of its own reads `status` on the body.
- keasy's API answers `application/problem+json`; delete the content-type branch in the web client and
  the `auth/session-required` and `auth/keys-unavailable` rows in its registry (`session/absent`,
  `idp/unreachable`).
