title: Discovery workspace
description: A recipe — the engine, one coordinator, a corpus attached by name, and the graph parts and charts on one crossfilter.
---

A discovery workspace is the graph and the panels that interrogate it: a canvas with its tools,
a legend over it, a footer that says where the graph is and how much of it there is, an **Info** panel to find and read a
vertex, a **Settings** panel for the picture, and charts that filter with the graph. It is how a host
composes a discovery page and how the [workspace showcase](/docs/showcases/workspace) is built.
Every piece is a library part; what the host writes is the arrangement and its own policy.

## The shape

```text
engine()                                           the page's one DuckDB and its coordinator
open("archive", { engine, url })                   the corpus, attached as a catalog
KanzoThemeProvider sections={[GRAPH_SECTION]}
└── MosaicProvider coordinator crossfilter         the page's one crossfilter
    └── GraphRoot from coordinator filterBy …      one root, one Mosaic client
        ├── header        view switch: Graph · Dashboard
        ├── main          GraphCanvas > GraphToolbar + GraphLegend   or the charts
        ├── dock
        │   ├── Info      GraphSearch + GraphInspector
        │   └── Settings  GraphLooks + the gestures
        └── footer        GraphStatus + GraphCounts
```

**One coordinator under everything.** The graph and every chart are clients of the same
coordinator — one DuckDB connection, one query cache — and share one crossfilter. **One root around
everything graph:** the canvas, the dock and the footer all read the same `GraphRoot`, so a search in
the dock reveals on the canvas and a look chosen in Settings repaints it.

## Step by step

<Steps>
<Step>

### Register the graph's preferences

`GraphLooks` writes `GRAPH_SECTION`'s axes and `useGraphPrefs` reads them; both need the section on
the theme provider. Hoist the array: a new one each render re-resolves every preference.

```tsx
import { KanzoThemeProvider } from "@kanzo-tech/ui";
import { GRAPH_SECTION } from "@kanzo-tech/graph/section";

const SECTIONS = [GRAPH_SECTION];

export function Providers({ children }: { children: React.ReactNode }) {
  return <KanzoThemeProvider sections={SECTIONS}>{children}</KanzoThemeProvider>;
}
```

</Step>
<Step>

### Attach the corpus, once, to the page's coordinator

`engine()` is the page's DuckDB-WASM and its coordinator, memoised per document. fossil's `open`
attaches the corpus to it under a name: a view per table — `"archive"."Sighting"` — and the
manifest as `"archive".fossil_tables` and `"archive".fossil_columns`. Attach once and keep the
`close` it answers for when the page lets the corpus go.

```tsx
import { open } from "@fossil-lang/corpus";
import { engine, MosaicProvider, Selection } from "@kanzo-tech/ui/analytics";

const e = await engine();
const crossfilter = Selection.crossfilter();
const close = await open("archive", { engine: e, url }); // a job: open(id, { engine: e, host })

<MosaicProvider coordinator={e.coordinator} crossfilter={crossfilter}>
  <Workspace />
</MosaicProvider>;
```

`url` is origin-qualified — DuckDB-WASM resolves a root-relative path in its own filesystem — and,
under a `basePath`, prefixed by hand.

</Step>
<Step>

### One crossfilter

The graph names the catalog and reads it through the same coordinator the charts use:

```tsx
const { coordinator } = useMosaic();
const crossfilter = useCrossfilter();

<GraphRoot from="archive" coordinator={coordinator} filterBy={crossfilter} onFailure={setFailure}>…</GraphRoot>
<ChartRoot table={verbatim('"archive"."Sighting"')}>…</ChartRoot>
```

A chart's brush greys out on the canvas the vertices it drops, and the reader's click or lasso is
published as a `dense_id` clause that every chart filters by and the graph does not. A clause naming
columns no vertex table has reaches `onFailure` as `graph/unfilterable`; a table that lacks them
just stays unfiltered.

</Step>
<Step>

### The root, with the look and its pairing

```tsx
import { GraphRoot, useGraphPrefs, type Channels, type LookPreset } from "@kanzo-tech/graph";

const KINDS = { Dataset: "Dataset", Keyword: "Keyword", Publisher: "Publisher" }; // key order = colour rank

const PAIRINGS: Record<LookPreset, Channels> = {
  nebula: { fill: "kind" },
  atlas: { fill: "kind", stroke: "var(--muted-foreground)" },
  ink: { fill: "var(--foreground)", symbol: "kind", stroke: "var(--muted-foreground)" },
};

const { look, sim, preset } = useGraphPrefs();

<GraphRoot
  from="archive"
  coordinator={coordinator}
  filterBy={crossfilter}
  categories={KINDS}
  r="degree"
  title="label"
  look={look}
  sim={sim}
  {...PAIRINGS[preset ?? "atlas"]}
  onFailure={setFailure}
>
```

`look` and `sim` come from the preferences, already memoised. The pairing is the host's: a look is
form, and which column wears colour or shape is a binding. `preset` is `null` once the reader
customises past all three looks, and the host decides what a custom picture wears.

</Step>
<Step>

### The canvas, with its chrome

```tsx
import { GraphCanvas, GraphLegend, GraphToolbar, useGraphState } from "@kanzo-tech/graph";

function GraphRegion() {
  const failed = useGraphState((s) => s.status === "failed");
  return (
    <GraphCanvas className="absolute inset-0">
      <GraphToolbar className="absolute end-2 top-2 z-10" />
      <GraphLegend className="absolute start-2 bottom-2 z-10" />
      {/* failed: the host's own failure view, keyed on the error's code */}
    </GraphCanvas>
  );
}
```

</Step>
<Step>

### The Info panel

```tsx
import { GraphInspector, GraphSearch } from "@kanzo-tech/graph";

function GraphInfo() {
  return (
    <div className="flex h-full flex-col">
      <div className="border-b p-2">
        <GraphSearch placeholder="Find anything in the graph…" />
      </div>
      <ScrollArea className="min-h-0 flex-1 p-3">
        <GraphInspector>{(detail) => <ProductFields detail={detail} />}</GraphInspector>
      </ScrollArea>
    </div>
  );
}
```

The search asks the corpus as the reader types, one `ILIKE` per vertex table; picking reveals the
vertex, and the inspector below reads its row. The render prop is where a product adds fields the
corpus does not carry.

</Step>
<Step>

### The Settings panel

```tsx
import { GraphLooks } from "@kanzo-tech/graph";
import { Kbd, KbdGroup } from "@kanzo-tech/ui";

const GESTURES = [
  { keys: <Kbd>Drag</Kbd>, what: "Pan — or move a node" },
  { keys: <Kbd>Wheel</Kbd>, what: "Zoom where you point" },
  { keys: <Kbd>Click</Kbd>, what: "Focus a node with its neighbours" },
  { keys: <KbdGroup><Kbd>Shift</Kbd><Kbd>Drag</Kbd></KbdGroup>, what: "Marquee, without picking a tool" },
  { keys: <Kbd>⌘ / Ctrl</Kbd>, what: "Add what you draw to the selection" },
  { keys: <Kbd>Alt</Kbd>, what: "Remove it from the selection instead" },
  { keys: <Kbd>Esc</Kbd>, what: "Back out — the drag, then the tool, then the selection" },
];

function GraphSettings() {
  return (
    <ScrollArea className="h-full p-3">
      <GraphLooks />
      <dl>{/* GESTURES, one row each */}</dl>
    </ScrollArea>
  );
}
```

`GraphLooks` is the looks and the axes under Customize; the forces are not in it, because a
layout is a run the toolbar pauses and re-runs, not a picture. Fit is the toolbar's, so the panel needs no camera
button. The gestures are the canvas's own; they are written down here because a reader scanning for
"how do I select two clusters" wants a table.

</Step>
<Step>

### The footer

```tsx
import { GraphCounts, GraphStatus } from "@kanzo-tech/graph";

<ShellFooter className="flex-row items-center gap-2">
  <GraphStatus />
  <GraphCounts />
</ShellFooter>;
```

One word for where the graph is — Loading, Laying out 42%, Ready, Failed — then the corpus:
"5K nodes · 8K edges", or "1.2K of 5K nodes match · 3K edges" under a filter. The word reads the
data's `status` and the layout's `motion` together, so the footer never says "idle" over a running
layout — two axes, see [Layout and camera](/docs/graph/layout#status-and-motion-are-two-axes).

</Step>
</Steps>

## What stays the host's

- **Attaching and detaching the corpus**, and what signs it.
- **The pairing of looks and channels**, and the names in `categories`.
- **What a failure says.** `onFailure` hands it over whole; the host keys on `code`.
- **What a selection means beyond the graph** — `onSelect` and `onFocus`, for a URL, a toast, a
  panel that opens.
- **The arrangement**: which views, which panels, what the header holds. None of it is a part,
  because none of it would survive a second host.
