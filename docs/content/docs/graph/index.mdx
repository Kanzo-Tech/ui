`@kanzo-tech/graph` draws a corpus fossil compiled. fossil is the backend and this package is the
view: the host opens the corpus, `GraphRoot` draws the whole of it, and nothing crosses between the
two but the corpus contract. No SQL is written here.

<Callout type="info">
The graph reads fossil's `fossil/1` format, which `@fossil-lang/corpus` publishes from
`0.3.0-alpha.15`.
</Callout>

It is a **sibling** of `@kanzo-tech/ui`, not part of it.

## Why it is not in the library

[The first admission rule](/docs/philosophy#admission) is *domain-free — nothing about RDF /
SHACL / **graphs** / auth*. Graphs are excluded by name, and deliberately: `ui` is the generic
vocabulary every product shares, and a renderer with a **required** WebGL peer would change what
that package is. A separate package is the same answer `palette` and `theme` already got — ours,
shipped, not `ui`.

## The one path

```tsx
import { open } from "@fossil-lang/corpus";
import { engine } from "@kanzo-tech/ui/analytics";
import { GraphCanvas, GraphInspector, GraphLegend, GraphRoot, GraphToolbar } from "@kanzo-tech/graph";

const corpus = await open(url, { engine: await engine() });

<GraphRoot corpus={corpus} r="degree" onFailure={setFailure}>
  <GraphCanvas>
    <GraphToolbar />
    <GraphLegend />
  </GraphCanvas>
  <GraphInspector />
</GraphRoot>;
```

**Opening is the host's.** Where the corpus is and what signs it are the host's to say: a corpus at
a URL opens as `open(url, { engine })`, and a private one under a name with a `host` that lends the
files, `` open(`jobs/${id}`, { engine, host }) ``. `GraphRoot` takes what came back and never opens
a second copy; closing it is the host's too. **`corpus` takes the opening itself** — the promise
`open` returns — and the root reports `status: "opening"` until it settles and `onFailure` if it
does not; `null` is no corpus at all. The canvas is mounted either way and waits over an empty
surface, because a canvas gated on its first answer has no camera to ask with.

It is the archive the [workspace showcase](/docs/showcases/workspace) draws, opened the same way —
one world, not a second one written for the docs. That showcase is the reference composition: the
graph beside a second main view, with a dock of panels around one `GraphRoot`.

## What the root and the parts own

`GraphRoot` holds the graph's state outside React: the loaded graph, the channels, the selection, the
focus and the motion. It is `useGraph` plus a context, and neither renders an element. The parts are flat
and each reads the root: `GraphCanvas` is the element — cosmos.gl's surface, and what the look
declares over it, the grid, the vignette, the labels, the hover card, plus the marquee and lasso
gesture — and its children are chrome positioned over it. `GraphLegend`, `GraphToolbar` and
`GraphInspector` are that chrome, and each is a part of the root rather than of the canvas, so it
can sit anywhere under it.

**The api is the commands; the state is a selector.** `useGraphContext()` answers with an object
that never changes — `zoomBy`, `fit`, `reveal`, `select`, `setTool` and the rest — and
`useGraphState(selector)` reads a slice of the state and re-renders only when that slice moves. The
state changes at frame rate, a hover and a load and a tick of the layout, so a part that read all of
it would re-render on every hover. It is TanStack Store's `useStore(store, selector)`; inside a
callback, `api.getState()` reads it without subscribing.

**Policy stays with the host, through the root's callbacks.** A click selects a vertex and its
neighbours and focuses it; a lasso selects what it encloses; a failure is reported. What the host
does with each is `onSelect`, `onFocus` and `onFailure`, and **no part takes a callback of its
own** — the package's barrel test holds that. `onFailure` is the one required prop: unhandled, a
browser with no WebGL context shows an empty box.

### Ark's four: `useGraph` and `GraphRootProvider`

`useGraph` **creates** the api, `GraphRoot` is `useGraph` plus the context, `GraphRootProvider`
takes an api a host built itself, and `useGraphContext` **reads** it — `useDialog`, `DialogRoot`,
`DialogRootProvider` and `useDialogContext`, one for one. Reach for the pair when the host needs the
api above the parts:

The count in the corner is a part: it selects `drawn` — the vertices on the canvas, which a filter
shrinks — `total`, the manifest's vertex count, which it does not, and `status`, which is `opening`,
`loading` or `idle` once the whole graph is drawn.

### `GraphToolbar`

<ComponentPreview componentName="graph" fileName="example-toolbar" hasMaxHeight />

The commands, drawn: the selection tools, the selection and what to do with it, zoom and fit, and the
layout's transport. The graph loads at the corpus's positions with no layout running; play runs the
force layout from where the points are, and pause leaves them there. Dragging a node while a layout
runs pins it where it is dropped, and the toolbar then offers to release the pins, which reheats the
layout so the released nodes flow back; with no layout running a drag only moves the node. Each cluster is a `ButtonGroup`, because a cluster is
a claim that its buttons do one job. Pick a tool and drag a box; Shift borrows the marquee whichever
tool is armed, and at release `Alt` removes what was drawn while `⌘`/`Ctrl` adds. The toolbar
declares no `toolbar` role: that role promises roving focus, and each button here is its own tab
stop. `orientation="vertical"` stacks the clusters.

### `GraphLegend`

<ComponentPreview componentName="graph" fileName="example-legend" hasMaxHeight />

The categorical scale the canvas draws, as rows: the glyph, the name, and how many vertices of that
category are drawn — then what is drawn of the whole. With nothing bound to `fill`, the categories
are the vertex types. **A row never moves.** The domain is fixed before the graph loads: the drawn
types in the manifest's order, or the keys of the root's `categories`, which is also what names the
values. A category past the palette's capacity is Other, on the legend as on the canvas.

The names are the root's, never the legend's, so the hover card and the inspector say the same
thing. A legend that renamed a category would be a part encoding one product's policy.

### `GraphInspector`

<ComponentPreview componentName="graph" fileName="example-inspector" hasMaxHeight />

The focused vertex — a click, or `reveal` — read and laid out. The loaded graph carries what the
channels project and nothing else, so the rest of the row is read when a reader focuses it: a scan of
its table, filtered to its `dense_id`, cancelled when the focus moves on. The fields are the table's,
in the order the manifest declares them. **`children` is a render prop** that receives the row and draws
fields of the product's own, a `DataListItem` each — the hall's name above, where the relation
stores its id.

**A label is the `title` column, read for the vertices that carry one.** The canvas labels the
biggest vertices by the `r` ramp, up to the look's label budget, and reads their text — the column
`title` binds, or each table's declared `identity` where it is unbound. The hover card reads the one
under the pointer the same way.

## The whole corpus, read once

When the corpus opens, the graph reads **every vertex table with a position** — fossil's layout, or
columns the program mapped — and **every relation whose two ends are drawn**, one scan per table, into
arrays indexed by each vertex's `dense_id`, and uploads them to cosmos.gl once. A type with no
position is not drawn. Nothing is read because the camera moved: panning and zooming are cosmos.gl's
alone. Changing a column binding re-reads that column and uploads colours and sizes; positions and
links stay where they were.

[The graph view](/docs/design/graph) has the reference each layer copies and the measurements that
decided each rule.

## The channels are bindings

What a point wears is **bound on the root**, under the names Plot gives a point mark: `fill`,
`symbol`, `r`, `stroke` and `title`.

```tsx
<GraphRoot corpus={corpus} fill="kind" r="degree" onFailure={setFailure}>
```

**Unbound, colour is the vertex type**, so a corpus with several types reads as several colours with
nothing passed. **A CSS colour is a constant; anything else is a column.** That is Plot's rule, and it is what makes
the monochrome picture a binding rather than a theme:

```tsx
<GraphRoot corpus={corpus} fill="var(--foreground)" symbol="kind" r="degree" onFailure={setFailure}>
```

Identity has moved to shape, colour is free to mean the selection, and nothing had to know which of
the two a look preferred. A bare word is always a column, so a corpus with a column called `red` is
not a trap.

**A binding is a projection.** `fill` and `r` as columns become the scan's `select` for each table
that has them; a table without the column draws its vertices as the null category. `fill` as a
constant and `stroke` never reach a scan.

**`x` and `y` are not channels.** A position is a fact rather than an encoding — a layout pass or the
program wrote it, and the manifest says which columns hold it.

A `Look` is **form only** — sizes, link width and curve, labels, vignette. Binding `symbol` takes on
an obligation — `gradeComposition(look, channels)` returns the four-pixel radius floor that shape and
size spent together require.

## A filter is a predicate, applied as a mask

`filterBy` is the page's crossfilter, a Mosaic `Selection`. The graph listens to it rather than
being a client of the coordinator: each clause is translated into scan's typed filter — comparisons,
`BETWEEN`, `IN`, `IS NULL`, `AND`, `OR`, `NOT` — read against each drawn table that has every column
it names, and the vertices that do not survive are hidden. A table without one of those columns is
not filtered. A clause it
cannot translate reaches `onFailure` and is never dropped, because a dropped clause draws an
unfiltered picture that reads as a filtered one.

**The reader's pick is published back.** A click or a lasso publishes a `dense_id` clause into the
same crossfilter, naming the graph as the clause's client — so every chart filters by it and the
graph does not, and a lasso of thirteen does not remove the other fifteen hundred.

## Identity

A `VertexId` is the corpus's `dense_id`, a `number`: fossil numbers every vertex of the corpus
`0 … V − 1` across all its tables, the drawn types first, so a drawn vertex's id is also its index in
cosmos.gl's buffers. An id from SQL — `SELECT dense_id FROM …` — is a vertex as it stands, for
`select` or `reveal`.

## How far it goes

Measured on an Apple M4 Pro, not quoted. The recorded tables are on [Benchmarks](/docs/graph/benchmarks),
and `/view/showcases/graph-bench` re-runs them.

**The viewer costs what cosmos.gl costs.** At 200,000 vertices, on the same positions and camera
path, `GraphRoot`'s p95 frame interval is 9.0 ms and cosmos.gl's alone is 9.3 ms.

| Nodes | Links | Per simulation step | Ceiling |
|---|---|---|---|
| 2,000 | 12.5k | 1.6 ms | 611 fps |
| 50,000 | 332k | 10.4 ms | 98 fps |
| 200,000 | 1.4M | 61.6 ms | 16 fps |
| 1,000,000 | 6.9M | 441 ms | 2 fps |

**The ceiling is not the renderer, it is the layout.** A live simulation is comfortable to about
50,000 points and finished by 200,000. Past that, positions are a column — so a simulation is **off
by default**, and the toolbar runs one from where the points are.

## The picture is declared, not hard-coded

Nothing about how a graph looks is a literal here. `lookFrom` and `simFrom` read the same
`Record<string, string>` a preferences section produces — `GRAPH_SECTION` on
`@kanzo-tech/graph/section` is the declaration, a panel draws it, and these two are the only
readers. A host under a preferences panel never calls them itself: `useGraphPrefs()` reads the
provider's resolved `sectionPrefs` for this section and answers `{ look, sim }`.

```tsx
import { GraphCanvas, GraphRoot, useGraphPrefs } from "@kanzo-tech/graph";
import { GRAPH_SECTION } from "@kanzo-tech/graph/section";

// <KanzoThemeProvider sections={[GRAPH_SECTION]}> somewhere above
const { look, sim } = useGraphPrefs();
<GraphRoot corpus={corpus} look={look} sim={sim} onFailure={setFailure}>
  <GraphCanvas />
</GraphRoot>;
```

## Things the source will not tell you twice

These are cosmos.gl behaviours that typecheck perfectly while being wrong.

- **`setConfig` resets everything.** In 3.x it restores defaults and *then* applies the argument.
  Use `setConfigPartial`. Only three fields are genuinely init-only: `initialZoomLevel`,
  `randomSeed` and `attribution`.
- **`getConnectedLinkIndices` is not a neighbourhood.** It returns only links whose *other* endpoint
  is also in the argument. `getNeighboringPointIndices` is the neighbourhood, in buffer indices.
- **Every index cosmos.gl hands you is a buffer position.** `findPointsInRect`, `onPointClick`,
  `getTrackedPointPositionsMap` — here a buffer position is the vertex's `dense_id`, because the
  graph uploads the corpus in id order; in another host it would name nothing stable.
- **`requestAnimationFrame` never fires in a background tab**, and the canvas draws on animation
  frames. A backgrounded graph is stopped, not slow — and `graph.ready` has no failure path, so a
  device that cannot be created leaves the promise unsettled rather than rejecting.

## API Reference

`packages/graph/src/index.test.ts` pins the list: adding a name fails that file until somebody
writes it in.

### The root and the parts

| Name | What it is |
| --- | --- |
| `GraphRoot` | `useGraph` plus the context. Renders no element. |
| `GraphRootProvider` | Takes an api a host built with `useGraph`. |
| `useGraph` | **Creates** the api: a store created once and given the props when one changes. |
| `useGraphContext` | **Reads** it, from any part under a root: the commands, stable for the root's life. |
| `useGraphState` | A slice of the state, and a render only when it moves. |
| `GraphCanvas` | The element, the grid, the vignette, the labels, the hover card and the gesture. |
| `GraphLegend` | The categorical scale the canvas draws, with the tally in view. |
| `GraphToolbar` | The tools, the selection, zoom and fit, and a live layout's transport. |
| `GraphInspector` | The focused vertex's row, with a render prop for fields a product adds. |
| `ShapeGlyph` | The glyph the canvas draws for a category, in the DOM — for a legend key or a card. |

### The picture

| Name | What it is |
| --- | --- |
| `lookFrom` | The axes a person chose, as a `Look`. |
| `simFrom` | The same axes, read as forces. |
| `useGraphPrefs` | Both, joined to the provider's resolved `sectionPrefs` for `GRAPH_SECTION`. |
| `scaleOf` | The categorical scale the channels imply: what colour and what shape a category wears. |

### The types

`GraphRootProps` is `UseGraphProps` plus `children`: `corpus` (or the promise of it), the channels,
`categories`, `filterBy`, `look`, `sim`, `simulate`, `onFailure`, `onSelect` and `onFocus`.
`GraphApi` is the commands — the `GraphCommands` (`zoomBy`, `fit`, `pause`, `resume`, `restart`,
`unpin`, `reveal`, `frameSelection`, `clear`), `select`, `setFocus`, `setTool` — with `subscribe` and
`getState`. `GraphState` is what `useGraphState` selects from: `status` (a `GraphStatus`), `total`,
`drawn` (a `Drawn`: `vertices`, `domain`, `tally`), `domain`, `selection`, `focus`, `hovered`,
`pinned`, `tool`, `motion`, `progress`, `options` and `corpus`. `GraphCanvasProps`, `GraphLegendProps`,
`GraphToolbarProps`, `GraphInspectorProps`, `GraphRootProviderProps` and `ShapeGlyphProps` are the
parts' props, and `VertexDetail` is what the inspector's render prop receives; `Channels`, `Look`,
`LookPatch`, `Shape`, `Sim`, `Motion`, `Selection`, `SelectionSource`, `Tool` and `VertexId` are the
vocabulary.
