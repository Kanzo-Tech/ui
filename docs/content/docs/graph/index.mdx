`@kanzo-tech/graph` draws a corpus fossil compiled. fossil is the backend and this package is the
view: the host opens the corpus, `GraphRoot` draws the whole of it, and nothing crosses between the
two but the corpus contract. No SQL is written here.

<ComponentPreview componentName="graph" fileName="example-workspace" hasMaxHeight />

That is the [discovery workspace](/docs/graph/workspace) in miniature — one root, the canvas with
its toolbar and legend, an Info panel, a Settings panel and the counts in the footer. Each piece is
taken apart below.

## Installation

```sh
pnpm add @kanzo-tech/graph @cosmos.gl/graph @fossil-lang/corpus @kanzo-tech/mosaic @kanzo-tech/ui lucide-react
```

Every peer is required. `@fossil-lang/corpus` reads the corpus, `@kanzo-tech/mosaic` is the page's
one DuckDB-WASM engine and its crossfilter, cosmos.gl draws, and the parts are built from
`@kanzo-tech/ui` and its icons.

<Callout type="info">
The graph reads fossil's `fossil/1` format and needs `@fossil-lang/corpus` `0.3.0-alpha.19` or
later, whose `open` and reads raise coded failures that `onFailure` hands on whole.
</Callout>

It is a **sibling** of `@kanzo-tech/ui`, not part of it. [The first admission
rule](/docs/philosophy#admission) is *domain-free — nothing about RDF / SHACL / **graphs** / auth*,
and a renderer with a required WebGL peer would change what `ui` is. A separate package is the same
answer `palette` and `theme` already got.

## Usage

```tsx
import { open } from "@fossil-lang/corpus";
import { engine } from "@kanzo-tech/ui/analytics";
import { GraphCanvas, GraphLegend, GraphRoot, GraphToolbar } from "@kanzo-tech/graph";
```

```tsx
const corpus = engine().then((e) => open(url, { engine: e }));

<GraphRoot corpus={corpus} r="degree" title="label" onFailure={setFailure}>
  <GraphCanvas>
    <GraphToolbar className="absolute end-2 top-2" />
    <GraphLegend className="absolute start-2 bottom-2" />
  </GraphCanvas>
</GraphRoot>;
```

<ComponentPreview componentName="graph" hasMaxHeight />

**Opening is the host's.** Where the corpus is and what signs it are the host's to say: a corpus at
a URL opens as `open(url, { engine })`, and a private one under a name with a `host` that lends the
files, `` open(`jobs/${id}`, { engine, host }) ``. `GraphRoot` takes what came back and never opens
a second copy; closing it is the host's too. **`corpus` takes the opening itself** — the promise
`open` returns — so the root reports `status: "opening"` until it settles and `onFailure` if it does
not; `null` is no corpus at all. The promise must settle: the root sets no deadline on it, because
the waits inside `open` are fossil's to bound. The canvas is mounted either way and waits over an
empty surface, because a canvas gated on its first answer has no camera to ask with.

## Anatomy

```text
GraphRoot                  the state and the commands; renders no element
├── GraphCanvas            the element: points, links, grid, labels, hover card, marquee and lasso
│   ├── GraphToolbar       selection tools, the selection, zoom and fit, the layout's transport
│   └── GraphLegend        one row per category: glyph, name, how many are drawn
├── GraphCounts            "1.2K of 5K nodes drawn · 8K edges"
├── GraphSearch            find a vertex by its text and reveal it
└── GraphInspector         the focused vertex's row
GraphLooks                 the picture's preferences; needs the theme provider, not a root
```

**Every part reads the root, not its parent.** `GraphCanvas`'s children are chrome positioned over
the surface, but `GraphToolbar`, `GraphLegend`, `GraphCounts`, `GraphSearch` and `GraphInspector`
each read the root's context directly, so each can sit anywhere under it — over the canvas, in a
dock, in a footer. `GraphLooks` is the exception the other way: it writes preferences, so it needs
`GRAPH_SECTION` on the theme provider and no root at all.

## The mental model

### The root holds the state; the api is the commands

`GraphRoot` holds the graph's state outside React — the loaded graph, the channels, the selection,
the focus and the layout's motion — and renders no element. **`useGraphContext()` answers with the
commands**, an object that never changes for the root's life: `zoomBy`, `fit`, `pause`, `resume`,
`restart`, `unpin`, `reveal`, `frameSelection`, `clear`, `select`, `setFocus` and `setTool`.
**`useGraphState(selector)` reads a slice of the state** and re-renders only when that slice moves.
The state changes at frame rate — a hover, a load, a tick of the layout — so a part that read all of
it would re-render on every hover. It is TanStack Store's `useStore(store, selector)`; pass a second
argument, an equality, when the selector builds an object. Inside a callback, `api.getState()` reads
the state without subscribing.

### Policy stays with the host, through the root's callbacks

A click selects a vertex and its neighbours and focuses it; a lasso selects what it encloses; a
failure is reported. What the host does with each is `onSelect`, `onFocus` and `onFailure`, and **no
part takes a callback of its own** — the package's barrel test holds that. `onFailure` is the one
required prop; [Failures](#failures) says why.

### Ark's four: `useGraph` and `GraphRootProvider`

`useGraph` **creates** the api, `GraphRoot` is `useGraph` plus the context, `GraphRootProvider`
takes an api a host built itself, and `useGraphContext` **reads** it — `useDialog`, `DialogRoot`,
`DialogRootProvider` and `useDialogContext`, one for one. Reach for the pair when the host needs the
api above the parts:

<ComponentPreview componentName="graph" fileName="example-provider" hasMaxHeight />

The badge is a host's own part: it selects `drawn`, `total` and `status`, and nothing else, so a
hover does not re-render it.

### `status` is the data's; `motion` is the layout's

`status` is where the **data** is: `none`, `opening`, `loading`, `idle` once the whole graph is
drawn, `failed`. `motion` is where the **layout** is: `running`, `paused` or `settled`, with
`progress` from `0` to `1`. They are two axes because each moves without the other — a filter loads
under a paused layout, and a layout runs over a graph with nothing left to read — so a footer that
says "laying out" reads `motion`, never `status`. [Layout and camera](/docs/graph/layout) has the
whole of it: what play does, what a drag pins, where the camera goes.

## Examples

### Toolbar

<ComponentPreview componentName="graph" fileName="example-toolbar" hasMaxHeight />

The commands, drawn: the selection tools, the selection and what to do with it, zoom and fit, and the
layout's transport. Pick a tool and drag; **Shift** borrows the marquee whichever tool is armed, and
at release **Alt** removes what was drawn while **⌘/Ctrl** adds; **Esc** backs out of the drag, then
the tool, then the selection. While a selection is held its cluster appears — the count, Frame and
Clear. Play runs the force layout from where the points are and pause leaves them there; while
nodes are pinned, Release joins the transport. Each cluster is a `ButtonGroup`, because a cluster is
a claim that its buttons do one job. The toolbar declares no `toolbar` role: that role promises
roving focus, and each button here is its own tab stop. `orientation="vertical"` stacks the
clusters.

### Legend

<ComponentPreview componentName="graph" fileName="example-legend" hasMaxHeight />

The categorical scale the canvas draws, **as rows and nothing else**: the glyph, the name, and how
many vertices of that category are drawn. With nothing bound to `fill` the categories are the vertex
types; with colour a constant and nothing on `symbol` there is no category to key, and the legend
renders nothing. **A row never moves.** The domain is fixed before the graph loads — the drawn types
in the manifest's order, or the keys of the root's `categories` — so a colour never changes hands. A
category past the palette's capacity is Other, on the legend as on the canvas.

The names are the root's, never the legend's, so the hover card, the search and the inspector say
the same thing. What is drawn of the whole is not the legend's: it is `GraphCounts`.

### Counts

<ComponentPreview componentName="graph" fileName="example-counts" hasMaxHeight />

What is drawn of the whole, in one sentence: **"1.2K of 5K nodes drawn · 8K edges"**. The first
figure shrinks with the page's filter and the second is the manifest's, so the sentence is the
filter's effect; an edge counts when both its ends are drawn. A figure not yet known is "—", and the
numbers are compact in the nearest `LocaleProvider`'s locale.

`spinner` draws a `Spinner` beside it — labelled "Loading" while the corpus opens or the graph
loads, "Laying out" while a layout runs — for a host with no status of its own. **`aria-busy`
follows the load alone**: only a load changes these figures, and a running layout moves the points,
not the counts, so a screen reader is not told the sentence is stale while it is not.

### Search

<ComponentPreview componentName="graph" fileName="example-search" hasMaxHeight />

Find a vertex by its text and go to it. Every drawn vertex's `title` — or its table's `identity` —
is read **once**, one two-column scan per table, and then filtered in the browser as the reader
types: no query per keystroke. The list is ordered by the `r` ramp, so with `r="degree"` the hubs
come first, and each match carries its category's name from the root's `categories`. Picking one is
`reveal`: the canvas frames it and selects it with its neighbours, and `GraphInspector` reads it. A
vertex the page's filter hides is not offered — there is nothing on the canvas to go to. `limit`
caps the list (50) and says so.

**A failed read is kept whole**: it reaches `onFailure` as thrown, and the input turns
`aria-invalid` with the placeholder "The names could not be read." rather than staying disabled.

It is a `Combobox` and not `ChartSearch` because of what the control means: `ChartSearch` publishes
a substring filter, which narrows the picture; picking is a value, which goes somewhere.

### Inspector

<ComponentPreview componentName="graph" fileName="example-inspector" hasMaxHeight />

The focused vertex — a click, a search or `reveal` — read and laid out. The loaded graph carries
what the channels project and nothing else, so the rest of the row is read when a reader focuses it:
a scan of its table, filtered to its `dense_id`, cancelled when the focus moves on. The fields are
the table's, in the order the manifest declares them. **`children` is a render prop**: it receives
the `VertexDetail` and draws fields of the product's own, a `DataListItem` each, after the corpus's —
here the hall's name, where the relation stores its id. "Find on canvas" reveals the vertex again.

### Looks

<ComponentPreview componentName="graph" fileName="example-looks" hasMaxHeight />

The picture's preferences, drawn: three **looks** — Nebula, Atlas and Ink, each a card with a
miniature drawn through the canvas's own glyphs and scale — and the axes themselves folded under
**Customize**. Wearing a look writes every axis it names; a look is checked exactly when the resolved
axes are its own, so no name is stored beside them, and a picture customised past all three checks
none and opens Customize. A look whose axes a tenant pinned is disabled.

**It needs `GRAPH_SECTION` on the theme provider** — without it there is nothing to write and it
renders nothing — and the root reads the answer through `useGraphPrefs()`:

```tsx
import { KanzoThemeProvider } from "@kanzo-tech/ui";
import { GraphLooks, GraphRoot, useGraphPrefs } from "@kanzo-tech/graph";
import { GRAPH_SECTION } from "@kanzo-tech/graph/section";

const SECTIONS = [GRAPH_SECTION]; // module scope: a new array re-resolves every preference

<KanzoThemeProvider sections={SECTIONS}>…</KanzoThemeProvider>;

// under it
const { look, sim, preset } = useGraphPrefs();
<GraphRoot corpus={corpus} look={look} sim={sim} {...PAIRINGS[preset ?? "atlas"]} onFailure={setFailure}>
```

**A look is form; the channels are the host's.** `preset` is `"nebula"`, `"atlas"`, `"ink"` or
`null`, for a host that pairs channels with a look. Ink's register spends identity on shape — `fill`
as one ink, `symbol` on the category — but that is a binding, and a binding is the host's to make:

```tsx
const PAIRINGS: Record<LookPreset, Channels> = {
  nebula: { fill: "kind" },
  atlas: { fill: "kind", stroke: "var(--muted-foreground)" },
  ink: { fill: "var(--foreground)", symbol: "kind", stroke: "var(--muted-foreground)" },
};
```

### Declared axes, without the panel

<ComponentPreview componentName="graph" fileName="example-axes" hasMaxHeight />

`lookFrom` and `simFrom` read the same `Record<string, string>` a preferences section produces —
`GRAPH_SECTION` on `@kanzo-tech/graph/section` is the declaration, and these two are its only

## The whole corpus, read once

When the corpus opens, the graph reads **every vertex table with a position** — fossil's layout, or
columns the program mapped — and **every relation whose two ends are drawn**, one scan per table,
into arrays indexed by each vertex's `dense_id`, and uploads them to cosmos.gl once. A type with no
position is not drawn. Nothing is read because the camera moved: panning and zooming are cosmos.gl's
alone. Changing a column binding re-reads that column and uploads colours and sizes; positions and
links stay where they were.

**A label is the `title` column, read for the vertices that carry one.** The canvas labels the
biggest vertices by the `r` ramp, up to the look's label budget, and reads their text — the column
`title` binds, or each table's declared `identity` where it is unbound. The hover card reads the one
under the pointer the same way.

[The graph view](/docs/design/graph) has the reference each layer copies and the measurements that
decided each rule.

## The channels are bindings

What a point wears is **bound on the root**, under the names Plot gives a point mark: `fill`,
`symbol`, `r`, `stroke` and `title`.

```tsx
<GraphRoot corpus={corpus} fill="kind" r="degree" onFailure={setFailure}>
```

**Unbound, colour is the vertex type**, so a corpus with several types reads as several colours with
nothing passed. **A CSS colour is a constant; anything else is a column.** That is Plot's rule, and
it is what makes the monochrome picture a binding rather than a theme:

```tsx
<GraphRoot corpus={corpus} fill="var(--foreground)" symbol="kind" r="degree" onFailure={setFailure}>
```

Identity has moved to shape, colour is free to mean the selection, and nothing had to know which of
the two a look preferred. A constant is `var(…)`, a hex or a colour function, so a bare word is
always a column, and a corpus with a column called `red` is not a trap.

**A binding is a projection.** `fill` and `r` as columns become the scan's `select` for each table
that has them; a table without the column draws its vertices as the null category. `fill` as a
constant and `stroke` never reach a scan. The graph holds **one** categorical column, so `symbol`
beside a `fill` column reads the same one.

**`categories` names the values and ranks them.** Its keys are the category's values — table names
when colour is the vertex type — and its values are what the legend, the hover card, the search and
the inspector call them. **The keys' order is the colour rank**, fixed before the graph loads.

**`x` and `y` are not channels.** A position is a fact rather than an encoding — a layout pass or the
program wrote it, and the manifest says which columns hold it.

## A filter is a predicate, applied as a mask

`filterBy` is the page's crossfilter, a Mosaic `Selection`. The graph listens to it rather than
being a client of the coordinator: each clause is translated into scan's typed filter — comparisons,
`BETWEEN`, `IN`, `IS NULL`, `AND`, `OR`, `NOT` — read against each drawn table that has every column
it names, and the vertices that do not survive are hidden. A table without one of those columns is
not filtered, the way a `WHERE` over a union of the tables would behave. **A clause it cannot
translate, or one no drawn table can answer, reaches `onFailure`** as `graph/untranslatable-filter`
and is never dropped, because a dropped clause draws an unfiltered picture that reads as a filtered
one.

**The reader's pick is published back.** A click or a lasso publishes a `dense_id` clause into the
same crossfilter, naming the graph as the clause's client — so every chart filters by it and the
graph does not, and a lasso of thirteen does not remove the other fifteen hundred. The
[workspace recipe](/docs/graph/workspace#one-crossfilter) shares one crossfilter with
`@kanzo-tech/ui/analytics`.

## Identity

A `VertexId` is the corpus's `dense_id`, a `number`: fossil numbers every vertex of the corpus
`0 … V − 1` across all its tables, the drawn types first, so a drawn vertex's id is also its index in
cosmos.gl's buffers. An id from SQL — `SELECT dense_id FROM …` — is a vertex as it stands, for
`select` or `reveal`.

## Failures

<ComponentPreview componentName="graph" fileName="example-failure" hasMaxHeight />

**`onFailure` is required**, because unhandled, a browser with no WebGL context shows an empty box.
It receives every failure **as it was thrown**: fossil's errors keep their `code` (`corpus/unreadable`
above, from a corpus that is not there), and the graph's own are a `GraphError`. The root reports
`status: "failed"` beside it, so a part can render the failed state without holding the error.

| `GraphError` code | When |
| --- | --- |
| `graph/no-webgl` | No WebGL context, or no GPU device came up. `data.after` is set when the 10 s device deadline fired. |
| `graph/context-lost` | The browser took the WebGL context back. |
| `graph/nothing-to-draw` | The corpus has no vertex type with a position. |
| `graph/untranslatable-filter` | A crossfilter clause the graph cannot ask the corpus. |

A part that reads on its own — the search's names, the inspector's row, a label's text — hands its
failure to the same `onFailure` and shows it in place. A host keys its message on `code` and falls
back to the message.

## Pitfalls

- **Memoise `look`, and hold `sim` steady.** The root repaints on `look`'s identity, so a fresh
  object per render is an upload per render; a fresh `sim` re-heats a layout that is running.
  `useGraphPrefs()` answers the same objects until a preference moves; a hand-built look belongs in
  `useMemo`.
- **`categories`' key order is the colour rank.** Reorder the keys and every category changes
  colour. Write the object once, in the order the colours should go, at module scope.
- **`onFailure` is not optional.** Without it a browser with no WebGL, a corpus that will not open
  and a filter that cannot be translated all look like an empty canvas.
- **A large corpus pays for the camera that follows the layout.** While a layout runs the camera
  re-frames every 900 ms, and so does Fit once a layout has run; each re-frame reads every position
  back from the GPU. Past tens of thousands of points that is a stall per re-frame —
  [Layout and camera](/docs/graph/layout#large-corpora) has what to do.
- **Register `GRAPH_SECTION` once, at module scope.** `GraphLooks` renders nothing without it, and
  a `sections` array built in render re-resolves every preference on every render.
- **A hidden tab is a stopped graph.** The canvas draws on animation frames, and
  `requestAnimationFrame` never fires in a background tab.

### cosmos.gl behaviours that typecheck while being wrong

- **`setConfig` resets everything.** In 3.x it restores defaults and *then* applies the argument.
  Use `setConfigPartial`.
- **`getConnectedLinkIndices` is not a neighbourhood.** It returns only links whose *other* endpoint
  is also in the argument. `getNeighboringPointIndices` is the neighbourhood, in buffer indices.
- **Every index cosmos.gl hands you is a buffer position.** Here a buffer position is the vertex's
  `dense_id`, because the graph uploads the corpus in id order; in another host it would name
  nothing stable.
- **`graph.ready` has no failure path.** A device that cannot be created leaves the promise
  unsettled, which is why the root sets its own deadline.

## How far it goes

**The viewer costs what cosmos.gl costs**: at 200,000 vertices, on the same positions and camera
path, `GraphRoot`'s p95 frame interval is 9.0 ms and cosmos.gl's alone is 9.3 ms. **The ceiling is
the layout, not the renderer** — a live simulation is comfortable to about 50,000 points and
finished by 200,000 — so a simulation is off by default. [Benchmarks](/docs/graph/benchmarks) has
the recorded tables.

`ShapeGlyphProps` are the parts' props; `VertexDetail` — `vertex`, `table` and `fields` — is what the
inspector's render prop receives. `Channels` (`fill`, `symbol`, `stroke`), `Look`, `LookPatch`,
`LookPreset`, `Shape`, `Sim`, `Motion`, `Selection`, `SelectionSource`, `Tool`, `VertexId`,
`GraphCommands`, `GraphStatus` and `Drawn` are the vocabulary, and `GraphError` is the class of the
graph's own failures.
