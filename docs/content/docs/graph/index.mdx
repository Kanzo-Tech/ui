`@kanzo-tech/graph` draws a corpus fossil compiled. The host attaches it to the page's DuckDB with
fossil's `attach`, under a catalog name; `GraphRoot` reads that catalog through the page's Mosaic
coordinator, like every chart beside it, and draws the whole graph with cosmos.gl. It imports
nothing of fossil's: the contract is the catalog.

<ComponentPreview componentName="graph" fileName="example-workspace" hasMaxHeight />

That is the [discovery workspace](/docs/graph/workspace) in miniature — one root, the canvas with
its toolbar and legend, an Info panel, a Settings panel and the counts in the footer. Each piece is
taken apart below.

## Installation

```sh
pnpm add @kanzo-tech/graph @cosmos.gl/graph @kanzo-tech/mosaic @kanzo-tech/ui lucide-react
```

Its stylesheet entry goes after `@kanzo-tech/ui`'s. The canvas is WebGL, but the palette, the
inspector and the legend are utilities, and a utility only this package writes is generated only
when something scans it:

```css title="app/globals.css"
@import "tailwindcss";
@import "@kanzo-tech/ui/tailwind.css";
@import "@kanzo-tech/graph/tailwind.css";
```

Every peer is required: cosmos.gl draws and lays out, `@kanzo-tech/mosaic` is the page's coordinator
and crossfilter, and the parts are built from `@kanzo-tech/ui` and its icons. The host attaches the
corpus with `@fossil-lang/corpus`'s `attach`, which attaches a catalog and answers the attachment
that detaches it; the graph never imports it.

It is a **sibling** of `@kanzo-tech/ui`, not part of it. [The first admission
rule](/docs/philosophy#admission) is *domain-free — nothing about RDF / SHACL / **graphs** / auth*,
and a renderer with a required WebGL peer would change what `ui` is. A separate package is the same
answer `palette` and `theme` already got.

## Usage

```tsx
import { attach } from "@fossil-lang/corpus";
import { engine } from "@kanzo-tech/ui/analytics";
import { GraphCanvas, GraphLegend, GraphRoot, GraphToolbar } from "@kanzo-tech/graph";
```

```tsx
const e = await engine();
await attach("archive", { engine: e, url }); // views "archive"."<Table>", fossil_tables, fossil_columns

<GraphRoot from="archive" coordinator={e.coordinator} r="degree" title="label" onFailure={setFailure}>
  <GraphCanvas>
    <GraphToolbar className="absolute end-2 top-2" />
    <GraphLegend className="absolute start-2 bottom-2" />
  </GraphCanvas>
</GraphRoot>;
```

<ComponentPreview componentName="graph" hasMaxHeight />

**Attaching is the host's**, and so is detaching: `attach` answers the attachment whose `detach()` gives the catalog
back. `from={null}` is no corpus yet. The canvas is mounted either way and waits over an empty
surface, because a canvas gated on its first answer has no camera to ask with.
[Discovery workspace](/docs/graph/workspace) is the whole wiring — the engine, one coordinator, one
crossfilter, the graph and the charts.

## Anatomy

```text
GraphRoot                  the state and the commands; renders no element
├── GraphCanvas            the element: points, links, grid, labels, hover card, marquee and lasso
│   ├── GraphToolbar       selection tools, the selection, zoom and fit, the layout's transport
│   └── GraphLegend        one row per category: glyph, name, how many are drawn
├── GraphStatus            where the graph is, in one word: Loading, Laying out 42%, Ready, Failed
├── GraphCounts            "5K nodes · 8K edges", or "1.2K of 5K nodes match · 3K edges"
├── GraphSearch            a palette: find a vertex, by text, type or column, and reveal it
└── GraphInspector         the focused vertex: its row
```

**Every part reads the root, not its parent.** `GraphCanvas`'s children are chrome positioned over
the surface, but `GraphToolbar`, `GraphLegend`, `GraphStatus`, `GraphCounts`, `GraphSearch` and `GraphInspector`
each read the root's context directly, so each can sit anywhere under it — over the canvas, in a
dock, in a footer. **The graph's settings are not a part.** They are `GRAPH_SECTION`, drawn by
`@kanzo-tech/ui`'s `PreferencesSections` or composed from its `<Pref>`, and the root is the section's
owner: it answers the corpus's columns and the cards' pictures to whatever sits beneath it —
[Settings](#settings).

## The mental model

### The root holds the state; the api is the commands

`GraphRoot` holds the graph's state outside React — the loaded graph, the channels, the selection,
the focus and the layout's motion — and renders no element. **`useGraphContext()` answers with the
commands**, an object that never changes for the root's life: `zoomBy`, `fit`, `pause`, `resume`,
`restart`, `reveal`, `frame`, `clear`, `select`, `setFocus` and `setTool`.
**`useGraphState(selector)` reads a slice of the state** and re-renders only when that slice moves.
The state changes at frame rate — a hover, a load, a tick of the layout — so a part that read all of
it would re-render on every hover. It is TanStack Store's `useStore(store, selector)`; pass a second
argument, an equality, when the selector builds an object. Inside a callback, `api.getState()` reads
the state without subscribing.

### Policy stays with the host, through the root's callbacks

A click selects a vertex and its neighbours and focuses it; a lasso selects what it encloses; a
failure is reported. What the host does with each is `onSelect`, `onFocus` and `onFailure`, and **no
part takes a callback of its own** — the package's barrel test holds that. `onFailure` is the one required prop;
[Failures](#failures) says why.

### Ark's four: `useGraph` and `GraphRootProvider`

`useGraph` **creates** the api, `GraphRoot` is `useGraph` plus the context, `GraphRootProvider`
takes an api a host built itself, and `useGraphContext` **reads** it — `useDialog`, `DialogRoot`,
`DialogRootProvider` and `useDialogContext`, one for one. Reach for the pair when the host needs the
api above the parts:

<ComponentPreview componentName="graph" fileName="example-provider" hasMaxHeight />

The badge is a host's own part: it selects `drawn`, `total` and `status`, and nothing else, so a
hover does not re-render it.

### `status` is the data's; `motion` is the layout's

`status` is where the data is — `none`, `loading`, `idle`, `failed` — and `motion` where the layout
is — `running`, `paused`, `settled`. [Layout and camera](/docs/graph/layout#status-and-motion-are-two-axes)
is the one page for both.

## Examples

### Toolbar

<ComponentPreview componentName="graph" fileName="example-toolbar" hasMaxHeight />

The commands, drawn: the selection tools, what is in full colour and what to do with it, zoom and
fit, and the layout's transport. Pick a tool and drag; **Shift** borrows the marquee whichever tool is
armed, and at release **Alt** removes what was drawn while **⌘/Ctrl** adds — to the canvas's
selection, or, with none, to what the page's filters keep. **Esc** backs out of the drag, then the
tool, then the canvas's selection, and never another place's filter: that is let go at its chip.
Whenever something is greyed out its cluster appears — *N of T*, with *· M hidden by other filters*
when the selection holds vertices another filter hides, then Frame, and Clear while the canvas holds
a selection. Play runs the force layout from where the points are and pause leaves them there. Each cluster is a `ButtonGroup`, because a cluster is
a claim that its buttons do one job. The toolbar declares no `toolbar` role: that role promises
roving focus, and each button here is its own tab stop. `orientation="vertical"` stacks the
clusters.

### Legend

<ComponentPreview componentName="graph" fileName="example-legend" hasMaxHeight />

The categorical scale the canvas draws, **as rows and nothing else**: the glyph, the name, and how
many vertices of that category are drawn. With nothing bound to `fill` the categories are the vertex
types; with colour a constant and nothing on `symbol` there is no category to key, and the legend
renders nothing. **A row never moves.** The domain is fixed before the graph loads — the vertex types
in `fossil_tables`' order, or the keys of the root's `categories` — so a colour never changes hands. A
category past the palette's capacity is Other, on the legend as on the canvas.

The names are the root's, never the legend's, so the hover card, the search and the inspector say
the same thing. How much of the corpus there is, and how much the filter keeps, is not the legend's:
it is `GraphCounts`.

### Counts

<ComponentPreview componentName="graph" fileName="example-counts" hasMaxHeight />

The corpus in one sentence: **"5K nodes · 8K edges"** with nothing filtered, and
**"1.2K of 5K nodes match · 3K edges"** under the page's filter. The whole is `fossil_tables`'
count and the part is `matching`, the vertices the filter keeps. A vertex the filter drops is greyed
on the canvas, not hidden, so the verb is "match" and never "drawn". An edge counts when both its
ends are drawn, so the edges shrink with the filter. A figure not yet known is "—", and the numbers
are compact in the nearest `LocaleProvider`'s locale.

**`aria-busy` follows the load alone**: only a load changes these figures, and a running layout moves
the points, not the counts, so a screen reader is not told the sentence is stale while it is not.
Whether a layout runs is `GraphStatus`'s word.

### Status

**Where the graph is, in one word**: Loading, Laying out 42%, Ready or Failed. It reads both axes
of the state — the data's `status` and the layout's `motion` with `progress` — so a layout running
over a drawn graph says "Laying out", never the data's `idle`; a load wins over a layout, and a root
with no corpus yet says Loading. A `Badge` with a `Status` dot: info while busy, success when ready,
destructive when failed.

The word is a polite live region, announced once per change; the percentage sits outside it, because
it moves at frame rate. The badge is `aria-busy` while loading or laying out.

```tsx
<footer className="flex items-center gap-2">
  <GraphStatus />
  <GraphCounts />
</footer>
```

### Search

Find a vertex and go to it — a palette in the shape of Raycast's and Linear's ⌘K, over Cosmograph's
search, built on `Command`. The workspace at the top of this page carries one: press
<kbd>⌘</kbd>+<kbd>K</kbd>, or the field in its Info panel.

**In the page it is a cue**: a button styled as a field that prints ⌘K and holds nothing, Shark's own
command trigger. It, ⌘K and Ctrl+K open the palette, centred and full-height over the canvas — a
`CommandDialog` with `hotkey="mod+k"`. One palette per page, so nothing arbitrates the key; the cue
declares it as `aria-keyshortcuts`. Each pause in typing (150 ms) asks the corpus once, through the
coordinator, for the first `limit` matches and how many there are of each type; nothing is read
before the reader types and no text is held in the page. Matches are grouped by vertex type — named by
the root's `categories` and counted past the limit — each with the glyph the canvas draws it in, the
typed text highlighted and, on the right, its identity's local name, as Linear prints an issue's key: a
title is not unique, and fifty rows reading "scout" are told apart by it. The palette keeps its height
whatever it holds, as Raycast's and Linear's do.

Three things narrow it, as Neo4j Bloom's search does:

| Typed | Keeps |
| --- | --- |
| `type:Person` | the vertices of one table |
| `<column>:<value>` — `team:2` | vertices whose column contains the value, case-insensitively |
| anything else | vertices whose `title` — or their table's `identity` — contains it |

A word is a prefix only when what precedes its colon is `type` or a column some vertex table has, so
an IRI typed whole stays text. Every statement is built with mosaic-sql's nodes: what the reader
typed is a literal, never part of the SQL.

**A prefix becomes a chip on <kbd>Space</kbd>** — a `TagsInput` sharing the palette's input, whose
`validate` is the same reading, so free text never becomes one. <kbd>Backspace</kbd> in an empty
input highlights the last chip, then removes it.

| Key | Does |
| --- | --- |
| <kbd>Enter</kbd> | `reveal`s the highlighted match — the canvas frames it and selects it with its neighbours, and `GraphInspector` reads it — and closes the palette |
| <kbd>⌘</kbd>/<kbd>Ctrl</kbd>+<kbd>Enter</kbd> | adds every match in the subset, past the limit, as the search's own clause — **Add N to the subset** in the footer does the same |
| <kbd>Esc</kbd> | closes the palette |

**Empty, the palette offers where to start**: the last five picks, which the root remembers for its
life — never in `localStorage` — as **Recent**, then every vertex type with how many it holds, as
**Narrow to a type**. Picking a type makes it a `type:` chip, as GitHub's palette offers its scopes.
`limit` caps the list (50), and the footer says how many matched and how many of them it shows.

**It searches the subset.** The matches are those every other clause on the crossfilter keeps —
`usePick("search").predicate()` — and the footer says how many more lie outside it: *12 matches ·
40 more outside the subset*, or *None in the subset · 40 outside it*. **Add N to the subset**
publishes the search's own clause over the N inside; one outside would be a clause the others
already exclude, since picks intersect. A reveal selects on the canvas, so the next search stays
inside that neighbourhood until its chip is removed.

**A failed read is kept whole**: it reaches `onFailure` as thrown, and the input turns
`aria-invalid` with the placeholder "The names could not be read." rather than staying disabled.

It is a `Command` and not `ChartSearch` because of what the control means: `ChartSearch` publishes
a substring filter, which narrows the picture; picking is a value, which goes somewhere.

### Pick from beside the canvas

<ComponentPreview componentName="graph" fileName="example-pick" hasMaxHeight />

A rule and the vertices that break it, an answer and the vertices it counted, a search's matches:
**`usePick(id)` publishes them as a clause of their own** on the crossfilter the graph filters by —
`key IN (ids)`, whose chip reads `label`. Every clause filters every client, the graph included,
which greys out the rest. `pick(ids, label)` replaces what that place picked before; `pick(null)`
withdraws it.

**Each place is its own source, so picks intersect.** A rule's pick and a lasso together keep the
vertices both hold, as Mosaic's crossfilter defines it; one place picking twice replaces its own
clause. `id` names the place and the source is the root's for its whole life, so a panel that closes
and opens again still owns the clause it left: `picked` is that clause's label, or `null`. The clause
outlives the component on purpose — it belongs to the page, and is retracted at its chip.

**`predicate()` is the subset as that place sees it**: every clause on the crossfilter but its own,
Mosaic's `Selection.predicate(client)`. A search reads its matches under it, and a rule validates
under it, so neither narrows by what it picked itself.

### Inspector

<ComponentPreview componentName="graph" fileName="example-inspector" hasMaxHeight />

The focused vertex — a click, a search or `reveal` — read and laid out after the Linkurious
inspector, in sections and rules rather than a card, which inside a dock would be a second border. The loaded graph carries what the channels bind and nothing else, so the row is
read when a reader focuses it: one `SELECT` of its table at its `dense_id`.

- **The header** names the vertex — its type over it, with the canvas's glyph when colour is the
  type, then its `title`, else its IRI's local name (what follows the last `#` or `/`), else `#id` —
  with **Locate** beside it: `reveal`, which frames it with its neighbours on the canvas and keeps the
  camera there through a resize or a settling layout.
- **The IRI under the name**, a link out with the copy button beside it: the identity is what a
  reader carries elsewhere, so it is never a row to hunt for.
- **Nothing selects the neighbours here.** A click on the canvas already selects a vertex with its
  neighbours, and so does Locate; the connections are the canvas's to show.
- **The fields** are the table's, two columns, in `fossil_columns`' order, grouped as **Values** and
  **Dates** — a date is a column whose declared type is a date or a time. An IRI is a link out, and a
  long text is clamped with "more". A `DataListItem` the render prop draws lines up with them without
  a class of its own.

**`children` is a render prop**: it receives the `VertexDetail` and draws fields of the product's own,
a `DataListItem` each, after the corpus's values — here the hall's name, where the relation stores
its id.

### Settings

<ComponentPreview componentName="graph" fileName="example-looks" hasMaxHeight />

**The graph's settings are its section, drawn whole: one line.** `GRAPH_SECTION` declares what may
be set — the picture, where the points come from and the forces — and `@kanzo-tech/ui` draws it. The
root is the section's owner, as the theme provider is the core's: it answers the attached corpus's
columns and the pictures on the cards to every `<Pref>` beneath it, so no host passes a list it
does not own. [Sections](/docs/sections) has the whole model.

```tsx
import { KanzoThemeProvider, PreferencesSections } from "@kanzo-tech/ui";
import { GraphCanvas, GraphRoot, useGraphPrefs } from "@kanzo-tech/graph";
import { GRAPH_SECTION } from "@kanzo-tech/graph/section";

const SECTIONS = [GRAPH_SECTION]; // module scope: a new array re-resolves every preference

<KanzoThemeProvider sections={SECTIONS}>…</KanzoThemeProvider>;

// under it
const { look, sim, placement } = useGraphPrefs(); // placement: {} | { x, y } | { cluster }
<GraphRoot from="archive" coordinator={coordinator} fill="kind" look={look} sim={sim} {...placement} onFailure={setFailure}>
  <GraphCanvas />
  <PreferencesSections namespace="graph" />
</GraphRoot>
```

The picture's axes are Cosmograph's configuration, read as choices a reader can name. There are no
named looks over them — Cosmograph and Gephi Lite's appearance panel offer the axes with good
defaults, and so does this section. A preference a tenant pinned is not offered.

| Preference | Values | What it draws |
| --- | --- | --- |
| Marks | Dense · Legible | How much ink a point spends — cards, each previewing the current picture with that mark. |
| Labels | None · Hovered · Top · Visible · All | Which points carry their title — below. A slider from None to All. |
| Edges | Hidden · Straight · Curved | `showLinks` and `curvedLinks` as one axis — cards with a preview. |
| Additive links | switch | Links add where they overlap. Offered only while edges are drawn (`when`). |
| Vignette · Dot grid | switches, two to a row | The backdrop. |
| Placement | Force · Map · Clustered | Where the points come from — [Placement](#placement). Cards with a picture of each mode. |
| X axis · Y axis | the corpus's numeric fields | Map's two columns. Offered only under Map. |
| Group by | the corpus's fields | Clustered's column. Offered only under Clustered. |
| Cluster pull | slider, its ends named | Offered only under Clustered: from *Links decide* to *Tight groups*. |
| Gravity · Repulsion · Link spring · Link distance · Friction | sliders | The forces. Offered only under Force. |

**Labels are one ordered scale**, each level adding to the one before. **None** draws no text at all,
not even the hover card. **Hovered** is the hover card and the focused point's label. **Top** adds the
150 biggest points by the size channel — Cosmograph's `showTopLabelsLimit` default. **Visible** adds
the 100 biggest of cosmos.gl's sample of the points in view (one per 100 px cell), taken again each
time the camera rests — Cosmograph's dynamic labels, `showDynamicLabelsLimit`. **All** adds every
point of that sample, with no count of its own: the bound is the screen's, one point per 100 px
square, so an 800 × 600 view adds at most 48 whether the graph holds a thousand points or 327,000.
Cosmograph has no unbounded label set either, and All once was one — a sort, a label element, a
tracked position and a title read per vertex. At every level a label that would overlap a bigger
point's is dropped rather than drawn over it, and the titles are read for the labelled points only. The levels are the type `LabelLevel`, the `labels` field of a `Look`.

**A look is form; the channels are the host's.** The preferences never change which column wears
colour or shape. A host that wants identity on shape binds `symbol` to the category and paints
`fill` one ink, and Legible marks are what make a shape readable.

### Placement

<ComponentPreview componentName="graph" fileName="example-placement" hasMaxHeight />

Where the points come from, composed here from the part — a page that wants placement alone writes
its `<Pref>`s, and each draws itself only when its declaration says so. **Force** is the GPU layout;
**Map** binds two numeric columns as `x` and `y`, and nothing simulates; **Clustered** runs the
layout with cosmos.gl's cluster force over one column. The columns are Cosmograph's `pointXBy`,
`pointYBy` and `pointClusterBy`, and their options are the corpus's own fields from
`fossil_columns`, answered by the root — numeric ones for Map, any for Clustered; fossil's
`dense_id` and identity are not fields. A column is a `Select`, because the data answers its list;
clearing it unbinds it.

```tsx
<GraphRoot from="archive" coordinator={coordinator} {...placement} onFailure={setFailure}>
  <Pref name="graph.placement" />
  <Pref name="graph.x-by" /> {/* only under Map */}
  <Pref name="graph.y-by" />
  <Pref name="graph.cluster-by" /> {/* only under Clustered */}
</GraphRoot>
```

**A column is the person's, not the corpus's.** It is stored with their preferences, so it reaches
corpora that lack it, and the root reads such a column as unbound — the layout runs — rather than as
a column of nulls. With one of Map's two columns chosen the layout runs too. **Latitude as `y` draws
north up**: cosmos.gl's space is y-up, and the placement into its square only scales and translates.

### Declared axes, without the panel

<ComponentPreview componentName="graph" fileName="example-axes" hasMaxHeight />

`lookFrom`, `simFrom` and `placementFrom` read the same `Record<string, string>` a preferences
section produces — `GRAPH_SECTION` on `@kanzo-tech/graph/section` is the declaration, and these three

## The channels are bindings

What a point wears is **bound on the root**, under the names Plot gives a point mark: `fill`,
`symbol`, `r`, `stroke` and `title`.

```tsx
<GraphRoot from="archive" coordinator={coordinator} fill="kind" r="degree" onFailure={setFailure}>
```

**Unbound, colour is the vertex type**, so a corpus with several types reads as several colours with
nothing passed. **A CSS colour is a constant; anything else is a column.** That is Plot's rule, and
it is what makes the monochrome picture a binding rather than a theme:

```tsx
<GraphRoot from="archive" coordinator={coordinator} fill="var(--foreground)" symbol="kind" r="degree" onFailure={setFailure}>
```

Identity has moved to shape, colour is free to mean the selection, and nothing had to know which of
the two a look preferred. A constant is `var(…)`, a hex or a colour function, so a bare word is
always a column, and a corpus with a column called `red` is not a trap.

**A binding is a column read.** `fill`, `r` and `cluster` as columns are read for each vertex table
that has them; a table without the column draws its vertices as the null category. `fill` as a
constant and `stroke` are never read. The graph holds **one** categorical column, so `symbol` beside
a `fill` column reads the same one. **`r` unbound sizes by degree.**

**`categories` names the values and ranks them.** Its keys are the category's values — table names
when colour is the vertex type — and its values are what the legend, the hover card, the search and
the inspector call them. **The keys' order is the colour rank**, fixed before the graph loads.

**`x` and `y` are where a point is drawn.** Both bound — `x="lon" y="lat"`, say — the points sit at
the data's values and nothing simulates; unbound, a GPU force layout places them. `cluster` names the
column a running layout pulls together by. [Layout and camera](/docs/graph/layout#when-the-layout-runs)
has the rule.

**`filterBy` is the page's crossfilter.** A chart's clause greys out on the canvas what it drops —
never hides it — and the reader's lasso or click is published back as a semi-join on
the vertex key, for every client and not for the graph. A pick from beside the canvas — `usePick` —
is a clause of its own, and filters the graph too. Removing that clause where it was published — a
`FilterBar` chip, the page's reset — clears the pick on the canvas too.

**A clause is column predicates, or a semi-join on identity.** A column clause filters each vertex
table that has every column it names. A semi-join — `clauseSemiJoin("dense_id", ids | query)` —
names `dense_id` alone, so it filters every vertex table whatever its subquery reads: the vertices a
rule found, the endpoints of an edge table, an answer's rows.

```tsx
import { Query, clauseSemiJoin } from "@kanzo-tech/ui/analytics";

// Everyone who lives in Saltmere, published by a panel: the graph greys out the rest.
crossfilter.update(
  clauseSemiJoin("dense_id", Query.select("src").from(livesIn).where(inSaltmere), { source: panel, label: "Saltmere" }),
);
```

[The clause rule](/docs/design/graph#the-clause-rule-column-predicates-or-a-semi-join-on-identity)
has why, and [the graph view](/docs/design/graph#the-graph-is-a-client-of-the-pages-coordinator)
has how the graph answers.

## Identity

A `VertexId` is the corpus's `dense_id`, a `number`: fossil numbers every vertex of the corpus
`0 … V − 1` across all its tables, each table one contiguous range, so a vertex's id is also its
index in cosmos.gl's buffers. An id from SQL — `SELECT dense_id FROM …` — is a vertex as it stands, for
`reveal` or a pick.

**The graph reads the key's name from the manifest, not from a constant**: it is the column
`fossil_columns` gives the `address` role, which fossil's writer names `dense_id`. Every clause the
graph publishes is a semi-join on it, and a corpus whose vertex tables have no such column is refused
as `graph/nothing-to-draw`.

### readJoinGraph

`readJoinGraph(coordinator, from)` is the same corpus as a `JoinGraph` — what
`@kanzo-tech/ui/analytics`' [relations](/docs/analytics/dashboard#relations) are built over. Each
vertex table is a type keyed by `dense_id` that projects the columns the writer gave no role, and
each edge table joins through its `src`, which holds its source vertex table's `dense_id`, and its
`dst`, which holds its destination's. The views a corpus is attached as declare no keys, so this is
what says an edge table joins anything. The charts never learn fossil; they take the graph as data.

```ts
const graph = await readJoinGraph(coordinator, jobId);
const table = relationQuery(graph, { root: "Person", path: [] });
<Dashboard table={table} publish={semiJoinOf("dense_id", table)} />
```

`publish` is what lets the dashboard sit on the graph's crossfilter: its tiles' clauses name
`Person.country`, which no vertex table has, so the page gets them as one semi-join on `dense_id`
instead — [what the page sees](/docs/analytics/dashboard#what-the-page-sees).

*Held by* `packages/graph/src/core/join-graph.test.ts`, "keys a type by its address, projects the
columns the writer gave no role, and joins edges on src and dst".

## Failures

<ComponentPreview componentName="graph" fileName="example-failure" hasMaxHeight />

**`onFailure` is required**, because unhandled, a browser with no WebGL context shows an empty box.
It receives every failure **as it was thrown**, and the graph's own are a `GraphError`. The root
reports `status: "failed"` beside it, so a part can render the failed state without holding the
error. A failed `attach` is the host's own — above, fossil's coded `corpus/unreadable`, routed to the
same handler and drawn by [`Problem`](/docs/data-display/problem), which reads the code off whatever
was thrown and takes the host's words for it.

| `GraphError` code | When |
| --- | --- |
| `graph/no-webgl` | No WebGL context, or no GPU device came up. `data.after` is set when the 10 s device deadline fired. |
| `graph/context-lost` | The browser took the WebGL context back. |
| `graph/no-positions` | The device came up but holds no positions for the points it was given, found when the camera read them back. `cause` is what the read threw. |
| `graph/nothing-to-draw` | The attached corpus has no vertex. |
| `graph/unfilterable` | A column clause naming columns no vertex table has. A table lacking a clause's columns just stays unfiltered by it; a semi-join on `dense_id` is answered by every table. |

A part that reads on its own — the search's names, the inspector's row, a label's text — hands its
failure to the same `onFailure` and shows it in place. A host keys its message on `code` and falls
back to the message.

## Pitfalls

- **Memoise `look`, and hold `sim` steady.** The root repaints on `look`'s identity, so a fresh
  object per render is an upload per render; a fresh `sim` re-heats a layout that is running.
  `useGraphPrefs()` answers the same objects until a preference moves; a hand-built look belongs in
  `useMemo`.
- **`categories`' key order is the colour rank.** Reorder the keys and every category changes
  colour. Write the object once, in the order the colours should go, at module scope.
- **`onFailure` is not optional.** Without it a browser with no WebGL, a corpus that will not read
  and a filter no table can answer all look like an empty canvas.
- **A large corpus pays for the camera that follows the layout.** While a layout runs the camera
  re-frames every 900 ms, and so does Fit once a layout has run; each re-frame reads every position
  back from the GPU. Past tens of thousands of points that is a stall per re-frame —
  [Layout and camera](/docs/graph/layout#large-corpora) has what to do.
- **Register `GRAPH_SECTION` once, at module scope.** The graph's settings draw nothing without it, and
  a `sections` array built in render re-resolves every preference on every render.
- **A hidden tab is a stopped graph.** The canvas draws on animation frames, and
  `requestAnimationFrame` never fires in a background tab.

### cosmos.gl behaviours that typecheck while being wrong

- **`setConfig` resets everything.** In 3.x it restores defaults and *then* applies the argument.
  Use `setConfigPartial`.
- **`getConnectedLinkIndices` is not a neighbourhood.** It returns only links whose *other* endpoint
  is also in the argument. `getNeighboringPointIndices` is the neighbourhood, in buffer indices.
- **Every index cosmos.gl hands you is a buffer position.** Here a buffer position is the vertex's
  `dense_id`, because the graph uploads the corpus in id order; in another host it would name
  nothing stable.
- **`highlightedPointIndices` does not grey links.** A link between two greyed points stays lit
  unless `highlightedLinkIndices` names the ones to keep — the filter sets both.
- **`graph.ready` has no failure path.** A device that cannot be created leaves the promise
  unsettled, which is why the root sets its own deadline.

## How far it goes

The layout is tuned by size — how long it cools, how big its square, whether links are drawn while
it runs — and done in about ten seconds at 200,000 vertices and at 500,000.
[Layout and camera](/docs/graph/layout#how-the-layout-scales) has the rules and the measurements;
[Benchmarks](/docs/graph/benchmarks) has the viewer against cosmos.gl alone.

## Testing

`GraphCanvasHarness` from [`@kanzo-tech/testing`](/docs/testing) drives a canvas and its toolbar.
It waits for the canvas's first drawn frame (`aria-busy` until then) and, after a gesture or
**Frame**, for a frame drawn after it, counted in `data-frame`. Points are in the data you bound to
`x` and `y`, through cosmos.gl's own space-to-screen conversion.

```ts
import { GraphCanvasHarness } from "@kanzo-tech/testing";

const graph = await env.harness(GraphCanvasHarness);
await graph.ready();
await graph.lasso([[-10, 40], [5, 40], [5, 55]], { in: "data", with: "Meta" });
await graph.frame();
```

### GraphApi

The commands, stable for the root's life — `GraphCommands` plus the state's door.

| Member | What it does |
| --- | --- |
| `zoomBy(factor)` | Zooms the camera by a factor. |
| `fit()` | Frames the graph: the bound positions' extent, or where the points are once a layout has run. |
| `pause()` / `resume()` | Pauses a running layout; resumes a paused one, or runs a settled one again. |
| `restart()` | Runs the layout from full heat. |
| `reveal(vertex)` | Selects and focuses a vertex with its neighbours and frames them — zooms into a vertex with none — taking the camera from any fit. |
| `frame()` | Frames what is in full colour: the canvas's selection within what the page's filter keeps, what the filter keeps when nothing is selected, or the whole graph when nothing is greyed out. |
| `clear()` | Clears the selection and the focus. |
| `setFocus(vertex)` | Focuses a vertex, or none. |
| `setTool(tool)` | Arms `"rect"`, `"lasso"`, or `null` for the reading posture. |
| `subscribe(listener)` / `getState()` | The store, for a callback; a render uses `useGraphState`. |
