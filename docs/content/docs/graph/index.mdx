description: The graph view over a fossil corpus — a tileset over its scan, drawn with cosmos.gl, inside the page's crossfilter.

`@kanzo-tech/graph` draws a corpus fossil compiled. fossil is the backend and this package is the
view: the host opens the corpus, `GraphRoot` draws it one tile at a time, and nothing crosses
between the two but the corpus contract. No SQL is written here.

It is a **sibling** of `@kanzo-tech/ui`, not part of it.

## Why it is not in the library

[The first admission rule](/docs/philosophy#admission) is *domain-free — nothing about RDF /
SHACL / **graphs** / auth*. Graphs are excluded by name, and deliberately: `ui` is the generic
vocabulary every product shares, and a renderer with a **required** WebGL peer would change what
that package is. A separate package is the same answer `palette` and `theme` already got — ours,
shipped, not `ui`.

## The one path

```tsx
import { open } from "@fossil-lang/corpus";
import { engine } from "@kanzo-tech/ui/analytics";
import { GraphCanvas, GraphRoot } from "@kanzo-tech/graph";

const corpus = await open(url, { engine: await engine() });

<GraphRoot corpus={corpus} fill="kind" r="degree" title="label" onFailure={setFailure}>
  <GraphCanvas />
</GraphRoot>;
```

<ComponentPreview componentName="graph" hasMaxHeight />

**Opening is the host's.** Where the corpus is and what signs it are the host's to say: a corpus at
a URL opens as `open(url, { engine })`, and a private one under a name with a `host` that lends the
files, `` open(`jobs/${id}`, { engine, host }) ``. `GraphRoot` takes what came back and never opens
a second copy; closing it is the host's too. Until it has opened, pass `corpus={null}` — the canvas
is mounted and waits over an empty surface, because a canvas gated on its first answer has no
camera to ask with.

It is the archive the [workspace showcase](/docs/showcases/workspace) draws, opened the same way —
one world, not a second one written for the docs.

## What the root and the canvas own

`GraphRoot` holds the graph's state outside React: the tiles, the channels, the selection, the focus
and the motion. It is `useGraph` plus a context, and neither renders an element. `GraphCanvas` is the
element: cosmos.gl's surface, and what the look declares over it — the grid, the vignette, the
labels, the hover card — plus the marquee and lasso gesture. Its children are chrome positioned over
it, and each reads the root through `useGraphContext`.

**Policy stays with the host, through the root's callbacks.** A click selects a vertex and its
neighbours and focuses it; a lasso selects what it encloses; a failure is reported. What the host
does with each is `onSelect`, `onFocus` and `onFailure`. `onFailure` is the one required prop:
unhandled, a browser with no WebGL context shows an empty box.

### Ark's four: `useGraph` and `GraphRootProvider`

`useGraph` **creates** the api, `GraphRoot` is `useGraph` plus the context, `GraphRootProvider`
takes an api a host built itself, and `useGraphContext` **reads** it — `useDialog`, `DialogRoot`,
`DialogRootProvider` and `useDialogContext`, one for one. Reach for the pair when the host needs the
api above the parts:

The count in the corner is a part: it reads `drawn` — the marks on the canvas and the vertices they
stand for — and `total`, the manifest's vertex count, which does not shrink with a filter. Over the
archive every tile is the finest one and the two agree; zoomed out over a larger corpus a mark is a
cell of fossil's pyramid, and one mark stands for many.

### The canvas's own overlays

<ComponentPreview componentName="graph" fileName="example-overlays" hasMaxHeight />

Pick a tool and drag a box; Shift borrows the marquee whichever tool is armed, and at release `Alt`
removes what was drawn while `⌘`/`Ctrl` adds. The tool is the root's state, so the toggle above is a
part that calls `setTool` and draws nothing else.

**A label is the `title` column, read with the tile.** The canvas labels the biggest vertices in view
by the `r` ramp, up to the look's label budget, with the text of the column `title` binds — so the
text is bytes in hand and hovering costs nothing. Unbound, there are no labels and the hover card
shows the address.

**An overlay is attached to a vertex, never to a slot.** Buffer positions do not survive a change of
tiles, so a label, a hover, a selection and a pin are held as a `VertexId` and resolved against each
composition.

## The camera is addressed

The canvas never asks a question per camera move. `tileMatrix(type)` lists every tile of every zoom
with its rows and its box when the corpus opens; the view culls those boxes against the camera, picks
**the finest zoom whose tiles in view hold at most `limit` rows** — 20,000 by default — and reads the
tiles it lacks, nearest the centre first, one at a time. A tile already read is never asked again; a
tile the camera has left is aborted, and the engine interrupts the running statement.

**A far view is a coarser zoom of fossil's cell pyramid.** Below the payload a row is a cell: a
summary the writer computed, drawn at the centroid of its members and sized by its count. There is
no sample and no zoom threshold. A cell summarises one channel, so on a cell `fill` is its `mode`
when `fill` binds the column the pyramid's mode is of, and `r` can only mean its count.

**An edge is drawn from bytes in hand.** Each tile's relations are read in both directions, and an
edge is composed when both of its ends are in tiles already read; below the payload the lines are
the pyramid's quotient between cells. An edge shorter than three screen pixels is not composed.

[The graph view](/docs/design/graph) has the reference each layer copies, deck.gl's `Tileset2D` for
the tiles and TanStack Query's store for the adapter, and the measurements that decided each rule.

## The channels are bindings

What a point wears is **bound on the root**, under the names Plot gives a point mark: `fill`,
`symbol`, `r`, `stroke` and `title`.

```tsx
<GraphRoot corpus={corpus} fill="kind" r="degree" onFailure={setFailure}>
```

**A CSS colour is a constant; anything else is a column.** That is Plot's rule, and it is what makes
the monochrome picture a binding rather than a theme:

```tsx
<GraphRoot corpus={corpus} fill="var(--foreground)" symbol="kind" r="degree" onFailure={setFailure}>
```

Identity has moved to shape, colour is free to mean the selection, and nothing had to know which of
the two a look preferred. A bare word is always a column, so a corpus with a column called `red` is
not a trap.

**A binding is a projection.** `fill`, `r` and `title` as columns become the scan's `select`, so
changing one builds a new scan over the same tiles, which reloads them while keeping the picture.
`fill` as a constant, `symbol` and `stroke` never reach a scan. A column the corpus does not carry
fails when the scan is built and reaches `onFailure`.

**`x` and `y` are not channels.** In a laid-out corpus a position is a fact rather than an encoding —
a layout pass wrote it, and it is the index every tile is culled against.

A `Look` is **form only** — sizes, link width and curve, labels, vignette. Binding `symbol` takes on
an obligation — `gradeComposition(look, channels)` returns the four-pixel radius floor that shape and
size spent together require.

## A filter is a predicate

`filterBy` is the page's crossfilter, a Mosaic `Selection`. The graph listens to it rather than
being a client of the coordinator: each clause is translated into scan's typed filter — comparisons,
`BETWEEN`, `IN`, `IS NULL`, `AND`, `OR`, `NOT` — and the canvas draws what survives. A clause it
cannot translate reaches `onFailure` and is never dropped, because a dropped clause draws an
unfiltered picture that reads as a filtered one.

**The reader's pick is published back.** A click or a lasso publishes a `dense_id` clause into the
same crossfilter, naming the graph as the clause's client — so every chart filters by it and the
graph does not, and a lasso of thirteen does not remove the other fifteen hundred.

## Identity

A vertex is `vertexId(type, dense)`: the pair, because `dense_id` numbers within one vertex type. It
is a `bigint`, because the pair is 64 bits and a `number` holds 53 — `mapbox/node-s2` binds the
reference C++ and still returns `1152921504606847000` where Java and Go give
`1152921504606846977`. `typeOf` and `denseOf` are the two halves back out, and `denseOf` is the way
down to SQL, where a clause is `dense_id IN (…)` over one relation.

cosmos.gl answers in **buffer indices**, and every one of them dies with the composition. The api's
`getResident()` resolves one to a vertex and back; nothing outside the package builds that map.

## How far it goes

Measured on an Apple M4 Pro, not quoted. The recorded tables are on [Benchmarks](/docs/graph/benchmarks),
and `/view/showcases/graph-bench` re-runs them.

| Nodes | Links | Per simulation step | Ceiling |
|---|---|---|---|
| 2,000 | 12.5k | 1.6 ms | 611 fps |
| 50,000 | 332k | 10.4 ms | 98 fps |
| 200,000 | 1.4M | 61.6 ms | 16 fps |
| 1,000,000 | 6.9M | 441 ms | 2 fps |

**The ceiling is not the renderer, it is the layout.** A live simulation is comfortable to about
50,000 points and finished by 200,000. Past that, positions are a column — so a simulation is **off
by default**: a corpus's positions are the index the tiles are culled against, and a force that moves
them moves the picture out from under its own index.

## The picture is declared, not hard-coded

Nothing about how a graph looks is a literal here. `lookFrom` and `simFrom` read the same
`Record<string, string>` a preferences section produces — `GRAPH_SECTION` on
`@kanzo-tech/graph/section` is the declaration, a panel draws it, and these two are the only
readers. A host under a preferences panel never calls them itself: `useGraphPrefs()` reads the
provider's resolved `sectionPrefs` for this section and answers `{ look, sim }`.

```tsx
import { GraphCanvas, GraphRoot, useGraphPrefs } from "@kanzo-tech/graph";
import { GRAPH_SECTION } from "@kanzo-tech/graph/section";

// <KanzoThemeProvider sections={[GRAPH_SECTION]}> somewhere above
const { look, sim } = useGraphPrefs();
<GraphRoot corpus={corpus} look={look} sim={sim} onFailure={setFailure}>
  <GraphCanvas />
</GraphRoot>;
```

**`adaptive(nodes)`** is the question a person should not be asked: what a corpus of *this* size
wants — repulsion down, friction up — computed continuously against vertex count, because a graph
crossing a threshold would visibly jump. It is tuning and not level of detail, and it leaves the
coordinate box alone: that box is the corpus's extent.

## Things the source will not tell you twice

These are cosmos.gl behaviours that typecheck perfectly while being wrong.

- **`setConfig` resets everything.** In 3.x it restores defaults and *then* applies the argument.
  Use `setConfigPartial`. Only three fields are genuinely init-only: `initialZoomLevel`,
  `randomSeed` and `attribution`.
- **`getConnectedLinkIndices` is not a neighbourhood.** It returns only links whose *other* endpoint
  is also in the argument. `getNeighboringPointIndices` is the neighbourhood, in buffer indices.
- **Every index cosmos.gl hands you dies with the composition.** `findPointsInRect`,
  `onPointClick`, `getTrackedPointPositionsMap` — all of them speak positions in the current
  buffers. Nothing raises when one is kept: it stays a valid index and starts naming a different
  vertex.
- **`requestAnimationFrame` never fires in a background tab**, and the canvas draws on animation
  frames. A backgrounded graph is stopped, not slow — and `graph.ready` has no failure path, so a
  device that cannot be created leaves the promise unsettled rather than rejecting.

## API Reference

`packages/graph/src/index.test.ts` pins the list: adding a name fails that file until somebody
writes it in.

### The root and the parts

| Name | What it is |
| --- | --- |
| `GraphRoot` | `useGraph` plus the context. Renders no element. |
| `GraphRootProvider` | Takes an api a host built with `useGraph`. |
| `useGraph` | **Creates** the api: a store created once, subscribed with `useSyncExternalStore`, given the props when one changes. |
| `useGraphContext` | **Reads** it, from any part under a root. |
| `GraphCanvas` | The element, the grid, the vignette, the labels, the hover card and the gesture. |
| `ShapeGlyph` | The glyph the canvas draws for a category, in the DOM — for a legend key or a card. |

### The picture

| Name | What it is |
| --- | --- |
| `lookFrom` | The axes a person chose, as a `Look`. |
| `simFrom` | The same axes, read as forces. |
| `useGraphPrefs` | Both, joined to the provider's resolved `sectionPrefs` for `GRAPH_SECTION`. |
| `adaptive` | What a graph of a given size wants from a live layout. |
| `scaleOf` | The categorical scale the channels imply: what colour and what shape a category wears. |

### Identity

| Name | What it is |
| --- | --- |
| `vertexId` | The pair `(type_idx, dense_id)`, packed into a `bigint`. |
| `typeOf` / `denseOf` | The two halves back out, each 32 bits. |

### The types

`GraphRootProps` is `UseGraphProps` plus `children`: `corpus`, `type`, the channels, `filterBy`,
`limit`, `look`, `sim`, `simulate`, `onFailure`, `onSelect` and `onFocus`. `GraphApi` is what a part
reads — `total`, `z`, `pending`, `drawn`, `selection`, `focus`, `hovered`, `pinned`, `tool`,
`motion` and `declined`, the `GraphCommands` (`zoomBy`, `fit`, `pause`, `resume`, `restart`,
`unpin`, `reveal`, `frameSelection`, `clear`), `select`, `setFocus`, `setTool`, and `getGraph` and
`getResident` for a callback created once. `GraphCanvasProps`, `GraphRootProviderProps` and
`ShapeGlyphProps` are the parts' props; `Channels`, `Look`, `LookPatch`, `Shape`, `Sim`, `Motion`,
`Selection`, `SelectionSource`, `Tool`, `VertexId` and `Resident` are the vocabulary.
