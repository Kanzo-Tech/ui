`Dashboard` owns the fields, the automatic layout and the editors. What it does not own is the
spec's home, who may edit it, and what a field's values *mean* in your product. This page is that
share, end to end. Toggle **Editable**, change a card, and watch one write land after you stop:

## 1. Load the saved spec

Read the pattern's spec before drawing, and hand `undefined` when there is none — the automatic
dashboard draws, and nothing is written for a pattern nobody has edited.

```tsx
const key = patternKey(pattern); // from @kanzo-tech/mosaic
const saved = useQuery({ queryKey: ["dashboard", key], queryFn: () => api.getDashboard(key) });
if (saved.isPending) return <Skeleton className="h-96 w-full" />;
```

**Do not draw while the read is pending, and do not fall back to the automatic dashboard when it
fails.** The first edit on a fallback hands `onChange` a whole spec built from the automatic one, and
saving it overwrites the reader's real dashboard. Show the failure instead — an error boundary
around the view is exactly for this.

## 2. Write after a pause

Every edit calls `onChange` with the whole next spec. Moving a tile, renaming a
title or ticking three columns is many edits and one decision, so the write waits for a pause.
`useDebouncedCommit` from the root barrel is that pause: `draft` follows every edit at once, and
`onCommit` runs once the edits stop.

```tsx
import { useDebouncedCommit } from "@kanzo-tech/ui";
import { Dashboard, type DashboardSpec } from "@kanzo-tech/ui/analytics";

function SavedDashboard({ pattern, saved }: { pattern: Pattern; saved: DashboardSpec | undefined }) {
  const key = patternKey(pattern);
  // `undefined` is *Reset to automatic*: the stored spec is deleted, not overwritten.
  const save = useMutation({
    mutationFn: (spec: DashboardSpec | undefined) =>
      spec === undefined ? api.deleteDashboard(key) : api.putDashboard(key, spec),
  });
  const { draft, change } = useDebouncedCommit(saved, (spec) => save.mutate(spec), 800);

  return <Dashboard relation={pattern} value={draft} onChange={change} />;
}
```

- **Draw `draft`, not the stored value.** The edit has to show at once; only the write waits.
- **Send the whole spec** and replace on the server — never a patch merged into what is stored.
- **A failed write is a toast, not a revert.** The reader's draft is still on screen and the next
  edit retries with the whole spec.
- `useDebouncedCommit` deliberately commits nothing on unmount (Strict Mode mounts twice). A host
  that navigates away inside the pause and must not lose the last edit calls `flush()` first.

**An edit made somewhere else is a decision, written at once.** *Add to the dashboard* on an
[answer](/docs/ai/data#the-answer-card) is one: the page keeps one store for the document, which the
editor and Ask both write — the editor with `change`, after its pause, and Ask with `commit`, now and
with whatever edit was pending, so neither overwrites the other. `commit` answers what `onCommit`
answered, so `(spec) => save.mutateAsync(spec)` gives the answer card the write to wait on.

## 3. Read-only

Leave `onChange` out. The dashboard draws the same spec with no pencils, no *Add tile*, no *Add a filter*
and no remove buttons. Filters, picks, brushes, chips and paging still work — a
viewer explores; a viewer does not rearrange.

```tsx
<Dashboard relation={pattern} value={draft} onChange={canEdit ? change : undefined} />
```

A viewer with nothing saved sees the automatic dashboard, which is the right default for a role that
cannot make one.

## 4. Your own labels and colours

`config` maps a field to a [`ChartConfig`](/docs/analytics/charts#chartconfig): for each value, the
label the legend shows, the colour the marks wear, and an icon so colour is never the only channel.
It applies wherever that field is drawn as a series.

```tsx
const CONFIG: Record<string, ChartConfig> = {
  "sighting.verdict": {
    confirmed: { label: "Confirmed", color: "var(--success)", icon: CheckCircle2Icon },
    disputed: { label: "Disputed", color: "var(--warning)", icon: CircleHelpIcon },
    hoax: { label: "Hoax", color: "var(--destructive)", icon: TriangleAlertIcon },
  },
};

<Dashboard relation={SIGHTINGS} config={CONFIG} value={draft} onChange={change} />;
```

- Use **tokens**, not hex: `var(--success)` follows the theme into dark mode and through the
  [theme generator](/theme-generator).
- A status scale wants the status tokens; an ordinary category wants nothing — fields without a
  config take the categorical scheme in order of frequency over the whole relation, so a filter never
  repaints a survivor.
- Keep `config` at module scope or memoised; it is part of what the plots compare between renders.

The config is the host's, not the spec's: it describes what a value means in your product, which is
true of every dashboard over that field, so it is not saved with any of them.

## 5. One dashboard per pattern

A spec names fields, `variable.property`, and so does every clause a part publishes. A clause says
the relation it was published on, so two patterns on the page's one selection never send each other
a column the other does not have: the page lands a clause on another pattern's vertex of the same
type, or carries it along the graph's one shortest path, or keeps none of it where there is no way
across ([across relations](/docs/analytics/charts#across-relations)). Give each pattern its own
dashboard, and its own spec.

A host over a graph hands the provider the graph, picks the pattern with `RelationPicker` and keys
everything by `patternKey`; the graph beside the dashboard follows its brushes through the pattern's
first vertex, with nothing to wire:

```tsx
const key = patternKey(pattern);
const saved = parseDashboards(stored); // throws on anything that is not a current document

// under <MosaicProvider engine={e} graph={graph}>
<RelationPicker graph={graph} value={pattern} onValueChange={setPattern} />
<FilterBar relation={pattern} rowNoun={pattern.length > 1 ? "paths" : "rows"} />
<Dashboard
  key={key}
  relation={pattern}
  value={saved.byPattern[key]}
  onChange={(spec) => {
    const { [key]: _, ...rest } = saved.byPattern; // `undefined` is a reset: forget the pattern
    change({ byPattern: spec === undefined ? rest : { ...rest, [key]: spec } });
  }}
/>
```

The graph and the dashboard share the page's crossfilter: a brush on a tile greys out on the canvas
every vertex but the first vertices of the rows it keeps, and a lasso on the canvas filters every
tile — [what the page sees](/docs/analytics/dashboard#what-the-page-sees).

`key` remounts the dashboard on a switch, and **the reader's filters stay**. A pick on one pattern's
chart is the page's filter, not the chart's: it stays in the `FilterBar` as a chip and filters the
next pattern by the vertex both hold, until the reader removes it — its chip, a re-pick on the
chart, or *Clear every filter*. Switch back and the chart draws the pick it still holds. A clause
published by something that stays mounted, like a graph's lasso, carries over the same way.

A named vertex's index is a column of the pattern and never a field, so there is nothing to exclude
for it. `Dashboards` is one document, written whole —
[the shape, and how it is read back](/docs/analytics/dashboard-spec#dashboards).

## 6. Where failures go

Pass `onFailure` to the `MosaicProvider`. Every card, tile and input reports its own query, with the thrown value — DuckDB's error, or `engine()`'s
`Problem` with its `code`. Each part also says so in its own frame, so the callback is for
telemetry and toasts, not for keeping the page legible.

```tsx
<MosaicProvider engine={e} onFailure={(error) => toastError(error, "A chart could not be read")}>
```

## Checklist

- [ ] One engine per page, and one `MosaicProvider` with the graph.
- [ ] `value` is `undefined` until the pattern's first save; the read's failure is shown, not
      replaced by the automatic dashboard.
- [ ] `onChange` writes the whole spec after a pause, keyed by `patternKey`.
- [ ] `onChange` is absent for viewers.
- [ ] `exclude` lists the host's keys and coordinates; `config` is stable.
- [ ] `onFailure` reaches your telemetry.
