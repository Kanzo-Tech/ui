`@kanzo-tech/ui/analytics` is a **subpath**, not a folder. Everything on it speaks to a live DuckDB
relation through [Mosaic](https://idl.uw.edu/mosaic/): a part declares the query it wants, the
coordinator runs it, and a brush on one chart filters every other part on the page without either
of them knowing about the other.

It holds two layers, and the second is made of the first:

- **The grammar** — `ChartRoot`, about sixty marks, the interactors, the inputs and `ChartStat`:
  Observable Plot's vocabulary as JSX, compiled to one `vg.plot(...)` per root.
  [Charts](/docs/analytics/charts) teaches it and the [gallery](/docs/analytics/gallery) draws every
  mark.
- **The BI kit** — `Dashboard` and its parts. A relation you have not seen, read from one
  `SUMMARIZE`, drawn as a filter row, tiles, chart cards and the rows, and kept as a JSON spec the
  host saves. [Dashboard](/docs/analytics/dashboard) teaches it.

## The mental model

Three things exist on a page that uses this subpath, and every part is one of them or reads one of
them.

### One coordinator, one provider

A Mosaic **coordinator** owns the connection to DuckDB, the query cache, and the clients (anything
that asks it for data). You make it — `engine()` boots DuckDB-WASM in the tab and hands it back — and
pass it to **`MosaicProvider`**. The provider never builds one, which is what keeps DuckDB out of
every Server Component.

```tsx
const { coordinator } = await engine();

<MosaicProvider coordinator={coordinator} onFailure={(error) => report(error)}>
  {/* every chart, input, stat and dashboard on the page */}
</MosaicProvider>
```

One coordinator per page. The provider registers it as vgplot's active coordinator, and that setter
is process-wide: a second coordinator leaves the first set of charts empty. Several providers may
share the one coordinator, each with its own selections — that is how the examples on these pages
stay independent of each other.

`onFailure` is the single path a failed query takes to the host. Every chart, stat, input and
dashboard under the provider calls it with the thrown value, whole — DuckDB's error, or `engine()`'s
`EngineError` with its `code` — and also says it failed in its own frame, so a failed part is never a
blank one.

### One crossfilter

A Mosaic **selection** is a set of **clauses**; a clause is one part's filter — a predicate, the
values behind it, and the `source` that published it. The provider holds a
`Selection.crossfilter()` that every part filters by. Crossfilter resolution means each part sees
every clause *except its own*: brush a histogram and the others narrow, while the histogram keeps
drawing the whole distribution under its brush.

Charts do not publish into the crossfilter directly. Each `ChartRoot` owns a selection of its own,
relayed into the provider's `selected` union and from there into the crossfilter. That indirection
is what lets a chart dim its own bars after a pick (`ChartHighlight` reads the chart's selection)
while every other chart filters —
[the long version](/docs/analytics/charts#feedback-on-the-chart-that-filters).

The provider also gives you the two operations a page-level control wants:

| Call | What it clears |
| --- | --- |
| `useMosaic().reset()` | every clause on the page: each chart's own selection, then the shared two |
| `useMosaic().retract(clauses)` | those clauses only, on the selection each was published into — what a chip's remove button wants |

A plain `crossfilter.reset()` is neither. A reset travels downstream only, so it leaves each chart
holding its own pick, still highlighted.

### Roots, marks, interactors

A **`ChartRoot`** is one plot. Its children are **descriptors** — inert elements that render no DOM:

- **marks** (`ChartBarY`, `ChartLineY`, `ChartRectY`, `ChartDot`, …) say what to draw, with
  channels that are column names or SQL aggregates (`x="hour" y={count()}`);
- **interactors** (`ChartPickY`, `ChartBrushX`, `ChartHighlight`, …) say what a gesture publishes,
  or what a selection dims;
- **axes and facets** (`ChartAxisX`, `ChartFacetX`) are plot attributes.

The root reads its children's props and compiles one plot. Mosaic turns each mark into SQL —
`SELECT bin("hour") AS "x", count(*) AS "y" FROM sightings WHERE … GROUP BY "x"` — so the browser
holds aggregates, never rows.

### What publishes into the crossfilter

Anything can, and a dashboard's chips show all of it, whoever published it:

- a chart's interactor: a pick (`region IN ('Saltmere')`), a brush (`hour BETWEEN 2 AND 5`);
- an input: `ChartFilter`, `ChartSearch`, `ChartSlider`, which are Mosaic clients without being
  charts;
- **a view drawn outside the plot**. [`@kanzo-tech/graph`](/docs/graph) is one more client of the
  coordinator, drawing a fossil corpus on the GPU; a lasso or a click publishes one `clauseSemiJoin`
  on the corpus's **identity** (`dense_id`) from that client, so the crossfilter skips it for the
  graph and applies it to every chart. The same call is open to any panel, with the keys or with a
  statement that selects them:
  `selection.update(clauseSemiJoin("dense_id", ids | query, { source, label }))`. Retract it with
  `null`, never `[]`: an empty list is a clause whose predicate is `FALSE`, which drops every row.

That is the clause rule. A clause is **column predicates on the same relation**, which only a
relation with those columns can answer — why
[a dashboard reads one relation](/docs/analytics/pitfalls#one-dashboard-per-relation) — or **a
semi-join on identity**, `key IN (…)`, which names the key alone: a subquery's columns are another
relation's. `clauseColumns(filter)` reads what a clause names on the relation it filters, so a client
over several relations applies each clause where it can. A dashboard over a vertex table follows a
lasso on the canvas beside it because the semi-join names `dense_id`, and every vertex table has one.
[The graph view](/docs/design/graph#the-clause-rule-column-predicates-or-a-semi-join-on-identity)
has the rule and what would reverse it.

## Why it is not on the root barrel

`import { Button } from "@kanzo-tech/ui"` has to work for a host that has never heard of DuckDB.
A single static `import` of an optional peer from the root barrel breaks that for **everyone** —
not with a warning, with `ERR_MODULE_NOT_FOUND` at load.

So the database half lives behind `/analytics`, and the door is held shut by a test that packs the
real tarball, installs it with none of the optional peers, and imports the root barrel. That check is
the only one that sees the built artefact rather than the source, and it is the reason this page can
state the boundary as a fact rather than an intention.

The parts that take a number and import no engine stay on the root barrel: `Stat` with `StatTrend`
and `StatDelta`, `Table`, `Card`. `ChartStat` and `DashboardStat` are their connected halves —
[the engine rule](/docs/philosophy#the-engine-rule).

## What to install

The peers are **optional in the manifest and required in practice** — optional means "npm will not
install them for you", not "the code works without them".

```bash
pnpm add @kanzo-tech/ui @uwdata/vgplot @uwdata/mosaic-plot @uwdata/mosaic-core @uwdata/mosaic-sql
```

DuckDB-WASM is not among them. The database in the tab is
[`engine()`](/docs/analytics/charts#the-pages-one-engine), and `@kanzo-tech/mosaic` depends on the
exact `@duckdb/duckdb-wasm` release it boots, so it arrives with the library. A host whose
coordinator talks to a server-side DuckDB instead never boots it.

If one is missing you find out at import time, which is the good failure. The bad one — a chart that
renders empty and says nothing — is what `onFailure` and the in-frame failure exist to rule out.

## Reaching the data directly

`useChartQuery` runs a query beside the charts and hands back rows, re-run under the crossfilter —
the supported way to read a relation without drawing it. A widget that runs a plain
`coordinator.query()` in an effect reports unfiltered totals next to filtered charts, which reads as
a bug in the crossfilter. `useFieldStats` is the other read the kit is built on: a relation's
columns, classified. And what a page reads once and draws as it is — a schema, a catalog — is
[`useQueryRows`](/docs/hooks/use-query-rows), which suspends on the statement.
