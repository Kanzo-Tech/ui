<Callout type="info">
This is a **grammar**, not a set of chart types. `ChartRoot` compiles its children into one
`vg.plot(...)`, so a bar and a line share a plot, any interactor pairs with any mark, and the
chart you need is the one you write — there is no `BarChart` to fork.

```tsx
import { count } from "@kanzo-tech/mosaic";
import { ChartRoot, ChartBarY, ChartToggleX } from "@kanzo-tech/ui/analytics";
```

Like [CodeEditor](/docs/forms/code-editor) with CodeMirror, the library wraps the engine and
never owns the runtime: it is **bring-your-own-coordinator**. No chart builds a `Coordinator` — you
take the page's one from `engine()` (or build your own) in a `"use client"` island and pass it in,
which is what keeps the analytics stack out of the base bundle and out of every React Server
Component.
`@kanzo-tech/mosaic`, `@uwdata/vgplot`, `@uwdata/mosaic-plot` and `valibot` are all **optional
peers**, so `import { Button }` keeps working for everyone who has not installed them.

**Mosaic itself comes through `@kanzo-tech/mosaic`, the one door to it** — `count` above, the
coordinator, the selections, the clauses, `Query`, `engine()`. This subpath holds the charts and
their parts and re-exports none of Mosaic ([why](/docs/design/analytics#mosaic-is-reached-through-kanzo-techmosaic-and-a-name-through-one-spelling)).
</Callout>

Four plots over **one** table, on the page's **one** crossfilter `Selection`: drag an interval
across the histogram or the hourly line, click a region bar, drag a box on the scatter — each
publishes to the selection, so brushing any one filters the other three. Nothing above is a chart
component; it is four `ChartRoot`s with two marks and an interactor each.

## Why a grammar

vgplot is ~40 marks, 19 interactors and ~250 attributes. A chart component — `Histogram`,
`BarChart`, `ScatterPlot` — exposes that as one photograph of it, and assembles the plot inside
itself, so the first thing it cannot do needs a fork: a line on top of bars, a brush where the
preset hardcoded a toggle, two marks against a selection you own.

A grammar has no such edge. The proof that it is expressive enough is that every shape a preset
would have covered is [ten lines of JSX](#the-five-charts) you can copy.

## Two kinds of children

`ChartRoot` takes children of two different natures, and the distinction is worth internalising
because it explains everything else on this page:

| | What they are | Idiom |
| --- | --- | --- |
| marks, interactors, axes | **inert descriptors** — they render `null` | Recharts / Observable Plot |
| `ChartRoot`, `ChartLegend`, your own parts | **real DOM** — `ark.*`, `data-slot`, `asChild` | Ark |

A descriptor has no DOM of its own. `ChartRoot` reads the compile function off the element *type*,
in source order, and turns the lot into a single `vg.plot(...)` — the mark never renders.

**Marks cannot be Ark parts**, and that is not a shortcut. vgplot paints imperatively: it returns
an SVG node that we mount with `host.replaceChildren(...)`. There is no element for a part to own,
no ref to forward, no `data-slot` to style. What *is* genuinely Ark here is `ChartRoot` plus
[`useChartContext()`](#usechart) — a context carrying the config, the selections and the coordinator, so
you can build a legend, a tooltip or a readout of your own without forking anything.

The practical consequence: descriptors cannot read context, because they are compiled before React
would render them. Pass values down from the component that owns the `ChartRoot`.

## Anatomy

```tsx
<ChartRoot relation="sightings" config={config} height={220}>
  <ChartBarY x="host" y={count()} fill="host" tip />
  <ChartRuleY at={0} />
  <ChartAxisX tickRotate={45} />
  <ChartAxisY grid />
  <ChartToggleX />
  <ChartLegend />        {/* real DOM: reads the config off the context */}
</ChartRoot>
```

Three rules cover the ordering:

1. **An interactor binds to the last mark declared before it.** Put `ChartToggleX` after the mark
   it should drive.
2. **Axes compile to plot attributes** (`xTickRotate`, `yGrid`), not to vgplot's `axisX`/`axisY`
   decorator marks — an attribute cannot steal the binding from the interactor that follows it.
   `ChartFrame`, `ChartGridX` and `ChartGridY` *are* marks and do shift it.
3. **Fragments and arrays flatten; `null` and `false` vanish.** Conditionals work, which is how you
   [swap an interactor](#swap-the-interactor) at runtime.

There is no `ChartTip`: the tooltip is a mark option, so it is the `tip` prop on any mark.

<Callout type="warn">
**A descriptor must be a direct child, not a child of one of your components.** The compiler walks
the element tree — it never renders it — so it sees `<YourThing />` and stops, exactly as Recharts
does. That includes [`Show`](/docs/layout/rendering#show): a `<Show>` element's type is `Show`, not a
`Fragment`, so whatever it wraps is silently never plotted. Conditional marks and interactors are
the one place in these docs that stays `&&` or a ternary — those compile to `false`, and rule 3 is
what makes them vanish cleanly.
</Callout>

The charts live on the `@kanzo-tech/ui/analytics` subpath, never the root barrel, because the
Mosaic/DuckDB stack is heavy and optional. Install the peers alongside the library —
`@kanzo-tech/mosaic` with its own two, mosaic-core and mosaic-sql; vgplot and mosaic-plot, which
plot; and `valibot`, which checks a dashboard spec:


## The page's one engine

`engine()` is the page's DuckDB-WASM database: one per document, however many islands ask, with
the Mosaic `Coordinator` over it and the file registry beside it. Hand its coordinator to
`MosaicProvider`, which registers it as vgplot's active coordinator and owns the page's one
`Selection`: every chart beneath it filters by it and publishes into it, and nobody passes one in.
Hand it `joins` — a join graph, `readJoinGraph` for a fossil corpus — and a clause published on one
relation reaches a chart reading another ([across relations](#across-relations)). DuckDB-WASM is browser-only, so ask for it in a
`"use client"` island loaded with `ssr: false`, render a skeleton until it is ready, and let the
chart hydrate:

```tsx
"use client";

import { useEffect, useState } from "react";
import { engine, loadObjects, type Coordinator } from "@kanzo-tech/mosaic";
import { MosaicProvider } from "@kanzo-tech/ui/analytics";

export default function Analytics({ children }: { children: React.ReactNode }) {
  const [coordinator, setCoordinator] = useState<Coordinator | null>(null);

  useEffect(() => {
    engine().then(async ({ coordinator }) => {
      await coordinator.exec(loadObjects("sightings", rows));
      setCoordinator(coordinator);
    });
  }, []);

  if (!coordinator) return <Skeleton className="h-40 w-full" />;

  return <MosaicProvider coordinator={coordinator}>{children}</MosaicProvider>;
}
```

`engine()` always settles. A worker that will not load, or a boot slower than 60 s, rejects with an
`EngineError` whose `code` is `"engine/unavailable"` (with `data.after` when the deadline fired), and
the failure is not kept: the next `engine()` boots again. `engine({ signal })` ends your own wait
without stopping the boot other islands share.

The engine also owns what DuckDB reads by name. `registerFiles({ name: url })` registers a URL under a
name — the same URL again is a no-op, a different one replaces the lease, so a re-signed URL never
meets DuckDB's `File already registered` — `registerFileBuffer(name, bytes)` registers a copy of a buffer, and
`dropFiles(names)` forgets them — DuckDB-WASM's names, which fossil's `Engine` uses too. `query(sql, { signal })` answers in columns — the Arrow table
DuckDB-WASM produced, uncached — and an abort interrupts the running statement and rejects with
`signal.reason`. That is the shape fossil's `Engine` asks for, so the engine you chart through is the
one a corpus attaches to.

It boots with DuckDB's `httpfs` loaded, so object storage is SQL rather than another method: a
reader holding a credential scoped to a prefix runs `CREATE OR REPLACE SECRET … (TYPE s3, …, SCOPE
's3://bucket/prefix/')` through `query` and reads `s3://…` by range. Lend under a name without a
scheme: with `httpfs` loaded, `https://…` and `s3://…` in SQL are read by it before the registry is
asked. DuckDB's `parquet` and `json` extensions are loaded beside it, for Parquet and for JSON —
`read_json_auto`, and `loadJSON`.

Nothing it runs comes from a CDN. DuckDB-WASM's worker and module and the `parquet`, `httpfs` and
`json` extensions are part of `@kanzo-tech/mosaic`, named with `new URL(…, import.meta.url)`, so your
bundler emits them as assets and the page loads them from your own origin — there is nothing to copy
into `public/`. DuckDB's autoloading is off, so a function from an extension the engine did not load
is DuckDB's error naming it, never a fetch from extensions.duckdb.org.
Serve `.wasm` as `application/wasm`, and the page's policy needs no host but yours and your
storage's: `script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self' <storage>`.

A backend that is not DuckDB-WASM — a socket or REST connector — is still a `Coordinator` you build
yourself and hand to `MosaicProvider`. `engine`, the loaders (`loadObjects`, `loadCSV`, `loadJSON`,
`loadParquet`, `loadSpatial`, `loadExtension`), `Coordinator` and `Selection` are
`@kanzo-tech/mosaic`'s, so you wire the backend without a direct `@uwdata` import. vgplot's own
`coordinator()` setter is exported by neither: `MosaicProvider` is the only thing that should ever
call it.

<Callout type="warn">
**One coordinator per page.** `MosaicProvider` registers its coordinator as vgplot's active one,
and that setter is process-wide: mount two providers with two different coordinators on the same
page and the last one wins, leaving the other page's charts empty. Share a single instance (every
example below does — see `docs/examples/charts/mosaic-boot.tsx`), or keep the demos on separate
routes. Several `MosaicProvider`s over the *same* coordinator are fine; each still owns its own
`Selection`.
</Callout>

## A relation in another catalog

Every `relation` — on `ChartRoot`, `ChartTimeline`, `ChartStat`, `ChartFilter`, `ChartSearch`,
`ChartSlider`, `FilterBar` and the dashboard's parts — is one word for what a part reads: a table by
name, a path over the provider's `joins` (a `Relation`, see [across relations](#across-relations)),
or SQL. A table reads the way Mosaic reads one. A **string is one
identifier** in the default catalog: `"sightings"` is `FROM "sightings"`, and a dot inside it is
part of the name, not a path. A relation anywhere else is a **mosaic-sql node**, which goes into
the SQL as written: `asTableRef(["guild", "sightings"])` for a path you hold in parts, `verbatim(sql)`
for a name a backend hands you already quoted.

A fossil corpus is the second case. `attach(name, …)` attaches every table as a view in the catalog
`name`, so a vertex type is `"<name>"."Sighting"`, catalog and all; the bare type name is nothing in
the default catalog:

```tsx
"use client";

import { count, verbatim } from "@kanzo-tech/mosaic";
import { ChartAxisX, ChartBarY, ChartRoot, ChartToggleX } from "@kanzo-tech/ui/analytics";

function SightingsByRegion({ relation }: { relation: string }) {
  return (
    <ChartRoot relation={verbatim(relation)} height={160}>
      <ChartBarY x="region" y={count()} fill="var(--chart-1)" />
      <ChartToggleX />
      <ChartAxisX label={null} />
    </ChartRoot>
  );
}

// after attach("archive", { engine, url }): relation is '"archive"."Sighting"'
```

A node is keyed by its SQL, not by its identity, so writing `verbatim(relation)` inline does not
rebuild the plot on every render.

## Across relations

A page draws more than one relation: a dashboard over people, another over their posts, a graph of
every vertex. The provider's selection is still **one** — Mosaic's crossfilter, its interactors, its
re-querying and its pre-aggregated views untouched — with the one thing Mosaic cannot do added
through its own extension point, the selection's resolver: a clause published on one relation, read
by a part on another.

- A part's `relation` is what its clauses are published on, and what a clause published elsewhere
  reaches it as. A **name** — `"Person"`, or a table — is one step; a **`Relation`**, a root type and
  hops over the joins, is longer, compiled with `relationQuery`.
- On **the same relation**, a clause arrives as published.
- On **another relation the joins reach**, it arrives as `key IN (SELECT key FROM T WHERE …)`: the
  rows of the relation it was published on, under every clause published there at once, crossed by
  their root's key into the step of this relation that is of that type.
- With **no step of that type**, it keeps none of the relation — `FALSE`
  ([why](/docs/design/crossfilter#the-thesis-everything-is-a-filter)).

`relation` may change: the chart re-queries and withdraws the clause it published on the old one, and
nothing else needs to know. A part handed SQL over a relation — a projection, an answer's rows — is
told which relation it is by a `MosaicClients relation={…}` around it.

The types: `RelationExpr` is what every `relation` prop takes — a `TableExpr` or a `Relation` — and
`RelationRef` the relation as the page knows it, a name or a path. A `MosaicClient` of your own takes
part by implementing `RelationClient` — a `relation` it reads now — and publishing its clauses through
`onRelation(clause, relation)`.

## Feedback on the chart that filters

Click a bar and every chart filters, **including a visible response on the chart you clicked** —
`<ChartToggleX />` and `<ChartHighlight />`, neither carrying a prop, exactly as in
[categorical bars](#categorical-bars) above. That is the default. It is worth knowing what is
underneath it, because one misplaced prop takes it away.

A crossfilter is defined by **hiding a clause from the client that published it**:

- `Selection.crossfilter()` is created with `cross: true`.
- The resolver skips a clause for any client listed in `clause.clients`, and a toggle's clause lists
  the marks of the plot it came from. That skip is what stops a chart filtering itself into a single
  bar the moment you click one.
- `ChartHighlight` resolves its predicate with `selection.predicate(mark)` — without the `noSkip`
  flag that `filterBy` uses. So against a crossfilter the predicate comes back empty, the test
  degrades to "everything matches", and nothing is dimmed.

The chart that publishes the click is therefore the only one that cannot read it back from the
page. So the interactors publish into the page's selection, and `ChartHighlight` reads by default a
**non-cross** selection of the chart's own, which the root fills from the page with its own
interactors' clauses only:

```tsx
// inside every ChartRoot, for you
const highlight = Selection.union();  // what ChartHighlight reads
// relayed from the page's selection, keeping only the clauses this chart's interactors published
```

Per chart, not per page, and that part is load-bearing. `ChartHighlight` does not filter: it appends
its predicate to the mark's **own** query as an extra output column, and on an aggregating mark that
query has a `GROUP BY`. So a predicate naming a column *this* plot does not group by is
`Binder Error: column "provider" must appear in the GROUP BY clause` — the query dies, vgplot
swallows it, and **the plot keeps its previous render**. No error on screen, no empty state, just a
chart frozen one state behind while its neighbours move.

Reading the page's selection guarantees that the moment a second chart filters by a second column,
which is the ordinary case. The chart's own cannot: the only clauses in it are the ones this plot's
own interactors published, over the columns its own marks group by. It follows the page, so a clause
retracted there stops highlighting here.

`useMosaic()` gives you `selection`, the page's one. A "Clear filters" button is Mosaic's own
`selection.reset()`, and a chip's × `selection.reset([clause])`: each takes the clause out and calls
its source back, so the brush or the pick that published it clears too.

### Two legends, and only one of them is a control

`ChartLegend` is ours and never publishes anything: an `ark.ul` you place where you like, reading
the root's `config`, with the label — not the swatch — carrying the accessible channel.
`ChartColorLegend` is vgplot's, drawn inside the plot, and it both publishes on click and reads the
selection back, dropping unselected swatches to 0.2 opacity.

The difference that looks like a detail and is not: its toggle is built with `peers: false`, so its
clause is **not** hidden from the plot it belongs to. Click a swatch and that plot filters itself —
where `<ChartToggleColor />` on the mark is skipped by the crossfilter for its own marks, which is
the whole of the section above.

<ComponentPreview componentName="charts" fileName="example-color-legend" />

Both legends only stay complete because the `config` pins the colour domain. Without it the scale
is ordered by the data, so filtering to one verdict leaves the legend holding one swatch.

### When you do wire it yourself

- **You pass your own `as` to an interactor.** Then you own its wiring: its clauses are not the
  page's, and `selection.reset()` does not reach them. Pair it with a matching `by` on the highlight,
  and keep to the rule above — one selection per plot, naming only columns that plot groups by.
- **A click should replace the previous pick, not add to it.** `Selection.single()` keeps one clause
  where the default union accumulates (shift/⌘-click adding to a pick is `Toggle`'s own behaviour,
  not ours).

Notes that hold either way:

- **`ChartHighlight` binds to the last mark declared before it**, like every interactor. In the
  dual-layer idiom that is the crossfiltered layer, which is the one you want dimmed.
- Interval brushes need none of this: the brush rectangle is its own feedback.

## What the presets could not do

### Bars and a line in one plot

Two marks, one x scale, one interactor. Under five preset components this needed a sixth component;
here it is one more child.

The interactor is a `ChartToggleX`, and where it sits matters twice over. It binds to the last mark
before it, so it goes between the bars and the line; and it is a toggle rather than a brush because
`ChartBarY` makes x a **band** scale even for an integer hour — an interval over a band throws, and
takes the rest of the page down with it ([why](#limitations)). Bin the x, or toggle it.

### Swap the interactor

Click-to-toggle and drag-to-brush differ by one child. A `false` child compiles to nothing, so the
plot is rebuilt with the other interactor and the marks stay exactly as written. The rebuilt plot
withdraws the clause the old interactor published; the example also calls `selection.reset()` on the
swap, so the page starts clean.

<ComponentPreview componentName="charts" fileName="example-interactor" />

### Bring your own selection

The page's selection is a default, not a cage. Own a `Selection` and wire it explicitly, mark by
mark, as vgplot does: `as` on the interactor that publishes, `filterBy` on the marks that read.
Everything else on the page stays still.

### An unwrapped mark

The layer wraps every mark vgplot ships but six: `axisX`, `axisY`, `axisFx`, `axisFy`, `gridFx` and
`gridFy`, left out on purpose because [axes compile to attributes](#anatomy) and an axis *mark*
would steal the binding from the interactor after it. A plot therefore draws one x axis — and the
scale repeated on the opposite edge, which a long bar list wants, is exactly what `ChartRaw` is for.

Both anchors are spelled out in the example, because Plot adds its implicit axis only while the plot
has no axis mark for that scale: declare one and you own them all. The scale stays `ChartAxisX`'s —
grid and label come from the descriptor, and the marks inherit them.

A raw directive is otherwise a mark like any other: it takes its place in source order (declare it
*after* the interactor you did not want it to capture), and it is a function, so hoist it or the
plot rebuilds on every render. An array is fine — `spec` takes one directive or several.

## ChartConfig

`Record<string, { label?, color?, icon? }>` — series key to presentation, in one place:

```tsx
const config = {
  ok: { label: "OK", color: "var(--chart-1)" },
  error: { label: "Error", color: "var(--chart-5)" },
} satisfies ChartConfig;
```

A non-empty config pins the plot's colour scale (`colorDomain` = the keys, `colorRange` = the
colours) and feeds `ChartLegend`. Pinning matters: without it vgplot orders the colour domain by the
data, so filtering out a series repaints the ones that survive.

`color` takes `var(--chart-1)`, `--primary`, a hex or an `rgb()`. Tokens are resolved against the
live DOM at mount and on every theme change, because Observable Plot cannot parse `oklch`,
`color-mix` or `color(srgb …)`. The same resolution applies to the `fill` and `stroke` props of any
mark — those two channels only, and only when the value looks like a token, so `fill="region"` stays
the *column* `region`. A series without a colour falls back to its slot in the categorical set — as
the token `var(--chart-N)`, not as a baked hex, so one answer follows both the light/dark flip and
whichever client is being served.

`chartSeriesColor(config, key)` is exported for anything outside the plot that has to agree with it
— a chip beside a row, a heading, a sparkline of your own. It answers what the chart answered:
`color` if the series declared one, its categorical slot if it did not, and `undefined` for a key
the config does not carry.

The categorical set belongs to the [tenant's palette document](/docs/theming),
not to this layer: N hues written into `--chart-1..8` by whoever authored the theme. A chart reads the token
and that is the **only** copy. A second source of truth in this layer — eight literal hexes, or a
table of them — makes the same series come out one colour through `ChartConfig` and another
through a token.

A theme need not author them: `tokens.css` declares eight on `:root`, chosen to clear contrast and
separation on every background the catalogue ships, so a theme that writes none still has a chart
channel and one that writes some overrides them slot by slot.

`CHART_SLOTS` is 8 because a stylesheet cannot have a variable number of custom properties. How many of those slots carry a *real* category is the theme's `--chart-capacity`, which can be lower: past
it `compile` writes `var(--muted-foreground)`, because naming five categories honestly beats naming
eight that a colour-blind reader sees as five. Past the eighth series, fold into "Other" —
`categoricalColor(i)` returns the muted token rather than cycling, because a ninth series wearing
slot 1 would claim to be the first one.

## useChartContext()

The context behind any DOM part you add — a legend, a tooltip, a caption:

```tsx
function Total({ rows }: { rows: number }) {
  const { color, formatNumber } = useChartContext();
  return <p style={{ color: color("hoax") }}>{formatNumber(rows)} sightings</p>;
}
```

| Field | What it is |
| --- | --- |
| `color(key)` | the series colour, already resolved to `rgb(...)` — safe in CSS and in Plot |
| `formatNumber(value, options?)` | the chart's `Intl.NumberFormat`, from the root's `locale` / `numberFormat` — one number vocabulary for axes, legend and tooltip |
| `config` | what the root was given |
| `table`, `relation` | what the marks read — the root's `relation`, compiled over the provider's `joins` — and the relation the page knows the chart by, what its clauses are on |
| `selection` | the page's one selection: what the marks read and the interactors write |
| `coordinator` | for a part that queries alongside the plot |
| `plot()` | the vgplot `Plot` on screen as `ChartPlot` — its `interactors` — or `null` before the first build; a part that moves a brush asks the brush, as `ChartTimeline` does |

It throws outside a `ChartRoot`; `useChartContextOptional()` returns `null` instead, which is how
`ChartLegend` also works standalone. Descriptors cannot use it — see
[two kinds of children](#two-kinds-of-children).

## A time filter that plays

`ChartTimeline` is a brushable histogram of one temporal column — a date, a timestamp, or a year
stored as its integer — with *Play time*, which plays the brushed range a bar at a time,
Cosmograph's `Timeline` on the page's selection. The bars behind are the column unfiltered, the
bars above what the page keeps, and the window is one clause: a chip in the `FilterBar` like any
control's.

```tsx
<ChartTimeline field="year" relation="awards" title="Awards by year" />
```

It counts the rows that have the column; a row without one has no bar to stand in. Over a graph,
`relation="vertices"` — every vertex type as one relation, which `readJoinGraph` includes — draws
every vertex with the column, and its window keeps only those: a type without the column is greyed,
as Cosmograph greys it.

The window sticks to the bars' edges, Cosmograph's `stickySelection`, so it reads *1910 – 1940*
and not where the pointer let go, and a year on the axis reads *1900*, never *1,900*. Playing asks
the brushed range's own clause for each frame: a clause belongs to the source that published it
([why](/docs/design/timeline)). The range never moves; play publishes *[its start, one bar
further]* until it holds the whole range, Kepler's `incremental` window, each step waiting for the
page — every client of its selection — to answer the last. With no range Play is
disabled, *Brush a range to play*. At the end it stops with the whole range, and the next Play starts
over; a pointer down on the bars pauses it; Space on the focused figure plays and pauses. While it
plays, its chip reads the window as it grows. *Play time* is a bare icon at the bars' left edge, and the bars take the
rest of the width. The button is `aria-pressed` while it plays, the window the clause holds is a
group whose `aria-valuetext` reads *1950 – 1960*, and a pause or the end is announced. A dashboard's temporal filter is this
part, in its chip.

## Escape hatches

Three, because wrapping vgplot must stay a convenience:

- **`<ChartRaw spec={…} />`** — a `vg.*` directive (or an array of them) in its source position,
  with the same interactor-binding semantics as a wrapped mark. What it is mostly reached for is
  one of the six axis marks the axis descriptors compile away from: `axisX({ anchor: "top" })` to
  repeat the measure scale at the top of a long bar list, `axisFy` to label a facet. Those six are
  on the subpath: they are vgplot's, the plotting half. No token resolution happens inside a raw spec, so pass a Plot-safe
  colour — `resolveTokenColor(host, "--chart-1")` is exported for exactly this, and reads the
  live cascade rather than a frozen copy of it.
- **`attributes` on `ChartRoot`** — raw directives applied *last*, so they win over anything the
  layer decided. For the ~225 plot attributes the axes do not cover.
- **The Mosaic client protocol**, for a view that is not a plot at all — a WebGL canvas, a map, an
  imperative widget. Subclass `MosaicClient` or wrap `makeClient`, declare a query, and publish one
  of the six clauses: Mosaic's `clausePoint`, `clausePoints`, `clauseInterval`, `clauseIntervals`,
  `clauseMatch`, and ours, `clauseSemiJoin` — `key IN (ids | subquery)`, the
  [semi-join on identity](/docs/analytics#what-publishes-into-the-crossfilter) that crosses
  relations. `clauseColumns` is the other half: the columns a clause names on the relation it
  filters, for a client deciding whether its relation answers it. That is the whole of it, and it is
  what makes such a view a **peer** of the plots rather than a readout drifting beside them. All nine
  are `@kanzo-tech/mosaic`'s, with `SemiJoinMembers`, `SemiJoinMetadata` and `SemiJoinOptions`, so
  this costs no direct `@uwdata` import.

  Turning the answer back into values is mosaic-core's `toDataColumns`. `numbers(answer, field)`
  is the one case worth a name: an id or a position read as a `number`, since Arrow hands back
  `BigInt` for some integer widths.

  So is the failure. A client's `queryError` is handed mosaic-core's `QueryError` — a fresh `Error`
  with the SQL appended to the message and the thrown value as its `cause` — so a host keying on a
  `code` finds none on it. `queryFailure(error)` gives the thrown value back, which is what every
  client in this library hands `onFailure`.

Neither hatch needs a source builder: `ChartRoot` already owns the `plot(…)` call, and a mark's
`data` / `filterBy` props already name its relation. A plot attribute still comes from
`@uwdata/vgplot` directly, which is what a hatch is. An expression builder is `@kanzo-tech/mosaic`'s
— the aggregates, `sql`, `verbatim`, `and`, `eq`, `isIn` and the rest it holds; one it does not hold
is mosaic-sql's own, and a host that keeps needing it is the case for adding it to the door.

Both are keyed by identity: a vgplot directive is a function, so building one inline rebuilds the
plot on every render. Hoist it to module scope or `useMemo` it, and keep the `attributes` array
referentially stable.

## Limitations

- **A descriptor wrapped in your own component is invisible.** `ChartRoot` inspects its children's
  element types, so `<MyBar />` — even when it returns `<ChartBarY />` — compiles to nothing. This
  is Recharts' limitation and it has the same cause. Write a function that *returns descriptors*
  and spread them, or make your component wrap the whole `ChartRoot`, as the examples do.
- **Descriptors cannot read React context**, for the same reason.
- **The plot rebuilds when the grammar changes.** Props are fingerprinted (SQL expressions by their
  SQL, so a fresh `count()` is free); functions and selections by identity.
- **An interval brush needs a continuous scale.** `ChartIntervalX` over a *band* scale — bars
  grouped by a string, or by an integer Plot bands — throws `Unrecognized scale type: band` inside
  Mosaic's pre-aggregator the moment the pointer enters the plot. The pre-aggregator belongs to the
  coordinator, so that one mistake blanks the *other* charts on the page, which report nothing of
  their own. Brush binned or continuous marks; toggle categorical ones. `ChartRoot` warns to the
  console in development when it compiles the pairing, because the runtime symptom points anywhere
  but at the chart that caused it.

## Dashboards

A dashboard is not only plots, and the pieces divide by whether they need the engine.

`ChartFilter`, `ChartSearch` and `ChartSlider` are real DOM controls that publish Mosaic clauses
without being charts, so they filter every plot below them. `ChartStat` is a `StatValue` read
from the relation under the same crossfilter, and `useChartQuery` is what it is built on — reach
for it whenever something that is not a plot has to move with the brush. A widget that runs a plain
`coordinator.query()` in an effect will sit there reporting unfiltered totals next to filtered
charts, which reads as a bug in the crossfilter.

`ChartFilter` is a [`FacetFilter`](/docs/forms/facet-filter) over a `GROUP BY`, and it takes that
component's `searchable`. Know what the field covers before you turn it on: it narrows the **fetched
page** — the `limit` most frequent values the control asked for, 50 by default — and asks nothing new
of DuckDB. When the page is truncated, both the footnote and the no-match message say so, because a
field that answers *no matching values* about a database it never queried is worse than no field.
Searching the column itself is `ChartSearch`, which publishes a match clause and does run a query.

`ChartSearch` is a **filter, not a picker** — the clause is a match over whatever you typed, and the
values it offers are completions. It asks for the `autocompleteLimit` distinct values of the column
(50 by default), narrows those in the browser as you type, and **says when that list is capped**;
picking one publishes exactly the clause typing it would have. Set `autocompleteLimit={0}` for a
plain search field with no lookup at all.

Its presentational half, **[`Stat`](/docs/data-display/stat), is in the root barrel** — it
takes a number, so making it cost DuckDB-WASM would be absurd. That split is
[the engine rule](/docs/philosophy#the-engine-rule), the same one behind `Table` and
`DataTableRoot`.

A titled frame is [`Card`](/docs/data-display/card) and a grid is a class list, so neither is a
component here. What *is* one is the whole arrangement, when it is chosen from the data rather than
written: [`Dashboard`](/docs/analytics/dashboard) draws a filter row, tiles, chart cards and the
rows from a relation's stats and a serializable [spec](/docs/analytics/dashboard-spec), and its parts
are exported for a host that arranges its own.

them. Click a region bar and watch which numbers move — and which one does not:

## Theming

vgplot hard-codes its fills; these charts read tokens off the live DOM instead, so a theme change
re-colours the marks along with everything else — the vgplot analogue of how `kanzoHighlighting`
re-skins CodeMirror. Axis text inherits `--foreground` through `currentColor`, so it stays legible
in light and dark. Tokens are resolved against the chart's own host element, so a scoped theme
override wins.


## The compile surface, for a mark this layer does not ship

Every chart child is **inert**: it renders `null` and carries its compilation on a static. That
shape is `ChartDescriptor<P>` and the function on it is `ChartCompile<P>` — `(props, ctx)` in,
directives out — so a host that needs a mark this layer does not wrap writes one child rather than
a fork.

What comes out is a `ChartDirective`, and it is plain data in all four of its cases: a
`ChartMarkDirective`, a `ChartInteractorDirective`, a `ChartAttributeDirective`, or a
`ChartRawDirective`, which is the escape hatch — a `vg.*` value the layer does not wrap, passed
through untouched. What goes in is `ChartSpecContext`, which carries the relation every table-backed
mark reads from; `ChartSpecOptions` extends `ChartFacetOptions` with the rest of what a spec needs,
and `ChartMargin` is the four numbers around it.

The mark's own shapes are `ChartMarkProps` and `ChartMarkSource` — data comes from the table, from a
literal array, or from a query — and `ChartInteractorProps` is the interactor equivalent. A series
is configured with `ChartSeriesConfig` and read back as a `ChartSeriesEntry`, a facet with
`ChartFacetOptions`, and a filter offers [`FacetFilterItem`](/docs/forms/facet-filter#api-reference)s,
the one facet item `FacetFilter` and `DataTableFacetFilter` take too.

Two of these are not about charts at all and are exported because the inputs are. `MosaicInputOptions<T>`
and `MosaicInputState<T>` are what a control needs to be a Mosaic client — the shape behind every
filter input on this page. `ExprValue` is anything Mosaic will accept where an expression is
expected; it is `@kanzo-tech/mosaic`'s, with the rest of Mosaic.

## Testing

`ChartHarness` from [`@kanzo-tech/testing`](/docs/testing) finds a chart as the `figure` its
`aria-label` names, and brushes and picks in data, through the chart's own Plot scales. It waits for
the chart to have drawn — `ChartRoot` is `aria-busy` until then and while a query runs. Pass the
`aria-label` yourself on a `ChartRoot` of your own; a dashboard tile passes its title.

```ts
import { ChartHarness } from "@kanzo-tech/testing";

const lon = await env.getHarness(ChartHarness.with({ title: "Count by Airport.lon" }));
await lon.brush({ x: [-125, -100] });
await (await env.getHarness(ChartHarness.with({ title: "Sightings by beast" }))).pick({ y: "boghound" });
```

## API Reference

### MosaicProvider

| Prop | Type | Default |
| --- | --- | --- |
| `coordinator` | `Coordinator` | — |
| `joins` | `JoinGraph \| null` — the graph a part's `relation` names a type or a path over, and a clause crosses relations through | `null` |
| `onFailure` | `(error: unknown) => void` | — |

`onFailure` receives what a failed query threw, whole — DuckDB's error, or `engine()`'s `EngineError`
with its `code` — from every chart, `ChartStat` and input beneath the provider. The part also says it
failed in its own frame: a failed chart reads *This chart could not be drawn.*, never a blank plot.
`useChartQuery` and `useMosaicInput` return the same value as `error`.

The provider owns the page's one selection; nobody passes one. `useMosaic()` returns
`{ coordinator, selection, joins, onFailure }` — `selection.reset()` clears every clause on the page,
`selection.reset([clause])` that clause, which is what a chip's remove button does, and `onFailure`
reports a failure of your own part the way the library's do. It throws outside a `MosaicProvider`.

### MosaicClients

| Prop | Type | Default |
| --- | --- | --- |
| `enabled` | `boolean` — whether the clients beneath it query; a nested `false` wins | `true` |
| `relation` | `string \| Relation` — the relation the clients beneath it read, for a part handed SQL over it | the enclosing one's |

`MosaicClientsProps` also takes `children`.

Mosaic's own `MosaicClient.enabled`, for every chart mark, input and `useChartQuery` beneath it. A
disabled client keeps its state and its clauses but asks nothing, and enabled again it runs the one
query it was owed. Wrap a panel that leaves the screen but should keep what the reader brushed in
it — a view swapped for another, a collapsed dock — and hide it rather than unmount it: unmounting
retracts its clauses.

```tsx
<MosaicClients enabled={view === "dashboard"}>
  <div hidden={view !== "dashboard"}>
    <Dashboard relation={relation} />
  </div>
</MosaicClients>
```

`relation` names what its clients read when what they are handed is SQL over it — a relation
projected for the plots, an answer's rows narrowed from it: their clauses are published on it, and a
clause on another relation reaches them crossed into it. A `Dashboard` does this for its own tiles.

*Held by* `packages/ui/src/charts/mosaic-clients.test.tsx`, "asks nothing while disabled, keeps
its rows, and runs the query it was owed once enabled".

### Marks

Props are the vgplot / Observable Plot mark options (`x`, `y`, `z`, `r`, `fill`, `stroke`,
`opacity`, `sort`, `limit`, `inset`, …) plus the common sugar: `filterBy` (this mark's selection,
`null` for the full relation), `data` (literal rows instead of the table), `at` (position a rule or
tick without a table), and `tip`.

One option is filled in for you. On the stacking marks — `ChartBarY`/`X`, `ChartArea`/`Y`/`X`,
`ChartRect`/`Y`/`X`, `ChartWaffleY`/`X` — a **column-valued** `fill` or `stroke` is copied to `z`
unless you pass one, because that is Plot's own default and Mosaic breaks it
([why](/docs/analytics/gallery#stacked-area)). `z={null}` opts out.

`ChartBarY` `ChartBarX` `ChartWaffleY` `ChartWaffleX` `ChartLine` `ChartLineY` `ChartLineX`
`ChartArea` `ChartAreaY` `ChartAreaX` `ChartDot` `ChartDotX` `ChartDotY` `ChartCircle`
`ChartHexagon` `ChartImage` `ChartRect` `ChartRectY` `ChartRectX` `ChartCell` `ChartCellX`
`ChartCellY` `ChartRuleY` `ChartRuleX` `ChartTickX` `ChartTickY` `ChartText` `ChartTextX`
`ChartTextY` `ChartVector` `ChartVectorX` `ChartVectorY` `ChartSpike` `ChartArrow` `ChartLink`
`ChartHeatmap` `ChartRaster` `ChartRasterTile` `ChartContour` `ChartDenseLine` `ChartDensity`
`ChartDensityY` `ChartDensityX` `ChartHexbin` `ChartRegressionY` `ChartErrorbarY` `ChartErrorbarX`

decorators: `ChartFrame` `ChartGridX` `ChartGridY` `ChartHexgrid` `ChartSphere` `ChartGraticule` ·

`gridFy` — because they are [attributes here](#anatomy). `ChartRaw` still takes them.

### Interactors

`as` chooses where the interaction publishes (default: the page's selection). Everything else is the vgplot interactor option — `peers`, `brush`, `pixelSize`,
`empty`, …

`ChartIntervalX` `ChartIntervalY` `ChartIntervalXY` `ChartToggleX` `ChartToggleY`
`ChartToggleColor` `ChartNearestX` `ChartNearestY` `ChartRegion` `ChartPanZoom`

Each is vgplot's name, and only that: `ChartToggle*` is a pick — click a category, get
`region IN (…)`, on a band scale — and `ChartInterval*` a brush — drag a range, get
`latency BETWEEN lo AND hi`, on a scale with a *between*. The gesture names `ChartPick*` and
`ChartBrush*` were aliases of these and are gone: one component, one name, the reference's.

`ChartHighlight` is the odd one out: it *reads* a selection (`by`) and dims the mark before it
rather than publishing. It cannot read a crossfilter's own clause, which is why `by` defaults to
the chart's own clauses and not to the page's selection ([the whole
story](#feedback-on-the-chart-that-filters)). `ChartPanZoom` carries no selection at all — it
rewrites the scales.

### Axes

`ChartAxisX` / `ChartAxisY`, each compiling to prefixed plot attributes:

| Prop | Type |
| --- | --- |
| `anchor` | `"top" \| "bottom" \| null` (X) · `"left" \| "right" \| null` (Y) — `null` hides the axis, keeps the scale |
| `label` | `string \| null` |
| `ticks` | count, interval name, or explicit values |
| `tickFormat` `tickSize` `tickRotate` | |
| `grid` `line` `zero` `percent` `nice` `reverse` | `boolean` |
| `domain` `scale` `inset` `padding` | |

Anything else goes through `ChartRoot`'s `attributes`.

`ChartFacetX` and `ChartFacetY` are the same descriptor over the `fx` and `fy` scales — the ones a
faceted plot puts its small multiples on. Same props, minus the four that only mean something on a
measure: a facet is always a band, so `scale`, `nice`, `zero` and `percent` are not there. `anchor`
still hides the axis while keeping the panels.

### Legends

- `ChartLegend` — our DOM (`ark.ul`, `data-slot="chart-legend"`). Reads the root's `config`, or
  takes its own `config` / `series` prop and works standalone. The label carries identity; the
  key is a [`Swatch`](/docs/data-display/swatch), so it is `aria-hidden` — colour is never the
  only channel.
- `ChartColorLegend` — vgplot's, drawn inside the plot and **interactive**: clicking a swatch
  publishes into the selection. Pass `as={null}` for a static key.

### Helpers

On the subpath: `bin`, made once per field and options so a re-render is not a new plot, and the six
axis marks the descriptors withhold on purpose, `axisX` `axisY` `axisFx` `axisFy` `gridFx` `gridFy`,
which are what [`ChartRaw`](#escape-hatches) is for. vgplot's ~250 plot attributes stay a direct
import — taking them raw is what an escape hatch *is*.

From `@kanzo-tech/mosaic`, and from nowhere else: the aggregates `count` `sum` `avg` `min` `max`
`median` `quantile` `stddev` `mode`, and `sql`; the boot vocabulary `engine` `Coordinator` `Selection`
and the `load*` loaders; [`Query`](/docs/hooks/use-chart-query) and `asc` `desc`, the two
directions its `.orderby()` takes; the relation algebra (`Relation`, `JoinGraph`, `relationKey`, …)
and `RelationExpr`, what every part's `relation` takes; `TableExpr`, `numbers` and `queryFailure`.

```tsx
import { count, engine, Query } from "@kanzo-tech/mosaic";
import { ChartBarY, ChartRoot, MosaicProvider } from "@kanzo-tech/ui/analytics";
```
