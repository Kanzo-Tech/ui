title: Dashboard
description: A mini BI over any relation — filters, tiles, chart cards and the rows, chosen from the relation's stats and kept as a JSON spec the host saves.
---

`Dashboard` is the charts grammar composed for a relation you have not seen. It reads the
relation's fields from one DuckDB `SUMMARIZE`, draws a dashboard from them — or from a spec you
saved — and lets the reader edit every part of it. The host brings three things: a
`MosaicProvider`, the relation, and somewhere to keep the spec.

<ComponentPreview componentName="dashboard" fileName="example-default" hasMaxHeight={false} />

```tsx
<MosaicProvider coordinator={coordinator}>
  <Dashboard table="sightings" value={spec} onChange={save} />
</MosaicProvider>
```

The references are Metabase and Superset for the dashboard — cards in an ordered layout, a filter
row scoping all of them, a spec that is plain JSON — and Metabase's X-ray for the dashboard a
relation gets before anybody has edited one.

## What is chosen from the stats

Every field is classified once, from its DuckDB type (through Mosaic's own `jsType`) and its
approximate distinct count:

| Field | Filter | Charts it can be |
| --- | --- | --- |
| A time | a brushable timeline, first in the row | the axis of a line, an area or a histogram; a trend |
| A number | a range slider | an axis, a measure, either side of a scatter; a trend |
| A category (≤ 50 values, or fewer than half the rows) | a facet filter with counts | bars; series (≤ 8 values); panels (≤ 6) |
| A key (`id`, `*_id`, `uri`, or nearly unique text) | a search box | — |

The limits are the dataviz ones: past eight series a chart wants to be a table, not more hues, and
past six panels small multiples stop being comparable. A type no chart can draw — a list, a struct,
a blob — is not a field at all.

## The spec

```ts
interface DashboardSpec {
  version: 1;
  filters: { field: string }[];
  stats: {
    id: string;
    label?: string;
    measure: DashboardMeasure;
    trend?: string;        // an ordered field: sparkline + the last step's change
    goodWhenUp?: boolean;
  }[];
  cards: {
    id: string;
    type: "bar" | "line" | "area" | "histogram" | "dot" | "regression";
    x: string;
    y: DashboardMeasure;
    color?: string;        // series
    facet?: string;        // small multiples
    span?: 1 | 2 | 3;      // columns of a three-column row
    title?: string;
  }[];
  detail: { columns: string[] } | null;
}

interface DashboardMeasure {
  op: "count" | "distinct" | "sum" | "avg" | "min" | "max" | "median" | "share" | "value";
  field?: string;
  equals?: string | number | boolean; // `share`: the % of rows whose field equals this
}
```

Order is layout: cards flow left to right through a three-column grid, and `span` widens one. A
facet is a channel and not a chart type — any line, area, histogram or scatter can be split into
panels — which is how Vega-Lite models it too.

`value` is `undefined` until somebody edits, and `Dashboard` draws `autoDashboard(fields)` meanwhile;
the first `onChange` hands the host the whole spec, automatic parts included. A spec naming a field
the relation no longer has draws that card as a message, not a broken chart.

## Interaction

Every part is on the provider's crossfilter. Bars pick, ranges brush — the rule that keeps a brush
off a band scale — and the chart that published a pick dims the rest of its own bars instead of
filtering itself away. Without a series, the whole relation stays drawn behind the selection in
grey. The readout under the filters counts the rows that survive and holds every clause on the page
as a chip, whoever published it: a brush, a bar, a lasso on a graph canvas.

A tile's figure is `ChartStat`. With a `trend` it adds the measure along that field as a
`StatTrend`, and a `StatDelta` comparing the last step with the one before — the period's own unit,
because a relation without dates has no "last quarter" to compare with.

## Series vocabulary

`config` maps a field to a `ChartConfig`, for a field drawn as `color` that has meanings of its own
— a status column wearing the status colours and their icons:

```tsx
<Dashboard
  table="sightings"
  config={{
    verdict: {
      confirmed: { label: "Confirmed", color: "var(--success)", icon: CheckCircle2Icon },
      hoax: { label: "Hoax", color: "var(--destructive)", icon: TriangleAlertIcon },
    },
  }}
/>
```

A field without one takes the categorical scheme in order of frequency over the whole relation, so
a filter never repaints a survivor.

## The parts

`Dashboard` is made of five exports, each usable on its own inside a `MosaicProvider`:
`DashboardFilters`, `DashboardStat`, `ChartCard`, `DetailTable`, and `FilterChips` with its
`useClauses`. `useFieldStats(table, { exclude })` and `queryFieldStats` are the field reading,
for a host that needs the fields elsewhere.

`DetailTable` is the root barrel's `Table`, not `/table`'s: TanStack sorts and pages in the browser,
and here DuckDB does both, so a relation of any size costs one page of DOM.

## API Reference

The spec's types are exported under the names above: `DashboardSpec`, `DashboardCardSpec`,
`DashboardStatSpec`, `DashboardFilterSpec`, `DashboardMeasure`, `DashboardChartType` and
`DashboardAggregate`; the fields' are `FieldStat`, `FieldKind`, `FieldRole`, `FieldStatsOptions` and
`FieldStatsState`. The props types are `DashboardProps`,
`DashboardFiltersProps`, `DashboardStatProps`, `ChartCardProps`, `DetailTableProps`,
`FilterChipsProps`.

### Dashboard

| Prop | Type | Default |
| --- | --- | --- |
| `table` | `TableExpr` | — |
| `value` | `DashboardSpec` | the automatic dashboard |
| `onChange` | `(spec: DashboardSpec) => void` | — (read-only without it) |
| `exclude` | `readonly string[]` | — the host's bookkeeping columns |
| `config` | `Record<string, ChartConfig>` | — |
| `rowNoun` | `string` | `"rows"` |

### The parts

| Part | Props beyond the element's |
| --- | --- |
| `DashboardFilters` | `table`, `fields`, `filters`, `onChange?`, `rowNoun?`; children trail the readout row |
| `DashboardStat` | `table`, `fields`, `stat`, `onChange?`, `onRemove?` |
| `ChartCard` | `table`, `fields`, `card`, `config?`, `onChange?`, `onRemove?`, `onMove?(offset: -1 \| 1)` |
| `DetailTable` | `table`, `fields`, `columns`, `onChange?`, `pageSize?` (25) |
| `FilterChips` | `selection?` (the crossfilter) |

`useFieldStats(table, options?)` returns `{ fields, error }`, `fields` being `null` until the
summary lands; `queryFieldStats(coordinator, table, options?)` is the same as a promise.
`autoDashboard(fields)` is the spec drawn when `value` is `undefined`.
