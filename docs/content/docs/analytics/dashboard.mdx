---
title: Dashboard
description: A dashboard over a pattern of a graph for finding what it holds — a filter bar and tiles (figures, charts, tables), chosen from what the graph says of each property, edited where they sit, and kept as a JSON spec the host saves.
---

`Dashboard` is the charts grammar composed for a relation you have not seen. Its relation is a
[pattern](#patterns) over the page's graph — a vertex, or a vertex and the edges and vertices taken
from it — and it reads the fields from what the graph says of each property, draws a dashboard from
them — or from a spec you saved — and lets the reader edit every tile of it. The host brings four
things: a `MosaicProvider` with the graph, the pattern, somewhere to keep the spec, and an aside for
the editor.

<ComponentPreview componentName="dashboard" fileName="example-default" hasMaxHeight={false} />

The references are Grafana's panel model — tiles of a kind in an ordered layout, each with a width —
edited in place the way Notion and Linear edit a block, Metabase's filter bar drawn as Linear's chips,
Metabase's X-ray for the dashboard a relation gets before anybody has edited one, and Looker's
explores and Malloy's sources for a relation that joins, written as GQL writes a `MATCH`. What it
leaves out is their query layer: every tile reads the one pattern the `Dashboard` is given, under
one crossfilter.

## Usage

```tsx
import { ShellAside, ShellBody, ShellMain } from "@kanzo-tech/ui";
import { Dashboard, FilterBar, MosaicProvider, TileEditorAside, useTileEditorOpen } from "@kanzo-tech/ui/analytics";

const SIGHTINGS: Pattern = [{ as: "sighting", type: "Sighting" }];

// `graph` is what `attachGraph` from `@kanzo-tech/graphar-duckdb` answered.
function Sightings({ e, graph, saved, save }: Props) {
  return (
    <MosaicProvider engine={e} graph={graph}>
      <ShellBody>
        <ShellMain>
          <FilterBar relation={SIGHTINGS} rowNoun="sightings" />
          <Dashboard relation={SIGHTINGS} value={saved} onChange={save} />
        </ShellMain>
        <Format />
      </ShellBody>
    </MosaicProvider>
  );
}

// Under the provider, so the dashboard reaches it; mounted always, shown while a tile is edited.
function Format() {
  return (
    <ShellAside aria-label="Format" side="end" width={352} hidden={!useTileEditorOpen()}>
      <TileEditorAside />
    </ShellAside>
  );
}
```

- **`value` is `undefined`** until somebody edits: the automatic dashboard is drawn, and a host
  persists nothing for a relation nobody has touched.
- **`onChange` makes it editable.** It is called with the *whole* next spec — the automatic parts
  included, the first time — so the host stores what it is handed and never merges. *Reset to
  automatic* calls it with `undefined`: the host deletes what it stored, and the dashboard follows
  the stats again — `undefined` meaning automatic in both directions, as Metabase's X-ray stays
  unsaved until it is saved.
- **Its filters are drawn in the page's [`FilterBar`](#filterbar)**, wherever the host puts it. A
  page without one shows no filters.
- **Its editor is drawn in the page's [`TileEditorAside`](#tileeditoraside)**, in an aside of the
  host's. A page without one offers no editing: the dashboard is read-only, `onChange` or not.
- **Without `onChange` it is read-only**: no pencils, no *Add tile*, no remove buttons. Filters,
  picks and brushes still work; reading is not editing.

Wiring that to a backend — a debounced save, a read-only role, your own labels and colours — is the
[host recipe](/docs/analytics/dashboard-host).

## Anatomy

```text
Dashboard                 — reads the fields, draws the spec or the automatic one
├── its filters           — drawn in the page's FilterBar, with "Add a filter" among its verbs
├── DashboardStat         — a `stat` tile
├── ChartCard             — a `chart` tile
├── DetailTable           — inside a `table` tile: the rows under the selection, paged by DuckDB
└── TileEditor            — the panel a tile is added and edited in, drawn in the page's TileEditorAside
```

The figures come first, as one band whose row they share equally, wrapping when they run out of
room: a figure is one number and its trend, and beside a chart it would stand as tall as the chart.
Charts and tables flow left to right through a three-column grid beneath it, each as wide as its
`span`. Every part is
exported and works on its own inside a `MosaicProvider`; `Dashboard` is what they make when the spec
decides the arrangement. [Arranging the parts yourself](#arranging-the-parts-yourself) is the other
way.

## How a pattern is read

`useFieldStats(pattern)` reads what the graph says of each property, and guesses nothing from a
column's name or a count. Every named vertex's properties are fields, named `variable.property` —
`sighting.beast`, `home.name` — each described by its type's property on the `Graph`: its DuckDB type,
whether it is the type's primary key, and the nulls, extent and distinct count its chunks' statistics
state. Nothing is queried, so a dashboard draws at once. Every field is classified twice — by
**kind**, from its DuckDB type through Mosaic's own `jsType` (so a column is numeric here exactly
when it is numeric to every mark), and by **role**, from what the graph declares.

| Kind | DuckDB types |
| --- | --- |
| `numeric` | every integer width up to `HUGEINT`, signed or not; `DOUBLE`, `FLOAT`, `REAL`, `DECIMAL` |
| `temporal` | `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMP_MS`, `TIMESTAMP_NS`, `TIMESTAMP WITH TIME ZONE` — a year stored as its integer is a number |
| `categorical` | `VARCHAR`, `ENUM`, `UUID`, `JSON`, `BOOLEAN` |
| — not a field | lists, arrays, structs, maps, blobs, `GEOMETRY`, and types Mosaic does not know (`INTERVAL`, `BIT`, `UHUGEINT`, `TIMESTAMP_S`, `TIME WITH TIME ZONE`) |

The last three read as a number and two times, and are still not fields: every vgplot mark runs
Mosaic's `jsType` on its columns before it queries, and throws on them. Write such a property as
a supported type, and it is a field like any other.

| Role | When | Used as |
| --- | --- | --- |
| `identifier` | the type's primary key | searched, never grouped |
| `measure` | every other number | aggregated, binned, either side of a scatter |
| `dimension` | every time; all other text | grouped, filtered, a series, a panel |

A property that is not its type's primary key is never an identifier, whatever it is called: a column
named `id` is a number or a text like any other. Declare the key where the graph is written, or
exclude it.

The filter control and the charts a field can be follow from those two words alone:

| Field | Filter control | Charts it can be |
| --- | --- | --- |
| A time | `timeline` — a brushable histogram over time, first in the row | the axis of a line, an area or a histogram; a tile's trend |
| A number (measure) | `ChartSlider`, a range | an axis, a measure, either side of a scatter; a tile's trend |
| A category (dimension) | `ChartFilter`, a facet filter with counts | bars; series (2–8 values); panels (2–6 values) |
| A key (identifier text) | `ChartSearch`, a match over what you type | — |
| A numeric key | none | — |

Past eight series a chart wants to be a table, not more hues; past six panels small multiples stop
being comparable. Those are the dataviz limits, and the editors enforce them.

A pattern with a time — the timeline over `contract.closed`, facet filters, and a slider over
`contract.reward`; a property the graph declares its type's primary key would add a search:

## The automatic dashboard

`autoDashboard(fields)` is the spec drawn while `value` is `undefined` — Metabase's X-ray, from the
stats alone and nothing else:

- **Filters** (at most six): the first time, up to three categories, the first text key, up to two
  measures.
- **Figures** (the band): a row count and the mean of up to two measures, each trending along the
  first time when there is one.
- **Charts** (at most six): the first six [the rules](#how-the-charts-are-chosen) propose for an overview.
- **A table**, full width: the first eight fields — categories, then times, measures and keys.

The last tile of a row is widened so no row ends in a hole.

It is exported for a host that wants the automatic spec without the component — to seed a saved
dashboard, or to diff against one.

### How the charts are chosen

`autoDashboard`'s charts, and *Add tile*'s first chart, are what a table of rules proposes for the
fields, heaviest first. It is CompassQL's and Draco's pipeline — **enumerate** what every rule matches, **rank** it,
**explain** each — with the weights set by hand and no solver, since a rule reads at most two
fields. Each answer is `{ spec, rationale, rule }`: a card valid for the fields, one sentence saying
why, and the rule that proposed it. Its ids are derived from the rule and the fields, so the same
fields always give the same answer.

The rules are not the library's own: each is a case of **Show Me** (Mackinlay, Hanrahan and Stolte,
2007), the automatic presentation behind Tableau's chart picker, and a rule no Show Me case covers
does not belong in the table. The weights are the one part with no published value.

| `rule` | Show Me | Reads | Draws | `overview` | `answer` | At most | Rationale |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `time-measure` | Lines (continuous) | a time and a measure | `line` of the measure's total | — | 100 | 3 | *day is a time and n a measure, so a line of total n over time* |
| `category-measure` | Bars | a category and a measure | `bar` of the measure's total | — | 90 | 3 | *type has 3 values and n is a measure, so a bar of total n per value* |
| `time` | Lines (continuous) | a time | `line` of counts, two thirds wide | 100 | 50 | 1 | *seen is a time, so a line of counts along it* |
| `category` | Bars | a category of 2 or more values | `bar` of counts | 80 | 40 | 3 | *type has 3 values, so a bar of counts per value* |
| `measure` | Histogram | a measure | `histogram` | 60 | 30 | 2 | *bounty is a measure, so a histogram of how its values spread* |
| `measure-pair` | Scatter plot, with a trend line | two measures | `regression` of one on the other, two thirds wide | 40 | 70 | 1 | *bounty and leagues are both measures, so a fit of one against the other* |

- **The intent** is `overview` for a dashboard over raw rows — what each field does on
  its own — or `"answer"` for one chart of a result set, whose rows are usually aggregated already,
  so a measure beside what it was grouped by comes first. A rule with no weight under an intent is
  not proposed for it.
- **Ties** keep the table's order, and a rule takes fields in the relation's order, up to its
  *at most*. A key is never drawn, and neither is a category with one value.
- *Add tile* opens the editor on the best chart of the first field a rule draws on its own,
  preferring a field the dashboard does not chart yet.

**A card says why it is there.** `autoDashboard` records the rule behind each card it proposes as
the card's `origin` (`{ rule }`), and while a card has one, `ChartCard` puts that rule's rationale
before the interaction hint and an *Automatic* badge beside the title. Edit the type, a field, the
measure, a series, a panel or the title and the origin goes, and both with it; the width is layout
and does not count. A card added by hand has no origin, whatever the rules would say of it. The
origin is part of the saved spec, and the sentence is read from the rule over the card's own fields
on every render.

## The parts

### FilterBar

**The page's one row of filters**, under its header — Metabase's filter bar, drawn as Linear's chips.
Every clause on the page's selection is a removable chip, read from `Selection.clauses`, so the row
reports filters it did not publish: a brush, a bar someone clicked, a lasso on a graph canvas. A
chip's label is read from the clause: *hour 2 – 5* for a range, *region Saltmere* for one value,
*beast · 3 selected* for more; a semi-join wears its publisher's label — *Lasso*, a rule's name —
and does not count what it keeps, which is the readout's to say, once. Removing one is Mosaic's `selection.reset([clause])`, which calls the clause's source
back, so the pick that made it un-highlights too.

A dashboard's filters are drawn in it too. Each `filters` entry names a field and is a chip reading
*region: Saltmere ▾*, or *region: Any ▾* while it filters nothing. The chip opens its control,
chosen from that field's stats and never written in the spec: a category is a facet list, a key a
search, a measure a range slider, a time a brushable timeline. A field that has no control (a
numeric key) or no longer exists is skipped. With `onChange`, each chip gets a remove button and
**Add a filter** — an icon among the bar's verbs, not among the chips — lists the fields that have
a control and no filter yet. The bar leaves those clauses to the dashboard's chips rather than
drawing them twice.

**The dashboard draws there through a slot**, a portal that keeps the dashboard's relation, so its
filters stay where the reader put them. A control stays mounted while its popover is shut,
because a control that unmounts retracts its clause, and a control in the bar queries as the bar
does. **The bar is the same in every view**: a dashboard hidden by
[`MosaicClients enabled={false}`](/docs/analytics/charts#mosaicclients) draws its chips, their
controls and **Add a filter** there as when it is shown, so the reader sets its filters from whichever
view they are in, and they reach the page on its relation as before. Pass `relation` in every view
too, and the readout says what they keep.

**The bar is one line at any count.** The chips scroll sideways, the native scrollbar hidden and a
fade at whichever edge hides more, and a chip added on its own is scrolled to. After a hairline the
verbs are pinned as icons, each named in a tooltip: a dashboard's **Add a filter**, then **Clear
every filter**, which is `useMosaic().selection.reset()` — disabled rather than gone while nothing
filters, so nothing beside it moves — then, with `relation`, the **readout** — *12 of 40
sightings*, `rowNoun` being the plural — and the children. With no filter at all the row reads *No
filters*, at the same height. `useClauses(selection)` is a selection's live clause list, for a host
that draws its own.

**A view swapped out keeps its clauses when it is hidden, not unmounted.** Wrap it in
`MosaicClients enabled={false}`: its clients stop asking, its clauses stay in the bar and its
filters stay in the bar to set; unmounted, it would retract them.

### DashboardStat

A `stat` tile: a `Stat` whose figure is `ChartStat` — the measure, re-queried under the crossfilter. With a
`trend` it adds the same measure along that field as a `StatTrend` sparkline, and a `StatDelta`
comparing the last step with the one before.

- A time trend is binned into about two dozen steps; a number with at most 60 values is its own step
  (the hours of a day are 24 already), and a longer one is binned like a histogram.
- The delta is in the step's own unit — *vs previous closed*, *vs previous hour* — because a relation
  without dates has no "last quarter" to compare with. A `share` measure's delta is in `pp`.
- `goodWhenUp: false` paints a rise as bad news: a hoax rate, an error count.

Figures format by measure: a `share` as `12.5%`, everything else to at most one decimal, compact
past 10,000.

### ChartCard

A `chart` tile, drawn. The chart is a `ChartRoot` with the
marks the type calls for and the interactor its scale allows — **pick on a band, brush on a range**,
the rule that keeps a brush off a band scale.

| `type` | Label | Draws | `x` | `y` | Interaction |
| --- | --- | --- | --- | --- | --- |
| `bar` | Bar | horizontal bars, the 12 largest groups | a category | a measure | click a bar |
| `line` | Line | a line; a time or a number with > 60 values is binned | a time or a number | a measure | drag a range |
| `area` | Area | an area, stacked by series | a time or a number | a measure | drag a range |
| `histogram` | Histogram | binned columns | a time or a number | a measure | drag a range |
| `dot` | Scatter | one dot per row | a number | a number (`op: "value"`) | drag a box |
| `regression` | Fit | the dots, a least-squares line and its 95% band | a number | a number (`op: "value"`) | drag a box |

**Series** (`color`) is a category of 2–8 values, on every type but `regression`. **Panels**
(`facet`) is a category of 2–6 values, on every type but `bar`: a facet is an encoding, not a chart
type — any line, area, histogram or scatter splits into small multiples sharing one pair of scales,
which is how Vega-Lite models it too. The domains are chosen over the **whole** relation — the top
bars by the measure, the top series and panels by count — so a filter never reorders a bar or
repaints a survivor.

Without a series, the whole relation stays drawn behind the selection in grey: the context a
filtered chart otherwise loses. A card with an `origin` shows
[why](#how-the-charts-are-chosen), under an *Automatic* badge. A card that names a field the relation no longer has draws *The
relation has no `hall` any more.* in place of the chart.

With `onEdit`, the header carries a pencil, and so do a figure's and a table's: what it opens is the
host's, and in `Dashboard` it is the [`TileEditor`](#tileeditor).
`actions`, on a chart's and a figure's, puts the host's own controls in the same place, before the
pencil — icon buttons, as the pencil is: an [answer's](/docs/ai/data#the-answer-card) verbs are there.

### DetailTable

The rows behind the charts: one page at a time, sorted and counted by DuckDB, so a relation of any
size costs one page of DOM. A header click cycles ascending, descending, unsorted; a new selection
returns to page one. Its columns are a `table` tile's, chosen in the editor.

It is the root barrel's `Table`, not `/table`'s: TanStack's row models sort and page in the browser,
and here the browser never holds more than the page.

### TileEditor

**The one editor** — the page's aside, the way draw.io's Format panel, Grafana's panel options and
Power BI's visualizations pane edit what is selected. *Add tile* and every tile's pencil open the
same panel, and it is not modal: the board keeps scrolling and stays live while it is open.
It lists, in this order, the **kind** as cards with an icon, like a chart's mark (Figure, Chart,
Table — a kind the relation cannot draw is disabled), the **fields** that kind reads, then the
title and — for a chart or a table — the **width** (a third, two thirds, full), with the position
among the figures or among the grid's tiles. **The tile is the preview**: it draws the draft in its
own slot under the page's crossfilter, outlined, and grows or shrinks with the width; a tile being
added gets a slot at the end of its band or grid, brought into view as the panel opens. The panel
fills the aside's height: a header with the title, the kind's hint and *Close*, one scrolling list,
and the actions in a footer.
Nothing reaches the dashboard until *Add* or *Save*; *Cancel*, the close button and Escape drop the
draft. A new position applies on save, so the tile never moves while it is edited.

`TileEditor` draws no tile and does not place itself. Hand it the draft as `tile` with `onChange`,
draw that draft in the tile's own view, pass the view's element as `anchor`, and put the editor in
an aside of your own, which it fills. Mount it while it is open.
The view stays mounted from the pencil to *Save*, so opening the editor does not rebuild its plot.
`Dashboard` loads it the first time somebody edits, so a read-only dashboard never fetches the
editor's code.

- A **chart** asks for its mark — a mark the relation cannot draw is disabled — `x`, the measure,
  series and panels. Every change goes through the same normalisation: an encoding the new mark can
  keep is kept, one it cannot is replaced by the first field that fits, and an optional one that fits
  nothing is dropped. A written title describes the encodings it was written for, so changing them
  retires it.
- A **figure** asks for the measure and the field it trends along.
- A **table** asks for its columns; a newly ticked column goes last.
- Changing the kind carries what carries over — a chart's aggregate becomes the figure, a figure's
  measure the chart's — and keeps the id, and the width between a chart and a table. A figure that
  becomes a chart moves from the band to the grid, and back.

Each kind is a row in three tables — how one is made, titled and converted (plain TypeScript, no
React), how it is drawn, and what its editor asks for — each mapped over the kinds, so a kind missing
from any of them does not compile and neither the board nor the editor switches on a kind.

### TileEditorAside

**Where a `Dashboard` draws its editor** — a part the host places in its own `ShellAside`, the way
it places a `FilterBar` under its header. The dashboard portals its `TileEditor` there, so the
editor keeps the dashboard's tree — the page's selection, the dashboard's relation, its draft — while
it sits at the page's edge. Like the bar's, the slot is the outermost `MosaicProvider`'s, so a dashboard
under a provider of its own, nested in the page's, still finds it; the aside has to be under that
provider.

`useTileEditorOpen()` is whether a dashboard is editing a tile, so the host shows its aside then —
draw.io swaps the Format panel in when something is selected. Keep the part mounted and hide the
aside instead: a dashboard offers editing only while a `TileEditorAside` is on the page, so a page
without one has read-only dashboards. The editor is drawn once the aside is shown, so it opens in
view and takes focus.

### useFieldStats and fieldStats

`useFieldStats(pattern, { exclude })` returns `{ fields, columns }` at once: `fields` are the
classified `FieldStat`s, `columns` every column of the pattern's relation in its own order — a column
per named vertex for its index, then every property of every named element — fields or not. It reads
the provider's `graph`, queries nothing, and throws where the provider has none.

A field carries what the graph says beside its kind and role: `distinct`, the exact count the chunks
state or the least they allow where they only bound it, `0` where they say nothing; and its extent,
where they state one.

`fieldStats(columns, options)` is the classification on its own: column descriptions in — a
`FieldColumn` is a `name`, a DuckDB `type`, whether it is `primary`, and its `stats` — the fields out,
nothing queried. `patternColumns(graph, pattern)` describes a pattern's columns under the names it
reads them by, for a host with a graph and no page:

```ts
const { described } = patternColumns(graph, [{ as: "person", type: "Person" }]);
const fields = fieldStats(described, { exclude: ["person.id"] });
```

### plotRelation

`plotRelation(table, { fields, columns })` returns `{ table, fields }` as the plots can read them:
the relation itself, or a projection without the columns named like a plot channel, and the fields
without those. `Dashboard` calls it on its own fields; a host placing the parts over a table of its
own with a layout's `x`/`y` calls it with that table's fields and hands the parts both halves —
[why](/docs/analytics/pitfalls#columns-named-like-a-channel).

`exclude` is for the host's bookkeeping — a key, an internal identity, a layout's coordinates —
named as fields are, `variable.property`. An excluded column is still in the relation (a clause on it still
applies); it is just never offered as a field.

## Interaction

Every part is on the page's one selection. A pick on a bar chart filters every other tile, and dims
the rest of its own bars instead of filtering itself away. A brush on a line, a histogram or the
timeline filters by a range. The readout counts what survives. A clause published by something else
on the page — a `ChartFilter` you placed above the dashboard, a lasso on a graph — is applied the
same way, and *Clear every filter* retracts it too.

The tiles publish on the dashboard's pattern, and a part on another relation — a graph, another
dashboard — reads them crossed by the vertices both hold; a clause from there reaches every tile the
same way — see
[what the page sees](#what-the-page-sees).

## Patterns

The `relation` is a `Pattern` over the provider's graph — `@kanzo-tech/graphar-duckdb`'s, as GQL
writes a `MATCH`: a vertex, then an edge and a vertex, any number of times, each vertex named by a
variable. The first vertex is what is measured: a bare `count` counts it once per group, however many
rows its edges make. A type on its own is a pattern of one vertex.

<ComponentPreview componentName="dashboard" fileName="example-relations" hasMaxHeight={false} />

```tsx
import type { Pattern } from "@kanzo-tech/graphar-duckdb";
import { patternKey } from "@kanzo-tech/mosaic";
import { Dashboard, MosaicProvider, RelationPicker } from "@kanzo-tech/ui/analytics";

const [pattern, setPattern] = useState<Pattern>([{ as: "person", type: "Person" }]);

<MosaicProvider engine={e} graph={graph}>
  <RelationPicker graph={graph} value={pattern} onValueChange={setPattern} />
  <Dashboard key={patternKey(pattern)} relation={pattern} value={byPattern[patternKey(pattern)]} />
</MosaicProvider>
```

- **`relationOver(graph, pattern)`**, from `@kanzo-tech/mosaic`, is what a pattern reads — the
  graph's `match` of it, with a column per named vertex holding its index within its type and one per
  property of every named element, `person.country`, `friend.country`. A pattern whose first vertex
  has no variable is refused: it is what the relation counts and crosses by.
- **`patternKey(pattern)`** is the identity a saved dashboard is keyed by: the elements as written.
- **`RelationPicker`** walks a pattern: the root as a select, then **+ Add related…**, a menu of
  sentences in two groups — *Follow from each Place* (*isPartOf → Place*) and *Bring in what points at
  it* (*Comment isLocatedIn → this Place*) — each sorted by fan-out and saying it, *~103 per Place*, in
  warning colour above ten. The fan-out is the edge type's `count` over the vertex type's, both on the
  `Graph`. Every vertex it adds is named by `variableFor` — the type's name, its first letter lower,
  and a number where the pattern already names one: `person`, `person2` — so its properties are
  fields. The path is chips, any of which can be removed, cutting the pattern there. A pattern's rows
  are its matches, so a root with no edge along a hop is left out. No noun is inflected, and the words
  are the graph's names. `phrase(edge, direction)` rewords a hop, and every word — the two sentence
  patterns among them — is an entry of `translations`:

```tsx
<RelationPicker
  graph={graph}
  value={pattern}
  onValueChange={setPattern}
  phrase={(e, direction) =>
    e.srcType === e.dstType ? (direction === "out" ? "Its parent place" : "Its child places") : undefined
  }
  translations={{ in: (source, label, destination) => `${source} · ${label} → ${destination}` }}
/>
```

### What the page sees

A tile's clause on a pattern names the pattern's columns — `"friend.country" IN ('ES')` — and nothing
else on the page has them. So the clause says which relation it was published on, and the page's
selection — `crossfilterOver(graph)` from `@kanzo-tech/mosaic`, which `MosaicProvider` makes —
crosses it for every reader that is on another one
([across relations](/docs/analytics/charts#across-relations)):

- the other tiles, on the same pattern, read it **as published** — they crossfilter each other on the
  pattern's columns;
- a graph beside the dashboard reads the indices of the first vertex the tiles keep, as the vertex's
  global id: it greys out every vertex but those;
- another pattern's dashboard reads the same, landed on its own vertex of that type — or, where it
  holds none, carried along the graph's one shortest path to its first vertex (`graph.reach`); where
  there is no path, or more than one of the same length, it keeps none of its rows.

The clauses on one pattern cross together, not one by one — on a pattern with a hop, *a person with a
row where a and b* is not *a person with a row where a, and one where b*. `FilterBar` shows each as
its own chip — *friend.country Spain* — and removing one retracts that clause alone, on the one
selection, calling back the tile that published it. A lasso on the graph reaches every tile crossed
the other way, and the graph stays exempt from its own pick.

A pattern's tiles are not pre-aggregated: Mosaic's pre-aggregator needs a base table it can trace,
and a pattern is the SQL text the graph's `match` answers. A chart of a host table under the same
provider still is.

## Series vocabulary

`config` maps a field to a `ChartConfig`, for a field drawn as `color` that has meanings of its own —
a status column wearing the status colours and their icons:

```tsx
<Dashboard
  relation={SIGHTINGS}
  config={{
    "sighting.verdict": {
      confirmed: { label: "Confirmed", color: "var(--success)", icon: CheckCircle2Icon },
      hoax: { label: "Hoax", color: "var(--destructive)", icon: TriangleAlertIcon },
    },
  }}
/>
```

A configured field is drawn in the config's order and colours, with its labels in the legend. A
field without one takes the categorical scheme in order of frequency over the whole relation, so a
filter never repaints a survivor.

## When the pattern cannot be read

A pattern the graph cannot match — a type or an edge it does not have — throws graphar's
`GraphArError` where the dashboard reads it, and a provider with no `graph` throws too: both are a
fault of the host's wiring, caught by the host's error boundary. A failed card, tile or input says
so in its own frame and reports to the provider's `onFailure`. Nothing fails blank.

## Testing

`DashboardHarness` and `FilterBarHarness` from [`@kanzo-tech/testing`](/docs/testing). A dashboard
is `aria-busy` while a tile reads, and `settled()` waits for nothing in it to be busy;
`tile(title)` finds a tile by its title. The bar is the region *Filters*, and its readout a `status`
that is `aria-busy` while it counts, which `readout()` waits out.

```ts
import { DashboardHarness, FilterBarHarness } from "@kanzo-tech/testing";

const dashboard = await env.getHarness(DashboardHarness);
await dashboard.settled();
await (await (await dashboard.tile("Sightings by beast")).chart()).pick({ y: "boghound" });
await expect.poll(async () => (await env.getHarness(FilterBarHarness)).readout()).toMatch(/ of /);
```
