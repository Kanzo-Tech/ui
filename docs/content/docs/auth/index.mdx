`@kanzo-tech/auth` is what a product needs once there is somebody signed in: the person read on the
server from the access token the platform's edge forwards, Keycloak's claim vocabulary read into one
session, and the role evaluation that knows about organizations. Signing in, keeping the session
alive and ending it are not here: they are the edge's, oauth2-proxy in front of the application
([the identity service](/docs/auth/service#the-sessions-edge)).

It is a **sibling** of `@kanzo-tech/ui`, not part of it. It does not depend on the library, and
nothing in the library may depend on it.

## The one rule to read before anything else

**What a client knows about its roles is for drawing, never for deciding.**

The roles in a session are a *copy*, and a copy is something an attacker owns the moment it reaches
the browser. `Gate` hides a control and `can` answers a question about what to draw; the resource
server, validating the access token it was sent, is what refuses the request behind the button. **A
product gated only here is ungated.**

The same rule one level down: **the browser never holds the access token.** The application's server
verifies the token the edge forwards and reads it into a `Session`, and the `Session` handed to the
browser holds no token at all.

<Callout type="warn">
This is physical rather than a preference, so there is no configuration that changes it and no
future release that softens it. Every other page assumes it and points back here rather than
arguing it again; [the auth layer](/docs/design/auth#the-client-draws-the-resource-server-decides)
is why it is the first thing this page says, and what else follows from it.
</Callout>

## Why it is not in the library

[The first admission rule](/docs/philosophy#admission) is *domain-free — nothing about RDF / SHACL /
fossil / graphs / **auth***. Auth is excluded **by name**, and there is a second, blunter reason that
the root barrel makes structural: a consumer who wants a `Button` must not pay for a session.
[The auth layer](/docs/design/auth) has the composite that made the rule, and why this package
depends on nothing of the library's.

## What it is not

**There is no sign-in screen**, no user menu and no organization switcher. A sign-in screen is a
logo, a legal line, a privacy notice and a button, and every product answers those differently —
`@kanzo-tech/ui` has the parts to draw all three, and [the auth
layer](/docs/design/auth#no-sign-in-screen-ships) is why none of them is shipped from here.

**There is no relying party in it either.** oauth2-proxy signs the person in with PKCE, keeps the
session in Valkey behind an opaque cookie, renews it and signs out at Keycloak; the application holds
no client secret, no session and no refresh token ([why](/docs/design/auth#the-session-is-the-platforms-edge)).

What is left after those two subtractions is the whole of the package: **the forwarded token verified
and read into one `Session`, handed to the browser, and a role predicate that understands
organizations — with a forwarder to the application's API and a CSP nonce beside them.**

## Adding auth to a product

The edge is a service the application extends ([the identity service](/docs/auth/service#the-sessions-edge)).
The application's half is one object and three files — [Next.js](/docs/auth/next) has them in full:

```ts title="lib/auth.ts"
import { kanzoAuth } from "@kanzo-tech/auth/next";

export const auth = kanzoAuth(async () => ({ issuer, clientId, jwks }));
```

```ts title="proxy.ts"
export const proxy = (request: NextRequest) => auth.proxy(request);
```

```tsx title="app/layout.tsx"
import { AuthProvider } from "@kanzo-tech/auth";

<AuthProvider session={await auth.session()}>{children}</AuthProvider>;
```

```tsx title="anywhere"
import { Gate, useSession } from "@kanzo-tech/auth";

const { session, signOutUrl } = useSession();

<Gate role="warden">
  <Button>Post a contract</Button>
</Gate>;
<a href={signOutUrl()}>Sign out</a>;
```

## Who is signed in

<ComponentPreview componentName="auth" />

`useSession` is the hook: the session, or `null` for nobody, from the first render, because the
server read it before the page was drawn. `signInUrl` and `signOutUrl` are links to the edge's pages.

Every example on these pages runs against a fabricated session rather than a realm, from one file —
`docs/lib/guild-auth.ts`, which builds a **claim set** and runs the package's own reader over it, so
what they draw is what a token would produce rather than a `Session` somebody typed.

[What the token actually carries](/docs/auth/keycloak#reading-it-yourself) puts that claim set and
the `Session` it becomes side by side, with the reading client id as a control: the machinery is on
screen rather than described.

## Installing it

```bash
pnpm add @kanzo-tech/auth
```

**The root barrel carries no engine** — `react` and nothing else — which is why the browser half
of every product imports it.

| Door | What it is | Peer to install |
| --- | --- | --- |
| `@kanzo-tech/auth` | Types, `can`, `organizationOf`, the provider, `useSession`, `Gate` and the console links | none |
| `@kanzo-tech/auth/server` | `sessionReader` — the forwarded token verified and read into a `Session` — and `claims` | `jose` |
| `@kanzo-tech/auth/next` | `kanzoAuth` — the server component's session, the proxy and the forwarder | `jose`, `next` 16 |

A door exists here only because it imports an engine, which is [the engine
rule](/docs/philosophy#the-engine-rule) the library's own subpaths follow. A consumer installs the
peer for the door they open and no other.

```bash
pnpm add @kanzo-tech/auth jose
```

The two Node doors never reach React: they import the modules under the root barrel directly, so a
server process does not pull a component library in behind an import of a JWT verifier.

## The realm it expects

[The identity service](/docs/auth/service) is the server half — Keycloak with its realm as code, and
the edge in front of each application — and it ships from this repository under the same tag as the
package. What this package needs from it is small and none of it is invented: role claims on the
access token, the application's API asked for by its scope, and organizations in the token.
[Keycloak](/docs/auth/keycloak) is that page, and it is the one to hand to whoever runs the realm.
