```tsx
import { AuthProvider, useSession, type Session } from "@kanzo-tech/auth";
```

A `Session` is the whole of what the client knows about who is signed in.

```ts
interface Session {
  user: AuthUser;
  roles: readonly string[];
  organizations: readonly Organization[];
  organization?: string;
  expiresAt: number;
}

interface AuthUser {
  id: string;
  email?: string;
  name?: string;
  username?: string;
}

interface Organization {
  alias: string;
  id?: string;
  roles: readonly string[];
  groups: readonly string[];
  groupsOverage: boolean;
}
```

`user.id` is the IdP's stable subject, never an email: an email can be reassigned to somebody else
and a subject cannot. Every other field is optional because a realm decides which scopes it grants,
and a token that merely omits one must not take the application down.

`expiresAt` is epoch **milliseconds**, and it is when the **access token** the session was read from
expires, from its `exp`. The edge renews the token, not this package, and the client never uses it to
decide access.

## The current organization is resolved per request

**The session says which organizations you are a member of. The request says which one you are
looking at.** Those are two different questions, and only the first is stored.

Membership comes from the token and is stable. The organization you are *in* is a property of the
request — its host, its path, a cookie — so the server resolves it on every request with
[`kanzoAuth`'s `organization`](/docs/auth/next#tenancy) and hands it over as
`session.organization`, on a server component's `session()`. It is never written into the edge's
session, which is what lets two tabs sit in two organizations at once.
Store it instead and those two tabs share one value: the last one to navigate wins in both, and the
reader of the other is looking at a hall they did not open.

The switcher above sets the alias in component state because an example has no URL to read; a
product's resolver reads it off the hostname or the path. `organization` is an address, not a proof
of membership: [`can`](/docs/auth/roles#asking-the-question) asks inside it by default, and answers
`false` for an organization the person does not belong to.

The other half of the same separation is on the shape above: `roles` are the realm and client roles,
global to the person, and the roles held *inside* an organization live on that `Organization`. They
are never merged — [being an owner of one says nothing about another](/docs/auth/roles#asking-the-question).

## The session is a prop

The relying party is the platform's edge: oauth2-proxy in front of the application signs the person
in, keeps the session in Valkey behind an opaque cookie, renews it and signs out at Keycloak, and
forwards the access token on every request it lets through. The application's server verifies that
token and reads it into a `Session` ([Server](/docs/auth/server)), once per request, and the server
layout hands it to the browser:

```tsx title="app/layout.tsx"
import { AuthProvider } from "@kanzo-tech/auth";
import { auth } from "@/lib/auth";

export default async function Layout({ children }: { children: React.ReactNode }) {
  return <AuthProvider session={await auth.session()}>{children}</AuthProvider>;
}
```

**The browser reads nothing.** There is no session endpoint, no cache to keep fresh and no renewal
for tabs to coordinate: the edge renews, and the next page the server renders reads the renewed
token. A copy as old as the page is enough for what the browser does with it, which is draw
([why](/docs/design/auth-failure#the-session-arrives-with-the-page)). A test or a documentation page
passes a `Session` made with `claims()` from `@kanzo-tech/auth/server`, so what it draws is what a
token produces.

## Signing in and out, at the edge

The edge serves its own pages under the prefix the application gave it,
`OAUTH2_PROXY_PROXY_PREFIX` — `/api/auth` unless `AuthProvider` and `kanzoAuth` are told otherwise:
`sign_in`, which goes straight to Keycloak, and `sign_out`, which ends the session in the edge's store
and at Keycloak. `useSession` hands out links to both, each coming back to a path on this origin:

```tsx
const { signInUrl, signOutUrl } = useSession();

<a href={signInUrl(pathname)}>Sign in</a>;
<a href={signOutUrl("/")}>Sign out</a>;
```

They are links rather than functions that navigate, so a sign-out works before the page hydrates and
from a server component's markup alike. A page behind the edge normally never needs `signInUrl`: the
edge signs a person in before the page renders. It is for a path the edge lets through without a
session.

### How a session ends

- **Signing out at the application** goes through `sign_out`: the edge drops its session and ends the
  one at Keycloak.
- **A session ended at Keycloak** — idle past `sso_session_idle_timeout`, past
  `sso_session_max_lifespan`, or signed out from another application — reaches the edge when the access
  token next needs renewing: within the realm's `access_token_lifespan`, five minutes here.
- **A token already forwarded** to an API is a bearer token until it expires
  ([the limit](/docs/design/auth-hardening#limits-the-layer-states-instead-of-fixing)).

## When a credential is refused, or nobody answers

A server read has three answers, and a product draws each differently:

| What happened | `session()` | `session({ required: true })` |
| --- | --- | --- |
| the edge forwarded no token | `null` | a redirect to the edge's `sign_in`, back to the page |
| the token did not verify | throws `token/refused` | a redirect to `problemPage?code=token/refused` |
| the realm's keys could not be fetched | throws `idp/unreachable` or `idp/silent` | a redirect to `problemPage` with that code |

The codes are the kernel's `Problem`s; test one with `isProblem(error, "token/refused")` from
`@kanzo-tech/kernel`. A refused token goes to the problem page and never to sign-in: the edge holds a
session and would forward the same token, which is a loop. [How the layer
fails](/docs/design/auth-failure) is why each answer is what it is.

## API Reference

### `useSession`

```ts
function useSession(): {
  session: Session | null;
  can(role: string, organization?: string): boolean;
  signInUrl(returnTo?: string): string;
  signOutUrl(returnTo?: string): string;
};
```

Throws outside an `AuthProvider`. `can` is [`can`](/docs/auth/roles#asking-the-question) bound to this
session, asking inside `session.organization` unless told which.

### `AuthProvider`

```tsx
<AuthProvider session={Session | null} prefix?: string>{children}</AuthProvider>
```

| Prop | Type | Default |
| --- | --- | --- |
| `session` | `Session \| null` | — the server's reading, from `auth.session()` |
| `prefix` | `string` | `"/api/auth"`, where the edge's `sign_in` and `sign_out` live |
