`@kanzo-tech/auth` reads what a realm emits. `services/auth/`, in this repository and under the same
release tag, is that realm: **Keycloak 26.8 with the platform realm as code** — one realm (`kanzo`),
organizations as the tenant model, and the claim mappers [the Keycloak page](/docs/auth/keycloak)
asks for, already set. Without the service the package has nothing to talk to; without the package
the service is a token nobody reads. [Each capability ships both halves](/docs/design/services).

## Run it

From `services/auth/`:

```sh
docker compose -f compose.yaml -f compose.dev.yaml up -d --wait   # Keycloak on :8080, the realm applied, the seed in
scripts/verify.sh             # ana: a real PKCE login, and her access token checked
scripts/verify.sh fede        # a member of acme with no role there
scripts/verify.sh dan         # no organization; a client role held directly
docker compose -f compose.yaml -f compose.dev.yaml down -v        # gone, the database and the Terraform state together
```

`up` brings Keycloak and its Postgres up, applies the realm with Terraform and seeds development
people into two organizations, `acme` and `globex`. The admin console is `/admin`, `admin` /
`admin`; `.env.example` lists what can be changed, and `KC_PORT` moves the issuer with it.
`services/compose.dev.yaml` runs the same beside [the gateway](/docs/ai/gateway).

`compose.yaml` is the service as a deployment runs it too: Keycloak in production mode behind the
deployment's edge, `KC_HOSTNAME` its public origin, the passwords from the environment.
`compose.dev.yaml` is what development adds: dev mode on `:8080`, the declarations in `dev/`, and the
seed.

`scripts/verify.sh` signs a seeded person in through `kanzo-conformance` — a client that exists to
prove the contract and names no application — with a real authorization-code login and PKCE,
checks what the **access token** says, then exchanges it for `kanzo-conformance-api` and one
organization and checks that token too: the one a resource server authorizes on. CI runs it for
every seeded person on every pull request, against a Keycloak it has just brought up: the job is `services` in `.github/workflows/ci.yml`.

## The contract

An application's roles in an organization are `organization.<alias>.resource_access.<clientId>.roles`,
on the access token and the ID token both, written by Keycloak from the role mappings of the
person's groups in that organization with composites expanded. Group names are never read, a role
held in one organization says nothing about another, and the scope to ask for is `organization:*`.
An application that grants to groups declares `groups: {}` and reads the ids of the person's groups
there from `organization.<alias>.groups` — or `groups_overage: true` past its threshold — written by
the platform's own protocol mapper, a provider jar in `mappers/` that the one-shot `auth-mappers`
service builds with Maven, against the pinned Keycloak, into the volume Keycloak loads providers
from. [Keycloak](/docs/auth/keycloak#groups-by-id) has the settings.
[Keycloak](/docs/auth/keycloak#roles-inside-an-organization) is that contract in full, with the
token `verify.sh` took off this service; [Roles](/docs/auth/roles) is how the package reads it.

## Declare an application and its organizations

The realm knows no application and no organization by name. It is applied from **declarations**:
YAML files mounted anywhere under `/declarations` in the `auth-realm` service, which the realm reads
(`services/auth/realm/declarations.tf`) and registers with `modules/app` and `modules/api`. An
organization is one line, on top of the compose file that runs its own services, so the list of
organizations is written once, where they are deployed:

```yaml title="orgs/acme.yaml"
x-organization: { alias: acme, name: Acme Corporation, domain: acme.com }
```

An application declares itself **from its own repository**: its client, its own API — a client with
no flow, and the scope whose audience mapper names it, which it [exchanges its token
for](/docs/auth/keycloak#the-apis-an-application-calls) — the platform's APIs it also calls, and its
roles with their composites. It is a compose `configs` entry, so it is interpolated and its origin
can differ between environments:

```yaml title="compose.yaml"
configs:
  board:
    content: |
      x-application:
        client_id: board
        api: board-api
        apis: [ai-gateway]                  # the platform's AI gateway
        origin: ${BOARD_ORIGIN}             # https://{organization}.board.example.com
        callback: /api/auth/callback        # one redirect URI per organization
        # where Keycloak posts a logout token; see Keycloak → Back-channel logout
        backchannel_logout: http://board:3000/api/auth/backchannel-logout
        client_secret_file: /run/secrets/board-oidc
        roles:
          reader: {}
          editor: { composites: [reader] }
          admin: { composites: [editor] }
```

The client's secret is a compose secret the application's server mounts too; the realm sends it to
Keycloak write-only, so it is never kept in Terraform's state. The application hands the
declaration, the secret and its organizations' folder to `auth-realm` from an override file of its
own — a `-f` file, such as the development or the production overlay — because a service an
`include:` brings in cannot be redefined in the including file:

```yaml title="compose.override.yaml"
services:
  auth-realm:
    configs: [{ source: board, target: /declarations/board/application.yaml }]
    secrets: [board-oidc]
    volumes: ["./orgs:/declarations/board/organizations:ro"]
```

The hierarchy is declared once, here: every token carries the expanded set, so `board` asks whether
`editor` is present and never ranks. A second application — `ledger` — is a second declaration in a
second repository, and neither one's roles reach the other.

## Map roles onto an organization's groups

Which of its people hold `board`'s roles is the organization's decision: its administrator maps a
role onto one of the organization's own groups, in the console. As a command — for an
organization's first administrators, and for seeds:

```sh
scripts/map-group-role.sh acme Admins board admin   # ALIAS GROUP CLIENT_ID ROLE
```

The group is created if the organization lacks it, and running it twice changes nothing. Over the
admin API an organization group's role mappings live **under the organization** —
`POST /admin/realms/{realm}/organizations/{orgId}/groups/{groupId}/role-mappings/clients/{clientUuid}` —
and the realm's own `/groups/{id}/role-mappings` answers 400 for one.

## Include it from an application

An application includes the service rather than copying it, by URL at the same release as its
packages — Compose clones the tag into its cache and resolves the files' paths there:

```yaml title="compose.yaml"
include:
  - path:
      - https://github.com/Kanzo-Tech/ui.git#${KANZO_UI_REF:-v0.35.0}:services/auth/compose.yaml
      - https://github.com/Kanzo-Tech/ui.git#${KANZO_UI_REF:-v0.35.0}:services/auth/compose.dev.yaml   # development only

services:
  board:
    build: .
    depends_on:
      auth-realm:
        condition: service_completed_successfully
```

`include:` merges the service's containers and volumes into the application's project, so their
names carry a prefix — `auth-postgres`, `auth-realm`, `auth-seed`, `kanzo-auth-db` — or are
`keycloak`, and a bare `postgres` of the application's own does not collide with them. Waiting on
`auth-realm` means the realm is applied, the application's client among it, before the application
starts.

## What is not there

- **No application.** The only client is `kanzo-conformance`, with its API `kanzo-conformance-api`,
  declared in `dev/`, which only development mounts. The realm's own APIs are `apis`: `ai-gateway`,
  the [gateway](/docs/ai/gateway) this repository ships.
- **No membership in Terraform.** Keycloak makes membership runtime — invitations, identity-provider
  brokering, enrolment by email domain — and the provider has no resource for it. Development seeds
  it (`seed/`); production invites.
- **No production values.** Hostnames, passwords, an upstream identity provider, SMTP and TLS are
  the deployment's, and nothing in this directory pretends to know them.
