```ts
import { claims, sessionReader } from "@kanzo-tech/auth/server";
```

The relying party is not in this package. oauth2-proxy, in front of the application, signs the person
in, keeps the session, renews it and signs out, and on every request it lets through it passes the
Keycloak access token as `X-Forwarded-Access-Token` ([the identity
service](/docs/auth/service#the-sessions-edge)). What a server does with that header is this door: verify
the token, and read its claims into a `Session`.

```ts
const read = sessionReader({
  issuer: "https://id.example/realms/kanzo",
  clientId: "board",
  jwks: "http://keycloak:8080/realms/kanzo/protocol/openid-connect/certs",
});

const session = await read(request.headers); // Session | null
```

`Headers` in, a `Session` out, and nothing of any framework in the signature: [`./next`](/docs/auth/next)
is a thin wrapper over it, and so is anything else. Build the reader once; it keeps the realm's keys
between requests.

## The token is verified, every time

The proxy verified the token too, and the reader verifies it again, because a header is anyone's to
set who reaches the application without the edge, and a token is only the realm's to sign. That is
what makes a header that did not come through the proxy worth nothing
([why](/docs/design/auth#the-forwarded-token-is-verified-on-every-read)). With `jose`, against the
realm's JWK set:

- **the signature**, by a key the realm publishes — an unsigned token, or one signed by any other key,
  is refused;
- **`iss`**, exactly the configured issuer — the **public** one, as every token names it;
- **`exp`**, which must be present and in the future;
- **`azp`**, which must be this application's `clientId`: a token issued to another application is
  somebody else's.

`aud` is not checked here. It names the APIs the token is for, and is each API's to check.
`X-Forwarded-User` and `X-Forwarded-Email` are never read: they are the edge's unsigned word for what
the token says with the realm's signature.

| What happened | The reader |
| --- | --- |
| no token forwarded | `null` |
| a token that does not verify, for any reason above | throws `token/refused` (401) |
| the keys could not be fetched within 10 s | throws `idp/silent` (504) |
| the keys could not be fetched at all | throws `idp/unreachable` (502) |

The last two are an outage, not a refusal: the token may be perfectly good. Each is a `Problem` from
`@kanzo-tech/problems`, and `isProblem(error, "idp/unreachable")` tells them apart.

## Reaching the keys from inside a cluster

The browser reaches Keycloak at its public origin, and the application usually cannot: in a Compose
network it reaches `http://keycloak:8080`. So `issuer` is the public URL every token names, and `jwks`
is where **this process** reaches the keys. Absent, `jwks` is the issuer's own,
`{issuer}/protocol/openid-connect/certs`. The keys are fetched on first use and kept; a token signed
under a key id the reader has not seen fetches them again, at most once per cooldown, which is the
answer to the realm rotating its keys.

## `claims`

`claims(raw, { clientId })` is the reader underneath: a decoded claim set in, a `Session` out, with no
verification and no network. It is the only place that knows what Keycloak calls things —
[Roles](/docs/auth/roles#roles-inside-an-organization-are-read-from-its-entry) and
[Keycloak](/docs/auth/keycloak#what-the-token-actually-carries) have the vocabulary — and it throws
`claims/no-subject` for a claim set with no `sub`. A test, or a documentation page, makes its
`Session` with it, so what it draws is what a token would produce.

## A group overage, and asking the realm

An organization's entry carries `groupsOverage: true` and no group ids when the person is in more
groups than the token should carry ([Keycloak](/docs/auth/keycloak#groups-by-id)). The lookup is the
application's: a service account with `view-organizations` and `view-users` reads the membership from
the realm's admin API. The package holds no such account and ships no lookup.

## API Reference

### `sessionReader`

`sessionReader(config: SessionReaderConfig): (headers: Headers) => Promise<Session | null>`.

| Prop | Type | Default |
| --- | --- | --- |
| `issuer` | `string`, the public issuer every token names | required |
| `clientId` | `string`, this application's client: `azp` must be it, and the roles are read from its `resource_access` entry | required |
| `jwks` | `string`, where this process reaches the realm's keys | `{issuer}/protocol/openid-connect/certs` |

### `claims`

`claims(raw: unknown, config: { clientId: string }): Session`.
