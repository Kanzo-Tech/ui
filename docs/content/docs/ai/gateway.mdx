title: The gateway

---

[`@kanzo-tech/llm`](/docs/ai/llm) names a model by alias behind a gateway. `services/ai/`, in this
repository and under the same release tag, is that gateway: [agentgateway](https://agentgateway.dev),
which holds the providers' keys, maps each alias to an upstream, speaks OpenAI's chat-completions
protocol whatever the upstream speaks, and trusts the same realm as everything else.
[Each capability ships both halves](/docs/design/services).

## Two aliases

An application names an **alias**, never a provider:

| Alias | For |
| --- | --- |
| `chat` | conversations and agents — [`Chat`](/docs/ai/chat), a `ToolLoopAgent` |
| `complete` | short completions asked on every pause in typing — [`Assist`](/docs/ai/assist)'s ghost text and suggestions, and the questions a [`Chat`](/docs/ai/chat) starts from |

Which model answers each one is one variable, `provider/model` — the shape LiteLLM, OpenRouter and the
AI SDK use — so the same `gateway("chat")` runs on a laptop's GPU in development and on a provider in
production:

```sh
AI_CHAT=anthropic/claude-sonnet-5-5
AI_COMPLETE=anthropic/claude-haiku-4-5
ANTHROPIC_API_KEY=sk-ant-…
```

Changing models is changing a line and restarting the gateway, not a release of every application
that calls it. Each alias is a `virtualModels` entry over the one model its variable names, and every
provider is a `provider/*` model marked internal: a caller can ask for `chat` or `complete`, and
nothing else.

| Provider | Variable value | Key |
| --- | --- | --- |
| Anthropic | `anthropic/<model>` | `ANTHROPIC_API_KEY` |
| OpenAI | `openai/<model>` | `OPENAI_API_KEY` |
| Google Gemini | `gemini/<model>` | `GEMINI_API_KEY` |
| Mistral | `mistral/<model>` | `MISTRAL_API_KEY` |
| OpenRouter | `openrouter/<vendor>/<model>` | `OPENROUTER_API_KEY` |
| On the machine | `local/<model>` | none; `LOCAL_MODELS_URL`, Docker Model Runner by default |

A provider without a key still loads; a request routed to it fails with the provider's own refusal,
which [`@kanzo-tech/llm`](/docs/ai/llm) hands the caller as `ai/unavailable`, reason included.

## The token is the credential

```text
browser ──▶ the application's server (BFF) ──Bearer <token for the gateway, one organization>──▶ gateway ──▶ upstream
```

The browser never holds a credential for the gateway. It calls its own application's route — the
`baseURL` it hands `createGateway` — and that server exchanges the user's access token for one the
gateway accepts, and forwards: an entry in [`kanzoAuth`'s `apis`](/docs/ai/llm#why-no-credential-is-in-the-page),
the same exchange as for every other API. The gateway then checks three things, all from the token and none
from a key of its own:

- **It was signed by the realm** (`issuer`, keys fetched from the realm) **and issued for the
  gateway** (`aud` names the gateway's audience).
- **It names exactly one organization.** A sign-in asks for `organization:*`, every membership at
  once, and a request charged to all of them is charged to none. The server asks Keycloak for
  `organization:<alias>` in the exchange; a token for every membership is refused with 403, and an
  organization the person does not belong to never reaches the token.
- **That organization is under its budget**, when the deployment set one.

The exchange is [OAuth 2.0 Token Exchange](https://www.rfc-editor.org/rfc/rfc8693) as Keycloak
implements it ([standard token exchange](https://www.keycloak.org/securing-apps/token-exchange)):
the application's server presents the access token it holds and asks for the gateway's scope and
one organization's. The gateway is a client of the realm like any API — `ai-gateway`, which the realm
registers by default — and an application that calls it lists it in its declaration's
[`apis`](/docs/auth/service#declare-an-application-and-its-organizations).

## What the gateway keeps

Every request is written to its database: who asked (`sub`), for which organization, the alias, the
tokens in and out, and their cost when the deployment prices its models. That table is the spend
report — per person and per organization — and it is plain SQL.

## Run it

From `services/`, beside the identity service it trusts:

```sh
docker compose -f compose.dev.yaml --profile local-models up -d --wait   # both aliases on local models
ai/scripts/verify.sh                                 # a real token, each alias, the refusals
```

The gateway answers on `http://localhost:4000`, and its OpenAI-compatible API is under `/v1`: that
is the path on which it reads a request, resolves the alias and counts the tokens, and a path outside
it is passed through unread. Its configuration is `ai/gateway.yaml`, the same file everywhere.

`ai/compose.dev.yaml` sets both aliases to open models served by **Docker Model Runner** on the host's
GPU — Docker Desktop 4.40 or later, with Model Runner turned on — and the `local-models` profile pulls
them, **about 6.5 GB** once; after that the loop is offline and costs nothing. They run with an
8192-token context, which fits a 16 GB laptop: the models declare 131072, and llama.cpp reserves the
cache for all of it when it loads one, about 16 GB for the 8B alone. With both aliases on a provider,
leave the profile off and nothing is pulled.

An application's own compose includes `services/ai/compose.yaml` (and `compose.dev.yaml` in
development) the way it includes [the identity service](/docs/auth/service#include-it-from-an-application),
by URL at the release of its packages. The containers are `ai-gateway` and `ai-postgres`, so nothing
of the application's collides with them. The gateway starts once the realm is applied, and fetches
its keys at `http://keycloak:8080` inside that network.

## Deploying

The same `compose.yaml`, with the deployment's values in its environment:

- **`AI_CHAT`, `AI_COMPLETE`** and the providers' keys. They have no value in `compose.yaml`, only in
  `compose.dev.yaml`: an alias left empty names no model and the gateway refuses to start, so a
  deployment names its models. **The production choice is the deployment's**, not this repository's.
- **`KC_HOSTNAME`**, the realm's public origin, shared with the identity service: the gateway's
  issuer is `<KC_HOSTNAME>/realms/<KC_REALM>`, and it fetches the keys from Keycloak inside the
  network.
- **`AI_DB_PASSWORD`**, for the request log.
- **`AI_TOKENS_PER_HOUR`** — how many tokens each organization may spend an hour, input and output
  together. The default is high enough to be no practical limit.

<Callout type="warn">
**The budget is counted in the gateway's memory.** It is a token bucket per organization, refilled
every hour, and a restart refills it; the gateway runs one replica, so there is one bucket. A budget
that must survive restarts, or be shared by replicas, is agentgateway's remote rate limit — Envoy's
rate-limit service and a store beside it — which this service does not run.
</Callout>

**The image is pinned by digest** in `compose.yaml`. The gateway holds every provider's key: move
the pin deliberately, to a release that has been out for a few days, never by tag.

## Timeouts

`gateway.yaml` gives an upstream 20 s to start answering and 20 s between chunks once it has. Both
are under [the client's 30 s bound on silence](/docs/ai/llm), so a hung upstream is ended at the
gateway, where it is logged, before the page gives up on it: the caller gets a 504 `request timeout`,
which `@kanzo-tech/llm` hands on as `ai/unavailable`.
