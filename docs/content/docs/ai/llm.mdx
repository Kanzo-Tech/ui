`@kanzo-tech/llm` is what `@kanzo-tech/ai` talks to a model through, and what a host builds its
agents with. It has no React in it.

```bash
pnpm add @kanzo-tech/llm ai
```

```ts
import { createGateway, stream, ToolLoopAgent, tool, jsonSchema } from "@kanzo-tech/llm";

const gateway = createGateway({ baseURL: "/api/ai" });
const model = gateway("chat");
```

## One copy of the SDK

`ai` is a **required** peer, not an optional one and not a dependency. There is nothing here without
it — that is what this package is — and installing it once is the point: `@kanzo-tech/ai`'s
components and the host's own agent must see the same `UIMessage`, the same `ToolLoopAgent` and the
same transport. Two copies of the SDK are two type universes whose messages do not assign to each
other, and the error that reports it names neither copy.

So the SDK's surface is re-exported here, and a host never imports `ai` itself. It is the standing
`@kanzo-tech/mosaic` has with Mosaic: the third party is a peer, its surface is passed through, and
what is ours is the door it does not have.

| Re-exported from `ai` | For |
| --- | --- |
| `ToolLoopAgent`, `stepCountIs` | An agent: a model, its tools, and when to stop calling them |
| `Agent`, `ToolSet` | The types of an agent and of its tools, for code that takes one |
| `tool`, `jsonSchema` | A tool the model may call, and its input's schema |
| `DirectChatTransport` | Run an agent in the page — what `@kanzo-tech/ai`'s `useAgentChat` runs it over |
| `Output` | Structured output for [`stream`](#stream): `Output.object` / `Output.array` |
| `getToolName`, `isToolUIPart` | Reading a message's tool parts |
| `UIMessage`, `InferAgentUIMessage` | A message as `useChat` holds it, and its type for a given agent |
| `ToolUIPart`, `DynamicToolUIPart`, `ReasoningUIPart` | Its parts |
| `LanguageModel`, `ChatStatus` | A model, and where a chat has got to |

The list is what the house's own code reaches for, not the SDK's whole surface. A name missing from
it is added here when a host needs it, so the one-import rule holds.

## `createGateway`

```ts
createGateway(settings: GatewaySettings): Gateway

interface GatewaySettings {
  baseURL: string;                    // the gateway's OpenAI-compatible API, as the browser reaches it
  headers?: Record<string, string>;   // sent with every request — a CSRF header a BFF asks for
  fetch?: typeof globalThis.fetch;    // for a host that routes through its own client
}

type Gateway = (alias: string) => LanguageModel;

class AiError extends Error {
  code: "ai/silent" | "ai/rate-limited";
  data: { after?: number; retryAfter?: number }; // the silence in ms; when to retry, in seconds
}
```

**A host names an alias, never a provider.** `gateway("chat")`, `gateway("complete")`: which
upstream answers is the gateway's configuration, so the host's code is the same in development, where
a local model answers, and in production. Changing models is an edit to the gateway, not a release of
every app that talks to it.

Four things a host would otherwise repeat are done once, here:

- **A relative `baseURL` is resolved against the page.** `/api/ai` is what a host behind a BFF is told
  to pass, and the provider underneath builds `new URL(baseURL + path)` with no base, which throws
  `Invalid URL` in the browser.
- **A model that reasons in tags gets its reasoning back as reasoning.** Open-weight models write it
  inline as `<think>…</think>`, because the chat-completions protocol has no field for it. It is
  lifted into the SDK's reasoning part, which is what [`Chat`](/docs/ai/chat) folds away. A model that
  never writes the tag is untouched.
- **Structured output is on.** `Output.array` asks the gateway for a JSON schema rather than prose
  the caller parses — the "return only JSON, no fences" prompt and its fence-stripping is what this
  ends. [`Assist`](/docs/ai/assist)'s candidates depend on it.
- **A stream that goes silent ends.** A streaming request's headers are due within 30 s, and each
  chunk of its body within 30 s of the last. Past that the request is aborted and the caller —
  [`stream`](#stream)'s readings, `Chat`, `Assist`'s `onFailure` — gets an `AiError` whose `code` is
  `"ai/silent"` and whose `data.after` is `30000`. A request that does not stream is not cut: its
  headers wait on the whole answer. Your own `abortSignal` still aborts as an abort. This is the
  only bound on a model's silence in the library; the reason is on
  [the failure page](/docs/design/failure).
- **A caller over its limit is told so.** A gateway that limits per tenant or per key answers 429,
  and the caller gets an `AiError` whose `code` is `"ai/rate-limited"`, with `data.retryAfter` in
  seconds when the gateway said when (`retry-after`, else `x-ratelimit-reset`). It is not retried:
  the limit is the answer, and asking again is how a caller stays over it.

The gateway speaks the OpenAI chat-completions protocol, through `@ai-sdk/openai-compatible` — a
dependency nobody outside this package names, the standing `@duckdb/duckdb-wasm` has behind
`engine()`.

## `stream`

```ts
stream(options: StreamOptions): Stream

interface StreamOptions {
  model: LanguageModel;          // gateway("complete")
  system?: string;
  prompt: string;
  output?: Output;               // Output.array(…) or Output.object(…); plain text when omitted
  abortSignal?: AbortSignal;
}

interface Stream {
  text: AsyncIterable<string>;     // the answer as it is written
  elements: AsyncIterable<E>;      // each element of an Output.array, once it is whole
  partial: AsyncIterable<P>;       // an Output.object as it grows
}
```

**The one door to a model's answer outside a conversation** — a field's continuation, a strip of
suggestions, anything that asks once and reads what comes back. Read one of the three, once: they
are views of the same request.

```ts
for await (const { text } of stream({ model, prompt, output: Output.array({ element }) }).elements) {
  offered.push(text);
}
```

- **A failure throws, once the stream ends.** The SDK reports a failed stream to `onError` and then
  ends it as if it had finished, so a refused call reads as a model with nothing to say. Each
  reading rethrows what was reported, whole: a silence as `ai/silent`, a limit as
  `ai/rate-limited`, a refusal as the provider's error.
- **Never retried.** The gateway retries its upstreams, and a silent gateway asked three times is
  three deadlines where the person waits for one.

`streamText` is not re-exported, and that is the rule rather than an omission: the raw call is the
one that passes a refusal off as a short answer, and two ways to one request are one too many. A
conversation is the other door — `ToolLoopAgent` behind `useAgentChat` — and it hands over what was
thrown itself.

*What would reverse it:* a caller that needs something of `streamText` that `stream` cannot pass —
tools in a single request, or a reading other than these three. Then the option goes on
`StreamOptions`; the raw call still does not come back.

## Why no credential is in the page

A credential that opens a gateway is a bill and a quota. In the page, it is everyone's: anybody who
opens the network tab has it, and nothing can take it back. So the browser talks to the **host's own
route** — a backend-for-frontend — which checks the session, gets a token for the gateway and
forwards. `baseURL` is that route, such as `/api/v1/ai`. `headers` is there for what the BFF asks of
the page, a CSRF token, and never for a credential.

The token the BFF forwards is the person's own, exchanged: [OAuth 2.0 Token
Exchange](https://www.rfc-editor.org/rfc/rfc8693) turns the access token the session holds into one
issued for the gateway and for **the one organization the request is for**. The gateway accepts
nothing else, so who asked and which organization pays are in the token, not in a key the
application was handed. It is the same exchange every API behind the BFF gets, so the gateway is one
more entry in [`kanzoAuth`'s `apis`](/docs/auth/next#api):

```ts title="lib/auth.ts"
export const auth = kanzoAuth(async () => ({
  …,
  organization: ({ url }) => url.hostname.split(".")[0],
  apis: { "/api/ai": { audience: "ai-gateway", target: process.env.AI_GATEWAY_URL } },
}));
```

```ts title="app/api/[...path]/route.ts"
export const { GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS } = auth.api;
```

```ts
const gateway = createGateway({ baseURL: "/api/ai" });
```

The application lists `ai-gateway` in its [`apis`](/docs/auth/keycloak#the-apis-an-application-calls)
in the realm. The forwarder streams the answer as it arrives, so a reply reaches the page a token at
a time through the BFF, not after it.

## Connecting a model

Three set-ups, and the page's code is the same in all of them — `createGateway({ baseURL })` and an
alias.

### An AI gateway

The production shape: [agentgateway](https://agentgateway.dev) as the platform's one door to models.
It holds the providers' keys, maps each alias to an upstream, speaks OpenAI's protocol whatever the
upstream speaks, and takes the realm's tokens as its only credential. It ships from this repository
as [the gateway](/docs/ai/gateway) — a development compose and a module to deploy it. The aliases are
its profile's `models`:

```yaml
models:
  - name: chat
    provider: <provider>
    params: { model: <model>, apiKey: $PROVIDER_API_KEY }
  - name: complete
    provider: <provider>
    params: { model: <a smaller model>, apiKey: $PROVIDER_API_KEY }
```

`kanzoAuth` forwards to it, as above. `complete` is a separate alias because a field's continuation is asked
on every pause in typing: it wants a small, fast model, and a chat wants a good one.

### A local model, for development

[The gateway's development compose](/docs/ai/gateway#run-it) already is one: both aliases on open
models through Docker Model Runner, so the whole loop runs without a provider key, and
`AI_GATEWAY_URL` is `http://localhost:4000`.

[Ollama](https://ollama.com) behind the same gateway works the same way: point an alias at it in the
gateway's `models` — an OpenAI-compatible model whose `baseUrl` is `http://localhost:11434/v1` — and
nothing else changes.

Without a gateway at all, `createGateway` can point at Ollama directly, since Ollama serves the same
protocol under `/v1`. The alias is then an Ollama model name, and `ollama cp` gives a model the alias
as its name:

```bash
ollama cp <model> chat
```

```ts
const gateway = createGateway({ baseURL: "http://localhost:11434/v1" });
```

That is a browser talking to a model with no session and no key in between, so it is for a laptop and
nowhere else. If Ollama refuses the page's origin, its `OLLAMA_ORIGINS` setting is the allowlist.

### A mock, for tests and these pages

Every example and showcase on this site runs with no network: the model is the AI SDK's own
`MockLanguageModelV4`, from `ai/test`, answering with canned text a word at a time. It is a
`LanguageModel` like any other, so `Assist`, `ToolLoopAgent` and `Chat` run unchanged over it — which
is the claim the examples make. `ai/test` is the one import of `ai` a host's tests may write directly:
it is test tooling rather than runtime surface, and nothing here passes it through.
