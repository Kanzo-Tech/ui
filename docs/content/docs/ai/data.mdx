---
title: Ask your data
description: Ask — questions about data answered with a dashboard tile over a relation, from a spec the model fills with names the page generated and a relation the page finds — the types it may answer about, the chat it runs in, the questions to start from, and the card each answer is drawn in — @kanzo-tech/ai/data.
---

`@kanzo-tech/ai/data` is `Chat` pointed at data. A question gets one answer, and an answer is a
**dashboard tile over a relation**. The model fills a **spec**: what is counted, how it is shown —
a figure, a chart or a table — and the conditions a dashboard's filters publish. It names no relation
and writes no SQL: every name it writes is an enum the page generated from the data it shows, and the
relation is the page's to find — the shortest path from what is counted through every type the spec
names. That is Ask as a [Task](/docs/design/tasks); [Asking data](/docs/design/ai) is why. The live
version is the **Ask** panel of the [workspace showcase](/docs/showcases/workspace): a recorded model,
but every tile is read for real, under the filter you set on the page.

| | For |
| --- | --- |
| `answerRelationsOf` | Which relations of a join graph may be read: each type alone (`hops: 0`), or through each of its hops too |
| `readAnswerRelations` | Their fields, as a dashboard over each reads them, and each category's most common values |
| `useAskChat` | The chat: one run of the `ask` Task per question, its answer read on the page's engine — `Chat` draws it |
| `askOffers` | Questions to start from: the Task's own proposals, each checked by its oracles |
| `ask` | The Task — linker, schema, oracles — for a host that runs it with `runTask` outside a chat |
| `answerSchema` | The JSON Schema an answer is written in: the fields, the aggregates and the chart kinds, as enums |
| `checkAnswer` | What refuses an answer outside that schema, in words the model reads |
| `AnswerCard` | The card an answer is drawn in: the dashboard's own tile, with *Filter the page to these rows* and *Add to the dashboard* in its header |

## Usage

```tsx
import { Chat, ChatSkeleton } from "@kanzo-tech/ai";
import { AnswerCard, askOffers, useAskChat, type AnswerCardProps, type AnswerRelation } from "@kanzo-tech/ai/data";
import { localModel } from "@kanzo-tech/llm/local";
import { DiagnosticList, Problem } from "@kanzo-tech/ui";
import { useMosaic, type Dashboards, type Engine, type JoinGraph } from "@kanzo-tech/ui/analytics";

const model = localModel("Qwen3-4B-q4f16_1-MLC", { worker });
```

```tsx
function Ask({ engine, graph, types, dashboards, onAdd }: { engine: Engine; graph: JoinGraph; types: AnswerRelation[]; dashboards: Dashboards; onAdd: AnswerCardProps["onAdd"] }) {
  const { selection } = useMosaic();
  const chat = useAskChat({ model, engine, graph, types, selection });
  // Cached per data space and per filter.
  const offers = useQuery({
    queryKey: ["offers", types, String(selection.predicate(null))],
    queryFn: ({ signal }) => askOffers({ model, graph, types, selection, signal }),
  });
  return (
    <Chat
      chat={chat}
      notice={
        offers.isError && (
          <DiagnosticList className="w-full">
            <Problem error={offers.error} />
          </DiagnosticList>
        )
      }
      proposals={offers.data ?? []}
      proposing={offers.isFetching}
      tools={{
        answer: (part, { stopped }) => <AnswerCard dashboards={dashboards} graph={graph} onAdd={onAdd} part={part} stopped={stopped} />,
      }}
    />
  );
}
```

`types` is `await readAnswerRelations(coordinator, graph, answerRelationsOf(graph, { hops: 0 }), { signal })`,
read once per data space: each type alone, with its fields. Until it is, draw `<ChatSkeleton />` in
the chat's place: it is the same layout, so nothing jumps when the chat replaces it. The cache is the
host's: `askOffers` is a promise, so TanStack Query (or an effect) holds it, keyed per data space and
filter. While it runs the strip shows pills in skeleton; if it fails the failure is drawn in the
pills' place (`notice`), and the chat works the same — see [Before the first question](/docs/ai/chat#before-the-first-question).

## The relations

`readAnswerRelations(coordinator, graph, relations, { values, signal })` answers an `AnswerRelation` per
relation, `{ relation, columns, fields }`, read from the engine the way a [dashboard](/docs/analytics/dashboard)
over the same relation reads them: `queryFieldStats` over `relationQuery`, without the keys
`relationIdentities` names, then `plotRelation`. Each category that is a dimension carries its most
common `values` — six by default, the most common first — counted over the relation.

`signal` ends the read: it rejects with the signal's reason and cancels the queries still queued on
the coordinator, so a page left mid-read stops taking the engine from the next one. Each query is
handed the signal too, for a connector that stops one in flight; DuckDB-WASM's finishes the statement
it is running and drops it. TanStack Query's `queryFn` hands one over.

So the model and the dashboard read **one list of fields**: a tile the model fills names the fields
`Dashboard` draws, and *Add to the dashboard* adds a tile the dashboard can draw.

Which relations are offered is the host's to say, and **`answerRelationsOf(graph, { from, hops })`**
says the usual answer: each type alone and through each of its hops (`hops: 1`, the default), in the
graph's order, from every type or from the types `from` names. A question that crosses a hop is what
a reader cannot see in any one table, and it is also the cost: each relation is a `SUMMARIZE` and a
count per category, once per data space, and a list of fields in every prompt. Over a graph shaped
like LDBC's social network at scale factor 1 — 8 types, 23 edges, 3.2 million vertices and 17
million edges — the types alone read in 1.2 s into a 3,600-character prompt, and with every hop in
41 s into a 39,000-character one. On a graph that size, offer the hops `from` the types the reader
is looking at, or `hops: 0`. [Asking data](/docs/design/ai#ask-reads-nothing-to-be-offered-its-fields) has the
measurement. The graph comes from whatever catalog the host has — [`readJoinGraph`](/docs/graph#readjoingraph)
for a fossil corpus.

*Held by* `packages/ai/src/data/answer.test.ts`, "reads each relation's fields as a dashboard over it
does, without its keys, and each category's most common values"; "hands each query the signal, and
ends on an abort with its reason, cancelling what is still queued"; "offers each type alone and
through each of its hops, in the graph's order".

## The answer

```ts
interface Answer {
  relation: Relation;            // a type, and the hops from it — the JoinGraph's
  where?: readonly Condition[];  // { field, in } | { field, between } | { field, contains }
  show: Tile;                    // the dashboard's Tile: a figure, a chart or a table
  top?: number;                  // rank show's x by its measure and keep these many
}
```

An `AnswerInput` is an `Answer` whose relation is its key — `"Person>knows>Person"`, as
`relationKey` writes it — and whose tile has no `id` and no `span`, which the page gives: the
answer's id, and the width a dashboard gives the kind. It is what the `answer` part carries, so a kept
transcript is names; the card turns the key back into the `Relation` it names. The spec the model
writes is the same, with `of`, the type it counts, in the relation's place.

`answerSchema(graph, relations)` is the JSON Schema an answer is written in. `relation` is an enum of
the offered relations' keys; every field slot — a condition's `field`, a chart's `x`, `color` and
`facet`, a measure's `field`, a figure's `trend`, a table's `columns` — refers to one enum of the
offered relations' fields, defined once under `$defs`; `op` is an enum of the dashboard's aggregates
and `type` of its chart kinds. The `ask` Task's schema is this one with `of` an enum of the linked
types in `relation`'s place. A provider that decodes against the schema cannot write a name that does
not exist.

The schema is one object rather than one branch per relation, because Anthropic and OpenAI refuse an
`anyOf` at the top. So **`checkAnswer(value, relations, graph)`** holds the rest: the relation is one
of those offered, every field is that relation's, the conditions have one operator each, `top` is a
whole number, and the tile is one [`parseTile`](/docs/analytics/dashboard-spec#reading-it-back)
reads. It is one of Ask's oracles, so a spec that fails is sent back and the model reads the
sentence: *show.x: Person2.gender is not a field of Person, whose fields are Person.gender,
Person.age, Person.born.*

**An answer compiles with what a dashboard compiles with.** `relationQuery` makes the relation and
`plotRelation` the table the plots read; each condition is the clause a dashboard filter of its kind
publishes — `clausePoints` for `in`, `clauseInterval` for `between`, over `Date`s for a time,
`clauseMatch` for `contains`; and the tile's rows are its measure, `measureExpr`, by its x, grouped
by the step a trend takes (`bucketExpr`). The page's crossfilter applies as it is when the answer
runs: each of its clauses whose columns the relation has, as [`clauseColumns`](/docs/design/graph#the-clause-rule-column-predicates-or-a-semi-join-on-identity)
reads them — a semi-join on the root's key always does.

**What the spec cannot say gets no answer.** A ratio of two measures, a window, a join the graph does
not have: there is no field or relation to write it with, and what the oracles refuse after the last
repair is said to the reader rather than answered as a different question. There is no SQL beside it
as a fallback; [Asking data](/docs/design/ai) says why, and what would reverse it.

*Held by* `packages/ai/src/data/answer.test.ts`, "the enums are the relations offered, by key, and their fields, listed once"; "an
answer compiles to the same query the dashboard tile reads"; "crosses a hop: whom the women know, by
gender, ranked"; "input outside the schema is refused before it runs".

## Ask

`useAskChat(options)` is `useChat` over a transport that runs the [`ask` Task](/docs/design/tasks#ask-from-agent-to-form)
once per question, in the page, and writes what it found into the transcript as an `answer` tool part
— the part `AnswerCard` draws — followed by a sentence. There is no tool loop and no second call to
the model: the spec is the model's, everything after it is the page's.

1. **The linker** keeps the types the question names — by the type, a field or a value it holds —
   with their neighbours one hop away, the type the previous answer was about, and the types the
   page's chips are on. The schema's enums are theirs, so a small model reads a small vocabulary.
2. **The model fills the spec**, `{ of, show, where?, top? }`, with `generateText` and
   `Output.object`: a provider that decodes against the schema cannot write a name that does not
   exist. A follow-up — *and in Germany?* — is told the previous spec and changes only what it asks.
3. **The resolver finds the relation**: `resolveRelation` from `@kanzo-tech/mosaic`, the shortest
   path from `of` that has a step of every type the spec's fields are on and meets the type each of
   the page's chips is on. None is a diagnostic sent back to the model, which repairs the spec, three
   attempts in all. **Two equally short paths are the reader's**: the reply asks *Which way should
   this be counted?* with each relation by its key, numbered, and the reader's next message — its
   number or its key — picks one, with the same spec.
4. **The answer compiles**: `checkAnswer` on the relation found, as a tile would be checked.
5. **It is read** with the page's engine under the page's chips, and the sentence after the tile is
   written from the rows — the figure, or the first two bars and how many there are — never by the
   model.

**It reads through `engine.query`, not the coordinator's queue.** The queue batches behind
`requestAnimationFrame`, which a hidden tab never fires. `query` goes to the same connection directly
and takes the chat's signal: *Stop* rejects the wait at once with the signal's reason.

**A chip reaches the answer as it reaches a tile.** A clause on the answer's own relation applies as
it is; one on another relation crosses to it by the key both reach, as the page's tiles are crossed;
one on a relation it shares no type with keeps none of the answer's rows, which the reply and the card
both say.

| Option | Type | |
| --- | --- | --- |
| `model` | `LanguageModel` | The host's — `localModel(…)`. Nothing here names a model |
| `engine` | `Pick<Engine, "query">` | The page's — `engine()` — so an answer is read on its one connection, outside the queue |
| `graph` | `JoinGraph` | The graph the relations are found in |
| `types` | `readonly AnswerRelation[]` | Each type alone, with its fields — `readAnswerRelations` at `hops: 0` |
| `selection` | `Selection` | The page's crossfilter: an answer must reach its chips, and is read under them |

The options are read anew on every question — the page's filter changes between two. The messages are
`AskMessage`: each turn keeps its spec as a `data-ask` part, an `AskTurn`, beside the `answer` part.
`askTransport(() => options)` is the transport alone, for a host with its own `useChat`; `readAnswer`
is the read alone. `AnswerOutput` is what a read answers: `{ answer, rows, truncated, under,
unanswered }` — the answer as placed, the rows its tile reads, whether the 1,000-row cap cut them,
the page's clauses it was read under, and those its relation cannot answer, each an
`UnansweredClause`, `{ clause, missing }`; a row is a `QueryRow`.

*Held by* `packages/ai/src/data/ask-chat.test.ts`, "answers with the tile the Task's spec is, read on
the page's engine, and words written from its rows"; "asks which way when two relations answer
equally, and reads the one the reader picks". `packages/ai/src/data/ask.test.ts`, "leaves the
relation to the resolver: prizes by university, under a chip on the prizes"; "sends a spec no
relation reaches back, and takes the repair". `packages/ai/src/data/page-clauses.test.ts`, "crosses a
chip on another relation by the key both reach, as the page's tiles are crossed"; "keeps none of a
relation's rows when it shares no type with the chip's".

## The chips

**`AskChips` draws what an answer was read as, each part editable**: what is counted, what a chart
is by, and each condition. A chip opens the values it can hold instead, and they are computed, not
asked of a model — every type, every other field, a condition's other values and *any* — and each is
offered only when Ask's own oracles accept it: the resolver reaches it by one shortest path, and it
compiles. Taking one sends the edited spec as the next message, and the transport asks it as it is:
the oracles run, the answer is read, and no model is called.

```tsx
answer: (part, { stopped }) => {
  const spec = part.state === "output-available" ? (part.output as AskOutput).spec : undefined;
  return (
    <>
      <AnswerCard graph={graph} part={part} stopped={stopped} />
      {spec && <AskChips onChange={(next) => chat.sendMessage(askEdit(next))} over={{ graph, types }} spec={spec} />}
    </>
  );
},
```

An `answer` part's output carries the spec it was read from (`AskOutput`), so the chips need nothing
the part does not hold. `askAlternatives(spec, input)` is the list without the drawing, and
`verify(task, value, input)` from `@kanzo-tech/ai/task` is the check without a model, for any Task.

*Held by* `packages/ai/src/data/ask.test.ts`, "offers each slot's other values, as whole specs";
"offers only what the oracles accept: no x two relations reach equally".
`packages/ai/src/data/ask-chat.test.ts`, "asks an edited spec as it is, with no model in between".

## The questions

**`askOffers(options)` is the same Task with no question asked**: the model writes as many specs as
`count` (four by default) in one answer, each is checked by the oracles that check an answer, and only
those that reach a relation unasked are offered, as a reader's question — `questionOf(spec)`. A pill
is therefore always one the chat can answer: taking it asks the question it says. The page's chips
are in its input, so the offers reach the rows the page is filtered to.

## The answer card

`AnswerCard` draws one `answer` call, from the part `Chat`'s `tools` hands over, at whatever state it
is in. Once there is an answer it is **the dashboard's own tile** over the answer's relation,
narrowed by its conditions — a chart is `ChartCard`, a figure `DashboardStat`, a table a
`DetailTable` — and like every tile it reads under the page's crossfilter: what the reader filters
afterwards, the card follows. A kept answer is names, not SQL, so a restored transcript draws it
again over the host's graph, and one whose relation that graph no longer has is a `Problem`.

In the tile's header, beside its title, are the two verbs the shape gives — icon buttons, named by
`aria-label` and by a tooltip, as a dashboard tile's pencil is ([why](/docs/design/ai#an-answers-verbs-are-on-its-tile-and-filter-is-there-only-when-it-filters)):

- **Filter the page to these rows** narrows the page to the answer: its conditions, and for a bar
  chart the categories it answered, published as one semi-join on the relation's root key — a
  [`clauseSemiJoin`](/docs/design/graph#the-clause-rule-column-predicates-or-a-semi-join-on-identity)
  over the answer's rows — so the graph and every panel that shares the key follow.
  It is `aria-pressed` while the clause holds, and pressed again it takes the clause back. Its chip
  in the page's `FilterBar` names what it filters, each clause as the bar reads one: *Ask:
  Person.gender female*, *Ask: browserUsed · 3 selected*. An answer with nothing to narrow to draws
  no button. **It is disabled when it would keep everything in view** — no conditions, a relation
  that is a type alone, and bars over every category of their column (none missing against the
  field's `distinct`, none null) — and its tooltip and description say so: *This answer keeps
  everything in view*.
- **Add to the dashboard** is drawn when the host passes `dashboards` and `onAdd`, which go together.
  `dashboards` is the host's [document](/docs/analytics/dashboard-spec#dashboards), a spec per
  relation, as it draws it. `onAdd` is called with the whole next document — the tile appended to the
  answer's relation's spec, or to its automatic dashboard when it has none, as `Dashboard` would draw
  it — and where it landed: `{ relation, key, id }`, the relation, its `relationKey` and the tile's id.
- **Open on the dashboard** takes its place once the tile is there, when the host passes `onOpen`: it
  is called with the same `{ relation, key, id }`, and the host switches to its dashboard view of the
  relation and brings the tile into view. Without `onOpen` the button says *On the dashboard*,
  disabled.

The tile goes on under the answer's own id, so **whether it is on the dashboard is read from
`dashboards`**, not kept by the card: a remounted card still offers *Open on the dashboard*, and once
the reader removes the tile and that is saved, the card offers the add again. When `onAdd` returns a
promise, the button is pending until it settles — whatever `dashboards` already shows — and a
rejection is drawn as a [`Problem`](/docs/data-display/problem) under the tile, the thrown value
whole, with the button back. `copy` is the host's words for a coded one, as `Chat` takes them. *On the dashboard* reads the host's `dashboards` and nothing else, so a host that draws the tile
before its write settles is saying it is there: it rolls the document back when the write fails, and
the card follows and offers the add again. The card says it
where the reader pressed, so a host that also toasts every failed save says it twice.

An add is a decision, not an edit: write it at once, as `useDebouncedCommit`'s `commit` does, with
any edit pending in the dashboard's editor, which it was made over. When a page has both, **one store
holds the document for the dashboard's editor and for Ask**: `dashboards` is the editor's draft, so an
answer added while a tile is being edited lands on the edit rather than on what the server held.

```tsx
// `save` is a mutation whose `onError` reports a failed write, for the edits nobody awaits.
const { draft, change, commit } = useDebouncedCommit(saved, (next: Dashboards) => save.mutateAsync(next), 800);

<AnswerCard
  dashboards={draft}
  graph={graph}
  onAdd={(next) => commit(next)} // the write, which the button waits on
  onOpen={({ relation, id }) => {
    setRelation(relation); // the dashboard view, onto the relation the tile landed on
    setView("dashboard");
    setFocused(id); // the tile, brought into view
  }}
  part={part}
  stopped={stopped}
/>
```

`commit` answers what `onCommit` answered, so the card waits on the save itself. The editor's
`change` goes through the same `onCommit` after its pause, where nobody awaits it.

Before there is an answer, and when there will be none:

- **While the model writes the answer and the engine reads it** the card is `aria-busy`, over a
  skeleton the chart's height, so nothing jumps when the tile lands. It stays busy until the tile, or
  its failure, is drawn in the skeleton's place.
- **A call that stopped** (`stopped`, from `Chat`) draws nothing that waits.
- **A refusal is a [`Problem`](/docs/data-display/problem)** under the card's title, *The answer
  failed*: input `checkAnswer` refused, the engine's failure, both from the part's `errorText`.

Under the tile, one line says what the read was under, as the model was told: *Read under the page's
filter: Person.gender female. Not applied, as this relation lacks the fields they filter: City.name
Madrid (City.name).* It is the read's, when it ran — the tile follows the page afterwards — and there
is no line when the page had no filter.

| Prop | Type | |
| --- | --- | --- |
| `part` | `ToolPart` | The `answer` call, at any state |
| `graph` | `JoinGraph` | The graph Ask was given |
| `stopped` | `boolean` | The call will never settle — `Chat`'s `stopped` |
| `dashboards` | `Dashboards` | The host's dashboards, as it draws them: whether the tile is on its relation's. With `onAdd` |
| `onAdd` | `(next: Dashboards, added: AnswerAdded) => void \| Promise<unknown>` | Makes *Add to the dashboard* an action. With `dashboards` |
| `onOpen` | `(added: AnswerAdded) => void` | Makes *Open on the dashboard* the action once the tile is there. With `onAdd` |
| `copy` | `ProblemProps["copy"]` | The host's words for a coded failure |
| `translations` | `Partial<AnswerCardTranslations>` | Every word it draws |

*Held by* `packages/ai/src/data/answer-card.test.tsx`, "Add to the dashboard hands the host its
dashboards with the tile in the relation's spec, and where it landed"; "is on the dashboard while the

back"; "is busy until answered, over a skeleton the chart's height, and not once stopped"; "draws a

## Testing

`AnswerHarness` from [`@kanzo-tech/testing`](/docs/testing) asks through the composer and reads the
newest `AnswerCard`. It waits for the card to stop being `aria-busy`, which it is until its tile or
its `Problem` is drawn, and a failed answer rejects with the `Problem`'s words. `addToDashboard()`
waits out the host's pending write for *Open on the dashboard*, and rejects with the card's `Problem`
when the host refused it; `openOnDashboard()` presses it. `filterTo()` rejects when the answer keeps
everything in view.

```ts
import { AnswerHarness } from "@kanzo-tech/testing";

const answers = await env.harness(AnswerHarness);
await answers.ask("What does the Amber Hall hold, by kind?");
await (await (await answers.answer()).chart()).settled();
await answers.filterTo();
```

## Installing it

A subpath, because it draws with `@kanzo-tech/ui`'s [analytics](/docs/analytics/charts) and table
layers, whose engines are optional peers: a host that only chats does not install DuckDB to import
`Chat`. A host of `/data` installs those layers' peers, plus one of its own:

```bash
pnpm add @kanzo-tech/mosaic
```

The types are exported as `Answer`, `AnswerInput`, `AnswerField`, `AnswerRelation`, `Condition`,
`ConditionValue`, `UnansweredClause`, `AnswerOutput`, `QueryRow`, `AskChatOptions`, `AskMessage`,
`AskOutput`, `AskTurn`, `AskChip`, `AskChipsProps`, `AskInput`, `AskSpec`, `AskContext`, `AnswerRelationsOfOptions`, `ReadAnswerRelationsOptions`,
`AnswerAdded`, `AnswerCardProps` and `AnswerCardTranslations`.
