---
title: Ask your data
description: An agent that answers questions about data with a dashboard tile over a relation, filled from names the page generated — the relations it may answer about, the schema it fills, the questions to start from, and the card each answer is drawn in — @kanzo-tech/ai/data.
---

`@kanzo-tech/ai/data` is `Chat` pointed at data. A question gets one answer, and an answer is a
**dashboard tile over a relation**: the model picks a relation of the page's join graph, narrows it
with the conditions a dashboard's filters publish, and says how it is shown — a figure, a chart or a
table. It writes no SQL: every name it writes is an enum the page generated from the data it shows.
[Asking data](/docs/design/ai) is why. The live version is the **Ask** panel of the
[workspace showcase](/docs/showcases/workspace): a recorded model, but every tile is read for real,
under the filter you set on the page.

| | For |
| --- | --- |
| `readAnswerRelations` | What may be asked about: each relation's fields, as a dashboard over it reads them, and each category's most common values |
| `dataAgent` | The agent: one `answer` tool, whose input is the schema below |
| `answerSchema` | The tool's JSON Schema: the relations' types, hops and fields, the aggregates and the chart kinds, as enums |
| `checkAnswer` | What refuses input outside that schema before anything runs, in words the model reads |
| `dataSuggestions` | Questions to start from, over those relations and the page's filter — `suggest()` with a data space's instructions |
| `AnswerCard` | The card an answer is drawn in: the dashboard's own tile, with *Filter to it* and *Add to the dashboard* |

## Usage

```tsx
import { Chat, ChatSkeleton, useAgentChat } from "@kanzo-tech/ai";
import { AnswerCard, dataAgent, dataSuggestions, readAnswerRelations, type AnswerCardProps, type AnswerRelation } from "@kanzo-tech/ai/data";
import { createGateway } from "@kanzo-tech/llm";
import { DiagnosticList, Problem } from "@kanzo-tech/ui";
import { relationHops, useMosaic, type JoinGraph, type Relation } from "@kanzo-tech/ui/analytics";

const gateway = createGateway({ baseURL: "/api/ai" });

/** A type alone, and each hop from it: what a reader of that type may ask about. */
const around = (graph: JoinGraph, type: string): Relation[] => [
  { root: type, path: [] },
  ...relationHops(graph, type).map(({ hop }) => ({ root: type, path: [hop] })),
];
```

```tsx
function Ask({ graph, relations, onAdd }: { graph: JoinGraph; relations: AnswerRelation[]; onAdd: AnswerCardProps["onAdd"] }) {
  const { coordinator, crossfilter } = useMosaic();
  const chat = useAgentChat(dataAgent({ model: gateway("chat"), coordinator, graph, relations, selection: crossfilter }));
  // Cached per data space and per filter; streamed, so the pills land one by one.
  const starters = useQuery({
    queryKey: ["starters", relations, String(crossfilter.predicate(null))],
    queryFn: streamedQuery({
      streamFn: ({ signal }) => dataSuggestions({ model: gateway("complete"), graph, relations, selection: crossfilter, abortSignal: signal }),
    }),
  });
  return (
    <Chat
      chat={chat}
      notice={
        starters.isError && (
          <DiagnosticList className="w-full">
            <Problem error={starters.error} />
          </DiagnosticList>
        )
      }
      suggesting={starters.fetchStatus === "fetching"}
      suggestions={starters.isError ? [] : (starters.data ?? [])}
      tools={{ answer: (part, { stopped }) => <AnswerCard graph={graph} onAdd={onAdd} part={part} stopped={stopped} /> }}
    />
  );
}
```

`relations` is `await readAnswerRelations(coordinator, graph, around(graph, "Person"))`, read once
per data space. Until it is, draw `<ChatSkeleton />` in the chat's place: it is the same layout, so
nothing jumps when the chat replaces it. The cache is the host's: `dataSuggestions` is an async
iterable, so TanStack Query's `streamedQuery` (or an effect) holds it, keyed per data space and
filter. While it streams the strip shows pills in skeleton; if it fails the failure is drawn in the
pills' place (`notice`), and the chat works the same — see [Before the first question](/docs/ai/chat#before-the-first-question).

## The relations

`readAnswerRelations(coordinator, graph, relations, { values })` answers an `AnswerRelation` per
relation, `{ relation, columns, fields }`, read from the engine the way a [dashboard](/docs/analytics/dashboard)
over the same relation reads them: `queryFieldStats` over `relationQuery`, without the keys
`relationIdentities` names, then `plotRelation`. Each category that is a dimension carries its most
common `values` — six by default, the most common first — counted over the relation.

So the model and the dashboard read **one list of fields**: a tile the model fills names the fields
`Dashboard` draws, and *Add to the dashboard* adds a tile the dashboard can draw.

Which relations are offered is the host's to say. A type alone and every hop from it is the usual
answer, because a question that crosses a hop is what a reader cannot see in any one table; each one
costs a `SUMMARIZE` and a count per category, once per data space. The graph comes from whatever
catalog the host has — [`readJoinGraph`](/docs/graph#readjoingraph) for a fossil corpus.

*Held by* `packages/ai/src/data/answer.test.ts`, "reads each relation's fields as a dashboard over it
does, without its keys, and each category's most common values".

## The answer

```ts
interface Answer {
  relation: Relation;            // a type, and the hops from it — the JoinGraph's
  where?: readonly Condition[];  // { field, in } | { field, between } | { field, contains }
  show: Tile;                    // the dashboard's Tile: a figure, a chart or a table
  top?: number;                  // rank show's x by its measure and keep these many
}
```

The model writes an `AnswerInput`: an `Answer` whose tile has no `id` and no `span`, which the page
gives — the call's id, and the width a dashboard gives the kind.

`answerSchema(graph, relations)` is the tool's JSON Schema. The relation's `root` and each hop's
`edge` are enums of the types and edges the relations offered take; every field slot — a condition's
`field`, a chart's `x`, `color` and `facet`, a measure's `field`, a figure's `trend`, a table's
`columns` — is an enum of the offered relations' fields; `op` is an enum of the dashboard's
aggregates and `type` of its chart kinds. A provider that decodes against the schema cannot write a
name that does not exist.

The schema is one object rather than one branch per relation, because Anthropic and OpenAI refuse a
tool whose input is an `anyOf` at the top. So **`checkAnswer(value, relations, graph)`** holds the rest:
the relation is one of those offered, every field is that relation's, the conditions have one
operator each, `top` is a whole number, and the tile is one [`parseTile`](/docs/analytics/dashboard-spec#reading-it-back)
reads. It is the AI SDK's `validate` on the tool's input, so input that fails is refused before
`execute` runs, and the model reads the sentence: *show.x: Person2.gender is not a field of Person,
whose fields are Person.gender, Person.age, Person.born.*

**An answer compiles with what a dashboard compiles with.** `relationQuery` makes the relation and
`plotRelation` the table the plots read; each condition is the clause a dashboard filter of its kind
publishes — `clausePoints` for `in`, `clauseInterval` for `between`, over `Date`s for a time,
`clauseMatch` for `contains`; and the tile's rows are its measure, `measureExpr`, by its x, grouped
by the step a trend takes (`bucketExpr`). The page's crossfilter applies as it is when the answer
runs: each of its clauses whose columns the relation has, as [`clauseColumns`](/docs/design/graph#the-clause-rule-column-predicates-or-a-semi-join-on-identity)
reads them — a semi-join on the root's key always does.

**What the spec cannot say gets no answer.** A ratio of two measures, a window, a join the graph does
not have: the model is told to say so in one sentence rather than answer a different question. There
is no SQL beside it as a fallback; [Asking data](/docs/design/ai) says why, and what would reverse
it.

*Held by* `packages/ai/src/data/answer.test.ts`, "the enums are the relation's fields only"; "an
answer compiles to the same query the dashboard tile reads"; "crosses a hop: whom the women know, by
gender, ranked"; "input outside the schema is refused before it runs".

## The agent

`dataAgent(options)` is a `ToolLoopAgent` with one tool, `answer`. The tool compiles the answer and
reads its rows on the page's coordinator — the reader sees the tile, the model reads the first 30
rows, cut to 4,000 characters, and the page's clauses the answer was read under, as a chip names
them. An engine failure throws, so the AI SDK hands the model the error and the card draws it.

| Option | Type | |
| --- | --- | --- |
| `model` | `LanguageModel` | The host's — `gateway("chat")`. Nothing here names a model |
| `coordinator` | `Coordinator` | The page's, so the agent reads through its one connection |
| `graph` | `JoinGraph` | The graph the relations are over |
| `relations` | `readonly AnswerRelation[]` | `readAnswerRelations`' answer. The model is told it is the whole of the data |
| `selection` | `Selection` | The page's crossfilter: an answer is read under its clauses when it runs |

**The instructions list fields, not DDL.** Each relation is named (`Person>knows>Person`), given as
the literal the model writes for it, and followed by its fields, each with its kind and what it
holds: `Person.gender: category (female, male)`, `Person.age: number (27 – 61)`, `Person.born: time
(1965-09-15 – 1999-01-20)`, and an identifier as `text, one per row`. The model never reads a table
name, so it never writes one.

**The model is told the tile is already shown.** The instructions end on it: say what the tile shows
— the numbers that matter, the pattern, the exception — and do not list its rows again. Genie's and
ChatGPT's answers read the same way.

`dataInstructions(options)` is the prompt, for a host that builds its own `ToolLoopAgent` around the
same tool; `DataTools` types the toolset, so `InferAgentUIMessage<ReturnType<typeof dataAgent>>` types
the messages. `AnswerOutput` is what a call answers: `{ answer, rows, truncated, under }` — the answer
as placed, the rows its tile reads, whether the 1,000-row cap cut them, and the page's clauses it was
read under; a row is a `QueryRow`.

*Held by* `packages/ai/src/data/agent.test.ts`, "tells the model each field with its kind and what it
holds, never DDL, and that the tile is already shown"; "hands the model a sample of the rows and the
page's filter that applied, after one tool call"; "stops after five steps, however often the model
calls the tool"; "throws when the chat was stopped, rather than answering nobody".

## The questions

`dataSuggestions` offers what crosses a hop first. A count or a top N over one type is what a BI
tool's first screen already shows; what a reader cannot see in any one table is how two connect, and
a relation written with `>` or `<` says exactly where that is. So the instructions favour a question
over a relation that crosses a hop, ask a count or top N over a type alone only when none is offered,
and have each rationale name the relation the question is over — which is what the pill's tooltip
then says. The page's filter, as its chips read, is in the prompt: the questions favour those rows.

The model is the host's `complete` alias, not `chat`: a handful of short questions is a completion,
and the reader is waiting on the strip, not on an answer.

*What would reverse it:* readers picking the count and top-N pills over the cross-hop ones, observed
in a discovery view, or hosts that offer no hop at all — then the instructions are favouring what
nobody has.

*Held by* `packages/ai/src/data/agent.test.ts`, "favours a question across a hop, and a rationale
naming the relation it is over"; "asks for questions over the relations and the page's filter, as
many as were wanted".

## The answer card

`AnswerCard` draws one `answer` call, from the part `Chat`'s `tools` hands over, at whatever state it
is in. Once there is an answer it is **the dashboard's own tile** over the answer's relation,
narrowed by its conditions — a chart is `ChartCard`, a figure `DashboardStat`, a table a
`DetailTable` — and like every tile it reads under the page's crossfilter: what the reader filters
afterwards, the card follows. A kept answer is names, not SQL, so a restored transcript draws it
again over the host's graph, and one whose relation that graph no longer has is a `Problem`.

Above it are the two actions the shape gives:

- **Filter to it** narrows the page to the answer: its conditions, and for a bar chart the
  categories it answered, published as one semi-join on the relation's root key — [`semiJoinOf`](/docs/design/graph#the-clause-rule-column-predicates-or-a-semi-join-on-identity),
  as a relation dashboard's tiles publish — so the graph and every panel that shares the key follow.
  It is a chip in the page's `FilterBar`, *Ask*, and pressed again it takes the clause back. An
  answer with nothing to narrow to draws no button.
- **Add to the dashboard** is drawn when the host passes `onAdd`. It is called with the relation's
  key, as `relationKey` writes it and a host keeps its dashboards by, and `add`, which answers the
  relation's spec with the tile appended under a new id — to the automatic dashboard when the spec is
  `undefined`, as `Dashboard` would draw it.

```tsx
<AnswerCard
  graph={graph}
  onAdd={(key, add) => change({ byRelation: { ...current.byRelation, [key]: add(current.byRelation[key]) } })}
  part={part}
  stopped={stopped}
/>
```

Before there is an answer, and when there will be none:

- **While the model writes the answer and the engine reads it** the card is `aria-busy`, over a
  skeleton the chart's height, so nothing jumps when the tile lands.
- **A call that stopped** (`stopped`, from `Chat`) draws nothing that waits.
- **A refusal is a [`Problem`](/docs/data-display/problem)** under the card's title, *The answer
  failed*: input `checkAnswer` refused, the engine's failure, both from the part's `errorText`.

| Prop | Type | |
| --- | --- | --- |
| `part` | `ToolPart` | The `answer` call, at any state |
| `graph` | `JoinGraph` | The graph the agent was given |
| `stopped` | `boolean` | The call will never settle — `Chat`'s `stopped` |
| `onAdd` | `(key, add) => void` | Makes *Add to the dashboard* an action |
| `translations` | `Partial<AnswerCardTranslations>` | Every word it draws |

*Held by* `packages/ai/src/data/answer-card.test.tsx`, "Add to the dashboard writes the tile into the
relation's spec"; "filters the page to the answer as one semi-join on the root key, and takes it
back"; "is busy until answered, over a skeleton the chart's height, and not once stopped"; "draws a
refusal as a Problem under the card's title"; "draws a kept answer whose relation the graph no longer
has as a Problem"; "draws the figure the answer is, read under its conditions".

## Testing

`AnswerHarness` from [`@kanzo-tech/testing`](/docs/testing) asks through the composer and reads the
newest `AnswerCard`. It waits for the card to hold its tile or its `Problem` — the card is `aria-busy`
while the model writes and the engine reads — and a failed answer rejects with the `Problem`'s words.

```ts
import { AnswerHarness } from "@kanzo-tech/testing";

const answers = await env.harness(AnswerHarness);
await answers.ask("What does the Amber Hall hold, by kind?");
await (await (await answers.answer()).chart()).settled();
await answers.filterTo();
```

## Installing it

A subpath, because it draws with `@kanzo-tech/ui`'s [analytics](/docs/analytics/charts) and table
layers, whose engines are optional peers: a host that only chats does not install DuckDB to import
`Chat`. A host of `/data` installs those layers' peers, plus one of its own:

```bash
pnpm add @kanzo-tech/mosaic
```

The types are exported as `Answer`, `AnswerInput`, `AnswerField`, `AnswerRelation`, `Condition`,
`ConditionValue`, `AnswerOutput`, `QueryRow`, `DataAgentOptions`, `DataSuggestionsOptions`,
`DataTools`, `ReadAnswerRelationsOptions`, `AnswerCardProps` and `AnswerCardTranslations`.
