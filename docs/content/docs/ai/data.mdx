---
title: Ask your data
description: Ask — questions about data answered with a dashboard tile over a relation, from a spec the model fills with paths the page generated, resolved by the page's joins — the types it may answer about, the chat it runs in, the questions to start from, and the card each answer is drawn in — @kanzo-tech/ai/data.
---

`@kanzo-tech/ai/data` is `Chat` pointed at data. A question gets one answer, and an answer is a
**dashboard tile over a relation**. The model fills a **spec**: what is counted, how it is shown —
a figure, a chart or a table — and the conditions a dashboard's filters publish. It writes no SQL:
every field is a path from the type it counts — `university.name`, `^laureate.category.name` — out of
an enum the page generated from the data it shows, and the relation is the one those paths lie on,
which the page's [`JoinResolver`](/docs/analytics/dashboard#the-joins-one-door) resolves. That is Ask as a [Task](/docs/design/tasks); [Asking data](/docs/design/ai) is why. The live
version is the **Ask** panel of the [workspace showcase](/docs/showcases/workspace): a recorded model,
but every tile is read for real, under the filter you set on the page.

| | For |
| --- | --- |
| `useAskChat` | The chat: one run of the `ask` Task per question, its answer read on the page's engine — `Chat` draws it |
| `askOffers` | Questions to start from: the Task's own proposals, each checked by its oracles |
| `ask` | The Task — linker, schema, oracles — for a host that runs it with `runTask` outside a chat |
| `AnswerCard` | The card an answer is drawn in: the dashboard's own tile, with *Filter the page to these rows* and *Add to the dashboard* in its header |

## Usage

```tsx
import { Chat, ChatSkeleton } from "@kanzo-tech/ai";
import { AnswerCard, askEdit, askOffers, useAskChat, type AnswerCardProps, type AskOutput } from "@kanzo-tech/ai/data";
import { localModel } from "@kanzo-tech/llm/local";
import { DiagnosticList, Problem } from "@kanzo-tech/ui";
import type { Engine } from "@kanzo-tech/mosaic/engine";
import type { JoinGraph } from "@kanzo-tech/relations";
import { useMosaic, type Dashboards } from "@kanzo-tech/ui/analytics";

const model = localModel("Qwen3-4B-q4f16_1-MLC");
```

```tsx
function Ask({ engine, graph, dashboards, onAdd }: { engine: Engine; graph: JoinGraph; dashboards: Dashboards; onAdd: AnswerCardProps["onAdd"] }) {
  const { selection } = useMosaic();
  const chat = useAskChat({ model, engine, graph, selection });
  // Cached per data space and per filter.
  const offers = useQuery({
    queryKey: ["offers", jobId, String(selection.predicate(null))],
    queryFn: ({ signal }) => askOffers({ model, graph, selection, signal }),
  });
  return (
    <Chat
      chat={chat}
      notice={
        offers.isError && (
          <DiagnosticList className="w-full">
            <Problem error={offers.error} />
          </DiagnosticList>
        )
      }
      message={askEdit}
      proposals={offers.data ?? []}
      proposing={offers.isFetching}
      data={{
        answer: (part, { stopped }) => (
          <AnswerCard answer={part.data as AskOutput} dashboards={dashboards} graph={graph} onAdd={onAdd} stopped={stopped} />
        ),
      }}
    />
  );
}
```

`graph` is [`readJoinGraph`](/docs/graph#readjoingraph) for an attached GraphAr graph, read once per data
space, and it is all Ask is given: what each type and field is and holds — its kind, its role, its
commonest values — is on the graph, and nothing more is read before the first question. Until the
graph is read, draw `<ChatSkeleton />` in the chat's place: it is the same layout, so nothing jumps
when the chat replaces it. The cache is the host's: `askOffers` is a promise, so TanStack Query (or
an effect) holds it, keyed per data space and filter. While it runs the strip shows pills in
skeleton; if it fails the failure is drawn in the pills' place (`notice`), and the chat works the
same — see [Before the first question](/docs/ai/chat#before-the-first-question).

## What the model is told

Ask is offered each type of the graph alone, with its fields as a [dashboard](/docs/analytics/dashboard)
over it reads them: `fieldStats` over the graph's descriptions of its columns (`relationColumns`),
without its key, then `plotRelation`. A type alone's fields go by their own names — `gender`,
`age` — which are the paths from it, and each carries what the graph's writer counted: its kind and
role, and its commonest `values`, the first six of which the model is told. Nothing is read from the
engine for it — no `SUMMARIZE` and no count — so the model, the dashboard and the answer's card are
told the same figures, the graph's.

So the model and the dashboard read **one list of fields**: a tile the model fills names the fields
`Dashboard` draws, and *Add to the dashboard* adds a tile the dashboard can draw. A graph whose
graph was written before fossil counted its columns offers the same fields without `values`.

*Held by* `packages/ai/src/data/answer.test.ts`, "describes a relation's fields from the graph, without
its steps' keys, each with the commonest values its writer counted"; "reads nothing from the engine:
what a field is and holds is the graph's".

## The answer

```ts
interface Answer {
  relation: Relation; // the type measured, and the hops the tile's paths take from it
  tile: Tile;         // the dashboard's Tile, its own `where` and `top` in it
}
```

An answer is a relation and a [dashboard tile](/docs/analytics/dashboard-spec#tile) on it, and the
tile holds the whole question: what is shown, its conditions (`where`) and its ranking (`top`). So an
answer added to a dashboard is still the question asked — *Physics prizes by university*, not
*prizes by university*. A kept transcript is names, not SQL.

The model writes an `AskSpec`: the tile without its `id` and `span` — which the page gives, the
answer's id and the width a dashboard gives the kind — with `of`, the type it counts, and its `where`
and `top` beside `show`:

```json
{
  "of": "LaureateAward",
  "where": [{ "field": "category.name", "in": ["Physics"] }],
  "show": { "kind": "chart", "type": "bar", "x": "university.name", "y": { "op": "count" } }
}
```

Every field is a path from `of`: an edge's label steps to the type it leads to, `^label` steps back to
the type it comes from, and the last name is a column of the type reached; a field of `of` itself is
its own name. The schema is one branch per type the linker offers, each `of` a constant beside its own
enum of the paths from it within three hops, so a provider that decodes against it cannot write a
path that does not exist — nor one from another type. Two paths that reach one field — a prize's
country by its laureate's birth or its university's address — are both in the enum, and the one the
model writes is the answer's.

**An answer compiles with what a dashboard compiles with.** `relationQuery` makes the relation and
`plotRelation` the table the plots read; [`tileQuery`](/docs/analytics/dashboard-spec#reading-it-back),
the dashboard's one compiler of a tile, makes its rows: each condition the clause a dashboard filter
of its kind publishes, one whose path leaves the relation read through the branch and crossed in at
the step it leaves, `top` the bars ranked first, and the measure — a `count` counting the measured
type's distinct keys, once per bar however many joined rows lead there. The page's crossfilter
applies as it is when the answer runs.

**What the spec cannot say gets no answer.** A ratio of two measures, a window, a join the graph does
not have: there is no path to write it with, and what the oracles refuse after the last repair is
said to the reader rather than answered as a different question. There is no SQL beside it as a
fallback; [Asking data](/docs/design/ai) says why, and what would reverse it.

*Held by* `packages/ai/src/data/answer.test.ts`, "reads its tile's rows with the one compiler the
dashboard's tile reads"; "crosses a hop by its path: whom the women know, by gender, ranked";
"crosses a condition off the shown path in at the root's key, counting each person once".

## Ask

`useAskChat(options)` is `useChat` over a transport that runs the [`ask` Task](/docs/design/tasks#ask-from-agent-to-form)
once per question, in the page, and writes what it found into the transcript as a `data-answer`
part — written as asked, then again under the same `id` once read; the part `AnswerCard` draws — followed by a sentence. There is no tool loop and no second call to
the model: the spec is the model's, everything after it is the page's.

1. **The linker** keeps the types the question names — by the type, a field or a value it holds —
   with their neighbours one hop away, the type the previous answer was about, and the types the
   page's chips are on. The schema's enums are theirs, so a small model reads a small vocabulary.
2. **The model fills the spec**, `{ of, show, where?, top? }`, with `@kanzo-tech/llm`'s `generate`,
   asked once, and `Output.object`: a provider that decodes against the schema cannot write a path
   that does not exist. The prompt lists the types' fields and the edges a path steps across. A
   follow-up — *and in Germany?* — is told the previous spec and changes only what it asks.
3. **The paths are resolved**: `JoinResolver.relation(of, shown)` is the relation the shown paths lie
   on, and `field` places each condition on it or through a branch. A path the graph does not have,
   or two shown paths that leave each other, is a diagnostic at its pointer — `relations/no-step`,
   `relations/unmatched`, `relations/invalid` — and so is a page's chip on a type the answer does not reach;
   the model repairs the spec, three attempts in all. Nothing is asked of the reader: two paths of
   one length are the model's to choose, and the chip offers the other.
4. **The tile compiles**: `parseTile` on the spec's tile, as a dashboard reads one.
5. **It is read** with the page's engine under the page's chips, and the sentence after the tile is
   written from the rows, never by the model: the figure, or the leading two groups of bars — ties
   named together with `Intl.ListFormat`, values with `Intl.NumberFormat`, *Physics: 230; Chemistry:
   200.* Its two separators are `translations`' `value` and `groups`; a table or a plot of rows gets
   none.

**It reads through `engine.query`, not the coordinator's queue.** The queue batches behind
`requestAnimationFrame`, which a hidden tab never fires. `query` goes to the same connection directly
and takes the chat's signal: *Stop* rejects the wait at once with the signal's reason.

**A chip reaches the answer as it reaches a tile.** A clause on the answer's own relation applies as
it is; one on another relation crosses to it by the key both reach, as the page's tiles are crossed;
one on a relation it shares no type with keeps none of the answer's rows, which the reply and the card
both say.

| Option | Type | |
| --- | --- | --- |
| `model` | `LanguageModel` | The host's — `localModel(…)`. Nothing here names a model |
| `engine` | `Pick<Engine, "query">` | The page's — `engine()` — so an answer is read on its one connection, outside the queue |
| `graph` | `JoinGraph` | The graph the relations are found in |
| `selection` | `Selection` | The page's crossfilter: an answer must reach its chips, and is read under them |
| `translations` | `Partial<AskChatTranslations>` | Every word the replies write: `value` (*: *) and `groups` (*; *), the sentence's separators; `empty`, `hidden` and `failed` |

The options are read anew on every question — the page's filter changes between two. The messages are
`AskMessage`: each turn keeps its spec as a `data-ask` part, an `AskTurn`, beside the `data-answer` part.
An answer is read as a TanStack Query query on the host's `QueryClient`, keyed by the engine and its
statement — which holds the page's chips — so the same answer under the same chips is read once. It
never retries, a failed read is not kept, and *Stop* cancels the query and ends the read at once.
`AnswerOutput` is what a `data-answer` part holds: `{ answer, rows?, truncated?, under?,
unanswered? }` — the answer, and once read the rows its tile reads, whether the 1,000-row cap cut
them, the page's clauses it was read under, and those its relation cannot answer, each an
`UnansweredClause`, `{ clause, missing }`; a row is a `QueryRow`. `AskOutput` adds the spec it was
read from.

**A decision is a data part, answered by the option's id.** When a Task's oracle needs the person —
a `Decision`, options and never free text — the turn ends with a `data-ask` part holding it, and
no words. Draw it with [`@kanzo-tech/ui`'s question part](/docs/ai/chat), and send the pick as
`askEdit(turn.spec, { [decision.id]: option })`: the reply's `data-ask` part settles the decision
as the option picked, and the spec is asked as it is.

```tsx
ask: (part) => {
  const turn = part.data as AskTurn;
  if (!turn.decision) return null;
  return (
    <Question name={turn.decision.id} onValueChange={(d) => chat.sendMessage(askEdit(turn.spec, { [turn.decision!.id]: String(d.value) }))}>
      <QuestionPrompt>{turn.decision.question}</QuestionPrompt>
      <QuestionChoices>
        {turn.decision.options.map((o) => <QuestionChoice key={o.id} value={o.id}>{o.label}</QuestionChoice>)}
      </QuestionChoices>
    </Question>
  );
},
```

*Held by* `packages/ai/src/data/ask-chat.test.ts`, "answers with the tile the Task's spec is, read on
the page's engine, and words written from its rows"; "words a bar chart's leading groups with Intl,
ties named together, through its translations"; "asks a decision as a data part, and settles it by
the option the reply picks, not by its words"; "reads an answer asked again under the same chips
once, on the host's client"; "ends the read with the chat's signal, keeps nothing of it, and reads
again when asked again". `packages/ai/src/data/ask.test.ts`, "takes the relation from the paths the
model wrote: prizes by university, under a chip on the prizes"; "sends a path the graph does not have
back, at its pointer, and takes the repair". `packages/ai/src/data/page-clauses.test.ts`, "crosses a
chip on another relation by the key both reach, as the page's tiles are crossed"; "keeps none of a
relation's rows when it shares no type with the chip's".

**A chat with Ask is kept as every chat is, and keeps structure only**: `useAskChat(options, { id, load, save })`
takes the chat hooks' `load` and `save` ([A chat kept](/docs/ai/chat#a-chat-kept)). Its two data
parts, `answer` and `ask`, are read through Ask's own schemas — as they stream and as a kept chat is
loaded — each rebuilt from the fields it holds, its tile read by `parseTile` as a dashboard reads a
stored tile; you do not pass `dataPartSchemas`. `keep` defaults to `askKeep`, which cuts an answer's
`rows` and `truncated` and leaves its spec, its tile and the clauses it was read under, so a stored
chat holds what was asked and none of the data. When the chat is loaded each answer is read again on
the page's engine, under the page's chips as they are then, and the card draws the rows it gets. The
assistant's reply sentence is a text part and is kept as written: it names figures, so have `keep`
drop it too where a figure must not be stored. A load whose read fails fails with what the engine threw. An answer with no
`rows` at all is one still being read, which a stopped message draws as nothing.

*Held by* `packages/ai/src/data/ask-chat.test.ts`, "keeps the structure of an answer and none of its
rows, and reads them again when the chat is loaded".

*Held by* `packages/ai/src/data/ask-parts.test.ts`, "reads back an answer and its turn as Ask wrote
them, and nothing they do not hold"; "refuses an answer whose tile a dashboard would not read, or
whose relation is not one".

## The chips

**`AskChips` draws what an answer was read as, each part editable**: what is counted, what a chart
is by, and each condition. A chip opens the values it can hold instead, and they are computed, not
asked of a model — every type, the nearest other paths, a condition's other values and *any* — and
each is offered only when Ask's own oracles accept it. Where the model wrote one of two paths of one
length to the same field, the other comes first. Taking one sends the edited spec as the next message, and the transport asks it as it is:
the oracles run, the answer is read, and no model is called.

```tsx
answer: (part, { stopped }) => {
  const answer = part.data as AskOutput;
  return (
    <>
      <AnswerCard answer={answer} graph={graph} stopped={stopped} />
      {answer.rows && <AskChips onChange={(next) => chat.sendMessage(askEdit(next))} over={{ graph }} spec={answer.spec} />}
    </>
  );
},
```

A `data-answer` part carries the spec it was read from (`AskOutput`), so the chips need nothing the
part does not hold. `verify(task, value, input)` from `@kanzo-tech/ai/task` is the check
without a model, for any Task.

*Held by* `packages/ai/src/data/ask.test.ts`, "offers each slot's other values, as whole specs";
"offers the other of two paths of one length to the same field first".
`packages/ai/src/data/ask-chat.test.ts`, "asks an edited spec as it is, with no model in between".

## The questions

**`askOffers(options)` is the same Task with no question asked**: the model writes as many specs as
`count` (four by default) in one answer, each is checked by the oracles that check an answer, and only
those the oracles accept are offered, whole — each the Task's `Proposal` of a spec. `Chat`
draws it as a reader's question, `questionOf(spec)`, through `askEdit`, and pressing it sends the spec
itself, which the chat asks as it is: a pill is always one the chat can answer, and taking it asks the
spec the oracles checked, not its words read again by the model. The page's chips
are in its input, so the offers reach the rows the page is filtered to.

## The answer card

`AnswerCard` draws one answer, `answer` — what a `data-answer` part holds, which `Chat`'s `data`
renderers hand over, read or still being read. Once it is read it is **the dashboard's own tile**
over the answer's relation, narrowed by its own conditions and ranking — `TileView`: a chart is
`ChartCard`, a figure `DashboardStat`, a table a `DetailTable` — and like every tile it reads under the page's crossfilter: what the reader filters
afterwards, the card follows. A kept answer is names, not SQL, so a restored transcript draws it
again over the host's graph, and one whose relation that graph no longer has is a `Problem`.

In the tile's header, beside its title, are the two verbs the shape gives — icon buttons, named by
`aria-label` and by a tooltip, as a dashboard tile's pencil is ([why](/docs/design/ai#an-answers-verbs-are-on-its-tile-and-filter-is-there-only-when-it-filters)):

- **Filter the page to these rows** narrows the page to the answer: the rows its tile reads —
  `tileQuery`'s, its conditions and ranking in them — and for a bar chart the categories it answered,
  published as one semi-join on the relation's root key — a
  [`clauseSemiJoin`](/docs/design/graph#the-clause-rule-column-predicates-or-a-semi-join-on-identity)
  — so the graph and every panel that shares the key follow.
  It is `aria-pressed` while the clause holds, and pressed again it takes the clause back. Its chip
  in the page's `FilterBar` names what it filters, each clause as the bar reads one: *Ask:
  gender female*, *Ask: browserUsed · 3 selected*. An answer with nothing to narrow to draws
  no button. **It is disabled when it would keep everything in view** — no conditions and no ranking, a relation
  that is a type alone, and bars over every category of their column (none missing against the
  field's `distinct`, none null) — and its tooltip and description say so: *This answer keeps
  everything in view*.
- **Add to the dashboard** is drawn when the host passes `dashboards` and `onAdd`, which go together.
  `dashboards` is the host's [document](/docs/analytics/dashboard-spec#dashboards), a spec per
  relation, as it draws it. `onAdd` is called with the whole next document — the tile appended to the
  answer's relation's spec, or to its automatic dashboard when it has none, as `Dashboard` would draw
  it — and where it landed: `{ relation, key, id }`, the relation, its `relationKey` and the tile's id.
- **Open on the dashboard** takes its place once the tile is there, when the host passes `onOpen`: it
  is called with the same `{ relation, key, id }`, and the host switches to its dashboard view of the
  relation and brings the tile into view. Without `onOpen` the button says *On the dashboard*,
  disabled.

The tile goes on under the answer's own id, so **whether it is on the dashboard is read from
`dashboards`**, not kept by the card: a remounted card still offers *Open on the dashboard*, and once
the reader removes the tile and that is saved, the card offers the add again. When `onAdd` returns a
promise, the button is pending until it settles — whatever `dashboards` already shows — and a
rejection is drawn as a [`Problem`](/docs/data-display/problem) under the tile, the thrown value
whole, with the button back. `describe` is the host's words for a coded one, as `Chat` takes them. *On the dashboard* reads the host's `dashboards` and nothing else, so a host that draws the tile
before its write settles is saying it is there: it rolls the document back when the write fails, and
the card follows and offers the add again. The card says it
where the reader pressed, so a host that also toasts every failed save says it twice.

An add is a decision, not an edit: write it at once, as `useDebouncedCommit`'s `commit` does, with
any edit pending in the dashboard's editor, which it was made over. When a page has both, **one store
holds the document for the dashboard's editor and for Ask**: `dashboards` is the editor's draft, so an
answer added while a tile is being edited lands on the edit rather than on what the server held.

```tsx
// `save` is a mutation whose `onError` reports a failed write, for the edits nobody awaits.
const { draft, change, commit } = useDebouncedCommit(saved, (next: Dashboards) => save.mutateAsync(next), 800);

<AnswerCard
  dashboards={draft}
  graph={graph}
  onAdd={(next) => commit(next)} // the write, which the button waits on
  onOpen={({ relation, id }) => {
    setRelation(relation); // the dashboard view, onto the relation the tile landed on
    setView("dashboard");
    setFocused(id); // the tile, brought into view
  }}
  answer={answer}
  stopped={stopped}
/>
```

`commit` answers what `onCommit` answered, so the card waits on the save itself. The editor's
`change` goes through the same `onCommit` after its pause, where nobody awaits it.

Before there is an answer, and when there will be none:

- **While the engine reads the answer** — the part written once, without its rows — the card is
  `aria-busy`, over a skeleton the chart's height, so nothing jumps when the tile lands. Once the rows
  land the tile is drawn at once: its fields are the ones the model was told, the graph's, and nothing
  more is read for them.
- **A read that stopped** (`stopped`, from `Chat`'s `data` renderer: the message will be written no
  more) draws nothing that waits; the chat's own error says why.
- **A kept answer the host's graph can no longer draw is a [`Problem`](/docs/data-display/problem)**
  under the card's title, *The answer failed*.

Under the tile, one line says what the read was under, as the model was told: *Read under the page's
filter: gender female. Not applied, as this relation lacks the fields they filter: City.name
Madrid (City.name).* It is the read's, when it ran — the tile follows the page afterwards — and there
is no line when the page had no filter.

| Prop | Type | |
| --- | --- | --- |
| `answer` | `AnswerOutput` | What a `data-answer` part holds, read or still being read |
| `graph` | `JoinGraph` | The graph Ask was given |
| `stopped` | `boolean` | The read will never land — `Chat`'s `stopped` |
| `dashboards` | `Dashboards` | The host's dashboards, as it draws them: whether the tile is on its relation's. With `onAdd` |
| `onAdd` | `(next: Dashboards, added: AnswerAdded) => void \| Promise<unknown>` | Makes *Add to the dashboard* an action. With `dashboards` |
| `onOpen` | `(added: AnswerAdded) => void` | Makes *Open on the dashboard* the action once the tile is there. With `onAdd` |
| `describe` | `ProblemProps["describe"]` | The host's words for a coded failure |
| `translations` | `Partial<AnswerCardTranslations>` | Every word it draws |

## Testing

`AnswerHarness` from [`@kanzo-tech/testing`](/docs/testing) asks through the composer and reads the
newest `AnswerCard`. It waits for the card to stop being `aria-busy`, which it is until its rows land
and its tile or its `Problem` is drawn, and a failed answer rejects with the `Problem`'s words. `addToDashboard()`
waits out the host's pending write for *Open on the dashboard*, and rejects with the card's `Problem`
when the host refused it; `openOnDashboard()` presses it. `filterTo()` rejects when the answer keeps
everything in view.

```ts
import { AnswerHarness } from "@kanzo-tech/testing";

const answers = await env.getHarness(AnswerHarness);
await answers.ask("What does the Amber Hall hold, by kind?");
await (await (await answers.answer()).chart()).settled();
await answers.filterTo();
```

## Installing it

A subpath, because it draws with `@kanzo-tech/ui`'s [analytics](/docs/analytics/charts) and table
layers, whose engines are optional peers: a host that only chats does not install DuckDB to import
`Chat`. A host of `/data` installs those layers' peers, plus its own:

```bash
pnpm add @kanzo-tech/mosaic @tanstack/react-query
```

Ask's reads — an answer's rows in `useAskChat`, a relation's fields in `AnswerCard` — are queries on
your `QueryClient`, so one `QueryClientProvider` sits above the page, as it does for a
[dashboard](/docs/analytics#what-to-install). Without it those hooks throw TanStack's own *No
QueryClient set*. `Chat` and `Assist` from `@kanzo-tech/ai`'s root read nothing through it and need
neither the package nor the provider.

```tsx
<QueryClientProvider client={queries}>
  <MosaicProvider engine={e} joins={graph}>
    <AskPanel />
  </MosaicProvider>
</QueryClientProvider>
```

The types are exported as `Answer`, `AnswerRelation`, `UnansweredClause`,
`AnswerOutput`, `QueryRow`, `AskChatOptions`, `AskChatTranslations`, `AskMessage`,
`AskOutput`, `AskTurn`, `AskChip`, `AskChipsProps`, `AskInput`, `AskSpec`, `AskContext`,
`AnswerAdded`, `AnswerCardProps` and `AnswerCardTranslations`.
