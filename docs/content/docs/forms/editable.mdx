```text
├── EditableArea

│   └── EditableInput
└── EditableControl

    ├── EditableCancelTrigger
    └── EditableSubmitTrigger
```

## Usage

```tsx
import {
  Editable,
  EditableArea,
  EditableCancelTrigger,
  EditableControl,
  EditableEditTrigger,
  EditableInput,
  EditablePreview,
  EditableSubmitTrigger,
} from "@kanzo-tech/ui";
```

```tsx
<Field>
  <FieldLabel>Contract title</FieldLabel>
  <Editable defaultValue="A wyrm under the granary">
    <EditableArea>
      <EditableInput asChild>
        <Input />
      </EditableInput>
      <EditablePreview />
    </EditableArea>
    <EditableControl>
      <EditableCancelTrigger asChild>
        <Button aria-label="Cancel" size="icon-md" variant="outline">
          <XIcon />
        </Button>
      </EditableCancelTrigger>
      <EditableSubmitTrigger asChild>
        <Button aria-label="Save" size="icon-md" variant="outline">
          <CheckIcon />
        </Button>
      </EditableSubmitTrigger>
    </EditableControl>
  </Editable>
</Field>
```

`EditableInput` and the triggers render bare: compose them over a styled `Input` (or `Textarea`)
and `Button` with `asChild`. Inside a `Field`, the label points at the input and the field's
`disabled`, `invalid`, `readOnly` and `required` reach the editable. Ark shows the edit trigger at
rest and the submit/cancel pair while editing, so neither needs a conditional.

## Submit modes

`submitMode` decides what saves: `"both"` (the default) saves on Enter and on clicking away,
`"enter"` reverts on clicking away, `"blur"` ignores Enter, and `"none"` leaves it to
`EditableSubmitTrigger`. Escape always cancels.

## API Reference

### Editable

Root. Manages edit mode and the value.

| Prop | Type | Default |
| --- | --- | --- |
| `activationMode` | `"focus" \| "click" \| "dblclick" \| "none"` | `"focus"` |
| `submitMode` | `"both" \| "enter" \| "blur" \| "none"` | `"both"` |
| `orientation` | `"horizontal" \| "vertical"` | `"horizontal"` |
| `selectOnFocus` | `boolean` | `true` |

`orientation` is ours, mirrored to `data-orientation`. The rest is Ark's, and so is everything
`React.ComponentProps<typeof ArkEditable.Root>` carries: `value` / `defaultValue`,
`onValueChange` / `onValueCommit` / `onValueRevert`, `edit` / `defaultEdit` / `onEditChange`,
`placeholder`, `maxLength`, `autoResize`, `disabled`, `invalid`, `readOnly`, `required`, `name`,
`form` and `ref`.

### EditablePreview

The value at rest.

| Prop | Type | Default |
| --- | --- | --- |
| `size` | `"sm" \| "md" \| "lg" \| "xl"` | `"md"` |
| `variant` | `ButtonProps["variant"]` | `"outline"` |
| `title` | `string` | the value, when truncated |

It is styled with `buttonVariants` at `clickEffect: false`, so it already looks like the control it
is about to become. There is no `xs`, for the reason [`Button`](/docs/actions/button) has none.

### Other parts

`EditableArea` and `EditableControl` take their Ark part's props. `EditableInput` and the three
triggers render bare — pass a styled `Input` / `Textarea` or `Button` with `asChild`;
`EditableInput` omits the native `size` attribute, the way [`Input`](/docs/forms/input) does.
`useEditable` re-exports Ark's `useEditableContext`.

`EditableProps`, `EditablePreviewProps` and `EditableInputProps` are exported, so a wrapper can
take the same props without restating them.
