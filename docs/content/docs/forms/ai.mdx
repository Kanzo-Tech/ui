There is no "AI component". Model assistance in this library is two props you declare on a
[`Field`](/docs/forms/field), each backed by a thin `AiAssist` provider that any control inside
the field can pick up:

- **Inline ghost completion** — `<Field complete>`. The surface opts in with `aiComplete`
  (`Input` for one line, `Textarea` for prose) and grows a greyed continuation as you type; Tab
  accepts, Esc dismisses.
- **Candidate suggestions** — `<Field suggest existing onPick>` plus a **`FieldSuggest`** part: a
  ✨ button that opens a streamed menu of candidates, reading the source from the provider.

Both rest on one engine, `useAiStream`, and one contract — a function returning an async
iterable, cancelled by an `AbortSignal`. That contract is worth understanding once.

## The library never calls a model

Everything takes a **function that returns an async iterable**, and cancels it with an
`AbortSignal`:

```tsx
// `complete` — yields continuation chunks of one value
complete: (value: string, signal?: AbortSignal) => AsyncIterable<string>

// `suggest` — yields discrete candidates
suggest: (signal?: AbortSignal) => AsyncIterable<Suggestion>
```

No API key, no provider, no prompt, no model name anywhere in the library. That is not an
oversight — it is what keeps this domain-free. Your product owns the model, the prompt, the auth
and the cost; the library owns the interaction.

It also means it works with anything that streams: a hosted model, a local one, a plain `fetch`
of a cached list, or a hard-coded array in a test.

## Why an async iterable

Because suggestions arrive over time and the user keeps typing while they do. An async iterable
is the smallest contract that gets both right:

- **Partial results render immediately.** The first chunk is on screen before the last one
  exists, which is the difference between a completion feeling instant and feeling broken.
- **Cancellation is built in.** Every keystroke invalidates the request in flight. The stream is
  aborted before the next one starts, so a slow response for text the user has already changed
  can never overwrite what they are typing now.

<Callout type="warn">
**Honour the `AbortSignal`.** If your implementation ignores it, stale responses keep arriving
and nothing can protect you from them — you get suggestions for text that no longer exists. Pass
it straight through to `fetch`, or check `signal.aborted` between yields.
</Callout>

## Writing one

```tsx
async function* complete(value: string, signal?: AbortSignal) {
  const res = await fetch("/api/complete", {
    method: "POST",
    body: JSON.stringify({ prefix: value }),
    signal,                                  // <- the whole cancellation story
  });

  const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
  while (true) {
    const { done, value: chunk } = await reader.read();
    if (done) break;
    yield chunk;                             // <- continuation, not the full text
  }
}
```

<Callout type="info">
`complete` yields **continuation chunks** — what comes *after* the current text, not the whole
value rewritten. `suggest` yields **whole candidates**, one object per row. The difference is why
the two signatures are not identical: one is completing a single value, the other is producing a
list.
</Callout>

## Inline completion — `<Field complete>` + `aiComplete`

Declare `complete` on the `Field` and opt the surface in with `aiComplete`: `Input` for a single
line, `Textarea` for prose. The surface paints a greyed continuation at the caret via an
`aria-hidden` mirror that tracks its own metrics — the `Input` overlay stays on one line; the
`Textarea` mirror wraps with the field. **Tab accepts, Esc dismisses.** The ghost shows only at
the end of the value (where the mirror can align); elsewhere the `Tab · Esc` hint carries it. The
control stays oblivious — it is a controlled `Input`/`Textarea`, nothing more.

```tsx
<Field complete={complete}>
  <FieldLabel>Title</FieldLabel>
  <Input aiComplete value={value} onChange={(e) => setValue(e.target.value)} />
</Field>
```

<Callout type="info">
`aiComplete` requires a **controlled** `value`, and with no `complete` in context it is a no-op —
`Input` / `Textarea` render exactly as before, no overlay, no extra hooks. The streaming itself is
headless (`useCompletion`, below) and pulls in no editor dependency.
</Callout>

## Candidate suggestions — `<Field suggest>` + `FieldSuggest`

Declare `suggest` (plus `existing` for the live dedup and `onPick` for where a chosen value goes)
on the `Field`, then drop a `FieldSuggest` wherever the ✨ affordance belongs — usually the label
row. It reads the source from the provider, owns only its open state, and renders the streamed
menu (loading / error / empty / list, each row pickable or dismissable).

<ComponentPreview componentName="ai" fileName="example-suggestions" />

The stream is fetched once per open-cycle and cached across reopen, so browsing away and back
does not re-bill the model. Closing the popover mid-load aborts the in-flight request through the
`AbortSignal` and refetches fresh next time. Candidates matching what's already chosen — or each
other, case-insensitively — are dropped before they are ever shown. Pass `renderItem` to control
a row's content, or `title` / `placement` / `label` for the chrome.

## The headless hooks

Underneath both surfaces sit headless hooks. They own the model interaction and nothing else: no
markup, no value, no styling — so you can attach them to a control the library did not
pre-assemble.

| Hook | Drives | What it gives you |
|---|---|---|
| `useCompletion({ complete })` | `Input` / `Textarea` `aiComplete`, and any input | `ghost` / `hasGhost`, `setValue` (debounced request), `request` (immediate, the ✨), `accept()`, `dismiss()`, `clear()` |
| `useSuggestions({ suggest, existing })` | `FieldSuggest`, or a `Popover` you compose | `items`, `loading`, `start()`, `cancel()`, `dismiss(i)` — a deduped, windowed candidate list |
| `useAiStream()` | both of the above | the raw engine: `start` / `restart` / `next` / `idle` / `abort` — reach for it only to build a third interaction |

The `AiAssist` provider that `Field` mounts is nothing more than these two hooks run once and
handed down through context, so a control reads whichever it needs (`useAiFieldOptional()`) without
the field owning its value. You can mount `<AiAssist>` directly to give a bare `Combobox` or
`InputGroup` the same capability without a `Field`.

The contract is exactly the one above — a function returning an async iterable, cancelled by an
`AbortSignal`. The hooks add the debounce, the min-length gate, the dedup and the abort
bookkeeping; they do **not** call a model and do **not** own your input's value.

<Callout type="info">
`useCompletion` deliberately does not hold the text. Your input owns it; `accept()` **returns**
the continuation string for you to insert where you want. That is what lets the same hook drive an
`Input`, a `Textarea`, or an inline `Editable` without any of them fighting over state.
</Callout>

## What none of this does

- **It does not validate.** A suggestion is a value like any other; the field's own validation
  applies unchanged. See [Validation](/docs/forms/validation).
- **It does not persist or debounce your commit.** `useCompletion` debounces its *request*, not
  your save. What you do with the value is yours.
- **It does not explain itself to assistive tech beyond the basics.** The ghost is document
  content with nothing marking it as a suggestion. If a suggestion is material to the task,
  announce it — an `aria-live` region alongside the field is the usual answer.
