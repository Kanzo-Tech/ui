---
title: Onboarding a tenant
description: Two colours in, one JSON out, one stylesheet served — the pipeline you run once per client.
---

There are two onboarding pipelines and they are easy to confuse, so this page is only the second
one.

**[Installation](/docs/installation) is per product, once**: the packages, the stylesheet, the
provider, the pre-paint script. **This is per client, once**: two colours come in, a measured
document goes to your database, and every surface the client ever sees is a reading of it.

The property worth stating before the steps, because it is what the whole shape is for: **adding a
client touches no code and needs no deploy.** A palette is data. If onboarding a tenant ever
requires a build, something above has been wired wrong.

```text
two colours  →  derivePalette()  →  a JSON document  →  compile()  →  one <style> in <head>
  the client       once, at            your database      per request      the attribute chooses
                   onboarding
```

<Steps>

<Step>

### Collect the seeds

A **brand** colour, and optionally a **base** — the neutral that paints most of the pixels. Take
them as the client gives them; nothing here asks for a scale, a ramp or a dark variant.

Leave the base out and it is built from the brand's hue, which is usually what a client with one
brand wants. A tenant publishing **more than one brand** must give a base of their own:
`derivePalette` refuses to carry a brand hue over, because a page tinted with the retail blue is the
wrong ground to paint the private gold on.

</Step>

<Step>

### Derive, once, out of the browser

```ts title="scripts/onboard.ts"
import { derivePalette } from "@kanzo-tech/palette";

const doc = derivePalette({
  id: "acme",
  label: "Acme",
  identities: [{ id: "acme", label: "Acme", brand: "#8839ef" }],
  base: "#9ca0b0",
});
```

A tenant with several brands lists them, and the first is the one `:root` carries unless
`defaultIdentity` names another:

```ts
const doc = derivePalette({
  id: "bank",
  label: "Northgate",
  identities: [
    { id: "retail", label: "Retail", brand: "#1d4ed8" },
    { id: "private", label: "Private", brand: "#a16207" },
  ],
  base: "#8f8f8f",
});
```

<Callout type="warn" title="This runs at onboarding, never at request time">
  The categorical search alone costs seconds per tenant. `@kanzo-tech/palette` is a
  **devDependency** so that is structural rather than a convention — the derivation is not merely
  something a browser should not import, it is something a browser cannot reach. Run this in a
  script, a job, or an admin route; store what it returns.
</Callout>

If the client's identity *is* a published scheme, the seeds and its syntax colours come together:

```ts
import { PALETTE_SEEDS, derivePalette, seedInput } from "@kanzo-tech/palette";

const doc = derivePalette(seedInput("dracula", PALETTE_SEEDS.dracula));
```

</Step>

<Step>

### Read the record, and tell the client what moved

`doc.record` is the part of onboarding that is a conversation rather than a computation. It carries
three lists:

| list | what it is |
| --- | --- |
| `adjustments` | a seed that failed a gate and was moved to the nearest legal value — with the rule, the ΔE and the signed OKLCH components |
| `relief` | an obligation that could not be met by moving anything |
| `crossChecks` | measurements that only exist once six ramps share one page |

An adjustment is what you read back to the client, and the components are why: *"darker, and
slightly less saturated"* is a very different sentence to hear than *"a different colour"*.

<Callout type="warn" title="Relief rows are usually the healthy answer">
  `carries-identity` fires when a ramp's solid step sits below the chroma floor, and **a tinted
  neutral is below that floor by definition** — so every correct two-seed document reports it on the
  base ramp. Distinguish by **ramp**, never by presence: on `base` it means nothing is wrong, on a
  brand it is something to tell the client. A screen that renders any relief as an alert makes every
  correct palette look broken.
</Callout>

A freshly derived document is `state: "draft"`, which is the flag to hang your review step on.

</Step>

<Step>

### Store the document

It is JSON. Put it wherever the tenant's other data lives.

Two fields make a stored document checkable later, and both matter the first time you change the
derivation: `schemaVersion` says which shape it is, and `engine` carries a hash of the obligation
table it was graded against. Compare it with `hashObligations` to find the documents that predate a
rule change and re-derive those, rather than all of them.

```ts
import { PALETTE_SCHEMA_VERSION, hashObligations } from "@kanzo-tech/palette";
```

</Step>

<Step>

### Serve every document, and let an attribute choose

Compile each one under its own scope and inline them together in `<head>`. There is no request-time
colour maths — `compile` is a string join over values that were solved at onboarding.

```tsx title="app/layout.tsx"
import { compile } from "@kanzo-tech/palette";

const css = documents.map((doc) => compile(doc, { scope: doc.id })).join("\n");

<style dangerouslySetInnerHTML={{ __html: css }} />;
```

<Callout type="info" title="Compiling on the server is fine; deriving is not">
  `compile` is cheap and pure, so calling it per request costs little — but the usual shape is to
  compile alongside the derivation and store the CSS too. What must never move to request time is
  `derivePalette`.
</Callout>

A tenant publishing **one** palette can skip the scope entirely: `compile(doc)` emits plain
`:root` / `.dark` blocks, and no attribute is written at all.

Choosing is then `data-palette` on `<html>`, written by the provider and by the pre-paint script
exactly like radius and density. That is the property that makes the choice correctable in the
browser without a flash, and it is why the server does not need to know which palette the user
picked.

</Step>

<Step>

### Offer the choice, if there is one

The panel needs one entry per published choice, with the brands nested inside their palette:

```tsx title="app/layout.tsx"
import type { PaletteOption } from "@kanzo-tech/theme";
import { KanzoThemeProvider } from "@kanzo-tech/ui";

const palettes: PaletteOption[] = documents.map((doc) => ({
  value: doc.id,
  label: doc.label,
  ...(doc.identities.length > 1
    ? { children: doc.identities.map((i) => ({ value: i.id, label: i.label })) }
    : {}),
}));

<KanzoThemeProvider palettes={palettes}>{children}</KanzoThemeProvider>;
```

**An id and a name, and no colour.** The panel draws each entry by setting `data-palette` on the
cell and letting the compiled document paint it — the same mechanism that paints the page, so the
preview cannot disagree with what selecting it will do. Anything you copy out of a document to
depict it can only be the same values or the wrong ones.

Publish one of each and **nothing appears**: [`Preferences`](/docs/layout/preferences) hides its
colour section below two choices, so a client wanting a single immutable brand does nothing to get
one.

<Callout type="info" title="The user chooses among colours, never authors one">
  This is the line that makes several published palettes safe. What a tenant publishes has been
  derived, graded and measured as a whole; what a user picks is one of those. There is no way to
  move *part* of a palette at runtime, and that absence is the feature — see
  [Theming](/docs/theming).
</Callout>

</Step>

<Step>

### Verify

The document grades itself, so verification is reading rather than testing: no unexpected
`adjustments`, `relief` only where the ramp explains it, and `crossChecks` clear.

If your product ships a package that contributes its own appearance tokens — the graph does —
check its payload against the manifest that owns it, which is what catches a name nobody declared
before it paints something plausible:

```ts
import { validateSection } from "@kanzo-tech/theme";
import { LOOK_SECTION } from "@kanzo-tech/graph/look-section";
```

</Step>

</Steps>

## What this costs, measured

The five documents this site publishes are **58 kB raw and 7.6 kB gzipped together**. That number is
the reason the pipeline has the shape above: while a document was assumed too big to ship more than
one of, the server had to choose from the request, the cookie was mandatory, and a choice already
made upstream could not be corrected in the browser without a flash. It was never measured. The
scale is repetitive and compresses hard, so every document travels and the choice became an
attribute.

## A worked example

The [palette showcase](/docs/showcases/palette) runs this pipeline in the browser — seeds in, the
derived document, the record and the compiled sheet, side by side with the authored original. It is
the fastest way to see what a given pair of colours produces before you run it against a real
client.

This site is itself a tenant that publishes several palettes, so `docs/lib/palette.ts` is the same
wiring at product scale: read the compiled documents, inline them once, map them to `PaletteOption`.
