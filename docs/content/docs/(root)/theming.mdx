title: Theming

Theming is `data-*` attributes on `<html>`, whose token values live in static CSS. Change an
attribute and every component re-skins, with no per-component work.

## The axes

| Axis | Attribute | Sets |
| --- | --- | --- |
| palette | `data-palette` | a whole base16 identity: surfaces, neutrals, the 13 syntax roles, `color-scheme` |
| base | `data-base` | the neutral scale (background / card / muted / border) |
| accent | `data-accent` | the six primary/ring tokens |
| scheme | `data-chart-scheme` | `--chart-1` … `--chart-8`, the colours that carry series identity |
| radius | `data-radius` | `--radius`, which drives the whole `rounded-*` scale |
| font | `data-font` | `--font-sans` |
| monoFont | `data-mono-font` | `--font-mono` |
| density | `data-font-size` | the root font-size |

`palette` and `base` overlap: both set the surfaces. A palette wins, because it is the broader
choice — that precedence is source order in the generated CSS, not a rule you can configure.

<Callout type="warn" title="They must be on <html>, not a wrapper">
  Ark's overlays — Dialog, Popover, Menu, Select, Tooltip, Toast, HoverCard, Command — portal
  into `document.body`, outside any element you render. Tokens set on a
  wrapper never reach them. Density is stricter still: it sets the root font-size, and every
  size in the system is `rem`.

  This is why there is exactly one provider. An earlier `KanzoTheme` wrapper component wrote
  the same attributes to a `<div>`; it could not theme a single overlay, and its `density` axis
  did nothing at all. It has been removed.
</Callout>

## Setting them

`KanzoThemeProvider` owns the preferences and writes the attributes:

```tsx
import { KanzoThemeProvider } from "@kanzo-tech/ui";

<KanzoThemeProvider defaults={{ accent: "blue", radius: "md" }}>{children}</KanzoThemeProvider>
```

Read or change them at runtime with `useKanzoTheme()`:

```tsx
const { accent, radius, set } = useKanzoTheme();
set({ radius: "none" }); // square corners everywhere
```

Or drop in the ready-made panel:

```tsx
import { Preferences } from "@kanzo-tech/ui";

<Preferences />
```

<Callout type="info">
  `Preferences` takes an optional `hotkey`. It has no default on purpose — a design system
  should not claim an unmodified key in its host's global keymap without being asked.
</Callout>

## Palettes

A palette is the colour *identity* — you pick "Dracula", not a neutral scale crossed with an
accent. Six ship: `kanzo` and `kanzo-dark`, `dracula`, `nord`, `catppuccin-latte` and
`catppuccin-mocha`.

```tsx
<KanzoThemeProvider defaults={{ palette: "dracula" }}>{children}</KanzoThemeProvider>
```

The shape is [base16](https://github.com/chriskempson/base16): sixteen slots with documented roles,
`base00`–`base07` neutrals and `base08`–`base0F` accents. The 13 `--kanzo-syntax-*` roles are a
*mapping* onto those slots, which is what lets one palette dress an editor and a UI at once.

A palette carries its own appearance. It emits `color-scheme`, so a dark one darkens form controls
and scrollbars without a mode being chosen alongside it, and it declares `pairsWith` — the partner
palette of the same identity, or `null`. Dracula has no partner: it is dark-first, and this library
will not invent a light side for it.

<Callout type="warn" title="A palette publishes its contrast, and some of them fail it">
  Every palette lists the slots that do not clear WCAG AA **as text** on their own background, in
  `relief`. These are properties of the palettes themselves, not of this mapping: Nord's comments
  are 1.7:1 in Nord, and Catppuccin Latte is low-contrast by design with eight slots under the bar.
  Unlike a chart scheme there is no relief channel to trade against, because every slot renders as
  text. `kanzo` and `kanzo-dark` clear everything.

  ```tsx
  import { PALETTES } from "@kanzo-tech/theme";

  PALETTES.nord.relief; // ["base03", "base08", "base09", "base0E", "base0F"]
  ```
</Callout>

A palette deliberately does not set `accent`, the status colours, or the chart scheme. base16
nominates no primary, so taking one would invent brand from a syntax slot; its red/yellow/green
slots mean *strings* and *classes*, so wiring them to destructive/warning/success would let a
palette say "this succeeded" in whatever hue it uses for literals; and a chart scheme is
[derived](/docs/data-display/charts) from a palette's hues and then measured, because no named palette passes the
categorical checks in its own values.

## Dark mode

Not owned by this library. The host toggles `.dark` on `<html>` and the generated dark rules
key off that ancestor. If you already run a theme manager, hand it over — the shape matches
next-themes:

```tsx
import { useTheme } from "next-themes";

const { resolvedTheme, setTheme } = useTheme();
<KanzoThemeProvider appearance={{ resolvedTheme, setTheme }}>{children}</KanzoThemeProvider>;
```

Omit the prop and the provider's built-in fallback toggles `.dark` itself. These docs use the
first form, handing fumadocs' theme manager to the provider.

## Tokens

Two families, two different rules — this trips people up, so it is worth stating plainly.

**Neutral and brand**: the base name is the FILL, and `-foreground` is the text that sits ON
that fill. `bg-primary text-primary-foreground` is a readable pair.

**Status** (`destructive` / `info` / `success` / `warning`): three tokens, not two, and the extra
one is the point. `-foreground` is a readable-on-**background** variant of the same hue — for error
text, invalid rings and destructive menu items. That it is not readable *on the fill* is not a
contrast bug; it is Shark's convention, adopted verbatim.

So on-fill text gets its own token, `-content`. `bg-destructive text-destructive-content` is the
readable pair. It used to be a literal `text-white`, described as the one sanctioned exception to
"token-backed utilities only" — and the exception is where the defect hid: measured, that white sat
at 2.13:1 on the warning fill and 3.81 on destructive. With no token there was nothing to measure,
and with nothing to measure there was no failing test.

<Callout type="warn" title="The status fills sit at -600, which is a declared divergence">
  Two measurements forced it, and both are re-run by `palettes.test.ts`. red-500 carries neither
  white (3.81) nor near-black (4.15) at AA, so no choice of ink rescues it — the fill had to move.
  And emerald-500/amber-500 land at 2.37 and 2.05 against the page, so a filled badge was barely
  visible *as a shape*, under the 3:1 WCAG asks of a non-text element.

  The ink is then split by measurement rather than by rule: `destructive` and `info` hold white,
  `success` and `warning` take near-black. Same choice in both modes, so a badge does not change its
  criterion when the mode flips.
</Callout>

## Generated themes

`themes.css` and `theme-data.json` are generated by `scripts/gen-theme.mjs` from Shark's exact
per-hue values. **Edit the generator, not the output** — CI regenerates and fails on any diff.
