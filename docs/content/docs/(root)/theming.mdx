title: Theming
description: Four user axes as data-* attributes on <html>, and colour as a per-tenant palette document.
---

Two different things wear the word "theme", and this page is mostly about keeping them apart.

**What a user chooses** is four axes plus appearance: how round, how dense, which typefaces,
light or dark. Those are `data-*` attributes on `<html>` whose values live in static CSS.

**What a client is** is a colour identity, and that is not an axis at all. It is a **palette
document** — derived and measured once at onboarding, stored as data, and applied at runtime as
one compiled stylesheet. Adding a client touches no code and needs no deploy.

## The user axes

| Axis | Attribute | Sets |
| --- | --- | --- |
| radius | `data-radius` | `--radius`, which drives the whole `rounded-*` scale |
| font | `data-font` | `--font-sans` |
| monoFont | `data-mono-font` | `--font-mono` |
| density | `data-font-size` | the root font-size, which every `rem` in the system scales from |

Appearance is the fifth preference and the only colour-adjacent one, and it writes a **class**,
not an attribute: `.dark` on `<html>`. It selects between the two blocks of the compiled
document rather than between two identities, which is why it is a user preference and a hue
is not.

<Callout type="warn" title="They must be on <html>, not a wrapper">
  Ark's overlays — Dialog, Popover, Menu, Select, Tooltip, Toast, HoverCard, Command — portal
  into `document.body`, outside any element you render. Tokens set on a
  wrapper never reach them. Density is stricter still: it sets the root font-size, and every
  size in the system is `rem`.

  This is why there is exactly one provider. An earlier `KanzoTheme` wrapper component wrote
  the same attributes to a `<div>`; it could not theme a single overlay, and its `density` axis
  did nothing at all. It has been removed.
</Callout>

### Setting them

`KanzoThemeProvider` owns the preferences and writes the attributes:

```tsx
import { KanzoThemeProvider } from "@kanzo-tech/ui";

<KanzoThemeProvider defaults={{ radius: "md", density: "compact" }}>{children}</KanzoThemeProvider>
```

Read or change them at runtime with `useKanzoTheme()`:

```tsx
const { radius, set } = useKanzoTheme();
set({ radius: "none" }); // square corners everywhere
```

Or drop in the ready-made panel:

```tsx
import { Preferences } from "@kanzo-tech/ui";

<Preferences />
```

<Callout type="info">
  `Preferences` takes an optional `hotkey`. It has no default on purpose — a design system
  should not claim an unmodified key in its host's global keymap without being asked.
</Callout>

## Colour: the palette document

There is one colour artefact per tenant and everything reads it — `--primary`, the surfaces,
the charts, the graph, the editor. There is no place to configure a chart's colours; there is a
palette, and the chart is a reading of it.

```text
two seeds  →  six ramps × two modes  →  the role table  →  compile()  →  one <style>
brand      →  brand, neutral,        →  65 tokens       →  ~4 KB      →  :root { … }
neutral    →  destructive, warning,                                      .dark { … }
              success, info
```

**Two seeds, from the client.** A brand colour and a neutral. The neutral is *tinted* — a low
chroma at a hue, Radix-style — and it supplies that hue; the brand hue is the fallback when
none is given. The four status families (`destructive` / `warning` / `success` / `info`) are
fixed by Kanzo and are not client-overridable, because "this succeeded" must not change meaning
per client. They are still **re-measured** per tenant: every obligation is graded against the
surface, and the surface is the tenant's neutral. Constant input, per-tenant verdict.

**Six ramps, twelve steps each, per mode.** Nothing in a ramp is chosen per token: three anchors
and a growth rate produce twelve values, and each step carries a measured obligation —
steps 1/2 are the page and its interchangeable twin, 3/4/5 are one component's normal / hover /
active surface, 6–8 are borders, 9 is the solid, 11/12 are ink. Light and dark are separate
generations, not a flip: a tint has to work harder against a dark ground, and the measured
chroma profiles say so.

**The role table** binds tokens to `(ramp, step)` — with three things that are *measured* rather
than written, because writing them would be wrong for most seeds:

| token | binding |
| --- | --- |
| `--background` `--card` `--popover` `--sidebar` | `(neutral, 1)` at a per-surface elevation |
| `--foreground` `--secondary-foreground` `--accent-foreground` | `(neutral, 12)` |
| `--muted` / `--muted-foreground` | `(neutral, 3)` / `(neutral, 11)` |
| `--faint` | `(neutral, 10)` |
| `--secondary` / `--accent` | `(neutral, 4)` / `(neutral, 5)` |
| `--border` | `(neutral, 6)` |
| `--input` | `(neutral, boundary)` |
| `--field` / `--secondary-wash` / `--accent-wash` | `(neutral, alpha 3 / 4 / 5)` |
| `--primary` / `--primary-foreground` | `(brand, fill)` / `(brand, on-fill)` |
| `--ring` | `(brand, boundary)` |
| `--destructive` / `-foreground` / `-content` | `(destructive, 9)` / `(…, 11)` / `(…, on-fill)` |
| `--destructive-wash` / `-wash-strong` / `-border` | `(destructive, alpha 3 / 4 / 6)` |
| `--chart-1` … `--chart-8` | categorical slot *i* |
| `--kanzo-syntax-*` | fixed — Kanzo's own, cross-checked per tenant |

### A wash is a level, painted onto something you do not own

Eight of those rows are alpha steps, and they exist because a library component does not know
what it was dropped onto. `bg-accent/50` on an accent backdrop measures ΔE **0.00** from the rest
state — a hover nobody can see — and solid `bg-secondary` measures 0.00 on a secondary one.
A percentage fails a second way as well: mapped onto the family's own alpha scale, `/4` is a3 in
light and a2 in dark, `/10` a4 and a3, `/20` a5 and a4, `/32` a6 and a5, because a tint has to
work harder against a dark ground. **Every `bg-X/NN` is correct in at most one mode.** A wash is
resolved against each mode's own ramp at derivation time, so one binding is right in both, and it
composites back to its own solid over the page by obligation.

The washes are named for the **level**, never for the state — `--accent-wash` is what `--accent`
is when the backdrop is unknown. The same two values are a card's hover, a calendar day's focus
and a table row's selected state, and a token named for the first of those would force the second
to mint a duplicate. `--field` is the a3 member under the name the `--input` split gave it.

`boundary` is the first step reaching 3:1 against step 1, and it is **seed-dependent, not
mode-determined**: measured over 118 seeds it is 9 in light for 97 of them and 8 for the rest,
8 in dark for 82 and 9 for the rest. A table that hard-coded `--ring: step 8` would be correct
for most clients and 2.3:1 for the others, with nothing saying so.

`on-fill` is whatever measures highest contrast on the solid, with no "prefer white when legal"
escape hatch — which is why Kanzo's own `--warning-content` is a near-black.

`fill` is step 9 normally, and step 12 for a ramp that carries no identity — see below.

### Elevation, not more tokens

A raised surface is the same ramp at an offset into the same band, and only in dark: light
expresses elevation with shadow, dark with value. Measured against the neutral ramp: page +0/+0,
card +0/+1, popover +0/+2, sidebar +0/+2, clamped at 5 so a raised surface can never climb into
the border band.

That is what "the sixteen `--sidebar-*` tokens are a surface parameter, not twelve more steps"
means: a sidebar and a popover are the same thing.

### A failing gate adjusts, and publishes what moved

Never accept-and-warn, never refuse. A client's brand red at 2.1:1 becomes a legal red of the
same hue, and the document carries the record of that happening — from, to, the rule that forced
it, ΔE, and the signed OKLCH components, so a person can be told "darker, and slightly less
saturated" rather than "a different colour".

There is exactly **one** obligation that can never become an adjustment: `carries-identity`,
which fires when step 9 sits below the chroma floor of 0.1. A colour below the floor has no
nearest legal value — the nearest chromatic colour would be a hue *we* chose — so it is published
as **relief** instead.

<Callout type="warn" title="Relief on the neutral ramp is the healthy answer">
  A tinted neutral is *by definition* below the chroma floor, so `carries-identity` fires on
  every one of them, by design. On the **brand** seed it is a warning: a monochrome brand has
  nothing but lightness to spend, so `--primary` takes step 12 (the ramp's ink) rather than
  step 9 (a mid-tone that reads as nothing). On the **neutral** seed it is the expected answer
  and means nothing is wrong.

  Distinguish by ramp, never by presence. Kanzo's own document publishes four relief rows and
  zero adjustments — see the [palette onboarding showcase](/docs/showcases/palette).
</Callout>

### One mechanism at runtime

`compile(doc)` emits `:root { color-scheme: light; … }` and `.dark { color-scheme: dark; … }` —
both modes, every colour token, literal hex, about 4 KB. The tenant is known at request time, so
the server inlines it as a static `<style>` in `<head>`: the colour maths is finished before a
byte is sent, and the pre-hydration script shrinks to reading the appearance preference,
toggling `.dark`, and writing the four non-colour axes.

```tsx
import { compile, derivePalette } from "@kanzo-tech/palette";

// once, at onboarding — the categorical search alone costs 0.2–7.4 s
const doc = derivePalette({ id: "acme", label: "Acme", brand: "#8839ef", neutral: "#9ca0b0" });

// every request — just the string
<style dangerouslySetInnerHTML={{ __html: compile(doc) }} />;
```

<Callout title="Two packages, because the boundary is the point">
  The derivation lives in **`@kanzo-tech/palette`** and nothing else does — ramps, the
  categorical search, the role table, `compile`. **`@kanzo-tech/theme`** is the runtime half:
  the stylesheets, the four non-colour axes and the preference types. `theme` depends on
  `palette` as a *devDependency*, so the 0.2–7.4 s search is not merely something a browser
  should not import — it is something a browser *cannot* reach.

  Install `@kanzo-tech/palette` where you onboard a tenant. A product that only paints with a
  stored document never needs it.
</Callout>

<Callout type="warn" title="data-palette, data-base, data-accent and data-chart-scheme are gone">
  All four were ways to express *part* of a palette at runtime, and a document expresses all of
  it at once. There is no custom-base-tint path, no custom-primary path, no inline
  `--color-custom-*` and no inline `--chart-*` override. There is also no palette *pairing*
  (`pairsWith`, `resolvePalette`, "pinned" palettes): a document carries both modes, so there is
  no pair to resolve.
</Callout>

### base16 identities are seeds now

Dracula, Nord and the two Catppuccins ship as `PALETTE_SEEDS`, and they go through
`derivePalette` exactly as a client does. They are not a second shape — a base16 palette is a
brand hue and a neutral hue, and two shapes for one idea is the defect this layer exists to
remove.

```tsx
import { PALETTE_SEEDS, derivePalette, seedInput } from "@kanzo-tech/palette";

const doc = derivePalette(seedInput("dracula", PALETTE_SEEDS.dracula));
```

The old rule — "a palette may be dark-only; do not invent a light side for Dracula" — was true
when a palette was a set of authored hexes. Under derivation it is not: a ramp keeps a foreign
seed's *hue* and gives up its mood, so a light Dracula is a **reading** rather than an
invention. Measured: Dracula's brand `#ff79c6` ships as `#e562af` at step 9, moved 7.3 ΔE by the
`visible-fill` rule.

`BASE16_SLOTS` still holds the sixteen authored slots, and two things read them: the
thirteen `--kanzo-syntax-*` roles, which are a *mapping* onto base16's slot vocabulary, and the
[showcase](/docs/showcases/palette) that puts the authored original beside the derived result.

## Dark mode

`.dark` on `<html>` is the only mode selector, and `KanzoThemeProvider` writes it. Hand it to a
host theme manager if you already run one — the shape matches next-themes:

```tsx
import { useTheme } from "next-themes";

const { resolvedTheme, setTheme } = useTheme();
<KanzoThemeProvider appearance={{ resolvedTheme, setTheme }}>{children}</KanzoThemeProvider>;
```

Omit the prop and the provider's built-in fallback toggles `.dark` itself, which is what these
docs do.

<Callout type="info" title="Why a class and not light-dark()">
  Two reasons, both measured. About 150 `dark:` variants need a class to key off; and
  `light-dark()` makes per-mode values unreadable to `getComputedStyle`, which is exactly how
  the [charts layer](/docs/data-display/charts) resolves `var(--chart-N)` for Observable Plot.
  Each compiled block carries its own `color-scheme`. Never write
  `documentElement.style.colorScheme` — an inline declaration outranks every rule, permanently.
</Callout>

## Tokens

Two families, two different rules — this trips people up, so it is worth stating plainly.

**Neutral and brand**: the base name is the FILL, and `-foreground` is the text that sits ON
that fill. `bg-primary text-primary-foreground` is a readable pair.

**Status** (`destructive` / `info` / `success` / `warning`): three tokens, not two, and the extra
one is the point. `-foreground` is a readable-on-**background** variant of the same hue (step 11)
— for error text, invalid rings and destructive menu items. That it is not readable *on the fill*
is not a contrast bug; it is Shark's convention, adopted verbatim.

So on-fill text gets its own token, `-content`, bound to the ramp's measured `on-fill`.
`bg-destructive text-destructive-content` is the readable pair. It used to be a literal
`text-white`, described as the one sanctioned exception to "token-backed utilities only" — and
the exception is where the defect hid: measured, that white sat at 2.13:1 on the warning fill and
3.81 on destructive. With no token there was nothing to measure, and with nothing to measure
there was no failing test.

## Generated output

`themes.css` and `theme-data.json` are generated by `scripts/gen-theme.mjs`; `palettes/` and the
colour half of `tokens.css` are generated by `scripts/gen-palette.mjs` — `palettes/kanzo.json` is
a tenant whose document happens to be committed, nothing more. **Edit the generator, not the
output** — CI regenerates and fails on any diff.
