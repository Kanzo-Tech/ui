<Callout type="warn">
**Feasibility probe, not a documented feature.** This page exists to answer one question: can a
node-link view participate in the same crossfilter as the rest of the charts, without a new
rendering client? Nothing here is exported from the library.
</Callout>

## The premise

A force layout is a function from a graph to two numbers per node. Run it once, store the result as
`x` and `y` **columns**, and a node-link view stops being a special renderer: it is a scatter plot
of a node relation with a `link` mark of an edge relation underneath.

Two relations, both plain DuckDB tables in the shared coordinator:

```sql
-- graph_nodes: id, category, degree, weight, x, y

CREATE OR REPLACE VIEW graph_edges AS
  SELECT s.id, s.category, s.degree, s.weight, s.x, s.y, t.x AS x2, t.y AS y2
  FROM graph_edge_pairs e
  JOIN graph_nodes s ON e.source = s.id
  JOIN graph_nodes t ON e.target = t.id;
```

The edge relation carries its **source** endpoint's columns under the node table's own names. That
is the whole crossfilter trick: a Mosaic clause is SQL over column names, so `weight BETWEEN 30 AND
50` lands on the edge relation without anyone teaching it what an edge is.

## Crossfilter, both directions

Drag a rectangle over the graph and the histogram and bars redraw — the lasso publishes
`id IN (…)`. Drag the histogram, or click a cluster bar, and nodes *and* edges drop out of the
graph.

No escape hatch anywhere in it. The two relations meet in one plot because a mark may name its own
`table`, so the edges are `<ChartLink table="graph_edges" x1="x" y1="y" x2="x2" y2="y2" />` and the
nodes are a `<ChartDot>` over the root's table. Everything else — the lasso, the dimming, the
tooltip, the legend — is vocabulary that already existed.

## Where it stops scaling

Observable Plot emits SVG, one element per mark datum. This is the same view with the ghost layers
removed, instrumented with the element count, the first paint and the time from a crossfilter
change to a rebuilt plot.

<ComponentPreview componentName="charts" fileName="example-graph-scale" hasMaxHeight={false} />

Measured in Chrome on an M-series laptop, warm (DuckDB booted, relations already built):

| nodes / edges | force layout | csv → duckdb | svg elements | first paint | filter → repaint | scroll |
| --- | --- | --- | --- | --- | --- | --- |
| 200 / 395 | 36 ms | 25 ms | 609 | 141 ms | 5 ms | 60 fps |
| 2 000 / 4 018 | 168 ms | 17 ms | 6 032 | 71 ms | 27 ms | 60 fps |
| 20 000 / 40 256 | 999 ms | 49 ms | 60 270 | 148 ms | 237–281 ms | 60 fps |

Nothing here is the wall. 60 000 SVG elements still scroll at 60 fps, a lasso's hit test over 40 256
elements costs 15 ms, and a crossfilter repaint stays under a third of a second. What actually
breaks is **legibility**: by 2 000 nodes the edge layer is already a fog, and at 20 000 the picture
is three coloured blobs joined by a white haze. The graph stops being readable an order of magnitude
before it stops being fast.

The one cost that grows superlinearly is the layout itself — and in a system that stores positions
as a column, that cost is paid once, offline, not by the browser.

## Above the ceiling: a WebGL renderer on the same crossfilter

Route A ends where a frozen layout does. Two things it structurally cannot do are **live layout** —
the simulation keeps running, so a filter can reshape the graph rather than just thin it — and
**continuous pan/zoom**, since Plot rebuilds the whole SVG on every transform.

[`@cosmos.gl/graph`](https://github.com/cosmosgl/graph) does both on the GPU, and it is a renderer,
not a Mosaic client. Making it one is ~60 lines, because `MosaicClient` asks for exactly two things:

```ts
class CosmosClient extends MosaicClient {
  // Observable: which rows survive the page's filters? Everything else is greyed out.
  query(filter) {
    return Query.from(this.table).select({ id: this.idField }).where(filter);
  }
  queryResult(data) { this.greyOutAllBut(column(data, "id")); return this; }

  // Controllable: the lasso publishes what it hit, and every other chart filters by it.
  publish(ids) {
    this.as.update(clausePoints([this.idField], ids?.map((id) => [id]), { source: this }));
  }
}
```

That is the same contract `ChartFilter` and `ChartSlider` implement — a control is Mosaic because it
declares a query and publishes a clause, not because it draws with Plot.

`column` is the one part of that the protocol does not hand you, which is why it is now exported
from `@kanzo-tech/ui/analytics` alongside `MosaicClient` itself. The coordinator answers with an
Arrow table, and Arrow only offers a typed column when the type allows one — `getChild` returns an
array for an integer `id` and nothing usable for a dictionary-encoded `label`. Every client that
implements `queryResult` meets both shapes, so the cast that looks like it works is a crash waiting
for the first query that selects a string.

### Why the lasso can only speak in ids

A Plot brush publishes `weight BETWEEN 30 AND 50` — an interval in data space — because Plot's `x`
*is* a column. cosmos.gl's `x` is a GPU simulation: the position exists nowhere in the database, so
no predicate over columns can describe the loop the user drew. Enumerating the hits is the only
honest translation, and its cost is the length of the `IN` list. That, not the frame rate, is this
route's ceiling.

### The one thing the greyout changed

A crossfilter normally exempts a client from its own clause, so you can widen a brush after it has
collapsed the chart underneath it. This client declines the exemption (`clients: new Set()`), because
cosmos.gl *greys* an excluded point instead of removing it — it is still on screen, still lassoable,
and the greyout is therefore the only brush the view needs to draw.

## Where this ended up

The [Workspace showcase](/view/showcases/workspace) now draws its discovery canvas this way. Route A
stays here, as the measurement that explains why: the frozen layout is legible to about two thousand
nodes and cannot pan continuously, and both of those are the reader's problem rather than the
renderer's.

What the showcase adds on top is appearance and gesture, not architecture — three interchangeable
looks, degree-scaled points, hub labels tracked frame by frame, hover and focus rings, a cluster
force keyed to `dcat:theme`, and force coefficients wired to live sliders. None of it queries: a
look is a `setConfig` and four buffer uploads, so the whole panel of controls costs zero round
trips. The only two gestures that reach SQL are still the lasso and a click.

<Callout>
Half of it went in, and finding out which half was the useful part. The objection on file was that
this drags an optional WebGL peer — but the client does not. `CosmosClient` imported nothing from
`@cosmos.gl/graph`; what it modelled was a view whose positions live outside the database, which
can therefore only ever publish an enumerated set of ids. That is a canvas, a map or any imperative
widget, so it ships as **`IdSetClient`** on `@kanzo-tech/ui/analytics`, named for what it exchanges
rather than for the renderer it was first written against.

What genuinely needs the peer is the canvas — the simulation, the looks, the gestures — and a
component that renders nothing without WebGL is still a poor fit for a design system that has so
far promised to work everywhere. That stays here.
</Callout>

## The Rules panel, in both directions

The showcase's Rules dock reads a SHACL shapes file, compiles the subset a column-shaped relation
can answer into `count(*) FILTER (WHERE …)`, and publishes the ids of a failing shape into the
crossfilter — so focusing a violation lights up the offending nodes on a canvas the panel never
imports.

The builder is that path run backwards. Picking a target class, a property path, a constraint and a
severity appends a `sh:property` block to the *same document*, which is then parsed and compiled by
the same code that reads an uploaded file. There is no second model: what the menus produce is
Turtle, and the panel's Source view shows the file you could have written by hand.

```turtle
kanzo:DatasetShape
  a sh:NodeShape ;
  sh:targetClass dcat:Dataset ;
  sh:property [
    sh:path dcat:keyword ;
    sh:maxCount 8 ;
    sh:severity sh:Info ;
  ] .
```

Two consequences are worth stating, because both are refusals rather than features.

The menus offer only the paths and targets the compiler maps, so a built rule always compiles —
the builder cannot express a constraint the report would then have to disown.

And it edits nothing it cannot write back whole. Regenerating a document drops whatever the reader
could not represent, so a file carrying an `sh:or`, a named property shape or a second shape on one
target puts the panel in read-only and names what it is protecting. A validator that quietly loses
half a shapes file is precisely the failure this panel exists to argue against; a builder that
quietly loses half of one is the same failure wearing a nicer hat.
