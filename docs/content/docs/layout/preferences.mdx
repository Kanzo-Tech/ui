The panel opens on arrival so there is something to look at. Toggle the trigger in the corner
to see the rest of it: the drawer is **non-modal**, so the form behind it stays usable while
the theme changes live.

## Usage

```tsx
import { Preferences } from "@kanzo-tech/ui";
```

```tsx
<Preferences hotkey="t" />
```

The all-in-one renders a floating trigger plus the drawer. It writes through `useKanzoTheme`,
which sets `data-*` attributes on `<html>` — that is why every component re-skins, including
Ark's portaled overlays, which render into `document.body` and would miss a wrapper element.

The panel is deliberately **non-modal**: you keep using the app while it re-skins live behind
the drawer, which is the only way to judge a theme. It still closes on an outside click, because
that is what a panel is expected to do — every change applies on selection, not on close, and the
hotkey reopens it where you left off.

There is no default hotkey. `hotkey` registers a bare, unmodified key on `window` (ignored
while you are typing in a field), and a design system must not claim one in its host's keymap
without being asked.

<Callout type="info" title="Colour is a preference — a hue is not">
  Six sections at most, two of them conditional. The rule is not "the user touches no colour", which
  was never true: `appearance` is colour. It is that the user never **authors** a colour value —
  they choose among colours someone already validated.

  So `Palette` and `Identity` are here, and base, accent, chart scheme and the "Copy CSS" export are
  not. Those let a user compose *part* of a palette a hue at a time; a
  [palette document](/docs/showcases/palette) is derived and measured once at onboarding and chosen
  whole. Both sections hide themselves below two published options, so a tenant with one brand and
  one palette sees the four axis sections and nothing else.
</Callout>

<Callout type="info" title="Appearance is in the header, not the body">
  `appearance` is a preference, but it is not a *section*.
  [`AppearanceToggle`](/docs/layout/appearance-toggle) sits beside the close button and flips
  light ⇄ dark in one click. The panel briefly carried a copy of it in the body as well, which is
  one preference wearing two controls; the button costs the body nothing.

  There is no third state on that flip: following the OS is `null`, the absence of a pinned side, and
  `DEFAULT_PREFS.appearance` is `null` — so an app with nothing stored follows the OS until the first
  click. **Reset**, below, is the way back: it spreads `DEFAULT_PREFS`, appearance included.

  Mount it anywhere else you like — the docs sidebar does — since it reads the same preference.
</Callout>

## Anatomy

```text
Preferences.Root
├── Preferences.Trigger
└── Preferences.Panel
    ├── Preferences.Palette    — only when the tenant publishes two
    ├── Preferences.Identity   — only when the tenant publishes two
    ├── Preferences.Density
    ├── Preferences.Radius
    ├── Preferences.Font
    └── Preferences.MonoFont
```

`Panel` renders that whole set when given no children, plus a pinned Reset · Done footer that
stays whatever the children are. Pass children to choose your own set.

The two colour sections come first and coarsest-first, so they read top-down as one choice at two
grains: a **palette** is a whole document (surfaces, statuses, syntax, brand) and an **identity** is
a brand inside one, sharing the tenant's neutral. Each guards itself rather than being guarded at the
call site — every section is exported flat for a host's own settings page, where a call-site guard
would be invisible.

## Choosing the sections

`Panel` renders the canonical set when given no children. Pass children to choose your own —
and the pinned footer stays. A typography-only panel, for instance. Same real drawer, floating
over the page, in its own viewport.

<PreviewIframe className="h-[42rem]" name="preferences-fonts" source="preferences/fonts" title="Typography preferences" />

```tsx
<PreferencesRoot hotkey="t">
  <PreferencesTrigger />
  <PreferencesPanel title="Typography">
    <PreferencesFont />
    <PreferencesMonoFont />
  </PreferencesPanel>
</PreferencesRoot>
```

<Callout type="warn">
Use the **flat** parts (`PreferencesFont`), not the `Preferences.Font` statics. The namespace is
built with `Object.assign`, and statics are lost when a module becomes a client reference under
RSC — `Preferences.Font` reads back as `undefined` there. We hit this for real.
</Callout>

## Extending the panel

The children are yours, so a product can lead with its **own** preferences and then fall back to
the library's axes — one drawer, product prefs and theme prefs together, all live. Here a
product `Sidebar side` control sits above the theme sections. This is the move the
[metadata-form showcase](/docs/showcases/metadata-form) uses for its Layout picker.

<PreviewIframe className="h-[42rem]" name="preferences-extended" source="preferences/extended" title="Extended preferences" />

```tsx
<PreferencesRoot hotkey="t">
  <PreferencesTrigger />
  <PreferencesPanel>
    {/* the product's own section, on top — the extension point */}
    <PreferencesField label="Sidebar side">
      <SegmentGroup value={side} onValueChange={(d) => d.value && setSide(d.value)}>
        <SegmentGroupItem value="start">
          <SegmentGroupItemText>Start</SegmentGroupItemText>
        </SegmentGroupItem>
        <SegmentGroupItem value="end">
          <SegmentGroupItemText>End</SegmentGroupItemText>
        </SegmentGroupItem>
      </SegmentGroup>
    </PreferencesField>

    {/* the library's own axes, flat, below the product's */}
    <PreferencesRadius />
    <PreferencesDensity />
  </PreferencesPanel>
</PreferencesRoot>
```

`PreferencesField` titles a single control; `PreferencesFieldSet` titles a **group** of them.
That split is a semantics call, not a styling one. `Field` addresses one control by id, and a
radio group has one hidden input per item, so there is no id for its label to point at —
`FieldSet` + `FieldLegend` is the answer, and Ark's `useRadioGroup` reads the legend's id
straight out of the fieldset context as the group's accessible name.

## Sections in your own page

Every section is exported flat, so the same controls can live **inline** in a product's own
settings page instead of the floating drawer — they edit the same live theme either way.

```tsx
<div className="flex w-80 flex-col gap-6">
  <PreferencesDensity />
  <PreferencesRadius />
  <PreferencesFont />
  <PreferencesMonoFont />
</div>
```

### Sections

Each reads and writes `useKanzoTheme()` directly. The four axis sections take no props; `Palette` and
`Identity` take a `label` for their legend, which is their one library-authored string — a palette's
or an identity's own name was written by the client and passes through verbatim.

`Palette` is the one section that writes a preference and repaints nothing by itself. A document is a
stylesheet, so the next load is the palette; a live swap is the host's to arrange, as the docs site
does. That is also why it has no attribute: there is no block in any compiled sheet for a
`data-palette` to select.

| Flat export | Static | Axis | Attribute |
| --- | --- | --- | --- |
| `PreferencesPalette` | `Preferences.Palette` | `palette` | **none** — the server serves the stylesheet |
| `PreferencesIdentity` | `Preferences.Identity` | `identity` | `data-identity` |
| `PreferencesDensity` | `Preferences.Density` | `density` | `data-font-size` |
| `PreferencesRadius` | `Preferences.Radius` | `radius` | `data-radius` |
| `PreferencesFont` | `Preferences.Font` | `font` | `data-font` |
| `PreferencesMonoFont` | `Preferences.MonoFont` | `monoFont` | `data-mono-font` |

### Containers

For sections of your own, so a product's controls are indistinguishable from the library's.

| Flat export | Props | For |
| --- | --- | --- |
| `PreferencesField` | `label`, `children` | one control (`Field` + `FieldLabel`) |
| `PreferencesFieldSet` | `label`, `children` | a group of controls (`FieldSet` + `FieldLegend`) |
