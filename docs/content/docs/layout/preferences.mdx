to see the rest of it: the drawer is **non-modal**, so the form behind it stays usable while
the theme changes live.

## What is a preference, and what is not

A preference answers *how this person reads*: the side they wear, the theme they wear on each side,
and how big everything is. Corner radius and typography answer *what the product looks like*, so they
belong to the theme and have no control here. A tenant that wants square corners or its own face
publishes a theme. The rule and the reasons are on [Preference or theme](/docs/design/preferences).

Motion and contrast are the platform's questions. The library honours `prefers-reduced-motion`, and a
tenant that wants more contrast than AA publishes a high-contrast theme for people to pick.

## One preference, four places it appears

A preference is **declared** once, where its values live. For the core that is the generator that
emits the CSS. Everything else follows from the declaration:

| | |
| --- | --- |
| **Declaration** | `kind`, options (or the name of whoever owns them), default, attribute, doc. `CORE_PREFS` for the core's three, a `SectionManifest` for an optional package's. |
| **Resolution** | one chain, most specific first: what a tenant pinned, what the person stored, where the tenant said to start, the declaration's default. `useKanzoTheme().corePrefs` / `.sectionPrefs` carry the answer, `via` says which link gave it, and `offered` says whether to draw a control at all. |
| **Renderer** | one control per `kind`, such as a radio list, a `Switch` or a `Slider`, so a surface never re-decides what a `range` looks like. The specimens are a lookup keyed by preference. |
| **Surfaces** | the drawer below, a settings page, a dock inside a canvas. All of them mount `PreferencesSections`. |

## Usage

```tsx
import { Preferences } from "@kanzo-tech/ui";
```

```tsx
<Preferences hotkey="t" />
```

The all-in-one renders a floating trigger plus the drawer. It writes through `useKanzoTheme`,
which sets attributes on `<html>`. That is why every component re-skins, including Ark's portaled
overlays, which render into `document.body` and would miss a wrapper element.

The panel is deliberately **non-modal**: you keep using the app while it re-skins live behind the
drawer, which is the only way to judge a theme. It still closes on an outside click. Every change
applies on selection, not on close, and the hotkey reopens it where you left off.

There is no default hotkey. `hotkey` registers a bare, unmodified key on `window` (ignored while you
are typing in a field), and a design system must not claim one in its host's keymap without being
asked.

## The sections

`PreferencesSections` draws every preference this host offers, in this order:

1. **The theme.** A light card and a dark card, described below. It is the control for both
   `appearance` and `themeByAppearance`.
2. **Density.** Compact, default and cozy, each a percentage of the browser's own font size.
3. **What installed packages contribute.** For example, the graph contributes which look the canvas
   draws. See [Contributing a section](/docs/sections).

It is the one way to mount a preference control. There is no per-axis export and no standalone theme
picker, so a host cannot mount a control that overrides its theme.

```tsx
<PreferencesSections />                          // everything, as the panel draws it
<PreferencesSections namespace="theme" />        // the core's alone: the theme, then density
<PreferencesSections namespace="graph" />        // one package's
<PreferencesSections namespace="theme" only={["density"]} />
```

`namespace` picks one namespace, and the core's is `theme`. `only` picks preferences by name, in your
order. For the core, `"appearance"` and `"themeByAppearance"` both name the theme cards, because the
cards are one control for the two of them. A name nothing declares draws nothing. A choice the tenant
pinned or withheld is not drawn at all.

## The theme cards

A theme is one mode, so a person does not choose "a theme". They choose one for light and one for
dark, and which side to wear. The cards draw exactly that, and **the card is the selector**:

- **Light theme** and **Dark theme** are two cards, side by side, and together they form one radio
  group, *Appearance*. Clicking a card anywhere but on a swatch wears its side: it writes
  `appearance`, and with it `.dark`.
- **Active** marks the worn card, which is the checked one: a primary border and the badge in its
  header.
- **Swatches.** Each card offers only its own side's themes, as a row of round swatches. Pointing at
  one (or focusing it) **previews** it in that card's `ThemePreview` and name, and nowhere else. The
  page does not change, and moving away puts the card's own theme back. **Clicking** a swatch commits
  it: the theme is filed under the card's side and that side is worn.

While nothing is stored, the side is the OS's `prefers-color-scheme`. Once the person picks a side,
the pick is stored and wins. A tenant's `policy.theme.appearance.default` outranks the OS.

Each side remembers its own theme (`themeByAppearance`), so wearing the other card brings back what
was chosen for it. With no choice stored, each card shows the default pair. The swatch row offers
exactly what the provider's `themes` lists, so narrowing the offer is a prop on the provider.

### What the tenant's policy draws

| `policy.theme` | What draws |
| --- | --- |
| nothing | both cards, as the *Appearance* choice, each with its swatches |
| `appearance: { pinned: "dark" }` or `{ hidden: true }` | only the worn side's card, with its swatches and no radio |
| `appearance: { default: "dark" }` | both cards, the dark one checked while nothing is stored |
| `themeByAppearance: { hidden: true }` or `{ pinned }` | both cards without swatches: the tenant's default pair, previewed. Choosing a card still picks the side |
| both withheld | no theme section; density and the rest still draw |
| `density: { pinned }` or `{ hidden: true }` | ignored. Density is always the person's; only `{ default }` applies |

### The retired-theme notice

When the stored theme is no longer in `themes`, because a tenant dropped a family or the library
retired the theme, the provider clears the choice and the cards show an *info* alert: "Brand updated —
“dracula” is no longer offered here. You are seeing the default." It is the same state, and the same
words, that [`ThemeNotice`](/docs/theming#retired-themes) shows as a toast. Translate both through
`copy.retired`.

### Accessibility

- The two cards are an Ark radio group named *Appearance* (`copy.appearance`). Each card's radio is
  its header, stretched over the card, so the whole card is the click target while no control is
  nested in another.
- Each card's swatches are a radio group named by the card's title, with **manual activation**: Tab
  enters the row on the chosen swatch, arrow keys (and Home / End) move focus and preview, Enter or
  Space chooses, and Escape puts the preview back. Choosing on every arrow would repaint the page on
  every key press.
- A swatch's accessible name is the theme's label, also shown as its tooltip. The swatch circles and
  the preview are decorative (`aria-hidden`).
- The cards sit on a container query, not a viewport one: side by side from a 36rem container,
  stacked in a 384px drawer, with nothing passed down.

## Choosing your own set

`PreferencesPanel` renders `PreferencesSections` when given no children. Pass children to compose
your own, and the pinned Reset · Done footer stays. A product can lead with its **own** preferences
and then place the library's:

<PreviewIframe className="h-[42rem]" name="preferences-extended" source="preferences/extended" title="Extended preferences" />

```tsx
<PreferencesRoot hotkey="t">
  <PreferencesTrigger />
  <PreferencesPanel>
    {/* the product's own section, on top */}
    <PreferencesField label="Sidebar side">
      <SegmentGroup value={side} onValueChange={(d) => d.value && setSide(d.value)}>
        <SegmentGroupItem value="start">
          <SegmentGroupItemText>Start</SegmentGroupItemText>
        </SegmentGroupItem>
        <SegmentGroupItem value="end">
          <SegmentGroupItemText>End</SegmentGroupItemText>
        </SegmentGroupItem>
      </SegmentGroup>
    </PreferencesField>
    {/* every preference the library offers, below the product's */}
    <PreferencesSections />
  </PreferencesPanel>
</PreferencesRoot>
```

**`children` replaces the default body**, so a composed panel must place `PreferencesSections` or it
drops every preference.

`PreferencesField` titles a single control; `PreferencesFieldSet` titles a **group** of them. That
split is about semantics, not styling. `Field` addresses one control by id, and a radio group has one
hidden input per item, so there is no id for its label to point at. `FieldSet` + `FieldLegend` is the
answer, and Ark's `useRadioGroup` reads the legend's id straight out of the fieldset context as the
group's accessible name.

## The other surface: a settings page

The same sections live **inline** on a product's own settings page, with no drawer anywhere. There
is no page component to import, because a settings page is your layout and your navigation with the
sections dropped in:

```tsx
<ShellMain>
  <SectionRoot className="mx-auto w-full max-w-5xl px-6 py-8">
    <div className="grid gap-8 md:grid-cols-[13rem_1fr]">
      <nav aria-label="Settings">{/* your own menu — ItemGroup / Item */}</nav>
      <div className="flex min-w-0 flex-col gap-8">
        <PreferencesSections />
      </div>
    </div>
  </SectionRoot>
</ShellMain>
```

The [settings showcase](/docs/showcases/settings) is that page finished. A section is never separated
from the next by a rule, in either surface: the heading is the separation.

### PreferencesCopy

| Key | Default |
| --- | --- |
| `theme` | `"Theme"` — the heading over the cards |
| `appearance` | `"Appearance"` — the accessible name of the two cards' radio group |
| `day` | `"Light theme"` |
| `dayDescription` | `"Worn while the appearance is light."` |

| `active` | `"Active"` |
| `retired` | `ThemeRetiredCopy` — `{ title?, formatDescription?({ theme }) }`, shared with `ThemeNotice` |

Density's label and its options come from the declaration. A contributed section's words are its
manifest's.

### Containers

For sections of your own, so a product's controls are indistinguishable from the library's.

| Flat export | Props | For |
| --- | --- | --- |
| `PreferencesField` | `label`, `children` | one control (`Field` + `FieldLabel`) |
| `PreferencesFieldSet` | `label`, `children` | a group of controls (`FieldSet` + `FieldLegend`) |

### ThemePreview

`ThemePreviewProps` extends a `div`'s props.

| Prop | Type | Default |
| --- | --- | --- |
| `theme` | `string` | inherits the surrounding cascade |
| `appearance` | `"light" \| "dark"` | the theme's own side |
| `className` | `string` | — |

There is no `Preferences.X` namespace: statics built with `Object.assign` do not survive the RSC
boundary, so the flat name is the only name. Every part's props are exported as an interface —
`PreferencesProps`, `PreferencesRootProps`, `PreferencesPanelProps`, `PreferencesSectionsProps` and
`PreferencesCopy`.
