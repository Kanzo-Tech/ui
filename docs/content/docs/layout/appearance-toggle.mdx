Two states, one button, one click: **light ⇄ dark**, a sun and a moon crossfading in place. It is
the **sole** control for the preference — the Preferences panel briefly carried a copy of it in the
body as well, which is one preference wearing two controls.

## There is no `system`

`prefers-color-scheme` is consulted either way; that part is not a feature, it is unavoidable.
Without it the first visit has to guess, and guessing wrong flashes white at every dark-mode user.
So the question was never "does the OS preference matter". It is: **is "follow the OS" a value, or
the absence of one?**

The absence of one. `Appearance` is `"light" | "dark"`, the preference is `Appearance | ""`, and
`DEFAULT_PREFS.appearance` is `""` — with nothing stored the app follows the OS. The first click
writes an explicit side and that side sticks; the toggle flips between the two and has no third face
because there is no third state to show.

That is the reference systems' own split, and which side of it you land on depends on which layer you
are. The theme-switching libraries make it a value: next-themes ships `defaultTheme = "system"` and
appends `"system"` to its `themes` array, MUI has `mode: "light" | "dark" | "system"`, Mantine calls
it `"auto"`. The **token** layers do not. daisyUI writes `themes: light --default, dark
--prefersdark`, where the OS preference is a flag on a theme and `data-theme` overrides it; Tailwind
has a media query or a class; Radix Themes declines to model it and hands the job to next-themes. And
CSS itself has no third keyword — `color-scheme: light dark` means "the OS decides", and an explicit
side overrides.

We are a token layer: a [palette document](/docs/theming#colour-the-palette-document) with a `:root`
block and a `.dark` block, and appearance selects between them. A host running next-themes is still
supported — `KanzoThemeProvider` translates its `"system"` to `""` in one place, and nothing else in
the package knows that `"system"` is a word.

`""` is what every deferral in this system is spelled as: `identity` and `palette` store it for
"defer to the document", and the write rule removes an attribute at it. One spelling is what lets
appearance be declared like every other axis, and a declaration can *offer* its unset state — which
is why the way back below is no longer only Reset.

<Callout type="info" title="The way back is Reset, or a control you write">
  [`Preferences`](/docs/layout/preferences) has a **Reset** in its pinned footer, and reset unsets
  every preference — which unpins appearance along with the other five axes, and lands wherever the
  tenant's document says rather than on ours. That is the supported way back to following the OS,
  and nobody will guess it, so say it in your product too.

  A control of your own does it directly: `setAppearance("")`. The unset state is a declared option
  (`{ value: "", label: "System" }`), so this is not an escape hatch — it is the type.
</Callout>

import { AppearanceToggle } from "@kanzo-tech/ui";

[`useKanzoTheme`](/docs/theming#setting-them), which is why every mount agrees: the toggle in the
Preferences header, the one in your app bar and the three below are the same preference read
several times.

## The accessible name does the work

`aria-pressed` is defensible on a two-state control — that is what the attribute is for — and this
one still does not carry it. Two reasons, and both are about this control rather than about the
attribute.

**The name already says more than the attribute can.** A screen reader reading a pressed toggle
says "Appearance, toggle button, pressed", and *pressed* is a bare bit: the listener has to already
know that on means dark. The name here carries both halves of the contract — what the control is in
right now, and what one click will do:

```text
"Appearance: Dark. Switch to light"
```

`aria-pressed` on top of that announces the state twice, once precisely and once vaguely.

**And it would have to be withheld until mount**, like everything else below — the resolved
appearance is not knowable on the server. A control that is a plain button in the server's markup
and a *toggle button* after hydration changes its role semantics mid-life, which is a worse trade
than not making the claim.

The name is the `title` too, so a pointer user gets the same sentence on hover.

<Callout type="info" title="No live region either">
  A visually hidden `role="status"` echoing the new state was rejected: screen readers re-announce
  the accessible name of the element that still has focus, and a button that never moves focus
  always is — so the status would duplicate the name and the change would be spoken twice.
</Callout>

## SSR: `themeScript` is not optional

The resolved appearance is only knowable in the browser — it comes from localStorage, a cookie or
`matchMedia`. So the state-bearing parts of the markup are **withheld until mount**: the state
clause of `aria-label`, `data-appearance`, and `title`. The server commits to
`aria-label="Appearance"` and nothing more.

Without that, the server emits `light`, the client hydrates `dark`, and React reports a hydration
mismatch it does **not** patch — the markup stays wrong for the life of the page.

It costs no flash of the wrong theme, because what paints is the sun/moon crossfade, and that is
keyed off `.dark` in CSS, which [`themeScript`](/docs/installation) sets on `<html>` before the
first paint. Which is the condition: inject the script.

```tsx
import { KanzoThemeProvider, themeScript } from "@kanzo-tech/ui";

<head>
  <script dangerouslySetInnerHTML={{ __html: themeScript() }} />
</head>
```

<Callout type="warn">
  Skip `themeScript` and the toggle still works, but the first paint is the default appearance and
  the page re-skins on hydration. Every control whose markup depends on the resolved appearance
  pays for it; this one is simply the most visible.
</Callout>

## Translating it

Two props, because the sentence has two parts a translator has to reach separately.

`labels` names the **states** — the words substituted for `Light` and `Dark`. `formatName` writes
the **frame** around them. Give only the first and a translated app gets half-English:
`"Apariencia: Oscuro. Switch to claro"`, which is what a hard-coded frame did to the tooltip this
control replaces.

<ComponentPreview componentName="appearance-toggle" fileName="example-i18n" />

`formatName` receives the already-translated pieces, so it never has to know the state names:

```tsx
formatName={({ label, current, next }) => `${label}: ${current}. Cambiar a ${next.toLowerCase()}`}
```

## API Reference

### AppearanceToggle

| Prop | Type | Default |
| --- | --- | --- |
| `label` | `string` | `"Appearance"` |
| `labels` | `Partial<AppearanceToggleLabels>` | `{ light: "Light", dark: "Dark" }` |
| `formatName` | `(parts) => string` | `` `${label}: ${current}. Switch to ${next.toLowerCase()}` `` |
| `variant` | `ButtonProps["variant"]` | `"ghost"` |
| `size` | `ButtonProps["size"]` | `"icon-md"` |
| `className` | `string` | — |

`label` is also the name announced **before** mount, on its own — the server has no state to add
to it.

### formatName parts

| Field | Type | Is |
| --- | --- | --- |
| `label` | `string` | `label`, translated by you |
| `current` | `string` | the current state, from `labels` |
| `next` | `string` | the state one click away, from `labels` |
